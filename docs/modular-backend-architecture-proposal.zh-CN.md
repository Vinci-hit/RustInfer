# 从单态单后端到可加载多后端运行时：RustInfer 的增量架构重构提案
> **RustInfer** 的架构重构提案 — 于 2026 年 6 月 20 日生成。范围：将硬件后端与 Rust 核心分开，启用运行时加载的异构执行，并从核心构建中删除强制性 GPU 工具链。本文档是一个设计提案，而不是已实施的变更；它基于当前的 `infer-worker` 代码库，并受到 PyTorch 调度程序、ONNX 运行时执行提供程序、TVM 运行时、OpenXLA/PJRT 和 TensorRT 的启发。

## 执行摘要RustInfer 是一个 Rust LLM 和扩散推理框架，其 GPU 运行时 `infer-worker` 被组织为干净的 DDD 分层：纯 Rust `domain/` 端口、CUDA `infrastructure/` 适配器和 `application/` 编排层。该设计是一项真正的资产，而该提案是故意建立在它之上而不是围绕它。问题不在于抽象，而在于抽象。抽象是在*编译时*完全解析的。 `Tensor<T, D>` 和 `Runtime<T, D, M>` 在设备类型 `D` 上是单态的，编译器根据 `impl` 来选择设备，29 个 `.cu` 内核位于工作器箱内，而 `default = ["cuda"]` 意味着如果没有完整的 CUDA 工具链，内核实际上无法构建， `libclang`、cuDNN 前端标头和主机 GPU，其计算能力由 `nvidia-smi` 融入工件中。没有进程内多后端，没有运行时加载的插件，也无法将无 GPU 的核心发布到 crates.io。
北极星是一个**运行时可加载的多后端运行时**，其中核心仅使用 `rustc` 构建，加速器内核作为独立构建、独立发布的插件提供，并且在*加载时*通过稳定的 C ABI 选择设备 - 而每个数据类型的 `match T::DATA_TYPE` 热路径在每个插件*内部*保持单态化，为每个 matmul 或注意调用精确地支付一个函数指针间接从不针对每个元素。主要决定有五项。 **首先**，静态通用世界结束，类型擦除世界从一个精确定义的接缝开始：现有的 `MemoryPort` 字节操作*和*高级操作入口点（`CoreOps` + `MathOps` + `DiffusionOps` + `FusedOps`）都作为不透明句柄跨越 ABI； `Tensor<T, D>` 保持在接缝上方，dtype 匹配保持在接缝下方。 **第二**，这条接缝不是通过当今端口的免费“对象安全投影”来实现的——它们不是对象安全的，因为每个操作都是一个通用的自由函数，没有 `&self` 接收器——而是通过一个故意新的、手写的 `BackendDyn` 特征加上每个数据类型的重新单态化适配器，这是实际工作的大部分，必须通过 CI 测试与通用表面保持同步。 **第三**，所有 `.cu` 都转移到一个独立的 `infer-backend-cuda` cdylib 中，该 cdylib 提供多架构 fatbin 并通过 `cudarc` 动态加载加载 CUDA，从而消除了 471 行 `build.rs` 耦合。 **第四**，基础从过度分割的设计崩溃为四个箱子（`infer-core`、`infer-backend-abi`、`infer-runtime`、`infer-models`），因为张量/执行/内存项在项级别上是相互递归的，并且任何分割都会产生牢不可破的 Cargo 循环。 **第五**，现有的 CPU 适配器保持*静态链接*作为始终存在的终端回退 - 诚实地警告它完全实现 `MemoryPort` 和执行，只是 `CoreOps`/`DiffusionOps` 的子集本机，并通过主机往返参考默认值继承 `FusedOps`，因此每操作回退是一个正确性路径，可以缩短延迟热操作并且必须计量。
分阶段的结果是确保安全的纪律：构建在每一步都保持绿色。源代码级内核提取首先落地，CUDA 仍静态链接；擦除的特征和支持 CPU 的服务循环位居第二，因此 `cargo test --no-default-features` 在 CPU 上运行；只有这样，动态加载才会到达，`default = ["cuda"]` 翻转才会最后发生。其结果是一个可发布的核心、无 GPU、在自己的列车上进行版本控制的后端，以及一个可以在一个狭窄的版本边界后面托管 CUDA、ROCm、Metal 和 CPU 的运行时。
## 当前状态：诚实的评估
### 什么已经很好了
该存储库的状况比大多数重构前的代码库要好得多，并且有三件事值得明确赞扬。**端口已经存在并且经过精心设计。** `infer-worker/src/domain/ports/` 定义了一个连贯的抽象系列 - `Device`/`MemoryPort`、`CoreOps` (`op_ports.rs`)、`MathOps` (`math_ops.rs`)、`DiffusionOps` (`diffusion_ops.rs`)、`FusedOps` (`fused_ops.rs`)、`CollectiveOps` 和毛毯组成的 `Backend = LlmBackend + DiffusionBackend` (`backend.rs`)。至关重要的是，`MemoryPort` 已经表示原始 `NonNull<u8>` 加上字节大小，而不是类型化张量。这意味着该提案所需的静态到动态的接缝“已经完成了一半”：抽象的最低层在本质上是类型擦除的。
**第二个后端已经实现了相同的端口。** `infrastructure/cpu/mod.rs` 提供了实现端口系列的 `Cpu` 标记类型。它的存在本身就证明了抽象是真实的——它可以托管非 CUDA 后端——而不是穿着特征服装的 CUDA 形状的界面。这是整个插件故事所依赖的经验基础。
**DDD 分层干净，调度路径严格。** `domain/` 是纯 Rust，FFI 为零； `infrastructure/cuda/` 持有适配器； `application/` 接线 `Runtime`、`DecodeEngine` 和 `serve_loop`。运行时调度路径是原则性的：特征方法进入 `ExecScope` 保护，解包流，并在 `match T::DATA_TYPE` 中触底，选择 `extern "C"` 内核符号。该设备是在编译时通过单态化选择的；数据类型匹配是唯一的运行时调度。 `match T::DATA_TYPE` 热路径是框架最大的性能资产，重构必须逐字保留它。
### 三个根本问题
**1.后端选择是编译时的，因此没有进程内多后端，也没有运行时插件。** `Tensor<T, D>` 将设备作为单态通用参数携带； `Runtime<T, D, M>` 同样是单态的； `serve_loop::run_with_model` 硬编码为 `M: DecoderModel<bf16, Cuda>`，并直接使用 `&Cuda`、`CudaScope` 和 `Runtime<bf16, Cuda, M>`。在运行时选择后端、从磁盘加载后端或在一个进程中运行两个后端在当今结构上是不可能的。将设备轴移动到运行时动态调度（稳定边界处的类型擦除张量和不透明设备句柄）是核心更改，而接缝落在的*哪里*是整个提案的关键。**2. `.cu` 内核位于工作器箱内，因此构建工作器会拉动整个 CUDA 工具链。** 29 个 `.cu` 文件位于 `infrastructure/cuda/kernels/` 下，471 行 `build.rs`（在 `cuda` 功能后面）遍历它们，通过 `cc::Build::cuda(true)` 编译每个文件进入静态 `infer_kernels` 库，在 cuDNN 前端和 cutlass 标头上运行 `bindgen`（需要 `libclang`），并使用 `nvidia-smi` 将工件固定到主机 GPU 的 `sm_XX`。对于 `default = ["cuda"]`，如果没有所有这些，*核心就无法构建*。
**3. CUDA 对于构建是强制性的，因此核心是不可发布和主机固定的。** `SKIP_BUILD_KERNELS` 转义只会推迟痛苦：跳过编译，静态 `extern "C"` 符号无法链接。该工件在构造上是特定于 GPU 的，无法访问 crates.io，并迫使每个 CI 运行者和贡献者使用完整的 GPU 工具链来接触纯 Rust 代码。
### 提案必须诚实地进行一项更正
CPU 后端“不”“实现每个端口”。 `cpu/mod.rs:42` 是 `impl FusedOps for Cpu {}` — 继承主机往返参考默认值的空 impl（`attention_paged_reference`、`scatter_kv_paged_reference`，通过 `to_host_vec` 往返）。 `Cpu` 类型完全实现 `MemoryPort` 和 exec，它是 `CoreOps`/`DiffusionOps` 的“子集”，并返回 `OpError::Unsupported` 的其余部分。回退故事必须反映这一点：每个操作 CUDA→CPU 回退仅对于 CPU 实际支持的操作是安全的，而像 `attention_paged` 这样的热操作回退是一条仅正确性的路径，可以缩短解码延迟 - 因此贯穿始终的计量和硬故障要求。
## 目标架构：北极星
最终状态将今天融合的三个问题分开：**单态核心运行时**（接缝之上）、**稳定的 C ABI**（接缝本身）和**加载的后端**（接缝之下）。模型代码和张量类型状态保持完全通用且零开销；设备轴成为运行时函数指针表； dtype 轴在每个插件内重新单态化。

### 箱子图（4个核心箱子，取代了过度分割的设计）
- **`infer-core`** — 基础：dtypes、`QuantScheme`、`OpError`、`MemoryPort`、*合并* `Device`/`ExecScope` 词汇、`Storage`、`Tensor<T,D>`、 `Workspace`/`ActiveGuard`/`StepCtx`。一个箱子，因为这些项目在项目级别上是相互递归的（`Tensor<T,D>` 需要 `MemoryPort`；`Storage<D>` 是唯一的分配调用者；`Device: MemoryPort`；`ExecScope::enter` 返回 `ActiveGuard<Self::Device>`），因此任何拆分都是一个牢不可破的 Cargo 循环。
- **`infer-backend-abi`** — 通过一个向下箭头位于 `infer-core` 之上：op-port 特征、新的 `BackendDyn` 擦除特征、`#[repr(C)]` vtable 和 per-op arg 结构，以及 `libloading` 注册表/加载器。这是稳定面；它*仅* `#[repr(C)]` 公共项目。
- **`infer-runtime`** — `Runtime`、`DecodeEngine`、`worker_state`、`worker_scheduler`、`serve_loop`，加上薄 `infer-worker` 主机接线（ZMQ 泵、插件发现）。
- **`infer-models`** — safetensors 加载器、LLaMA/Qwen、层组件。
### 命名理由
后端 crate 名为 **`infer-backend-cuda` / `-rocm` / `-metal` / `-cpu`**（供应商作为后缀）。这是提案中每个具体工件使用的形式 - cdylib 文件名 `libinfer_backend_cuda.so`、发布树和 `RUSTINFER_BACKENDS=cuda:/path/libinfer_backend_cuda.so` 发现约定 - 因此它被统一采用，覆盖任何早期的 `infer-cuda-backend` 排序。该模式读作“`infer` 后端，用于 `cuda`”，将所有后端在 `ls` 中相邻分组，并保持文件名/板条箱名称对应关系简单。

- 所有成功的稳定边界共享的关键 ABI 安全三位一体，RustInfer 必须逐字采用：(1) 删除器/分配器随句柄移动 — 由 CUDA 插件 cudaMalloc 分配的缓冲区仅由该插件的 free fn 释放（tvm-ffi 的 #1 规则；当插件由不同工具链构建时，防止跨 DLL 双重释放）； (2) 错误作为 int-return + opaque-handle 访问器交叉，绝不作为展开 — 每个 extern"C" 条目都包装 `catch_unwind`（跨 FFI = 即时 UB 的恐慌）； (3) 在第一次调用时通过 struct_size/abi_version (PJRT) 进行版本控制，并在不匹配时大声拒绝 - 未经检查的不匹配是 UB，而不是错误。
- RustInfer 的架构赋予了它一种每个参考系统都缺乏或遗憾的功能，并且设计应该倾向于它：每个 OP 运行时跨后端回退。 PJRT 和 TensorRT 只能回退到整个程序/构建粒度； ORT 和 PyTorch 执行每操作回退，但通过静默主机往返来减少 LLM 延迟。因为 RustInfer 拥有 DEVICE 级别的抽象，并且进程内 CPU 后端已经为每个端口返回 OpError::Unsupported，所以它可以保持干净的每操作 CUDA→CPU 后备链 - 前提是 CPU 后端作为始终存在的终端保持静态链接（不在 C ABI 之后），并且记录每个主机往返，因此它永远不会默默地降低推理延迟。
- 预先存在的 ZMQ 工作程序作为子进程模型是解决插件信任问题的一个未被充分重视的资产。每个参考系统都具有完全的进程内信任（后端 .so 运行未沙盒的任意静态初始化代码）。对于多租户服务器，RustInfer 可以在现有工作子进程中隔离不可信/实验性后端，而不是将其放入调度程序/服务器进程中 — 对于可信插件，在 C ABI 处进行版本控制；对于不可信插件，通过现有 ZMQ 接缝进行进程隔离。
- 不要过度设计调度密钥。 PyTorch 的 64 位 DispatchKeySet（后端位 × 功能位、别名扩展、BackendSelect）被明确标记为 RustInfer 所不具备的自动分级/功能化分层所产生的意外复杂性。一个简单的 `(op_id, dtype, backend_id)` 在模型加载时解析一次的 fn-ptr 表（TensorRT 的预解析 DAG 课程）就足够了；在存在具体的第二轴之前，请抵制推广到多轴键集。同样拒绝 ORT 尴尬的按 OrtMemoryInfo 分割分配器查找 — RustInfer 现有的 ExecScope/Stream/Workspace 所有权模型更加清晰；保持边界的清晰度，并将内存种类（HBM/固定/统一）暴露为可发现的属性（PJRT_Memory 的难以学习的设备与内存分离）。
- Burn 的装饰器模式（Autodiff/Fusion/Router 的后端包装后端）是添加 RustInfer 想要的横切功能（CUDA 图形捕获、量化层选择、跟踪/分析）的零内核接触方式，作为端口特征的包装器，而不是对内核或 ABI 进行编辑。结合 PyTorch 的分解内核思想（根据原语定义的复合操作，自动重新调度），仅实现原语的后端可以“免费”获得广泛的操作覆盖范围。这使得插件表面在功能集增长的同时保持较小。### 每个维度的建议
**静态通用世界结束和动态/C-ABI世界开始的地方（核心变化，张力＃1）。**在现有端口方法处剪断接缝——特别是在`MemoryPort`（已经采用原始`NonNull<u8>` +大小）和高级操作调用的边界处`OpBackend`/`FusedOps`/`MathOps`。接缝上方保持 `Tensor<T,D>`/`Runtime<T,D,M>` 模型代码完全单态。在接缝处，将每个高级操作降低为平面 `#[repr(C)]` vtable 调用，采用不透明的 `DeviceTensor`（原始设备 ptr + 运行时 dtype 标记 + shape/strides POD + 拥有后端 id）、不透明的 `StreamHandle(*mut c_void)` 和小型 `#[repr(C)]` args 结构。在接缝下方，在每个插件 .so 内部，立即重新单态化：不透明句柄的 dtype 标记逐字驱动现有的 `match T::DATA_TYPE -> kernel_bf16x8` 路径。因此设备调度变成了运行时 fn-ptr； dtype 调度保持在插件内编译时。每个 matmul/attention 支付一个 vtable 间接，而不是每个元素。 *（受到特征形状的 wgpu-hal（HAL 特征 + 不透明设备/队列/缓冲区 + 运行时适配器枚举）的启发；用于不透明张量表示的 PJRT_Buffer / c10 类型擦除 Tensor / DLPack；用于确切调用形状的 TensorRT 的每操作排队（desc，ptrs，stream）。）* - 端口已经在精神上进行了类型擦除（MemoryPort）讲的是原始字节；CPU+CUDA 都实现了它们）——这证明了抽象可以在不重写的情况下托管接缝。在高级操作（而不是元素）处擦除意味着 vtable 成本在整个 matmul/attention 上摊销，与 wgpu 和 PyTorch 在操作粒度上放置调度的方式相匹配。在插件内保持 dtype 单态化可以保留 RustInfer 最大的当前资产：零开销 `match T::DATA_TYPE` 热内核。**插件模型和稳定的 ABI。** 手工制作的 `#[repr(C)]` struct-of-extern"C"-fn-pointers，一个导出的条目符号 `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`，其中 `u32 abi_version`（或 `usize struct_size`）作为 vtable 的第一个字段，并且是每个 args 结构的第一个字段，字段仅附加。对 vtable 进行分组以镜像 TRT 的核心/构建/运行时分割：始终存在的标识块（名称、abi_version、backend_id、目标计算容量）、注册/构建块和热路径运行时块（alloc/free/upload/copy_d2d/enqueue-per-op）。对可选/供应商操作（fp8 层、qkv_norm_rope_scatter、集合）使用类型化链表扩展链，以便核心 vtable 保持较小且稳定。错误交叉为平面 `#[repr(C)] i32` 代码 + 带有访问器 fns 的不透明错误句柄；切勿展开 — 将每个条目 fn 包装在 `catch_unwind` 中。插件分配的内存只能由该插件的空闲 fn (deleter-travels-with-handle) 释放。如果表面需要收集，请保留 abi_stable/stabby 供以后使用。 *（受到作为主要模型的 PJRT（一个 GetPjrtApi 符号 + struct_size 仅附加版本控制 + 类型化扩展链）的启发；用于所有权/错误规则的 tvm-ffi（带有对象的删除旅行，通过 int-return-not-unwind 的错误）；用于 vtable 分组的 TensorRT（核心/构建/运行时功能拆分，字符串三重身份）。）* — 操作集很小，固定，并且已经枚举为端口，因此手卷 vtable 是务实的选择 - 比 abi_stable 更少仪式，完全控制小表面。 PJRT 的 struct_size+append 规则可实现向前和向后兼容，无需冻结主要版本，这是最便宜的稳定机制。扩展链是“在不破坏 ABI 的情况下添加融合操作”的明确答案。每个跨界走私 C++ 的参考系统（PyTorch C++ ABI、ORT 提供程序桥、TRT vtables）都被视为 AVOID 的 #1 反模式 - 窄版本 C ABI 是解药。**内核构建/JIT 解耦（张力 #2：worker 内部的 .cu）。** 将所有 .cu 从 infer-worker 移至独立的 `infer-backend-cuda` cdylib 箱及其自己的 build.rs 中。该板条箱将内核编译为 PTX/fatbin，覆盖一组拱门（sm_80/86/89/90 + PTX 回退），并在运行时通过 CUDA 驱动程序 API 通过 `cudarc` 和 `dynamic-loading` 功能（dlopens libcuda/libcudart/libnvrtc）加载它们。然后，worker CORE 使用 ZERO CUDA 工具链进行构建 — 没有 nvcc、没有 libclang、没有 cuDNN 前端发现、没有 nvidia-smi 主机架构检测。将 `default=["cuda"]` 从硬编译依赖项翻转为仅“在运行时加载捆绑的 cuda 插件”。驱动程序在模块加载时将 PTX JIT 到正在运行的 GPU，并缓存在磁盘上。 *（受 PyTorch/ORT/TVM/PJRT 的启发，所有推送内核构建完全在后端 .so 之后（核心编译零内核）；cudarc 的运行时动态加载用于无链接时间 CUDA 解锁；TVM 的 CUDAModule(PTX→cuModuleLoadData) 和 TRT 的 PTX+cubin fatbin 用于多架构 + JIT-at-load。）* — 这直接解决了最严重的问题：今天的 `default=["cuda"]` 意味着如果没有完整的 CUDA 工具链和主机 GPU，核心就无法构建，并且该工件是主机架构固定的。每个参考运行时都将工具链保留在供应商插件内； cudarc 可以在纯 Rust 中实现这一点，而消费者中无需链接时 CUDA。传送 fatbin+PTX（不是 nvidia-smi→单个 sm_XX cubin）会以驱动程序缓存的首次加载 JIT 为代价消除主机 GPU 特异性。**功能发现和优雅的回退。** 每个插件都会导出 `extern "C" capabilities() -> #[repr(C)] Capabilities`（dtype 位集、op 位集、最大工作空间、cuda-graph/paged-attention 标志、最小/目标计算上限、量化层），在任何工作之前在加载时进行查询。显式分割两个轴：功能功能（支持（op，dtype） - 可查询）与硬件兼容性（粗略计算能力门 - 加载时接受/拒绝）。主机调度程序从与探测功能相交的显式配置中选择每个请求的后端。保留 `OpError::Unsupported` 作为每操作运行时回退信号，映射到 `#[repr(C)] i32`；在不受支持的情况下，逐个操作回退到始终存在的进程内 CPU 后端（它已经实现了每个端口）。使每个跨后端主机往返都可观察/记录。 *（受到 wgpu 功能/限制 + ORT 两层（GetSupportedDevices + 每个模型 GetCapability）+ 始终附加的 CPU EP 回退的启发；TensorRT 对supportsFormatCombination 与 HardwareCompatibilityLevel 的划分；PyTorch 的可记录盒装 cpu_fallback。）* — RustInfer 在这里可以比 PJRT/TRT 做得更好：因为它在设备级别拥有抽象（不是整个程序），它保留了 PJRT/TRT 无法做到的每操作回退。 CPU 后端已经返回 Unsupported 并实现了每个端口 - 将其形式化为有保证的终端回退（ORT 的强制 CPU EP）。拆分功能与硬件功能（TRT 的课程）可以让 CUDA 插件干净地拒绝 fp8 或拒绝带有明显、响亮错误的太新的架构。记录静默主机往返可以避免 ORT/PyTorch 在 LLM 热路径中消除延迟的隐藏 Memcpy 枪。**注册、发现和分发。** 显式入口点注册，而不是静态初始化魔法：主机扫描配置/环境列出的插件目录（窃取 PJRT_NAMES_AND_LIBRARY_PATHS=name:path;... ），`libloading::Library::new`，查找单个 `rustinfer_get_backend_api` 符号，检查 abi_version，查询功能（），在平台名称+优先级下注册返回的 vtable到一个拥有的、可删除的 `Registry` 对象中（不是进程全局单例）。每个后端作为独立的 .so/.dylib/.dll (`infer-backend-cuda`/`-rocm`/`-metal`/`-cpu`) 提供，每个后端独立构建/版本控制，具有内部 PTX/fatbin。 CPU 后端既是静态链接的（linkme 自注册、始终可用的基线）又可作为插件使用。每个插件都会记录其构建所依据的协议/ABI 版本；不匹配 = 清除大声的加载时错误，绝不是 UB。使库在其创建的每个资源的生命周期内保持活动状态（插件的寿命比其句柄/流的寿命长）。 *（受 PJRT 启发（env 名称：路径列表 + register_plugin(priority) + 独立版本轮子仅在 C ABI 处相遇）；ORT（通过路径显式 RegisterExecutionProviderLibrary，而不是目录扫描魔法）；TVM（字符串 type_key→运行时索引，因此独立构建通过名称而不是共享常量达成一致）；linkme 仅用于二进制 CPU 自注册。）* — 通过 static-init 副作用注册的每个参考系统（PyTorch、TVM、TRT）被标记为顺序脆弱、不可卸载且容易出现段错误。主机在 dlopen 之后调用的显式入口点提供确定性加载和卸载（真正的热插拔），并让注册表成为可删除的每服务器对象 - # 第二部分——详细设计
以下八个部分中的每一部分都对应于一项设计任务。每个部分之前都有一个单段桥，将其放置在更大的架构中，并接地于现有的 `infer-worker` 端口和适配器，而不是新建的理想环境。
## 1. 存储库结构*我们从 crate 拓扑开始，因为后来的每一个决定——ABI 所在的位置、哪些代码是主机连接与运行时、没有 CUDA 可以构建什么——都受到 Cargo 依赖 DAG 的限制。核心发现是基础必须“崩溃”，而不是进一步分裂：张量、执行和内存项在项级别上相互递归，因此任何分裂都会产生牢不可破的循环。*
### 起点和塑造一切的约束
RustInfer 现在是一个包含五个 crate 的 Cargo 工作区 (`resolver = "3"`)：`infer-protocol`（无依赖共享消息类型）、`infer-scheduler`（请求调度和 KV 分配器编排）、`infer-server`（axum HTTP/SSE 前端）、`infer-worker`（DDD 分层 GPU 运行时）和`infer-frontend`（2021 版的独立 Dioxus WASM UI）。只有 `infer-worker` 具有真正的架构重量，只有 `infer-worker` 承担痛苦：它的 `build.rs`（472 行，在 `default = ["cuda"]` 功能后面进行门控）遍历 `src/infrastructure/cuda/kernels/*.cu`，通过 `cc::Build::cuda(true)` 将所有 29 个 `.cu` 文件编译为静态文件`infer_kernels` lib，在 `wrapper.h` 上运行 `bindgen`，并使用 `nvidia-smi` 检测主机计算能力和引脚 `-arch=sm_XX`。结果很明显：因为 `cuda` 是默认功能和硬*编译*依赖项，如果没有完整的 CUDA 工具链、libclang、cuDNN 前端和物理存在的 GPU，则无法构建整个核心。 `SKIP_BUILD_KERNELS`逃生舱口仅将故障转移到链接时间。
因此，这种重组的单一设计目标是精确的：*添加或构建后端绝不能触及（甚至编译）核心。*以下所有内容均由此而来。
### Monorepo-with-workspaces，加上每个后端的分割 - 混合的，合理的
存在三种可能的形状：一个巨大的板条箱（今天的 `infer-worker`）、完全的多存储库设计（核心存储库 + 每个后端一个存储库）或混合 - 一个核心单一存储库工作区加上*可单独构建的*后端板条箱，这些后端板条箱可能位于树中，但独立编译和发布。我推荐混合型，我刻意拒绝这两个极端。完全的多仓库分割还为时过早。端口（`Device`、`MemoryPort`、`OpBackend`、`crates/infer-worker/src/domain/ports/` 中的 `FusedOps`/`DiffusionOps`/`Backend` 层次结构）仍在移动；在不稳定的特征表面上强制跨越存储库边界进行版本和发布握手将会对发布舞蹈中的每个更改造成负担，并且 CI 将失去在 `cargo test` 中测试核心加 CUDA 的能力。相反，将 `.cu` 保留在工作箱内是经过验证的故障模式。该混合保持“源”在一个工作区中可发现，同时为每个后端提供自己的 `build.rs`、自己的工具链要求和自己的工件，因此 `cargo build -p infer-runtime` 根本不需要 nvcc。
决定性的边界是*编译到核心*的代码和*由核心*加载的代码之间。 CUDA、ROCm 和 Metal 后端成为具有自己的构建脚本的独立 `cdylib` 包，通过单个稳定的 C ABI 符号出现在运行时，并且从未出现在核心的依赖关系图中。 CPU 后端是一个例外，它证明了这一规则——它保持静态链接，作为始终存在的终端后备（更多内容见下文）。四个强制后端 crate 的名称准确：`infer-cuda-backend`、`infer-rocm-backend`、`infer-metal-backend`、`infer-cpu-backend`。
### 不要过度分割基础：它是一个递归集群
第一个诱惑是追求一个干净的分层分类法——一个用于 dtypes 的箱子，一个用于张量的箱子，一个用于端口的箱子——现有来源教给我们的第一课是，这种分类法是类型系统不会让你说出来的谎言。基本类型不是独立层的堆叠；它们是一个单一的相互递归结，您必须仔细阅读 `crates/infer-worker/src/domain/` 才能了解原因。追踪参考文献。 `Tensor<T, D>`（在`tensor.rs`中）由`D: MemoryPort`参数化并拥有`Arc<Storage<D>>`； `Storage<D>`（在`storage.rs`中）是`MemoryPort::alloc_bytes`/`free_bytes`的*唯一调用者*。 `MemoryPort: Device`。但实际上有**两个** `Device` 特征，将它们混为一谈正是陷阱。 `domain/ports/device.rs` 定义了 `Device` 以及关联的 `type ExecCtx` — `Tensor<T, D>` 的原始类型状态轴。 `domain/exec.rs` 定义了*第二个* `Device: MemoryPort` 携带 `type Scope: ExecScope<Device = Self>`，加上 `enter_device`/`restore_device`。执行层 `Device` 与 `ExecScope`（其 `enter()` 返回 `ActiveGuard<'_, Self::Device>`）、`Stream`、`Workspace<D: Device>` 和 `StepCtx<'a, D: Device>` 交织在一起 - 并且 `ActiveGuard<D>` 本身是通用的`Device` 并在其 `Drop` 中回调 `scope.device().restore_device(...)`。其中每一个都在自己的定义中提到了其他的名称。这些项目没有非循环排序到单独的板条箱中，因为 Rust 板条箱不能具有循环依赖关系，并且这些定义在*项目级别*是循环的。
往上一层会变得更紧。机会特征并不高于这个集群——它们被编织到其中。 `MathOps: Device`（执行 `Device`）采用 `scope: &Self::Scope` 和 `&Tensor<T, Self>` 参数； `FusedOps` 采用 `ctx: &StepCtx<'_, Self>` 和 `&mut Tensor<T, Self>`。因此 `MathOps`/`FusedOps`/`DiffusionOps` 同时参考 `Self::Scope`、`StepCtx<Self>`、*和* `Tensor<T, Self>`。早期的本能是将 `Tensor` 放在一个板条箱中，第二个中是执行特征，第三个中是操作端口，产生了三个相互需要的板条箱——设计声称“设计出来”但从未真正切断这个循环。
解决方案是在类型系统显示“不要拆分”的地方停止拆分。以下所有内容都共同存在于一个基础 crate 中（称之为 **`infer-core`**），因为它们通过构造相互递归，将它们分开只会导致与借用检查器和 crate DAG 的对抗：- `Dtype`/`DataType` 和混凝土叶 dtypes (`F32`/`BF16`/`F16`/`I32`/`I8`/`Fp8E4m3`/`Fp8E5m2`)， `quant::QuantScheme` 和 `OpError`/`OpResult` 错误类型（现在为 `domain/dtype/`、`domain/types.rs`、`domain/ports/error.rs`）；
- `MemoryPort` 和 **两者** `Device` 特征 — **必须在移动过程中合并为一个或重命名一个**（见下文），因为跨已发布的板条箱边界传送两个名为 `Device` 的特征是一种可用性危险；
- 整个执行词汇：`ExecScope`、`Stream`、`Workspace<D>`、`ActiveGuard<D>`、`StepCtx<D>`、`Rank`/`TopologyShape`/`QuantTier`（今天的`domain/exec.rs`）；
- `Storage<D>` 和 `Tensor<T, D>`（现为 `domain/storage.rs`、`domain/tensor.rs`）。
这是八路核心分裂的刻意后退。早期的提案试图将 `Tensor` 提升为 `infer-tensor`，并将端口特征提升为 `infer-backend-abi`；这些板条箱将通过 `MemoryPort`、`Storage`、`Self::Scope` 和 `Tensor<T, Self>` 相互引用，并且无论经过多少仔细的排序都不会消除循环，因为循环是固有的。折叠它们会产生一个干净的 DAG。具体针对两个 `Device` 特征：建议合并是将 `ports::Device::{ExecCtx, name}` 折叠到执行层 `Device`（该层已经具有 `device_id`、`enter_device`、`restore_device` 和 `MemoryPort` 超级特征），以便一个 `Device` 特征携带`type ExecCtx`、`type Scope: ExecScope<Device = Self>` 和生命周期挂钩。如果完全合并证明在重构过程中具有破坏性，则后备方案是将执行层重命名为 `ExecDevice` 并保留 `ports::Device` 作为纯类型状态标记 - 但无论哪种方式，重复的名称都不会保留在 `infer-core` 的公共表面中。

### 静态通用世界结束，类型擦除世界开始
这就是症结所在，现有的代码已经告诉我们从哪里切入。 `MemoryPort` *已经在精神上进行了类型擦除*：`alloc_bytes(size) -> NonNull<u8>`、`free_bytes(ptr, size)` 和主机/设备复制原语讲原始字节和原始指针，并且 `Cpu` 和 `Cuda` 都以相同的方式实现它们。这就是接缝，半建成的——它位于 `infer-core` 中，位于 op-port 特征下方。在接缝之上，一切都像今天一样保持单一形态。 `infer-core` 的 `Tensor<T, D>`、`infer-runtime` 的 `Runtime<T, D, M>` 和所有 `infer-models` 保持其编译时类型状态；模型作者编写了相同的通用 Rust，并且 `match T::DATA_TYPE` 热路径未受影响。在接缝处，每个高级操作（`matmul`，`attention_paged`，`scatter_kv_paged`，`fused_add_rmsnorm`）降低为单个`#[repr(C)]` vtable调用，携带不透明的`DeviceTensor`（原始设备指针，运行时dtype标签，POD形状/步长和拥有`backend_id`)，一个不透明的 `StreamHandle`，以及一个小的仅附加参数结构。在接缝下方 - *在插件 `.so`* 内 - dtype 标签立即逐字重新单态化回现有的 `match T::DATA_TYPE -> add_kernel_bf16x8` 调度。设备选择成为每个高级操作的一个运行时 fn 指针； dtype 调度在插件*内*保持编译时状态。我们为每个 matmul 或注意力支付一个间接，而不是每个元素。
具体来说，`infer-backend-abi` 公开了进程内路径的 op-port 特征*和*加载路径的 `extern "C"` fn 指针的 `BackendVTable` 结构。 CPU后端直接实现特征并静态链接。 CUDA 后端在内部实现这些特征，然后将它们包装在导出的 `rustinfer_get_backend_api(abi_version) -> *const BackendVTable` 符号后面的 vtable 中。加载器（也在 `infer-backend-abi` 中，由 `infer-worker` 使用）`libloading` 加载 `.so`，检查版本字，并将 vtable 注册到拥有的、可删除的 `Registry` 中，而不是进程全局中。这就是它是增量重构而不是重写的全部原因：`infrastructure/cpu/mod.rs` 中的 CPU 后端*已经*实现了每个端口，并且*已经*为它缺少的操作返回 `OpError::Unsupported`，证明在我们编写一行 C ABI 之前抽象可以托管非 CUDA 后端。
### 添加后端如何永远不会触及核心使用此布局，`infer-cuda-backend` 依赖于 `infer-backend-abi` 和 `infer-core`，但依赖关系箭头永远不会指向回：没有核心 crate 依赖于任何后端 crate。构建 `infer-runtime`、`infer-backend-abi`、`infer-core` 或 `infer-worker` 仅需要 rustc。 `.cu` 文件、`bindgen`、`nvidia-smi` 架构探针和 cuDNN 发现都转移到 `infer-cuda-backend/build.rs` 中，它编译为多架构 PTX/fatbin 并在运行时通过驱动程序 API 加载 - 因此即使是 CUDA *消费者*也不需要链接时 CUDA。添加 `infer-rocm-backend` 就是创建一个实现相同端口并导出相同符号的 `cdylib` 箱；核心工作区不会获得依赖项、功能标志或 `cfg`。旧的 `default = ["cuda"]` 硬编译耦合最多成为运行时默认值，表示“加载捆绑的 CUDA 插件（如果存在）”，并且核心最终在任何机器上构建 - 并针对静态 CPU 后端进行测试 - 除了 Rust 工具链之外什么都没有。

## 2. 后端抽象层
*随着箱子边界的确定，下一个问题是整个提案的关键：编译时单态世界到底在哪里结束，类型擦除的动态世界从哪里开始？本节将接缝固定在现有的 `MemoryPort` 字节操作和高级操作调用上，并正面面对现有端口“不是”对象安全的 — 擦除的表面是新的手写代码，而不是自由投影。
### 问题，准确表述如今，RustInfer 在运行时没有后端抽象——它在*编译*时有一个后端抽象。 `domain/tensor.rs` 中的 `Tensor<T: Dtype, D: MemoryPort>` 将其设备作为通用参数 `D`，`domain/exec.rs` 中的执行机制参数化为 `ExecScope<Device = D>` 并关联 `Stream`/`Workspace<D>`，应用程序 `Runtime<T, D, M>` 加上 `serve_loop::run_with_model<M: DecoderModel<bf16, Cuda>>` 为单态化并硬编码为 `<bf16, Cuda>`。 op 特征（`CoreOps`、`DiffusionOps`、`domain/ports/` 中的 `FusedOps`）在 `Self: Device` 上是通用的，并且完全静态分派：对 `CoreOps::add` 的调用在编译时解析为 `impl CoreOps for Cuda`，进入 `ExecScope` 防护，解包`CudaStream`，并在 `kernels::add::add` 中触底，`match T::DATA_TYPE => add_kernel_bf16x8(...)` 也是如此。没有内核注册表，没有设备表 - *设备通过单态选择，数据类型通过 `match`* 选择。因此，两个后端无法共存于一个进程中，并且运行时无法加载任何内容。
重新设计必须引入运行时、对象安全的后端模型和跨后端边界流动的类型擦除张量，而无需重写模型代码或丢弃零开销 `match T::DATA_TYPE` 热路径，这是 RustInfer 的单一最大性能资产。整个设计取决于一个问题：**静态通用世界在哪里结束，动态世界在哪里开始？**我将首先回答这个问题，因为所有其他决定都由此而来。
### 接缝所在的位置
该接缝正好位于现有的 `MemoryPort` 边界和 `CoreOps`/`DiffusionOps`/`FusedOps` 的高级操作调用边界上 — 并且*没有更好的地方*。这不是一个需要发明的新产品线；而是一个新产品线。它已经建成了一半。 `MemoryPort`（在`domain/ports/device.rs`中）已经以原始`NonNull<u8>`和字节数表示：`alloc_bytes(size) -> NonNull<u8>`、`unsafe upload(dst, src, size)`、`unsafe copy_device_to_device(...)`。 `Storage<D>`（在 `domain/storage.rs` 中）已经是 `alloc_bytes`/`free_bytes` 的“唯一”调用站点——正如其自己的文档注释所说，“内存安全的基石”，是板条箱中唯一允许分配或释放的东西，每个 `Tensor` 将其作为 `Arc<Storage<D>>` 持有，其`Drop` 释放分配。至关重要的是，`Cpu` 和 `Cuda` 都已经实现了相同的端口集。因此，我们需要的抽象是“可证明可托管的”：非 CUDA 后端 (CPU) 已经存在于这些特征后面。在接缝之上，没有任何变化。 `Tensor<T, D>` 保持单态； `models/` 和 `application/` 中的模型代码不断针对通用后端边界写入 `Self::matmul(...)`；无法将主机指针传递给 CUDA 内核的类型状态保证会逐字保留。在接缝下方，*在每个后端的编译工件内*，也没有任何变化：数据类型驱动的 `match T::DATA_TYPE => add_kernel_bf16x8` 重新出现不变。这种转换*仅在接缝处*发生，并且它的成本恰好是**每个高级操作一次间接调用** - 每个 `matmul`、每个 `attention_paged`、每个 `fused_add_rmsnorm` - 从不是每个元素，也从不是每个张量视图。这种操作粒度放置与 wgpu-hal 和 PyTorch 调度程序做出的选择相同，并且出于相同的原因：在整个 GEMM 或 flash-attention 内核上分摊的 vtable 间接寻址是免费的；分摊到一个元素上的一个是致命的。
具体来说，设备调度变成了运行时函数指针； dtype 调度在编译时保持 `match` *在插件内部*。 RustInfer 今天合并的两个轴——“哪个设备”和“哪个 dtype”——被清晰地分开：设备动态，dtype 在后端保持静态。
### 进程内对象安全特征系列
我们引入了四个 `dyn` 可用的特征，它们一对一地反映了现有的端口——它们不是平行宇宙，而是 `Device`/`MemoryPort`/`ExecScope`/`Allocator` 的对象安全*投影*：- `dyn Backend` — 已加载后端实例的面向注册表的句柄。它拥有身份（`backend_id`、`name`、目标计算能力）、公开 `capabilities() -> Capabilities`、枚举设备并出售 op vtable。它是 `domain/ports/backend.rs` 中现有毯子 `Backend: LlmBackend + DiffusionBackend` 超级特征的对象安全兄弟。
- `dyn Device` — `domain/exec::Device` 的对象安全投影。持有 `DeviceId`，创建流，并且*是*一个分配器（它承担 `dyn Allocator` 的角色，而不是像 ONNX Runtime 那样通过内存信息查找来分割分配 — RustInfer 的 `Storage`/`ExecScope` 所有权模型更清晰，我们保持这种清晰度）。
- `dyn Stream` — `exec::Stream` 的对象安全投影，包装不透明的 `StreamHandle(*mut c_void)`（用于 CUDA 的 `cudaStream_t`，用于 CPU 的 `()`/单元）。现有的 `ActiveGuard`/`enter()` 设备绑定规则映射到 `dyn Device` 上的输入/恢复对。
- `dyn Allocator` — 现有 `Allocator` 的对象安全投影（基于 `Layout` 的端口已被扩散 VAE 池使用）。分配和释放都绑定到所属设备，因此*删除器随句柄移动*（更多内容见下文）。
这些是“进程中”特征——每个消费者编程所针对的抽象，无论后端是静态链接还是动态加载。静态链接的 CPU 后端直接实现它们，无需 FFI。 `Box<dyn Backend>` 是注册表存储的内容。
### 类型擦除的张量和值
穿过接缝流动的是 `DeviceTensor`：一个*借用的视图*，从来不是所有者，并且 - 这是关键 - 仅在单个同步 vtable 调用期间有效。它是一个携带 `{ raw_ptr: *mut c_void, dtype: DTypeId, rank: u8, shape: [i64; MAX_RANK], strides: [i64; MAX_RANK], byte_offset: u64, owner_backend_id: u32 }` 的 `#[repr(C)]` 普通旧数据结构。它故意镜像 **DLPack `DLTensor`** 形状，以便与 PyTorch/CuPy/JAX 的互操作是布局巧合而不是转换，但它不是 `Tensor` 的免费 Arc-less 别名 - 并且必须明确说明所有权故事，因为这里的擦除是 RustInfer 的编译时 RAII 保证暂时中止的地方。有两个基本事实使得建筑成本低廉。首先，运行时 dtype 标记*已经存在*：`domain/dtype/mod.rs` 使用稳定常量（`BF16 = 2`、`F8E4M3 = 5`，...）和从 id 1024 开始的可扩展注册表定义 `DTypeId(u16)`。编译时 `Dtype::DATA_TYPE` 和运行时 `DTypeId` 已经是同一事实的两个视图； Seam 只是选择运行时的一个。其次，描述符所需的每个字段都已在 `Tensor<T, D>` 内部具体化 - `shape`、`strides`、`numel`、`is_contiguous` 和 `offset_elems` - 因此构建 `DeviceTensor` 是一个字段副本加上两次廉价转换，而不是分配。
但它“不是”“免费、零拷贝导出”，而且差距很重要。 `Tensor<T, D>` 通过 `storage: Arc<Storage<D>>` (tensor.rs:21) 拥有其字节，其 `Drop` 在最后一个 `Arc` 释放时释放设备分配。 `DeviceTensor` 只携带 `raw_ptr` ——它不能携带 `Arc`，因为该结构必须在 C-ABI 交叉中幸存下来，而 Rust 的 `Arc` 机制没有任何意义。因此，导出遵循 **主机端保持活动契约**：投影 `&Tensor<T, D> -> DeviceTensor` 借用张量，并且调用者（始终是主机）通过在同步提交中将拥有的 `Tensor` 保留在其自己的堆栈帧上来保证支持 `Arc<Storage<D>>` 的寿命比调用长。因为从主机的角度来看，每个 op-vtable 调用都是同步的——它将工作提交到后端的流上并返回；在流完成后主机丢弃 `Tensor` 之前，`Storage` 不会被释放 — 借用是健全的，无需任何跨 FFI 引用计数传输。还有第二个更窄的转换来协调：描述符的 `raw_ptr` 和 `byte_offset` 是绝对字节，而 `Tensor` 存储 `offset_elems` 和 `is_contiguous` 标志；导出将 `offset_elems * T::SIZE_BYTES` 折叠为 `byte_offset`（或直接折叠为 `raw_ptr`）并逐字复制步幅，因此非连续或子视图张量会忠实地交叉，而不是默默地假定为稠密。这种分割 - *插件拥有它分配的缓冲区，并用句柄运送它们的删除器；主机拥有 `Storage` 支持的缓冲区，它仅借给一次调用* - 是完整的所有权规则。这两个方向不是对称的，不能混为一谈：主机拥有的 `Arc<Storage>` 被“借用”到插件中，持续一段调用时间，主机上有保持活动的义务；插件分配的必须持续存在的缓冲区（工作空间、VAE 池板）由插件“拥有”，并通过与其句柄一起移动的删除器释放。 `DeviceTensor` 从来不拥有任何东西；它是一个描述符。
固定的 `[i64; MAX_RANK]` 数组施加了具体的排名上限，我们将其设置为 `MAX_RANK = 8` — 舒适地高于代码库中的每个 LLM 和扩散张量（最深的是 5-D 转换激活）。超出等级的张量不会被默默地截断：导出返回 `OpError::Unsupported` 而不是产生格式错误的描述符，并且堆指针 `shape_ptr`/`strides_ptr` 变体被保留作为未来的后备，以防真正的高等级消费者出现。选择一个小的内联上限使描述符成为单个缓存行友好的 POD，它按值传递或按 `&` 传递，而无需堆接触，这就是每个操作跨越一次的全部意义。
我故意拒绝 c10 将 `DispatchKeySet` 烘焙到擦除张量中的方法。 RustInfer 没有自动分级，也没有功能化层，因此多轴 64 位键集是由于我们不存在的问题而产生的意外复杂性。所有者身份是单个`u32 backend_id`，仅此而已。
继承自 ORT 的 `OrtValue` 课程的关键规则：擦除将编译时 `match T::DATA_TYPE` *保证* 转变为运行时 `DTypeId` *检查，必须在边界重新验证*。错误的 `dtype` 标记是内存损坏，而不是类型错误；主机未能使其 `Storage` 保持活动状态的陈旧 `raw_ptr` 也是如此。在插件的内部 `match` 运行之前，接缝会在进入每个后端调用时重新验证 `dtype` 和 `owner_backend_id`。这种验证与保活合约一起构成了擦除的代价，并且每次操作只需支付一次。
### 算子执行调度操作如何找到正确的后端内核？我们在模型加载时*一次解析设备轴，而不是每次调用——TensorRT 通过预先解析其 DAG 学到的教训。在加载时，为模型选择的后端是固定的，并且它的 op vtable 被捕获；然后模型的调用站点通过捕获的 `dyn Backend` / op vtable 进行调度。没有每次调用的注册表遍历，也没有在热路径上进行字符串查找。一次解析简单的 `(op_id, dtype, backend_id)` 映射就足够了；在存在具体的第二轴之前，我们明确拒绝推广到多轴调度网格。
在后端内部，调用使用当前存在的“相同”代码。对于 CUDA，vtable 的 `add` thunk 在传入的 `DTypeId` 上重新单态化，并调用现有的基于 `match` 的包装器 - `add_kernel_bf16x8` 和朋友保持不变。该插件是静态调度重生的地方：设备动态停止在 `.so` 边界； dtype 调度在少数臂上保持分支预测的 `match`。
### 能力描述符和后备
每个后端公开一个 `Capabilities` 描述符 - 在任何工作之前*查询的 `#[repr(C)]` 值：dtype 位集、op 位集、最大工作空间、功能标志（分页注意力、cuda-graph 捕获、fp8 层 `KvQuantTier`）和计算能力范围。我们遵循 TensorRT 来之不易的教训，将 RustInfer 当前的“编译或不编译”模型无法区分的两个轴分开：*功能能力*（是否支持 `(op, dtype)`？ - 可查询，细粒度）与 *硬件兼容性*（这个 GPU 拱形是否在范围内？ - 加载时粗略接受/拒绝）。这使得 CUDA 后端拒绝 Ampere 卡上的 fp8，并产生与完全拒绝太新的架构不同的、响亮的错误。为了优雅降级，我们保留现有的 `OpError::Unsupported`（已由 CPU 后端的部分操作返回）作为每操作运行时回退信号。这是 RustInfer 相对于 PJRT 和 TensorRT 的结构优势，后者只能在整个程序粒度上回退：因为 RustInfer 拥有*设备*级别的抽象，并且 CPU 后端已经实现了*每个*端口，所以它可以逐个操作从 CUDA 回退到 CPU。不可协商的条件是 CPU 后端保持**静态链接**作为始终存在的终端回退（ORT 的强制 CPU EP），永远不会落后于插件 ABI，并且**每个跨后端主机往返都被记录**。静默 `Memcpy` 插入是一种延迟枪，会悄悄破坏 ORT 和 PyTorch 中的 LLM 解码吞吐量；使其可观察是强制性的，而不是可选的。主机往返还会以相反的方向重新参与上面的保持活动合约：暂存的主机缓冲区必须比副本寿命更长，而 `Storage` 所有权使这一点变得明确而不是偶然。
### 共存和注册表
多个后端实例共存，因为注册表是一个拥有的、可删除的对象 - 一个 `Registry` 持有由平台名称和优先级键入的 `Vec<Box<dyn Backend>>` - 而不是由静态初始化副作用突变的进程全局单例。多租户推理服务器可以保存自己的注册表，注册静态 CPU 基线以及任何动态加载的插件，从与探测到的 `Capabilities` 相交的配置中为每个请求选择一个后端，然后彻底删除整个内容。静态CPU后端通过`linkme`进行自注册（仅限链接时）；动态后端在加载后显式注册。这提供了确定性启动，并且因为没有什么是全局的、真正的卸载和热插拔——这正是现有的 ZMQ 工作子进程模型已经想要的。
### 为什么这是重构，而不是重写决定性的观察结果是代码库中已经存在接缝。 `MemoryPort` 已经以原始字节进行流量； `Storage` 已经将所有分配集中在单个 RAII 所有者背后； `DTypeId`已经提供了运行时标签； `DLTensor`形擦除是布局选择，不是新机械； CPU 后端已经证明非 CUDA 后端可以满足每个端口。接缝上方的静态通用世界被完整保留，接缝下方的 dtype `match` 也被完整保留，唯一真正的新东西是每个高级操作一个 fn-ptr 间接、一个借用的带有主机端保持活动合约的 `DeviceTensor` 描述符，以及一个用于保存共存后端的注册表对象。 C-ABI 插件垫片（在 ABI/加载部分中介绍）固定在这些进程内特征之上；它不会取代它们。

## 3. 异构执行引擎：Dispatcher、Placement 和 Scheduler
*定义了接缝后，我们确定了第一个版本中实际穿过接缝的范围。这里的决定性举措是限制：MVP 的目标是每个模型只有一个活动后端 — 匹配当今的单设备、单流、`block_size == 1` 不变式 — 并将整个跨后端放置、分区和对等传输子系统推迟到仅附加扩展链后面，因此第一个稳定的 ABI 不会过度适合未执行的功能。
### 针对当前代码陈述的问题
如今，RustInfer 仅有一种执行模型，并且完全由 Rust 类型检查器解决。 `Tensor<T, D>`携带设备作为通用参数，`Runtime<T, D, M>`对其进行单态化，公共入口点`serve_loop::run_with_model<M>`绑定到`M: DecoderModel<bf16, Cuda>`并构造一个具体的`Runtime<bf16, Cuda, M>`。每个运算符调用（`MathOps::add(scope, a, b, dst)`、`FusedOps::attention_paged(...)`）都是一个静态特征方法，在 CUDA impl 内部，进入 `ExecScope` 防护，解包 `CudaStream` 和 `T::DATA_TYPE` 上的 `match` 以选择内核符号。没有运行时内核注册表，也没有运行时设备选择；设备是在编译时通过单态选择的，数据类型是由优化器崩溃的 `match` 选择的。这是 RustInfer 最大的性能资产，下面的设计一定不能丢弃它。它还限制了首先交付的现实情况。今天的运行时仅驱动一个设备，每个 `ExecScope` 运行单个流，并在 `block_size == 1` 下运行。没有进程内的第二个后端，没有跨设备指针，也没有操作符在 `Tensor` 的 `D` 所说的地方之外的任何地方运行的概念。任何诚实的计划都必须区分使现有单后端世界在运行时可加载的变化（即可交付成果）与现有代码从未使用过的多后端机制。我们在下面明确地画出这条线，并让它控制进入第一个稳定 ABI 的内容。
我们最终要求满足的约束与代码假设的相反：不要假设单个活动后端。最终，我们必须发现后端，查询它们的功能，将每个算子放在最好的算子上，同时安排多个算子的工作，并在它们之间移动张量——CPU+CUDA、CUDA+Metal、多 CUDA、任意混合。但“最终”是关键词。本节的知识核心是一个问题：静态通用世界在哪里结束，类型擦除、动态调度世界在哪里开始？首先针对单个运行时加载的后端准确地回答这个问题，然后多后端故事就变成了附加扩展，而不是第二种架构。
### 接缝所在的位置
接缝已经完成了一半，位于内存端口 (`device.rs`) 和高级操作端口处。 `alloc_bytes`、`upload`、`download` 和 `copy_device_to_device` 已经以原始 `NonNull<u8>` 加上字节数表示，而不是以 `Tensor<T, D>` 表示。 `Cpu` 和 `Cuda` 都已经实现了相同的端口集，并且 CPU 后端已经为它缺少的操作返回 `OpError::Unsupported` - 回退信号已经在类型系统中。这证明了抽象可以托管非 CUDA 后端而无需重写，这是自然的切线。现实的路径不是对运行时张量的重写；而是对运行时张量的重写。它将这些现有端口视为进程内后端特征，并在其上安装 C-ABI 插件垫片。规则是：在接缝之上，保持 `Tensor<T, D>` 和 `Runtime<T, D, M>` 的模型代码完全单态；在接缝处，将每个高级运算符降低为通过不透明张量进行的单个平面 C-ABI vtable 调用；在接缝下方，在每个后端内，立即在 dtype 标记上重新单态化并逐字运行现有的 `match T::DATA_TYPE -> kernel_bf16x8` 路径。设备调度成为每个 matmul 或注意力支付一次的运行时函数指针； dtype 调度保持在后端编译时。我们为每个高级操作支付一个间接费用，而不是每个元素。这是 wgpu-hal 放置（以 op 粒度调度），而不是 PyTorch 的每元素 TensorIterator，并且它是唯一保持热内核不受影响的放置。
具体来说，不透明张量（命名为 `DeviceTensor`）是一个 `#[repr(C)]` POD，携带原始设备指针、一个 `dtype_tag: u16`、一个 `device_kind` 和 `device_id`、一个小型固定容量形状/步幅/偏移块以及一个 `owner_backend_id`。它特意采用 DLPack `DLTensor` 形状，并用螺栓固定了所有者字段；在 FFI 边缘采用 DLPack 布局基本上可以免费购买与 PyTorch/CuPy/JAX 的零拷贝交换，并且是比我们发明自己的更好的有线格式。 `owner_backend_id` 字段从第一天起就值得保留，即使 v1 运行时从未读取它来做出放置决策：它是两个字节，它是未来多后端传输层将关键的内容，并且它是我们希望在单后端情况下强制执行的删除器旅行与句柄规则（如下）的锚点。现在携带它不需要任何费用，并且可以避免以后出现 ABI 中断。我们明确拒绝在张量上携带 c10 风格的 `DispatchKeySet`：该 64 位多轴键集的存在是为了分层自动分级和功能化，而 RustInfer 没有。 `DeviceTensor` 携带数据和身份，仅此而已。
我们大声指出硬安全后果，因为这是腐败隐藏的地方：张量跨越接缝的那一刻，编译时 `match T::DATA_TYPE` 保证变成了运行时 `dtype_tag` 检查，后端必须重新验证。错误的标签是内存损坏，而不是类型错误。这是 OrtValue 的教训，边界必须在每个条目上强制执行它，在单后端构建中不低于在任何未来的多后端构建中。
### v1 是什么，以及延迟的是什么
我们致力于分阶段的范围，并且我们使 ABI 中的阶段边界成为承载而不是期望。**v1（MVP，可根据今天的代码发布）。** 每个模型只有一个活动后端 - 运行时已经强制执行相同的不变量，只是现在后端是在运行时选择的，而不是通过单态化。整个模型都依赖于那个后端；注意，RMSNorm、RoPE 和分页 KV 操作保持共存；解码期间没有任何内容跨越设备边界，因为图片中没有第二个设备。工作是：将现有端口降低到 C-ABI vtable，加载一个后端（CUDA）作为插件，在模型加载时将每个操作解析为函数指针，然后运行。成功标准是“单后端运行时加载端到端工作”——工作线程启动 `dlopen` CUDA 插件，解决计划，并以与当今的单态构建相同的方式提供解码服务。 v1 中的任何内容都不需要传输矩阵、分区器、对等副本或一致性协议，因为操作可以运行的位置永远不会超过一个。
**后 MVP（端到端工作在 v1 后面）。** 多后端布局：能力驱动的分区器、跨后端传输节点、专用传输端口、对等复制矩阵和流依赖一致性。这是一个真正的新子系统 - 如今只有一个设备、每个范围一个流、`block_size == 1` 和零跨设备移动，因此当前代码或测试中都没有模拟。推测性地将其构建到第一个稳定的 ABI 中会使该 ABI 过度适合未使用的功能。所以它不会进入核心vtable。它稍后作为通过类型化扩展链（在 ABI 下描述）的附加扩展到达，以我们已经携带的 `owner_backend_id` 为密钥。因此，第一个稳定的 ABI 描述了一个单活动后端世界——这正是代码库的其余部分已经存在的世界——并且在没有重大修订的情况下增加了多后端支持。
这种分阶段并不是对异质性的退却，而是异质性的退却。正是这种纪律让第一个 ABI 变得小而正确。以下部分详细说明了 v1 调度和 ABI，然后勾勒出延迟放置/传输设计，以便了解其最终形状，并且 v1 ABI 可证明与其向前兼容。
### 调度模型 — 解析一次，而不是每次调用我们故意不构建 PyTorch 风格的每次调用调度表。参考系统在这里清晰地分开：PyTorch 在每次调用时通过 `DispatchKeySet` 索引 fn-ptr 网格； ONNX 运行时通过 `GetCapability` 在加载时对图进行一次分区，并冻结每个节点的计划； TensorRT 在构建时解析 DAG，运行时队列根本没有查找。 RustInfer 的解码循环运行相同的运算符序列数百万次，因此 TensorRT/ORT 模型是正确的模型：在模型加载时将放置一次解析到计划中，然后以零调度开销执行。
因此，调度键是最小的三元组 `(op_id, dtype, backend_id)`，在模型加载时解析为每操作函数指针一次。 `op_id` 枚举现有的端口方法（`MathOps` / `FusedOps` / `DiffusionOps` 表面）； `dtype`为现有的`Dtype::DATA_TYPE`； `backend_id` 是布局决策。在 v1 中，`backend_id` 是一个常量 - 有一个后端 - 因此解决的计划只是“每个操作都指向其 `(op_id, dtype)` 的一个加载后端的 fn-ptr”。三元组的形状使得后 MVP 的情况（其中 `backend_id` 实际上每个操作都不同）不需要更改键，只需要一个填充它的分区器。我们拒绝将其概括为多轴键集，直到具体的第二轴（自动分级，功能化）实际存在 - 每个首先构建通用键集的参考作者现在都将其描述为偶然的复杂性。
|关注|拒绝接近|选择的方法|为什么 |
|---|---|---|---|
|什么时候发货 |每次调用表 (PyTorch DispatchKeySet) |一次性解决计划 (ORT/TRT) |解码循环重复相同的操作；支付决议一次|
|钥匙形状| 64 位多轴按键组 | `(op_id, dtype, backend_id)` 三重 |不存在 autograd/functionize 轴来证明它的合理性 |
|数据类型处理 |运行时注册表查找| `match T::DATA_TYPE` 后台内部 |保留现有的零开销内核选择 |
|张量恒等式 |张量上的 c10 键集 | DLPack 形状的 POD + 所有者 ID |免费换乘；没有继承的复杂性|
|多后端投放 |在 v1 核心 ABI 中 |推迟到延伸链|今天没有锻炼；保持第一个稳定的 ABI 较小 |
### 放置和分区（延迟 - 设计草图）该子系统是后 MVP 的；它仅在单后端运行时加载端到端工作后才发布，并且通过扩展链而不是核心 vtable 进入。我们指定其预期形状，以便 v1 ABI 可以显示以附加方式容纳它。
布局将是一个两阶段、功能驱动的分区，以 ONNX Runtime 的 `GetCapability` 为模型。加载时，主机枚举已注册的后端，将每个后端的探测到的 `Capabilities`（`#[repr(C)]` 结构：dtype 位集、op 位集、最大工作空间、分页注意力和 CUDA 图形标志、最小/目标计算能力、定量层）与操作员级配置和模型所需的操作相交。然后向每个后端提供操作员列表，并按优先级降序声明其支持的内容。无论加速器声称的是什么，都落在 CPU 后端的身上，它始终存在且始终最后 — ORT 强制-CPU-EP 规则。输出是冻结的布局计划：（op、后端、解析的 fn-ptr）的有序列表，在分区边界插入显式跨后端传输节点。请注意，`Capabilities` 在 v1 中也很有用——即使是单个后端也必须回答“你支持这个 `(op, dtype)` 吗？”因此主机可能会在加载时而不是在解码过程中大声失败——因此功能查询条目保留在核心虚函数表中；只有跨多个后端使用它的多后端分区程序才会被延迟。
特别是对于 LLM 解码路径，现实的计划将整个模型保留在一个后端上，这正是 v1 根本不需要分区器的原因：对于单个常驻后端，分区很简单“这里的一切”。当分区器确实到达时，它仍然足够通用，可以分割扩散图或卸载单个不支持的操作，并且它遵循横切警告，即LLM热路径中的静默主机往返会破坏延迟——每个传输节点都是显式的且可记录的，因此解码步骤内的CUDA→CPU回退在加载时是可见的，在运行时并不神秘。
我们将功能分为两个轴，直接学习 TensorRT 课程：功能功能（是否支持 `(op, dtype)` - 可查询，驱动每个操作的放置）与硬件兼容性（加载时的粗略计算能力接受/拒绝门）。这使得 CUDA 后端可以干净地拒绝旧卡上的 fp8，并因拒绝太新的架构而产生明显的、响亮的错误。功能能力查询是 v1 中的部分；每操作放置消费者是延迟部分。### 跨后端内存传输和一致性（延迟 - 设计草图）
转会也是MVP后的，也是通过延伸链进入的。 v1 恰好有一个后端，因此唯一的内存移动是主机↔设备流量，现有的 `upload`/`download`/`copy_device_to_device` 已经在一个后端内执行 - 没有跨后端传输需要设计，并且它不属于第一个稳定的 ABI。
当多后端落地时，传输将由一个专用传输端口（称为 `DeviceTransfer`）拥有，与计算分开，就像 ORT 和 c10 将数据移动与内核分开一样，并作为扩展结构添加，而不是嵌入核心运行时块。传输矩阵按后端对解析：相同后端相同设备使用现有的 `copy_device_to_device`； CPU↔加速器采用现有的`upload`/`download`；同一供应商（多 CUDA）上的加速器↔加速器使用可用的对等副本，否则使用主机阶段的反弹；跨供应商（CUDA↔Metal）始终通过固定主机内存进行阶段。一致性故事故意简单且按流排序，重用现有的 `ExecScope`/`Stream`/`synchronize` 模型：传输节点在目标流上排队，依赖于源的完成，并且现有的 `ActiveGuard` 设备恢复规程可扩展到多个设备，因为 `DeviceId` 已经是一流的`exec.rs` 中的值。一致性模型重用了已经存在的原语，这就是推迟它是安全的原因——我们并没有把自己逼到墙角，只是拒绝在 v1 中发送一个未执行的矩阵。不可协商的所有权规则由每个不会崩溃的稳定边界共享，即使只有一个后端也已经适用于 v1：删除器随句柄移动。 CUDA 后端分配的内存只能由该后端的 free 函数释放。每个拥有存储的 `DeviceTensor` 都被包装在 Rust 端的 `Drop` 中，该 `Drop` 调用拥有后端的销毁函数（PJRT_Buffer 所有权模型），由我们从第一天开始携带的 `owner_backend_id` 作为密钥。当后端由与主机不同的工具链构建时，这可以防止跨 DLL 双重释放 - 在任何后端被 `dlopen`ed 时（早在第二个后端出现之前）就存在这种危险。内存种类（HBM、固定、统一）作为分配器上的可发现属性公开，而不是作为单独的内存信息分配器查找 — 我们保留 RustInfer 清晰的 `ExecScope`/`Workspace` 所有权，并拒绝 ORT 尴尬的 `OrtMemoryInfo` 间接寻址，同时仍然尊重 PJRT 艰难学习的设备与内存区别。
### ABI 以及后端的加载方式插件 ABI 是一种手工制作的 `#[repr(C)]` 结构 `extern "C"` 函数指针，带有一个导出的入口符号 `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`。 vtable 和每个 args 结构的第一个字段是 `abi_version`/`struct_size`，并且字段是仅附加的 - PJRT 唯一最便宜的向前和向后兼容性机制，以及允许稍后添加延迟传输/放置条目而不会破坏已加载插件的精确机制。 vtable 被分组，镜像 TensorRT 的 Core/Build/Runtime 分割：始终存在的标识块（名称、abi_version、backend_id、目标计算容量）、注册/构建块（`capabilities()`、计划构建）和热路径运行时块（alloc/free/upload/copy/per-op enqueue）。 v1 核心 vtable 就是这么多，仅此而已：身份、单后端能力查询、单后端计划解析和每操作排队路径。多后端传输 (`DeviceTransfer`)、对等复制和跨后端分区器挂钩不在核心 vtable 中；与其他可选和供应商操作（fp8 层、`qkv_norm_rope_scatter`、集体）一样，它们挂在类型化链表扩展链上，因此核心保持小而稳定，并且第一个稳定的 ABI 不会过度适合未执行的功能。我们暂时拒绝 `abi_stable` 和 `stabby`：操作集很小，固定，并且已经枚举为端口，因此手工卷起的 vtable 不那么繁琐，并提供完全控制；如果表面需要传递 Rust 集合，它们仍然是后备。错误以 `i32` 代码加上带有访问器函数的不透明错误句柄的形式交叉，而不是作为展开 - 每个入口函数都包装 `catch_unwind`，因为跨 FFI 边界的恐慌会立即发生 UB。 CPU 后端已返回的 `OpError::Unsupported` 映射到保留代码并保留每操作回退信号。发现是明确的，而不是静态初始化魔法。主机读取 config/env 列表（PJRT `name:path;...` 形式），每个 `libloading::Library::new`，查找单个条目符号，检查 `abi_version`，调用 `capabilities()`，并将平台名称和优先级下的 vtable 注册到拥有的、可删除的 `Registry` 中，而不是进程全局单例。每个通过静态初始化副作用注册的参考系统（PyTorch、TVM、TensorRT）都被记录为顺序脆弱且不可卸载；显式入口点提供确定性负载、真正的卸载/热插拔以及每服务器注册表对象，这正是多租户推理服务器所需要的。 `Library` 在其创建的每个资源的生命周期内都保持活动状态 - 该插件的寿命比其句柄和流的寿命长。在 v1 中，注册表通常保存两个条目（静态 CPU 基线和一个加载的加速器），模型绑定到其中一个；注册表的多条目形状对于 MVP 后的情况来说已经是正确的，无需更改。
CPU 后端很特殊并且一直很特殊：它既是静态链接的（通过 `linkme` 自注册，因为 `linkme` 是仅链接时间的并且在 `dlopen` 中无用）并且可以作为插件使用。静态链接使其成为始终存在的终端回退，任何 `dlopen` 故障都无法消除。在 v1 中，这保证了即使 CUDA 插件加载失败，worker 也始终可以启动 CPU 驻留模型；在后 MVP 世界中，这也是使每操作 CUDA→CPU 回退安全的原因。
### 解耦构建（.cu 的痛苦）这是 MVP 的另一半，它独立于运行时加载工作并与之互补：它可以根据自己的优点进行交付，并且不等待任何多后端功能。所有 CUDA 内核源代码都从 `infer-worker` 移至具有自己的 `build.rs` 的独立 `infer-backend-cuda` cdylib。该板条箱编译为多架构 PTX/fatbin（sm_80/86/89/90 加上 PTX 回退），并在运行时通过 CUDA 驱动程序 API 通过 `cudarc` 的动态加载功能加载它们，其中 `dlopen` 是 `libcuda`/`libnvrtc`。然后，工作核心使用零 CUDA 工具链进行构建——没有 nvcc、没有 libclang、没有 cuDNN 前端发现、没有 `nvidia-smi` 主机架构检测——直接消除了 472 行 `build.rs` 耦合和 `default = ["cuda"]` 硬依赖。 `default = ["cuda"]` 将含义从“编译并链接工具链”更改为“在运行时加载捆绑的 CUDA 插件”。运送 fatbin+PTX 而不是单个主机检测到的 `sm_XX` cubin 会消除主机 GPU 特异性；驱动程序在模块加载时 JIT PTX 到正在运行的 GPU，并将其缓存在磁盘上。每个参考运行时都将内核工具链保留在供应商插件内；这只是采用这种纪律。因为这种解耦正是产生第一个可加载单后端插件的原因，所以它和 v1 调度/ABI 工作集中在同一个可交付成果上：一个在运行时构建干净并加载 CUDA 的工作程序。
### 与调度程序和运行时集成现有的 `Runtime<T, D, M>` 作为每个后端执行单元保留下来，每个常驻后端一个单态实例，位于接缝下方。在其上方，`DecodeEngine` 和 `serve_loop` 丢失其硬编码的 `DecoderModel<bf16, Cuda>` 绑定和具体的 `Runtime<bf16, Cuda, M>` 构造，而是驱动从注册表解析的类型擦除的 `BackendHandle`。在 v1 中，该句柄解析为单个加载的后端，因此对 `serve_loop` 的更改是“在运行时选择后端，而不是在通用绑定中命名它”——包含的编辑，而不是重新架构。 `infer-scheduler` 板条箱的协议未受影响：它已经通过 `protocol` 消息类型通过 ZMQ 与工作程序通信，并且子流程接缝是一项潜在资产 - 不受信任或实验性后端可以在工作程序子流程中隔离，而不是 `dlopen` 进入调度程序/服务器流程，从而提供参考系统没有的沙箱选项。 C ABI 上的可信后端版本控制；不受信任的进程通过现有的 ZMQ 泵进行隔离。调度程序的放置输入是加载时间计划；它的运行时作业——批处理、通过 `GlobalKvAllocator` 进行 KV 分配、请求准入——没有改变，因为放置已解决一次，并且热循环仍然看到已解决的函数指针的固定序列。这一切都不依赖于现有的多后端布局；无论计划来自简单的单后端解决方案还是未来的分区程序，调度程序都会看到相同的固定 fn-ptr 序列。
最后，RustInfer 需要的横切功能——CUDA 图形捕获、量化层选择、跟踪——被添加为包装端口特征的 Burn 风格的装饰器后端，而不是对内核或 ABI 的编辑，并且瘦后端的广泛操作覆盖范围来自 PyTorch 风格的分解内核（以原语表示的复合操作，自动重新调度）。当功能集增长时，插件表面保持较小，并且多后端放置和传输子系统在到达时以相同的方式增长：在单后端运行时加载可交付成果被端到端证明之后，通过扩展链进行附加。

## 4.动态加载、插件架构和稳定的ABI*仅当边界本身在独立编译下健全时，接缝才成立。本节指定稳定的 ABI：一个入口符号 `rustinfer_get_backend_api`、一个 `#[repr(C)]` 仅附加 vtable、不透明句柄，以及主机和插件共享相同 *源* 版本的 `infer-core`/`infer-backend-abi` 但绝不是编译工件的规则 - 因此 `OpError` 被降低为 `i32` 并且从不传输作为跨线的 Rust 枚举。*
### 本节解决的问题
如今，RustInfer 是一个静态链接的单态二进制文件。 `Tensor<T, D>` 将其设备作为通用参数（`tensor.rs`、`PhantomData<T>` over `Arc<Storage<D>>`），`Runtime<T, D, M>` 在设备上单态化，`serve_loop::run_with_model` 硬绑定到 `M: DecoderModel<bf16, Cuda>`（在 `application/serve_loop.rs:71` 确认）。该设备由编译器选择； dtype 由每个内核包装器内的 `match T::DATA_TYPE` 解析（例如，`kernels/fused_qk_norm_rope.rs:120` 调度到 `fused_qk_norm_rope_cu_bf16`）。没有运行时后端选择，没有进程内多后端，也根本没有插件界面。更糟糕的是，因为每个 `.cu` 文件都位于 *内部* `infer-worker` 和 `build.rs`（471 行，在 `default=["cuda"]` 上门控）通过 `cc::Build::cuda(true)` 将所有文件编译到静态 `infer_kernels` 存档中，而 bindgen 在 cuBLAS/cuDNN 标头上运行，因此如果没有，核心包实际上无法构建完整的 CUDA 工具链、libclang、cuDNN 前端和主机 GPU，其计算能力 `nvidia-smi` 烘焙到 `sm_XX` 中。该工件在构造上是特定于主机 GPU 的。 `SKIP_BUILD_KERNELS` 作为转义存在，但随后链接失败。
目标是让后端独立于运行时被发现、加载、版本协商和升级，并让核心使用零 CUDA 工具链进行构建——而不丢弃单态热路径，这是 RustInfer 最大的性能资产。
### 静态、动态、插件、运行时加载：建议
这四个选项并不相互排斥，正确的答案是分层组合而不是单一机制：|机制|买什么 |成本/为什么被拒绝作为*唯一*答案 |
|---|---|---|
|纯静态（今天）|零调度开销，最简单的构建图 |没有 CUDA 就无法构建 Core；没有运行时后端选择；没有独立升级|
|货物功能（编译时`cuda`/`cpu`）|便宜，无 ABI |仍然每个二进制文件一个设备；重建以交换；工具链耦合不变|
| `dyn`-trait 进程内（单个二进制文件，多个后端链接）|运行时选择，无 FFI |所有后端仍然链接到一个工件 → 构建二进制文件仍然需要 CUDA 工具链；没有独立升级|
|通过 `libloading` 的 C-ABI 插件（推荐）|独立构建/版本/升级；核心不需要nvcc；真正的热插拔|每个操作一个 vtable 间接；必须手工构建并管理稳定的 ABI； FFI 风险恐慌 |
建议是：将 CPU 后端静态链接为始终存在的进程内基线（它已经实现了 `infrastructure/cpu/` 下的每个端口，`OpError::Unsupported` 用于它拒绝的操作 - 由 `op_ports.rs:24` 的 `CoreOps` 文档合同和 `infrastructure/cpu/mod.rs` 的 CPU 模块前导码确认），并移动每个加速器（首先是 CUDA， ROCm/Metal 稍后）位于运行时使用 `libloading` 加载的 C-ABI 插件后面。这是同时解耦构建（张力＃2）并启用独立后端升级的唯一选项，而静态 CPU 基线保留了零 FFI 回退路径，这里没有参考系统（不是 PJRT，不是 TensorRT）可以在*每操作*粒度上提供该路径。
请立即注意这引入的不对称性，因为它是整个设计的关键：静态链接的 CPU 后端和 `dlopen` 的 CUDA 插件是*相同端口特征的两种不同类型的使用者*，并且必须故意保持它们不同。 CPU 后端在进程中作为普通 Rust 特征对象/单态化使用 - `Tensor<T, D>`、`OpError`、`CoreOps` 都作为本机 Rust 值流动，没有 FFI，没有 ABI 问题。 CUDA 插件在 `.so` 边界上使用，其中*没有* Rust 类型可以作为值流动。相同的后端逻辑，两种传输。将它们混为一谈正是接下来几节要避免的陷阱。
### 静态通用世界结束，类型擦除世界开始（紧张#1）这就是症结所在，repo 已经把缝缝好了一半。剪切线是现有的 `MemoryPort` 特征 (`ports/device.rs`)：每种方法都已经讲原始 `NonNull<u8>` 加上字节大小 - `alloc_bytes`、`free_bytes`、`upload`、`upload_async`、`download`、`copy_device_to_device`、 `synchronize`。 `Cpu` 和 `Cuda` 的实现方式相同。这证明抽象可以托管非 CUDA 后端，而这正是 C ABI 想要操作的粒度。
接缝位于高级操作端口 (`CoreOps`/`DiffusionOps`/`MathOps`/`FusedOps`) 及其每设备实现之间的边界。具体来说：
- **接缝上方** — 型号代码，`components/`、`Runtime<T, D, M>`、KV 机械（`kv.rs`、`global_kv_alloc.rs`） — 与 `Tensor<T, D>` 相比保持完全单态。没有模型作者见过类型擦除的张量。这将保留编译时类型状态和 `Arc<Storage<D>>` RAII 不变。
- **在接缝处** — 每个高级操作调用都会降低为单个 `#[repr(C)]` vtable fn 指针调用，返回 `i32` 状态。参数是一个不透明的 `DeviceTensor` POD (`{ raw_ptr: *mut c_void, dtype_tag: u8, rank: u8, shape: [i64; MAX_RANK], strides: [i64; MAX_RANK], offset_elems: i64, owner_backend_id: u32 }`)、一个不透明的 `StreamHandle(*mut c_void)` 和一个小的 `#[repr(C)]` 每操作参数结构，其第一个字段是 `struct_size`。
- **接缝下方 - *内部*插件 `.so`** - 一个薄的 `extern "C"` thunk 验证参数，然后 `dtype_tag` 立即重新单态化：它逐字驱动*现有的* `match T::DATA_TYPE → add_kernel_bf16x8` 路径，登陆插件自己的私有 `impl CoreOps for CudaInner` 。设备调度成为一个运行时 fn 指针； dtype 调度保持编译时*在插件内*。
成本是每个 matmul/attention/rmsnorm 一次间接调用——而不是每个元素。这与 wgpu-hal 和 PyTorch 调度程序放置间接（操作粒度）的位置相匹配，并且它是 PJRT_Buffer 和 DLPack 的 `DLTensor` 的表示规则：携带 dtype 和 dims 作为纯数据的不透明句柄。我们故意拒绝 c10 的多轴 `DispatchKeySet` — RustInfer 没有 autograd/functionize 轴，因此 `(op_id, dtype_tag, backend_id)` 在模型加载时解析一次表（TensorRT 的预解析 DAG 课程）就足够了，而且简单得多。必须明确说明一个硬性后果：将 `Tensor<T, D>` 擦除为 `dtype_tag` 会将编译时保证转换为运行时检查。边界处的错误 `dtype_tag` 是内存损坏，而不是类型错误（OrtValue 警告）。因此，边界层必须在调试*和*发布中根据操作的入口声明签名来验证 `dtype_tag`。
### 插件到底是什么：共享源代码，单独的工件（独立编译合约）
上述一切都取决于一个易于陈述且易于违反的规则，因此它有自己的处理方式。 `infer-backend-cuda` 箱在内部是*普通的 RustInfer 代码*。它依赖于 `infer-core` 并重用端口特征 - 它包含一个私有 `CudaInner` 类型，其中包含 `impl MemoryPort for CudaInner`、`impl CoreOps for CudaInner`、`impl FusedOps for CudaInner`，其编写风格与今天的 `infrastructure/cuda/` 相同。它看到 `OpError`，它看到 `Tensor`，它看到 `Capabilities` 作为 Rust 类型，这很好 - *因为它只在自己的编译单元中使用它们*。这些特征实现是插件的私有实现细节； **它们永远不会像 Rust 值一样跨越 `.so` 边界。** 该插件是由它自己的 `rustc`/codegen 构建、单态化和布局的，而主机是由可能不同的一个构建的。这就是独立构建和发布的全部要点。
结果是不可协商的，必须以合同形式说明：**在 `.so` 边界上仅存在** `#[repr(C)]` `BackendVTable`、`#[repr(C)]` args/`DeviceTensor`/`Capabilities` POD、不透明句柄（`*mut c_void` 为缓冲区、流和错误详细信息）和 `i32` 状态代码。没有 `Vec`、没有 `String`、没有 `dyn`、没有 `&T`、没有 `OpError`、没有特征对象、任何类型的 `repr(Rust)` 值在写入另一侧后都不会在一侧读取。原因是精确的而不是迷信的：`repr(Rust)` 布局在独立编译中明确*不稳定*稳定，因此由插件生成并由主机读取（或反之亦然）的 `Vec`、`OpError` 或 `Capabilities`-as-Rust-struct 正在读取其字段顺序、填充、利基优化和判别编码主机不同意的字节到。这是未定义的行为，句号。 `#[repr(C)]` 是两个独立编译的工件保证一致的“唯一”布局，这正是它（而不是其他任何东西）被允许交叉的原因。这迫使对 `OpError` 进行特定的、重要的处理。 `OpError` 今天是一个实时的 `repr(Rust)` 枚举 - `pub enum OpError { Unsupported { backend, op }, … }` 位于 `ports/error.rs:5` - 现有的每操作后备故事取决于后端能够“说”“我拒绝这个操作”。将枚举越过边界是很诱人的，也是错误的。相反：插件 thunk 捕获其内部 `Result<_, OpError>`，将其降低到保留的 `i32` 状态代码（`Unsupported` 具有独特的众所周知的代码，以便主机知道回退到 CPU 基线），并可选择将结构化负载（有问题的后端名称和操作名称）隐藏在不透明的 `ErrorDetail` 句柄后面，主机稍后可以通过专用的查询`extern "C"` 访问器函数（返回长度并复制到主机提供的缓冲区中，从不返回 Rust `String`）。主机在看到代码后，**根据该数字代码加上从 `ErrorDetail` 句柄中提取的任何内容，在自己这边构造一个新的 `OpError`**。 Rust 枚举本身就存在于两侧；它根本就不是旅行的东西。这使现有的 `OpError` 驱动的控制流（包括 `OpError::Unsupported` 触发的每操作 CUDA→CPU 回退）保持完整，同时线路保持纯数字。
发出这种声音的兼容性窗口同样精确：**主机和每个插件必须从相同的*源*版本的 `infer-core` 和共享的 ABI 箱构建，但不需要共享已编译的工件、`rustc` 或代码生成设置。**他们同意的是 C ABI 的*数字含义* - `repr(C)` 结构的字段顺序和整数编码、状态代码枚举，vtable 槽排序——从来没有任何 `repr(Rust)` 布局。为了使该协议机械化而不是理想化，`#[repr(C)]` 边界类型位于一个小型专用板条箱 `infer-backend-abi` 中，其中*仅*包含 `repr(C)` 定义和整数常量，并且*不*包含 `repr(Rust)` 公共类型；主机和插件都依赖于它。 CI ABI 快照测试将每个边界结构和 vtable 的布局与签入的黄金文件进行比较，并且 lint 禁止任何非 `repr(C)` 公共项目出现在 `infer-backend-abi` 中。然后，`abi_version` / `struct_size` 门（如下）在加载时强制执行窗口。这是一条干净、可机械检查的线路，使插件成为真正独立的工件，同时保持安全。### 稳定的 ABI：手卷 `#[repr(C)]` vtable，因为 Rust 没有
没有稳定的 Rust ABI：根据上述合约，我们绝不会跨越边界发送 `Vec`、`String`、`dyn` 或任何 `repr(Rust)` 类型。存在三名候选人。 `abi_stable` 带来了布局哈希验证和稳定的集合，但繁重的仪式和较大的依赖性； `stabby` 更轻，但仍然强加了它的世界观；手动卷起的 vtable 可以完全控制*小、固定、已枚举的*操作表面。因为操作集正是现有的端口 - 大约 30 个 `CoreOps`/`DiffusionOps`/`FusedOps` 方法，由 `op_ports.rs:299` 处的 `OpBackend: CoreOps + DiffusionOps` 毯子实现枚举 - 手卷 `#[repr(C)]` 结构的 `extern "C"` 函数指针是实用的选择。仅当 Surface 需要跨线运送 Rust 系列时，我们才会保留 `abi_stable`，而当前的设计完全避免了这种情况。
该设计大量借鉴了 PJRT 的纪律。一个导出的条目符号：
```
#[no_mangle]
pub extern "C" fn rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable;
```
`
`abi_version`（`u32`，与 `struct_size` 配对，作为 `BackendVTable` 和每个 args 结构的第一个字段）是通用版本门，在 *first* 调用时检查；字段**仅追加**。这在不冻结主要版本的情况下购买了向前和向后兼容性 - 已知最便宜的稳定机制，直接源自 PJRT 的 `struct_size` 约定。 vtable 被分组以镜像 TensorRT 的核心/构建/运行时分割：始终存在的 **身份块**（`name`、`abi_version`、`backend_id`、目标计算能力）、**注册/构建块**（`capabilities()` *按值*返回 `#[repr(C)] Capabilities` POD，分配器设置），以及**热路径运行时块**（`alloc`/`free`/`upload`/`copy_d2d`/每个操作排队，每个插槽返回 `i32`）。可选或特定于供应商的操作（来自 `QuantTier`、`qkv_norm_rope_scatter` 的 fp8 层，来自 `ports/collective.rs` 的集合）挂起类型化链表**扩展链**，因此核心 vtable 保持较小且稳定 - 这是“在不破坏 ABI 的情况下添加融合操作”的明确答案。
每个成功的稳定边界（tvm-ffi、PJRT）都共享并逐字采用的三个不可协商的安全规则：
1. **删除器随手柄移动。** CUDA 插件的缓冲区 `cudaMalloc` *仅*由该插件的 `free` fn 释放。不同的插件可能由不同的工具链构建；跨`.so` `free`是双免等待发生。每个返回的句柄——缓冲区、流、*和*上面描述的 `ErrorDetail` 句柄——都被包装在一个 Rust `Drop` 中，它调用原始插件的 destroy fn。
2. **错误作为 `i32` + 不透明错误句柄交叉，永远不会通过展开，也永远不会作为 Rust 枚举。** `extern "C"` 上的恐慌是即时的 UB。每个条目 fn 都包装 `std::panic::catch_unwind`，将捕获的恐慌转换为保留的错误代码，然后返回。 `OpError` 是从代码（以及任何 `ErrorDetail` 有效负载）在主机端重建的，从未作为值进行传输。对于其内核可以合法地 `OpError::Unsupported` 的框架来说，这是最重要的一条规则。
3. **版本控制大声。** 未经检查的 ABI 不匹配是 UB；检查过的一个是明显的加载时错误。 `rustinfer_get_backend_api` 在不支持的 `abi_version` 上返回 null，并且主机拒绝注册。
###发现、注册、版本协商、自主升级注册是**显式入口点**，而不是静态初始化魔法。每个通过构造函数副作用自行注册的参考系统（PyTorch、TVM、TensorRT）都被标记为顺序脆弱、不可卸载和容易出现段错误。相反，主机会扫描配置/环境列表 - 窃取 PJRT 的形状，例如`RUSTINFER_BACKENDS=cuda:/opt/ri/libinfer_backend_cuda.so;rocm:...` — 然后对于每个条目：`libloading::Library::new`，解析单个 `rustinfer_get_backend_api`，检查 `abi_version`，调用 `capabilities()`（按值返回 `#[repr(C)] Capabilities` POD），并将返回的 vtable 根据平台名称和优先级注册到*拥有的、可删除的* `BackendRegistry` 对象中（不是进程全局单例）。因此，握手是：首先是 ABI 版本门，然后在任何工作之前查询 `#[repr(C)] Capabilities` POD（dtype 位集、op 位集、最大工作空间、cuda 图形/分页注意力标志、最小/目标计算能力、量化层）。请注意，`Capabilities` 精确地作为平面 `repr(C)` 值进行交叉，因此它“不会”违反独立编译合约——它是数据，而不是通过引用传递的 Rust 结构。多租户推理服务器正是需要这样的：它可以构造、填充和删除每个服务器的注册表，从而提供确定性的加载*和*卸载——真正的热插拔。 `Library` 在其创建的每个资源的生命周期内都保持活动状态（插件必须比其句柄、流和*和*其 `ErrorDetail` 句柄的寿命更长）。
独立升级不属于这种设计：因为唯一的契约是仅附加的 C vtable 加上功能 POD，并且因为双方仅共享源版本兼容性，而不是编译工件，所以新的 `libinfer_backend_cuda.so`（较新的内核、较新的 CUTLASS、扩展链节点后面的新融合操作）会直接插入，而无需重新编译运行时，就像 PJRT 供应商轮仅在 `GetPjrtApi()` 处与核心相遇一样。 `linkme` 严格保留用于二进制 CPU 基线的自注册 - 它仅在链接时运行，对本机 Rust 特征对象进行操作，并且在 `dlopen` 中无用（且不必要）。
### 解耦构建（张力#2）所有 `.cu` 文件、`build.rs` 的 `cc::Build::cuda(true)` 调用、bindgen-over-cuDNN 步骤和 `nvidia-smi → sm_XX` 检测都从 `infer-worker` 移出到独立的 `infer-backend-cuda` cdylib 箱及其*自己的构建脚本中。该板条箱仍然依赖于 `infer-core`（为其私有 `CudaInner` 实现重用端口特征）和 `infer-backend-abi`（用于 `repr(C)` 边界类型），但这些是编译到插件自己的工件中的“源”依赖项 - 主机既不链接插件的内核也不链接其 Rust 实现。该插件将内核编译为多架构 PTX/fatbin 集（sm_80/86/89/90 加上 PTX 回退），并在运行时通过 `cudarc` 的 CUDA 驱动程序 API 及其动态加载功能（`dlopen`s `libcuda`/`libcudart`/`libnvrtc`）加载它们。驱动程序在模块加载时将 PTX JIT 到正在运行的 GPU，并将其缓存在磁盘上。然后，worker *core* 会在没有 nvcc、没有 libclang、没有 cuDNN 前端发现、没有主机架构检测的情况下进行构建 — `default=["cuda"]` 从硬编译依赖降级为“在运行时加载捆绑的 CUDA 插件”。这就是 PyTorch、ORT、TVM 和 PJRT 所做的事情：核心编译零内核；该工具链位于供应商 `.so` 内。
### 哪些内容跨越了边界，哪些内容仍在进程中跨越 C ABI，仅此而已：不透明设备缓冲区句柄、`DeviceTensor` POD（ptr + dtype 标记 + shape/strides）、`StreamHandle`、每操作 `#[repr(C)]` args 结构、`Capabilities` POD、不透明 `ErrorDetail` 句柄，以及`i32` 状态代码 — 命令*提交*，采用 TensorRT 的 `enqueue(desc, ptrs, stream)` 形状。坚定地保持进程内和单态化，*作为每一侧的原生 Rust 值*：`Tensor<T, D>`、`Runtime<T, D, M>`、`OpError`（从数字代码重构主机端）、插件自己的私有 `impl CoreOps for CudaInner` 特征对象、调度程序端 KV 编排， `ExecScope`/`Workspace`/`ActiveGuard`所有权（`exec.rs`），以及所有模型图逻辑。进程内特征路径（静态 CPU 后端，作为 Rust 特征使用）和 C-ABI 路径（CUDA 插件，作为 `extern "C"` 指针的 vtable 使用）是两个*相同后端逻辑的单独使用者*，而不是跨边界流动的相同对象 - 这种区别是保持独立编译声音的原因。主机拥有该流并提交；该插件拥有其工作空间（TensorRT 的分割）。 Burn 的装饰器模式（后端包装后端）是一种零 ABI 接触方式，可对 CUDA 图捕获、量化层选择以及稍后在端口特征之上进行跟踪，从而在功能增长时保持插件表面较小。预先存在的 ZMQ 工作子进程接缝（`serve_loop` 控制/数据泵）仍然是*不受信任的*后端的逃生口：C ABI 上的版本门可信插件，但通过 ZMQ 处理隔离实验插件，而不是 `dlopen` 将任意静态初始化代码放入服务器中。

## 5.后端构建系统：独立构建和发布
*定义 ABI 后，我们最终可以消除激发整个工作的构建耦合。删除工作线程的 471 行 `build.rs` 并将所有 `.cu` 编译重新定位到后端板条箱自己的构建中，这样就可以在没有 `nvcc`、`libclang` 和 `nvidia-smi` 主机架构固定的情况下构建核心 - 并且固定的多架构 fatbin 取代了主机检测，因此工件是可移植的。*
### 我们正在拆解的问题如今，GPU 工具链已融合到 Rust crate 图中。 `crates/infer-worker/Cargo.toml` 声明 `default = ["cuda"]`，`cuda` 功能将 `cc`、`bindgen` 和 `walkdir` 作为构建依赖项。然后，471 行的 `crates/infer-worker/build.rs` 做了四件不应该是工人工作的事情：它遍历 `src/infrastructure/cuda/kernels/**/*.cu` 并通过 `cc::Build::cuda(true)` 将所有 29 个 `.cu` 文件编译成静态存档 `infer_kernels`；它针对 `cuda_runtime`/`cublasLt`/`cudnn`/`cudnn_frontend` 标头在 `wrapper.h` 上运行 `bindgen`（需要 `libclang`）；它对 CUDA、cuDNN 前端和供应商的 cutlass 标头执行大量 conda/venv 发现，如果缺少任何标头，则会出现恐慌；而且——最具破坏性的是——它在 `detect_cuda_arch()` 中向 `nvidia-smi --query-gpu=compute_cap` 支付，以选择单个 `-arch=sm_XX`。因此，该工件被固定到构建主机中的任何 GPU，并且如果没有完整的 CUDA 工具链加上可见的 GPU，核心实际上无法编译。 `SKIP_BUILD_KERNELS` 逃生舱口只是推迟了痛苦：`kernels/add.rs` 中的静态 `extern "C"` 符号及其 27 个同级符号随后无法链接。
本节的架构目标是狭窄而具体的：使每个后端存储库在其*自己的*工具链上构建一个版本化共享库和多架构内核工件，并使 `infer-worker` 在没有 nvcc、没有 libclang、没有 cuDNN 前端发现和没有 `nvidia-smi` 的情况下构建。构建系统问题是本提案中其他地方描述的运行时接缝的下游，并且必须服务于该接缝：`.cu` 文件从工作器移出到独立的 `infer-backend-cuda` cdylib，并且工作器在运行时通过 CUDA 驱动程序 API 加载它。我们选择的构建工具是最能将 cdylib 的内核编译成可移植的多架构 blob 的工具。

### 每个后端存储库如何构建其共享库+内核工件
每个后端都成为一个独立的箱子，生成 `cdylib`：`infer-backend-cuda`、`infer-backend-rocm`、`infer-backend-metal` 和 `infer-backend-cpu`（最后一个是特殊的 - 见下文）。构建有两个阶段。第一阶段，内核，由 CMake 所有。对于 CUDA，它编译当前在 `crates/infer-worker/src/infrastructure/cuda/kernels/` 下的每个 `.cu` — `flash_attn_gqa`、`matmul`、`scatter_kv_batch`、`qkv_norm_rope_scatter` 等等 — 但它不是 `-arch=sm_XX`，而是发出一个 **fatbin 跨越固定的拱形集 ** 加上一个虚拟 PTX 后备： `-gencode arch=compute_80,code=sm_80` 到 `compute_90` 和 `-gencode arch=compute_90,code=compute_90`，因此较新的 GPU（sm_100 等）仍通过嵌入式 PTX 的驱动程序 JIT 加载。输出*不是*消费者链接的静态存档。它是一个可重定位的内核 blob（`infer_kernels_cuda.fatbin` 或 PTX 模块），cdylib 在运行时通过 CUDA 驱动程序 API（`cuModuleLoadData` / `cuModuleLoadFatBinary`）通过 `cudarc` 的动态加载功能加载，该功能会 dlopens `libcuda`/`libnvrtc` 而不是链接绑定它们。这是当前模型的精确反转：worker 依赖的符号表（`add_kernel_bf16x8` 等，在 `kernels/add.rs` 中声明为 `unsafe extern "C"`）不再是 `infer-worker` 的链接时依赖项，而是成为插件内的运行时模块查找。
第二阶段，Rust cdylib，由 Cargo 所有。后端 crate 的 `build.rs` 调用 CMake，然后告诉 Cargo 捆绑生成的 fatbin（通过 `include_bytes!` 嵌入单文件插件，或与 sidecar 路径一起发送并解析）。今天从 `wrapper.h` 生成 `OUT_DIR/bindings.rs` 的 bindgen 步骤也移至此处 — 只有 CUDA 后端需要 `libclang`，并且仅在实际重建该后端时才需要。至关重要的是，dtype 分派没有改变：在插件内部，内核包装器中现有的 `match T::DATA_TYPE -> add_kernel_bf16x8` 路径会逐字保留，因为 C-ABI 接缝会擦除*device*（运行时 fn-ptr），同时保持插件内部的*dtype* 单态化。构建系统的改变使得运行时接缝变得可交付；它本身不会移动接缝。
HIP 和 Metal 后端重用相同的两阶段形状：CMake `--offload-arch=gfx90a,gfx942` 用于通过 HIP 模块 API 加载的 ROCm fatbin； `metal`/`metallib` 适用于 Metal，在运行时加载。添加它们不需要工作人员进行更改 - 它们是主机通过路径发现的新 cdylib。CPU 后端是故意的例外，也是这次重构是增量而不是重写的原因。 `crates/infer-worker/src/infrastructure/cpu/` 已经实现了每个端口（`Device`、`MemoryPort`、`MathOps`、`FusedOps`、`DiffusionOps`），有些返回 `OpError::Unsupported`。它使用纯 Rust 进行编译，没有 GPU 工具链。它作为始终存在的终端回退保持**静态链接**到工作程序中，并且*也*可以作为插件 cdylib 发布以实现对称。这证明了抽象可以托管非 CUDA 后端，这意味着第一个可交付成果（使用零 CUDA 工具链构建的工作器）只是带有 CPU 后端的 `default = []`，不需要新内核。
### 替换`nvidia-smi`主机检测和`build.rs`内核编译
构建消除了两种最糟糕的行为。删除`detect_cuda_arch()`及其`nvidia-smi`脱壳； arch 选择从构建主机检测转移到由驱动程序在*加载*时解析为正在运行的 GPU 的*固定编译时矩阵*（上面设置的 gencode），正如 TVM 的 `CUDAModule` 和 TensorRT 的 fatbin 所做的那样。该架构集位于 `infer-backend-cuda` 的 CMake 预设中，随内核版本化，不会从插入 CI 运行器的任何卡中发现。该工人的`build.rs`被删除； `cc`/`bindgen`/`walkdir` 完全保留了工人的构建依赖性。 `default = ["cuda"]` 变为 `default = []`（CPU 基线），“使用 CUDA”变为*运行时*决策：主机扫描配置的插件目录（PJRT 样式的 `name:path` 列表）、`libloading::Library::new` cdylib、检查 `abi_version`、查询 `capabilities()`。 `find_cudnn_frontend_include` 和 `find_cuda_path` 中的 conda/venv/cuDNN 前端扫描仅限于 CUDA 后端的 CMake，其中缺少工具链是合法的“您无法构建此后端”错误，而不是“核心无法编译”。

## 6. 内核开发工作流程
*将内核移动到插件中会改变内核作者的日常工作方式，因此本节定义了开发人员工作流程。它将内核拆分为自动调整的 AOT fatbin（GEMM、flash-attention、融合操作）和 NVRTC-JIT-with-disk-cache tail（elementwise/reshape），并且坦率地说，只有在通用启动 shim 替换了每个符号 `extern "C"` 包装器之后，每个内核才会获得标题“编辑 `.cu`，零 Rust 重建”循环。*
### 当前成本模型，根据源衡量如今，每次内核编辑都会付出最坏情况的代价。 `crates/infer-worker/build.rs`（472 行，在 `cuda` 功能后面门控）遍历 `src/infrastructure/cuda/kernels/**/*.cu`，收集所有 29 个翻译单元（`add/add.cu`、`matmul/matmul.cu`、`flash_attn_gqa/*.cu`、`kv_cache/scatter_kv_batch.cu`、`qkv_norm_rope_scatter/*.cu` 和其余），然后将整个集合到单个 `cc::Build::cuda(true).opt_level(3).flag("-arch=sm_XX")` 调用，该调用生成一个静态存档 `infer_kernels`。然后，该存档通过 `cargo:rustc-link-lib=static=infer_kernels` 静态链接到工作程序中。因为编译单元是“将所有内核放入 Rust 对象文件链接的一个 `.a`”，所以触摸 `add.cu` 中的单个字符会触发该文件的 `nvcc` 重新编译、重新存档，并且（因为存档是链接输入）`infer-worker` 二进制文件的完整重新链接。更重要的是，`detect_cuda_arch()` 将 `nvidia-smi --query-gpu=compute_cap` 脱壳，并将一个 `sm_XX` 烘焙到构建中，因此该工件被固定到主机 GPU； `bindgen` 重新运行 `wrapper.h`（cuda_runtime + cublasLt + cudnn + cudnn_frontend）需要 `libclang`；和 `find_cuda_path`/`find_cudnn_frontend_include` 执行 `panic!` 不存在时的大量 conda/venv 发现。最终的效果，在简报中被称为张力 #2，是 `default=["cuda"]` 使得在没有完整的 CUDA 工具链和物理 GPU 的情况下无法构建核心包，而内核作者的编辑-构建-测试循环由工具链重新进入和重新链接主导，而不是由内核更改本身主导。 `nvrtc` 库已链接 (`build.rs:54`)，但不存在运行时编译代码路径 - 该链接是自重的。值得精确了解“如何”达到内核，因为迭代成本不仅在 `build.rs` 中，而且在 `build.rs` 中。它被纳入调用约定中。如今，每个内核前面都有一个手写的 Rust 包装器，该包装器将其 CUDA 入口点声明为每个数据类型 `unsafe extern "C"` 符号，并通过 `match T::DATA_TYPE` 梯子分派给它们。 `add.rs:9-80` 是规范的形状：它声明 `add_kernel_bf16x8`、`add_kernel_fp16x8`、`add_kernel_float2_forward`（以及就地变体），每个都具有完全拼写的 C 签名，然后 `add::<T>` 打开 `T::DATA_TYPE` 并使用 `dst.data_ptr_mut()` 调用匹配符号， `a.data_ptr()`、`b.data_ptr()`、`n`、`stream`。每一个符合 JIT 条件的内核 — `softmax.rs`、`rope.rs`、`scalar.rs`、`swiglu`、`ewise_mul.rs`、`broadcast_mul.rs`、`cast_fill`、`permute`、`split_cols`、 `rope_interleaved` — 遵循相同的模板：每个 dtype `extern "C"` 声明的块和在链接时解析为 `infer_kernels` 中的静态符号的 dtype 匹配。这是重新设计必须面对的关键细节：包装器绑定到*链接时符号*，因此通过它根本无法访问其主体在运行时重新编译的内核。仅通过将编译重新定位到 NVRTC 无法实现快速循环。
### 目标：一个后端边界后面的两个编译机制
重新设计将内核分为两种状态，并将它们从工作核心中移出。这依赖于提案中其他地方建立的接缝：所有 `.cu` 和所有 CUDA 工具链依赖项都重新定位到具有自己的 `build.rs` 的独立 `infer-backend-cuda` cdylib 中，使 `infer-worker` 使用零 CUDA 工具链进行构建。然后，内核作者永远不会重建 Rust 核心来迭代内核 - 他们重建单个 `.so`，或者在 JIT 机制中（一旦下面的先决条件垫片就位），根本没有 Rust。第一个方案是提前 fatbin。稳定、性能关键、自动调整的内核 — GEMM 及其 cublasLt 路径（`matmul.rs` 中的 `gemm_cublaslt_bf16`，它已经通过 `workspace`/`workspace_size` 进行线程化）、flash-attention 系列（`flash_attn_paged_decode`、`flash_attn_gqa_prefill`）、`scatter_kv_batch`、融合的 `qkv_norm_rope_scatter` 和 `fused_add_rmsnorm` — 由后端 crate 的 `build.rs` 一次编译到多架构 fatbin 中。至关重要的是，拱门列表变成了一个“集合”——`sm_80;sm_86;sm_89;sm_90` 加上 `compute_90` PTX 条目作为前向兼容的后备——取代了今天单个 `nvidia-smi` 派生的 `sm_XX`。这是 TensorRT/PyTorch 模型：运送一个覆盖部署队列的 fatbin，让驱动程序在模块加载时选择匹配的 cubin，并在任何较新的架构上 JIT 嵌入式 PTX。 fatbin 在运行时通过 CUDA 驱动程序 API (`cuModuleLoadFatBinary` / `cuModuleGetFunction`) 通过 `cudarc` 及其 `dynamic-loading` 功能加载，其中 `dlopen` 是 `libcuda`/`libnvrtc` 而不是链接绑定它们 - 这就是让 *consumer*（工作核心）不携带链接时 CUDA。我们保留这些内核 AOT，因为它们的性能取决于自动调整和模板实例化（`third_party` 下的 cutlass/cute），我们不想在进程启动时重新付费，而且因为相对于它们的运行频率，它们很少被编辑。分区也是一个硬约束，而不是偏好：NVRTC 无法轻松摄取可爱模板重的源，因此每个依赖 cutlass 的内核必须保留在 AOT 一侧。源审计确认下面的 JIT 合格集不会拉出 cutlass/cute 标头，因此 cutlass 模板完全保留在 fatbin 路径后面。第二种机制是 NVRTC-JIT-with-disk-cache，它是赢得迭代速度的地方。元素和形状改组内核的长尾 - `add`、`ewise_mul`、`broadcast_mul`、`cast_fill`、`scalar`、`permute`、`split_cols`、`swiglu`、`softmax`、 `rope`/`rope_interleaved` - 是源码较小的内核，其 dtype 专业化是机械的（`add.rs` 中的 `match T::DATA_TYPE -> add_kernel_bf16x8` 梯子），并且内核作者不断调整。这些转移到运行时编译：`.cu` 源（或 `&str` 模板）在第一次使用时交给 NVRTC，编译为 PTX，由驱动程序 JIT 组装到 cubin，并且生成的 `CUfunction` 在由 `(arch, kernel_source_hash, compile_flags)` 键入的进程内缓存。回报是作者编辑了 `.cu`，并且因为源代码是在运行时读取的（从后端板条箱的数据目录或覆盖路径），所以没有 Rust 重建，也没有重新链接 — 下一次调用仅重新编译该内核。
### 先决条件：一个通用的 NVRTC 启动垫片，可以淘汰每个符号的包装器
“仅编辑 `.cu`，零 Rust 重建”循环并不是将编译移至运行时的免费结果；它是一个必须通过替换调用约定本身来逐个内核“构建”的属性。如上所述，今天的 `add::<T>` 通过由 `match T::DATA_TYPE` 梯子（链接时绑定）选择的硬声明的 `extern "C"` 符号到达其内核。运行时重新编译的内核会生成一个新的 `CUfunction`，没有这样的声明名称，因此根本无法通过这种方式到达。具体来说，JIT 机制取决于首先登陆一个通用的名称和参数启动垫片，该垫片取代了每内核 `extern "C"` + JIT 子集的匹配臂。填充程序采用内核*名称*（例如 `"add_bf16x8"`），从缓存中查找 `CUfunction`（在未命中时进行编译，如下），将启动参数打包到驱动程序的 `void**` 参数数组中，计算启动几何结构，并在 `ExecScope` 的流上调用 `cuLaunchKernel`。绘制为界面：
```
rust
struct KernelSpec { name: &'static str, source_key: SrcHash, args: ArgLayout, grid: GridFn }
fn launch(scope: &CudaScope, spec: &KernelSpec, args: &[KernelArg]) -> OpResult<()>;
```
`
`KernelSpec` 成为先前在 `extern "C"` 签名（参数类型和顺序）和匹配阶梯（数据类型到符号名称解析）中传播的内容的单一事实来源。类型系统今天执行的 dtype 专业化（选择 `add_kernel_bf16x8` 与 `add_kernel_fp16x8`）被重新表示为名称派生 (`format!("add_{}x8", T::DATA_TYPE.suffix())`) 加上 NVRTC 标志中传递的宏定义，因此相同的 `(arch, src_hash, flag_hash)` 键控自然地分隔了 dtype 变体。
该填充程序是跨 29 个包装器文件的 JIT 子集的调用约定的真正的、有界的重写，并且该提案将其视为显式先决任务而不是紧急好处。老实说，有两个后果。首先，“编辑 `.cu` 并重新运行，根本没有 `cargo`”开发人员体验*仅适用于已经迁移到 shim 上的内核*；对于仍然带有旧的 `extern "C"` 包装器的符合 JIT 资格的内核，编辑 `.cu` 仍然意味着更改 Rust 包装器，就像今天一样，因为包装器仍然解析过时的符号。因此，迁移是渐进式的，并且 DX 声明的范围仅限于迁移的边界。其次，填充程序交换编译时保证，每个符号签名为我们提供了编组到 `void**` 中的运行时描述的参数列表（每个参数的指针类型和由 Rust 类型系统在 `add.rs` 中的调用站点检查的计数）。 `KernelSpec` 声明的 `ArgLayout` 与内核的真实签名之间的不匹配是静默内存损坏，而不是编译错误，因此在删除旧包装器之前，必须针对其旧包装器的行为对每个内核的编组进行测试验证。 AOT 内核不受影响：它们将类型化的 `extern`/cublasLt 调用路径保留在后端 `.so` 内，工具链仍然静态链接它们。
### 缓存，以（arch、kernel-hash、flags）为键磁盘缓存是一种机制，可以在进程重新启动时保持 JIT 便宜，并将“编辑后首次运行”变成唯一的慢速运行，并且它与启动垫片参考的结构相同：垫片通过 `(arch, src_hash, flag_hash)` 向缓存询问函数，缓存从其进程内映射、磁盘或通过调用 NVRTC 进行应答。关键是一个三元组：设备计算能力字符串 (`sm_90`)、规范化内核源代码加上任何包含的标头的哈希值，以及 NVRTC 标志向量的哈希值（`--gpu-architecture`、快速数学、`-default-device`、寄存器上限和专门用于启动的宏定义 - 包括定义垫片发出的 dtype）。该值是编译后的cubin（或原始PTX）。当缓存命中时，我们完全跳过 NVRTC 并直接进入 `cuModuleLoadData`；如果有失误，我们会进行编译、保存和加载。在键中包含“标志”是自动调整声音的原因：同一源的两个调整仅在块大小 `-D` 定义上有所不同，从而产生不同的键并共存，并且相同的机制使每个数据类型的变体保持分开。磁盘布局是内容寻址目录 (`$XDG_CACHE_HOME/rustinfer/kernels/<arch>/<src_hash>-<flag_hash>.cubin`)，因此可以安全地跨进程共享并在容器映像中进行预热。这与 TensorRT 用于其序列化定时缓存和 ONNX Runtime 用于其编译子图缓存的“相同”键控规则是故意的；我们不是发明一种方案，而是采用经过验证的方案。 `RUSTINFER_KERNEL_CACHE=off` 转义和缓存版本字节（当 NVRTC 主要版本或我们的代码生成更改时发生碰撞）可防止陈旧的 cubin 损坏。
### 内核作者实际上做了什么开发者的体验才是重点。对于 AOT 内核，作者编辑 `.cu`，运行 `cargo build -p infer-backend-cuda`（它仅重新编译该箱子更改的翻译单元并重新链接一个 `.so`，而不是工作线程），并且正在运行的服务器在下一次加载时选择新的后端。对于已迁移到启动垫片上的 JIT 内核，作者编辑 `.cu`，将 `RUSTINFER_KERNEL_OVERRIDE_DIR` 设置为指向其工作树，然后重新运行 - 垫片注意到源哈希已更改，NVRTC 在第一次调用时重新编译该内核，对其进行缓存，并且循环在几秒钟内关闭，根本没有调用 `cargo`。对于尚未迁移的符合 JIT 资格的内核，循环仍然是 AOT 样式的 `cargo build -p infer-backend-cuda`，因为 `extern "C"` 包装器必须与 `.cu` 一起重新生成 — 这正是迁移它的动机。无论哪种方式，与今天的对比都是鲜明的：对 `add.cu` 的单行更改当前强制 `nvcc` + 重新存档 + 完整的 `infer-worker` 重新链接；在目标中，在最坏的情况下，它会强制执行单个 crate `.so` 重建，而在最好的情况下，它会强制执行 `add.cu` 的单独 NVRTC 编译，仅此而已。
开发期间后端 `.so` 的热重载类似于 AOT 机制。因为后端是显式加载的（路径上的 `libloading::Library::new`，然后是单个 `rustinfer_get_backend_api` 条目符号，根据注册设计），开发模式文件观察器可以检测到 `infer-backend-cuda.so` 已重建，静默设备（排出正在运行的流，现有的 `ExecScope::synchronize` 已经为我们提供了障碍），删除旧的 vtable 及其`Library` 和 `dlopen` 是新的。 ABI 安全三位一体的硬性规则适用：`Library` 必须比它生成的每个句柄都存活得更久，因此重新加载仅在静态点是安全的，其中旧 `.so` 分配的 `DeviceTensor`、流或 `CudaConfig` 工作空间仍然存在。在实践中，开发循环拆除 `Runtime`、交换库并重建 `Runtime` — 编译内核的完全热交换，无需重新启动调度程序或服务器进程。
### 自动调整自动调节完全位于后端 `.so` 内部，并通过相同的 `(arch, hash, flags)` 缓存进行写入。对于可调内核（JIT 逐元素内核的图块大小，或 GEMM 的候选 cublasLt 算法），后端在第一次遇到问题形状时，会在实时 GPU 上对一小组候选者进行乘法（正是 `gemm_cublaslt_bf16` 已经接收到 `workspace` 来完成实际工作的方式），选择获胜者，并保留由 `(arch, src_hash, problem_shape)` 键入的所选标志集。对于 JIT 内核，这直接使用启动垫片：每个候选图块大小只是 NVRTC 标志向量中的不同宏定义，因此候选者已经是不同的缓存键，并且获胜者是垫片记录该形状的 `(src_hash, flag_hash)` 的那个。后续运行从缓存中读取决策并跳过计时。这是 TensorRT 策略选择模型，范围缩小到我们的小操作集；它是每个内核选择加入的，并且永远不会阻止超出第一次观察形状的请求热路径。因为结果本质上是主机 GPU 特定的，所以它会被缓存，永远不会被烘焙到分布式工件中 - 附带的 fatbin 保持可移植性，并且每次部署都会对其进行专门调整。
### ROCm 和金属类似物
政权分裂是可移植的。 `infer-backend-rocm` cdylib 使用 `hipcc` 将其 AOT 内核编译为通过 HIP 模块 API 加载的多目标代码对象 (`gfx90a;gfx942`)，其 JIT 尾部在相同的启动垫片和相同的 `(arch, source-hash, flags)` 磁盘缓存后面使用 `hipRTC` — `gfx90a` 简单地替换`sm_90` 在钥匙中。 `infer-backend-metal` cdylib 倾向于 Metal 的运行时着色器编译模型，默认情况下是 JIT：`.metal` 源在运行时编译为 `MTLLibrary`，使用 Metal 自己的管道状态缓存以及由 `(gpu-family, shader-hash, function-constants)` 键入的预编译 `.metallib` 的磁盘缓存。在这三个原则中，原则都成立：工具链（`nvcc`/`hipcc`/`metal`）和运行时编译器（`nvrtc`/`hiprtc`/`MTLDevice`）位于供应商`.so`内部，工作核心不使用它们构建，而是使用单个名称键控的启动垫片前端是运行时编译的函数，缓存将重复和交叉重新启动的编译转变为跨供应商具有相同键控的一次性成本。

## 7. 运行时依赖管理和检测*必须在运行时而不是在构建时发现、检查版本并优雅地降级可加载后端。本部分将检测分为两个明确的轴 - 功能功能（可查询的操作/数据类型位集）与硬件兼容性（粗略驱动程序/计算帽门） - 并将 `OpError::Unsupported` 针对静态链接的 CPU 基线形式化为每个操作回退信号，并对每个跨后端往返进行计量。
### 我们实际解决的问题
如今 RustInfer 没有运行时依赖管理；它具有*构建时*依赖性*耦合*，这更糟糕。 `infer-worker` `build.rs`（472行，在`default=["cuda"]`上门控）遍历`crates/infer-worker/src/infrastructure/cuda/kernels/*.cu`，针对单个`nvidia-smi`检测到的`sm_XX`，用`cc::Build.cuda(true)`编译每一个，硬链接`cublas`， `cublasLt`、`cudnn`、`nvrtc`、`cudart` 和 `panic!`（如果找不到 cuDNN 前端标头或 libclang）。 `SKIP_BUILD_KERNELS` 转义仅将失败从编译转移到链接。实际结果是，如果没有完整的 CUDA 工具链和匹配的主机 GPU，“整个核心无法在机器上构建”，并且它生成的工件会固定到该主机的计算能力。不存在“CUDA 驱动程序太旧”、“cuBLAS 不存在”或“回退到 CPU”的概念 - 这些条件根本无法表示，因为依赖关系是由链接器而不是程序解决的。
本提案中其他地方描述的重新设计将 CUDA 内核移至通过 `libloading` 在运行时加载的独立 `infer-backend-cuda` cdylib，其中工作核心针对零 CUDA 工具链构建。这一举措*创造*了真正的运行时依赖项检测的需求：一旦后端是在启动时发现的 `.so` 而不是在构建时解析的链接符号，主机必须在信任它之前回答三个问题 - *库是否可加载，其传递性本机依赖项是否存在且版本兼容，以及它实际上可以接受哪些工作子集*。本节定义探测序列、它生成的功能和运行状况报告以及使用它的降级策略。我们故意将当前构建合并的两个问题分开，ONNX Runtime 和 TensorRT 都学会了拆分：**功能功能**（`(op, dtype)` 与后端支持配对 - 可查询的细粒度属性）与**硬件/运行时兼容性**（驱动程序、工具包和计算功能版本上的粗略接受/拒绝门）。 build.rs 将两者折叠为“nvcc 是否成功用于 `sm_XX`”。我们将它们保留在不同的轴上，以便 CUDA 插件可以拒绝 Ampere 卡上的 fp8（功能差距、操作级回退），而太旧的驱动程序则拒绝整个插件（兼容性门、加载时间拒绝），并出现明显的、响亮的错误。
### dlopen-probe 版本符号
对于本机依赖性检测，我们选择 **dlopen-probe 带有类型化握手符号**，而不是读取导出的版本常量。具体来说，主机从不链接`libcuda`、`libcublas`或`libcudnn`； `infer-backend-cuda` 插件在内部进行自己的发现（通过 `cudarc` 的动态加载功能，其中 `dlopen` 是 `libcuda`/`libnvrtc`/`libcudart`），并通过单个 C-ABI 入口点将该发现的“结果”公开给主机。主机的工作只是`dlopen`插件并调用`rustinfer_get_backend_api(abi_version)`；该插件的工作是在内部探测其自己的本机堆栈并报告它。我们拒绝让主机直接使用 CUDA 库中的 `dlsym` 版本符号（如 `cudaRuntimeGetVersion`）的替代方案，原因有以下三个：PyTorch 和 JAX 的实际行为方式。首先，符号存在并不能很好地体现可用性：`cudaRuntimeGetVersion` 解析不会告诉您 `cudaMalloc` 是否会在存在但太旧的驱动程序上成功 - 经典的“CUDA 驱动程序版本不足以支持 CUDA 运行时版本”故障，仅在第一次实际调用时出现。其次，主机不需要知道每个后端的内部本机依赖关系*图*；该知识属于插件，就像 PJRT 将所有设备发现推向 `GetPjrtApi()` 和供应商 `.so` 一样。第三，dlopen-probe 通过构造优雅地降级：失败的 `libloading::Library::new` 或失败的握手是普通的 `Result`，而*链接*库中丢失的符号是一个从未启动的进程。这反映了 PyTorch 如何延迟初始化 CUDA — `torch.cuda.is_available()` 是一个探针，它捕获缺失并返回 `false` 而不是中止 — 以及 JAX 如何枚举 PJRT 插件并默默地忽略那些无法初始化的插件，将 CPU 后端作为底层。
### 启动时的探测序列
主机拥有一个可删除的 `BackendRegistry`（不是进程全局单例 - 请参阅注册部分），并针对从 config/env 插件列表中发现的每个候选插件运行以下有序探测。顺序很重要：每个阶段都比下一个阶段更便宜、更基础，并且任何阶段的失败都会记录为结构化的 `BackendHealth` 条目而不是恐慌，因此服务器总是以*某些*可行的后端完成启动。|舞台|问题 |机制|故障处理|
|---|---|---|---|
| 0.CPU基准|是否存在终端后备？ |通过 `linkme` 自注册静态链接 `Cpu` — 永不丢失 |不能失败；这是地板|
| 1.加载| `.so` 是否可以打开并且我们的符号存在？ | `libloading::Library::new` + `dlsym("rustinfer_get_backend_api")` |记录`Unloadable{path, dlerror}`，跳过插件|
| 2.ABI门|它是根据兼容的边界构建的吗？ |返回的 vtable 的第一个字段 `abi_version`/`struct_size`，在读取任何其他字段之前进行检查 |记录`AbiMismatch{built, host}`，大声拒绝，跳过|
| 3.本机探针| libcuda/cublas/cudnn 是否存在且驱动程序是否足够新？ |插件内部 `probe() -> NativeProbe`：dlopens 自己的本机依赖项，​​调用 `cudaDriverGetVersion`/`cudaRuntimeGetVersion`，与内置版本进行比较 |记录`RuntimeIncompatible`，降级插件，保持注册表健康 |
| 4、五金门|实时 GPU 是否满足插件的最小计算上限？ | `capabilities().min_compute_cap` 与被探测设备计算能力对比 |拒绝该后端设备；其他设备仍可能通过 |
| 5.能力查询|实际支持哪些 `(op, dtype)`？ | `capabilities() -> Capabilities`（dtype 位集、op 位集、定量层、cuda-graph/paged-attention 标志、最大工作空间）|记录每个操作的间隙；稍后通过后备解决 |
第 0 阶段使整个方案变得安全。因为 `crates/infer-worker/src/infrastructure/cpu/mod.rs` 中现有的 `Cpu` 适配器已经实现了每个端口 - `Device`、`HostDevice`、`MemoryPort` 和 `std::alloc` 上的 `MemoryPort` 以及操作特征，GPU 特定的操作返回 `OpError::Unsupported` - 它是 ORT 形式化为其始终附加的有保证的终端回退CPU EP。我们将其保持*静态链接*并且永远不会落后于 C ABI，正是因为 `linkme` 注册是链接时的并且在 `dlopen` 中无用；即使每个插件都无法加载，CPU 后端也必须存在。
第 1 阶段和第 2 阶段是边界要求的 ABI 安全规则：在取消引用任何其他 vtable 字段之前*首先*读取 `abi_version`/`struct_size`，因为未经检查的布局不匹配是未定义的行为，而不是错误。这是 PJRT 的 `struct_size`-as-universal-version-gate 逐字应用。第 3 阶段和第 4 阶段是 build.rs 目前无法表达的运行时兼容性检查。插件内的本机探针会比较必须对齐的三个版本：**驱动程序**版本（`cudaDriverGetVersion`，`libcuda` 报告的内容）、**工具包/运行时**版本（`cudaRuntimeGetVersion`，`cudart` 的构建版本）以及在自己的构建时嵌入到插件中的**构建**版本。 CUDA 的次要版本兼容性保证（针对 12.x 构建的运行时在任何 y≥x 的 12.y 驱动程序上运行）正是此阶段编码的规则：在主要版本内跨次要版本向前兼容，跨主要边界大声拒绝。将内核作为多架构 PTX+fatbin（sm_80/86/89/90 加上 PTX 回退）而不是单个 `nvidia-smi` 派生的 cubin 进行交付，这让第 4 阶段“接受”插件并非专门针对的 GPU：驱动程序在模块加载时 JITs PTX，TensorRT 的 fatbin 和 TVM 的 `cuModuleLoadData` 提供的方式JIT-at-load 向前兼容性。这直接删除了当前构建中包含的主机 GPU 特异性。
### 能力和健康报告结构
两个不同的 `#[repr(C)]` 结构跨越边界，反映了功能/硬件的划分。 `Capabilities` 是 `capabilities()` 返回的静态、可查询的特征描述符：`dtype_mask`（`F32/BF16/F16/I32/I8/Fp8E4m3/Fp8E5m2` 上的位集，匹配 `domain/dtype`）、端口方法的稳定 `op_id` 枚举上的 `op_mask`、受支持的 `KvQuantTier`、用于 cuda-graph 捕获和分页注意的布尔标志（形式化 `domain/exec.rs` 中已存在的现有 `ExecScope::supports_graphs()`）、`max_workspace_bytes` 和 `min`/`target_compute_cap`。 `BackendHealth` 是主机在探测期间累积的动态每次尝试报告：达到的阶段、结构化故障原因，以及（对于加载的后端）已解析的驱动程序/运行时/构建版本三元组以及枚举设备及其每设备计算能力和可用内存。注册表向上显示给调度程序，并通过 `infer-scheduler` 中现有的 `prometheus` 指标路径向外显示，因此“CUDA 插件降级：驱动程序 535 < 所需的 545”是一个可观察的启动事件，而不是一个静默的功能漏洞。
### 向调度员报告能力并自动选择选择是明确的操作员意图与探测能力的交集，而不是神奇的自动检测。调度程序从配置声明的优先顺序中为每个请求选择一个后端，过滤到 `BackendHealth` 健康且 `Capabilities` 覆盖请求所需的 `(op, dtype)` 集的后端 - 模型的 dtype、是否需要分页关注、是否需要 fp8 层。这是 wgpu 的 `Features`/`Limits` 模型和 ORT 的两层 `GetSupportedDevices` + 每个模型 `GetCapability`，而不是 PyTorch 意外的 64 位 `DispatchKeySet`； RustInfer 没有自动梯度或功能化轴，因此在模型加载时构建的一次性解析 `(op_id, dtype, backend_id) -> fn_ptr` 表（TensorRT 的预解析 DAG 课程）就足够了，我们明确拒绝泛化到多轴键集，直到存在具体的第二个轴。
当前的`serve_loop::run_with_model<M: DecoderModel<bf16, Cuda>>`被硬编码为`<bf16, Cuda>`；这是自动选择替换的调用站点。选择发生在静态通用接缝之上：主机选择一个 `backend_id`，并且为选定的设备实例化单态 `Runtime<T, D, M>`，该设备位于小型调度枚举或调度部分中定义的类型擦除边界后面。能力报告使该选择变得安全，而不是硬编码。
### 优雅的、可观察到的退化降级在两个粒度上进行，RustInfer 在这里可以比 PJRT 或 TensorRT 做得更好，后者仅在整个程序或构建粒度上进行回退。在**加载粒度**，在第 1-4 阶段失败的后端不会出现在注册表中；调度程序根本不会选择它，并且请求会落在下一个首选项（最终始终存在的 CPU 基线）上——当 PJRT 插件无法初始化时 JAX 的行为。在**操作粒度**，现有的 `OpError::Unsupported { backend, op }`（已在 `crates/infer-worker/src/domain/ports/error.rs` 中定义，并已由 CPU 适配器和未实现的 CUDA 操作返回）成为每个操作的后备信号：拒绝 fp8 matmul 的 CUDA 插件返回 `Unsupported`，并且调度程序通过主机往返将*该操作*路由到 CPU 后端。从 ORT 和 PyTorch 消除延迟的隐藏 `Memcpy` 插入中学到的关键原则是，每次此类跨后端往返都会被记录和计量 - LLM 解码热路径中的静默降级是要避免的枪口。因此，CPU 后端的每操作 `Unsupported` 不是需要删除的缺陷，而是后备链的形式化终端，保持静态链接，因此可以无条件访问。
最终效果：工作核心在没有 CUDA 工具链的情况下构建，启动探针将“不会链接”变成结构化的、可观察的运行状况报告，服务器从 CUDA 降级为禁用操作集，再沿着明确的、版本控制的、从不未定义行为的路径设置为纯 CPU。

## 8. 分发和安装
*最后，独立构建意味着独立*发布*。本节定义了三个分发列车 - crates.io 上的无 GPU 核心、OCI 注册表上的后端 cdylibs 以及额外索引上的 PyTorch 风格的 `+cuXXX` 同伴轮 - 仅在 C ABI 上满足，在任何 `dlopen` 之前具有显式的 `name:path` 注册表发现和签名验证。*
### 我们正在分发什么，以及为什么当前的形状会阻挡它RustInfer 今天没有提供任何可分发的东西。工作区 `Cargo.toml`（解析器 3，五个 crate）使用 `default = ["cuda"]` 声明 `infer-worker`，并且该功能将 `dep:cc`、`dep:bindgen` 和 `dep:walkdir` 拉入构建图中。 471行`crates/infer-worker/build.rs`然后遍历`src/infrastructure/cuda/kernels/*.cu`，通过`cc::Build::cuda(true)`编译所有29个`.cu`文件，通过`wrapper.h`运行`bindgen` `cuda_runtime`/`cublas`/`cudnn`/`cudnn_frontend`，并链接`cublas`/`cublasLt`/`cudnn`/`nvrtc`。它通过 conda/venv 启发式发现 CUDA，并从 `nvidia-smi` 派生出单个 `sm_XX`。最终效果：如果没有完整的本地 CUDA 工具链、`libclang`、cuDNN 前端标头、`third_party` 下供应的 CUTLASS 以及将运行它的*精确主机 GPU*，则无法构建*核心*包，更不用说发布了。 `SKIP_BUILD_KERNELS` 存在，但链接失败。没有 crates.io 故事，没有轮子，生成的二进制文件是主机架构固定的。
因此，分销策略不是包装后的想法；这是本提案其他地方描述的运行时加载重构的外部可见结果。一旦静态通用接缝在 `crates/infer-worker/src/domain/ports/device.rs` 中现有的 `MemoryPort` 边界处被切断（原始 `NonNull<u8>` + 大小 - 已经在精神上进行了类型擦除，已经由 `Cpu` 和 `Cuda` 实现），内核就会从核心移出到独立的 `infer-backend-cuda` cdylib，并且*只有这样*才可以核心成为一个干净的、无 GPU 的、可以发布的 Rust 箱。我描述了工件分类法、注册/发现机制、兼容性矩阵和具体的最终用户 UX，反映了 PyTorch 和 ONNX 运行时人体工程学，它们赢得了声誉，而 RustInfer 可以做得更好。
### 工件分类：三个独立的发布系列
我建议*仅*在稳定的 C ABI 处满足三个分发列车，就像 PJRT 轮和 ONNX Runtime EP `.so` 文件仅在 `GetPjrtApi()`/`GetApi(N)` 处满足一样。|火车 |神器|包含 | *使用*的工具链 |登记处 |
|---|---|---|---|---|
|铁锈核心| `infer-worker`、`infer-protocol`、`infer-scheduler`、`infer-server` 板条箱 |纯 Rust、端口 + 单态 `Tensor<T,D>` + 静态链接 CPU 后端 |仅稳定 Rust，无 CUDA | crates.io |
|后端插件 | `infer-backend-{cuda,rocm,metal}` cdylib (`.so`/`.dylib`/`.dll`) | PTX/fatbin（多架构）+ `#[repr(C)]` vtable + `cudarc` 动态加载器 |仅 GPU 驱动程序（无 nvcc，无链接时 CUDA）| OCI/CDN 注册 |
|蟒蛇 | `rustinfer` 轮 + `rustinfer-cuda12x` 轮 |服务器/CLI 二进制文件 + 捆绑核心；后端 `.so` 有效负载 | `pip`，manylinux glibc | PyPI + 额外索引 |
从 PJRT 的 `struct_size` 优先规则和 tvm-ffi 的删除器旅行带手柄规则中逐字获取的基本规则是，这些列车中没有一个共享 Rust ABI。核心板条箱发布到 crates.io，且*无* GPU 依赖性，因为 `default` 不再暗示 `cuda`； `cuda` 功能从“进程中编译内核”降级为“在运行时，找到 `dlopen` 捆绑的 CUDA 插件”。 `infer-backend-cuda` 内的缓冲区 `cudaMalloc` 仅由该插件的 `free` fn-ptr 释放，因此这三个列车可以由三个不同的工具链构建，并且仍然可以安全地互操作。
### Rust crate 分发（crates.io，无 GPU 依赖）
发布要求 `infer-worker` 在 docs.rs 和干净的 CI 运行器上构建。具体来说：删除`[build-dependencies] cc/bindgen/walkdir`块，删除`build.rs`的内核编译，并通过`linkme`自注册使CPU后端（`src/infrastructure/cpu/mod.rs`，它已经实现了每个端口并返回`OpError::Unsupported`用于仅GPU操作）始终静态链接的基线。然后，Rust 用户编写 `cargo add infer-worker` 并获得机器上 CUDA 为零的仅 CPU 推理运行时 - 相当于 `pip install torch --index-url .../cpu`。 GPU 加速是在运行时而非编译时选择加入的。插件板条箱 (`infer-backend-cuda`) 不是普通的库板条箱，也不应该是主要的 crates.io 依赖项，因为它们携带大量 PTX/fatbin 有效负载和供应商的内核构建。它们被构建为 `crate-type = ["cdylib"]` 并作为二进制工件发布（如下），在 crates.io 上有一个薄的 `infer-backend-cuda-sys` shim，仅供想要自己编译插件的用户使用。这反映了 `torch` 轮子和 CUDA 内核的解耦方式：99% 的用户下载了预构建的工件；重建的 1% 使用源板条箱。
### Python 轮分布（许多linux + 本地版本标签）
对于从未接触过 Rust 的推理用户来说，Python 表面必须与 `pip install torch` 无法区分。我推荐 PyTorch *和* PJRT 混合体：一个基轮加上每个 CUDA 系列本地版本标识符，由额外索引提供。
基础 `rustinfer` 车轮是 `manylinux_2_28_x86_64`（和 `aarch64`，加上 `macosx_*_arm64` 金属）。它捆绑了服务器/CLI 二进制文件、编译的核心包和静态链接的 CPU 后端——无需 GPU 即可运行。 GPU 支持作为*伴侣*轮提供，携带后端 `.so`，标记为本地版本：`rustinfer-cuda==0.5.0+cu124`。 `+cu124` 本地版本段是 PyTorch 的确切约定，pip 遵循它。由于 PyPI 禁止本地版本上传，因此这些配套轮存在于额外的索引上，记录的安装命令为：
```
pip install rustinfer rustinfer-cuda --extra-index-url https://download.rustinfer.org/whl/cu124
```
`
对于仅 CPU 路径：`pip install rustinfer` — 无索引体操。我故意拒绝将每个 CUDA 系列提供给一个胖轮（该工件将是数 GB 的，并且在每次小碰撞时都会重新下载），并且我拒绝在安装时自动选择 CUDA（pip 无法探测 GPU）。相反，*CLI* 会在安装后探测 GPU 并获取正确的后端，这比 pip 的索引 URL 猜测更可靠，也是 RustInfer 应该改进 PyTorch 人体工程学而不是复制它们的地方。
### 为检测到的 GPU 获取正确后端的 CLI
这是最终用户 UX 的核心，也是取代 `build.rs` 的 `nvidia-smi → sm_XX` 主机固定的部分。在 `pip install rustinfer`（或 `cargo install infer-cli`）之后，用户运行：
```
rustinfer backend install --auto
```
`
CLI 通过 `cudarc` 的动态加载路径加载 `libcuda`，查询驱动程序的计算能力和 CUDA 驱动程序版本，根据发布的 *ABI 矩阵*（如下）进行解析，从注册表下载匹配的 `infer-backend-cuda` 工件，验证其校验和和签名，并将其写入具有注册表文件条目的插件目录中。 `rustinfer backend list` 显示已安装的后端、其 ABI 版本、目标计算上限和功能位集； `rustinfer backend install cuda --arch sm_90` 针对气隙或交叉配置情况强制使用特定工件。这是 ONNX 运行时的显式 `RegisterExecutionProviderLibrary(path)` 哲学 - 通过显式路径注册，而不是目录扫描魔法 - 包含在获取步骤中。该工件附带 *fatbin + PTX* 覆盖 `sm_80/86/89/90`，因此单个下载可以在一系列 GPU 上运行，并且驱动程序 JITs PTX 对于任何更新的内容都可以运行，并将结果缓存在磁盘上。我们用 `build.rs` 的构建时主机固定来交换一次性首次加载 JIT，这正是 PyTorch/TensorRT fatbin 的权衡。
### 运行时自动发现后端
Discovery 遵循 PJRT 的 `PJRT_NAMES_AND_LIBRARY_PATHS` 模型，针对意外版本不匹配进行了强化。主机（服务器或工作线程）按以下优先顺序解析后端：显式 `RUSTINFER_BACKENDS=cuda:/path/libinfer_backend_cuda.so;cpu:builtin` 环境变量；然后是 CLI 编写的位于 `$XDG_DATA_HOME/rustinfer/backends.toml` 的注册表文件；然后是二进制文件旁边的默认插件目录。对于主机调用 `libloading::Library::new` 的每个条目，查找单个导出符号 `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`，检查 ABI 版本，调用 `capabilities()`，并将平台名称和优先级下的 vtable 注册到*拥有的、可删除的* `Registry` 中，而不是由 static-init 突变的进程全局单例。这对于多租户 `infer-server`（axum/SSE 箱）很重要：注册表是每个服务器的对象，后端可以热交换，并且 `Library` 在它创建的每个流/缓冲区的生命周期内保持活动状态。静态链接的 CPU 后端始终作为终端后备存在，因此发现永远不会产生空注册表。
### 多版本兼容性：运行时↔后端ABI矩阵三个独立的版本轴必须在加载时进行协调，千万不要像 UB 那样：*协议*版本（`infer-protocol` v0.1 消息类型）、*插件 ABI* 版本（`#[repr(C)]` vtable 合约）和*后端↔硬件*版本（计算能力和 CUDA 驱动程序）。我推荐 PJRT 最便宜的单一机制：`u32 abi_version`（或 `usize struct_size`）作为 vtable 和每个 args 结构的第一个字段，字段仅附加。主机拒绝注册 `abi_version` 超出其理解范围的插件，并且针对比正在运行的核心更新的协议构建的插件会导致握手失败并显示明确的消息。已发布的*兼容性矩阵*是注册表元数据的一部分：每个工件记录 `(plugin_abi_version, protocol_version_range, min_compute_cap, target_compute_caps, cuda_driver_min)`，而 CLI 的 `--auto` 分辨率只是对此矩阵的查询。这是 ONNX Runtime 的提供者桥*缺乏*（精确版本锁定，公认的反模式）的规则，并且 `GetApi(N)` 的插件 EP 路径是正确的。
### 二进制工件管理：注册表、校验和、签名
后端 `.so` 工件很大且安全敏感（它们在进程内运行非沙箱，除非隔离在现有 ZMQ 工作子进程接缝后面）。我建议使用与 OCI 兼容的注册表/CDN 作为事实来源，通过内容摘要进行寻址，以 `download.rustinfer.org` 为开头。每个工件都带有记录在注册表文件中的 SHA-256 校验和，并在 `.so` 成为 `dlopen` 之前由 CLI 进行验证，并使用 CLI 中嵌入的公钥进行签名（sigstore/cosign 或 minisign）；未签名或不匹配的工件会被拒绝，不会被警告。 Python 配套轮子携带相同的 `.so` 有效负载和相同的摘要，因此轮子路径和 CLI 获取路径汇聚在相同的、可验证的二进制文件上。这缩小了每个参考系统（PyTorch 的导入时静态初始化、TVM 的注册表构造器）简单假定的信任差距，并且它是“首次调用时的版本门，大声拒绝”ABI 规则的自然补充：我们在加载之前验证“出处”和在加载时验证“兼容性”。
### 端到端用户体验总结Python 用户对 CPU 运行 `pip install rustinfer rustinfer-cuda --extra-index-url .../cu124` 或 `pip install rustinfer`，然后运行 ​​`rustinfer serve --model ...`。 Rust 用户运行 `cargo add infer-worker`（立即支持 CPU）和 `rustinfer backend install --auto` 来获取与其检测到的设备匹配的 GPU 插件。在这两个世界中，核心都是无 GPU 的，后端是通过显式路径或注册表文件发现的单独版本的签名工件，它们之间的唯一契约是一个狭窄的、仅附加的 C ABI——同样的分离允许 PyTorch、ONNX 运行时和 PJRT 提供一个小核心和许多独立发布的后端。

## 迁移路线图：始终绿色、增量
管理规则是**构建在每个阶段结束时都是绿色的**并且**`default = ["cuda"]` 翻转发生在最后**。围绕设计的危险是具体的：`serve_loop::run_with_model` 被硬编码为 `M: DecoderModel<bf16, Cuda>`，并且工作箱有 `required-features = ["cuda"]`。在 CPU 或擦除的服务循环存在之前从 `default` 中删除 `cuda` 会产生一个可以编译但无法构造运行时的工作线程。下面的每个阶段都会重用现有的端口接缝，而不是重写它。
### 第 0 阶段 — 协调两个 `Device` 特征（机械、编译器检查）
今天实际上有两个名为 `Device` 的特征：`exec.rs:13` (`type Scope: ExecScope<Device = Self>`) 和 `ports/device.rs:8` (`type ExecCtx`)。在移动任何板条箱之前，将它们折叠成一个，或者将 exec-layer 特征重命名为 `ExecDevice` 作为后备。这必须是机械的、编译器驱动的传递，因为拙劣的合并会更改 `Tensor<T,D>` 和 `ExecScope::Device == Self` 不变量的类型状态轴。建筑保持绿色；没有行为改变。
### 第 1 阶段 — 折叠基础并仅在*源*级别提取内核
重组为`infer-core` / `infer-backend-abi` / `infer-runtime` / `infer-models`（无循环DAG）。将 29 个 `.cu` 文件和内核编译逻辑从工作线程移至新的 `infer-backend-cuda` 箱中 — **但保持其静态的工作线程依赖 Cargo 并保留 `default = ["cuda"]`**。这只是*源所有权*的构建解耦； Worker 仍然链接 `infer_kernels` 并运行不变。交付：内核不再存在于工作树中，基础 DAG 是非循环的。为 CUDA 和（尚未）CPU 构建绿色。
### 第 2 阶段 — 引入 `BackendDyn` + CPU 适配器 + 支持 CPU 的服务循环在 `infer-backend-abi` 中定义新的手写 `BackendDyn`（已擦除、`&self`、dtype-tag，*不是*在 `T` 上通用），再加上一个瘦适配器，可将标签重新单态化回现有的通用 `Self::add::<T>`——大约 30 个操作中每个操作的每个数据类型有一个匹配臂。添加 CI 测试，断言已擦除表面和通用表面保持同步。将支持 CPU 的路径连接到 `serve_loop`，以便设备不再硬编码到 `Cuda`。 CUDA 始终保持静态链接。 **退出标准：`cargo test -p infer-runtime --no-default-features` 在 CPU 上端到端运行模型。** 这是获得将 `cuda` 从默认值中删除的权利的阶段。
### 第 3 阶段 — 引入动态加载并将 CUDA 降级为运行时加载
构建 `#[repr(C)]` vtable、per-op arg 结构（包括将 `KvView`/`LayerKv` 展平为 `DeviceTensor` 加 `BatchPlan` POD 数组的多张量融合操作结构）、`rustinfer_get_backend_api` 条目符号和 `libloading`注册表。将 `infer-backend-cuda` 编译为 cdylib，传送多架构 fatbin，通过 `cudarc` 动态加载加载 CUDA。保留 `--features cuda-static` 后备，以便经过验证的静态路径保持可用，直到验证插件路径。交付 CI ABI 快照测试和恐慌边界 lint。交付：在运行时加载 CUDA 的工作人员；静态CPU后端通过`linkme`进行自注册。
### 第 4 阶段 — 翻转默认设置并拆分分发列车
现在仅将 `default = ["cuda"]` 翻转为 `default = []`（CPU 基线）。将 `infer-core` GPU-free 发布到 crates.io；在自己的火车上发布后端 cdylibs；添加 `+cuXXX` 配套轮和 GPU 探测安装 CLI。内核作者的 JIT 工作流程（Stage-3 启动 shim、NVRTC 磁盘缓存、静止点热重载）逐​​个内核地附加到这里，无需进一步更改 ABI。
### Post-MVP — 多后端，附加
延迟的跨后端子系统（功能分区器、`DeviceTransfer` 端口、对等复制矩阵、流依赖一致性）插入到类型化扩展链中，而不触及 v1 核心 vtable。 `owner_backend_id` 已位于 `DeviceTensor` 中，并且 `(op_id, dtype, backend_id)` 计划已具有正确的形状，因此分区器仅填充 `backend_id`。

## 风险登记册
以下风险是跨部分的风险；每个详细部分都有其自身的局部风险。**解码热路径上的动态调度开销（中等可能性，高影响）。**解码循环重复相同的操作序列数百万次；每次调用注册表遍历或字符串查找将是致命的。 *缓解措施：*在模型加载时将设备轴解析为捕获的每操作 fn-ptr 计划 (`(op_id, dtype, backend_id)`)，在插件*内部*保持 dtype `match T::DATA_TYPE` 单态化，并仅在操作粒度上进行擦除 — 每个 matmul/attention 一个间接，而不是每个元素。接缝故意位于 `MemoryPort` 的字节操作和高级操作调用之上，而不是在张量元素级别。
**独立编译下的 ABI 健全性（中等可能性，严重影响）。** 不会影响 `abi_version` 的 `repr(C)` 布局漂移、非 `catch_unwind` 的恐慌越线、没有主机分配缓冲区的跨 `.so` 或传输 `OpError`（`repr(Rust)` 枚举，已确认） （`ports/error.rs`）作为 FFI 中的 Rust 值都是静默 UB，而不是错误。 *缓解措施：* CI ABI 快照测试加上“`infer-backend-abi` 中没有 `repr(Rust)` 公共项目”lint；恐慌边界 lint 迫使每个条目出现 `catch_unwind`；带手柄的删除器旅行，按键为 `owner_backend_id`； `OpError` 降低至 `i32` 状态加上不透明的 `ErrorDetail` 句柄并重建主机端。
**擦除的表面是新代码，而不是投影（高可能性，高影响）。** 已验证的基本事实：`math_ops.rs:16` `fn add<T: Dtype>(...)` 和 `FusedOps` 方法是通用自由函数，没有 `&self` 接收器，而 `Backend` 是它们之上的全面超级特征（`backend.rs`） - 所以端口*不是*对象安全和 `Box<dyn Backend>` 目前无法编译。 *缓解：*范围 `BackendDyn` 及其每个数据类型适配器作为动态调度工作的主体，并通过针对通用表面的 CI 锁步测试对其进行控制。到处都丢掉“投影”这个词。
**融合操作不能作为单个 `DeviceTensor` POD 交叉（高可能性，高影响）。** `attention_paged` 采用 `KvView<'_,T,Self>`，`scatter_kv_paged` 采用 `LayerKv<'_,T,Self>`，每个融合方法采用 `StepCtx<'_,Self>`（已验证的 `fused_ops.rs:62-98`）。单独的 DLPack 形状描述符无法对这些进行编码。 *缓解：*每个融合操作都有一个不同的 `#[repr(C)]` arg 结构，将聚合展平为 `DeviceTensor` 句柄数组和 `BatchPlan` POD；将其视为从特征表面再生或针对特征表面进行测试的真实的~30结构表面。**dtype-tag 擦除将类型保证转换为内存安全义务（中等可能性，严重影响）。** 在线 `dtype_tag` 在 **u16** 进行标准化，以匹配 `DTypeId` 和 ≥1024 注册表范围。错误的标签是损坏，而不是可恢复的错误。 *缓解措施：*每个后端条目都会在取消引用之前重新验证 `dtype_tag`、`owner_backend_id` 和形状/步幅，并进行对抗性测试。
**CPU 回退掩盖了性能悬崖（中等可能性，高影响）。** CPU 后端完全实现 `MemoryPort`/exec，但仅本地实现 `CoreOps`/`DiffusionOps` 的“子集”，并通过主机往返默认值继承 `FusedOps`（`cpu/mod.rs:42` 是 `impl FusedOps for Cpu {}`）。像 `attention_paged` 这样的热操作回退是正确的，但会降低解码延迟。 *缓解措施：*记录并计量每个跨后端往返到调度程序的普罗米修斯路径中；提供生产硬故障模式，因此热路径回退是一个启动错误，而不是无声的运行时意外。
**Fatbin 大小和首次加载 JIT 延迟（中等可能性，中等影响）。** 多架构 fatbin + PTX 将主机固定换成冷启动驱动程序 JIT 和更大的 cdylib。 *缓解措施：*发布 `sm_80/86/89/90 + compute_90` PTX，依赖驱动程序的磁盘上 JIT 缓存，在容器映像中和服务器预热时进行预热，并在 `include_bytes!` 膨胀成为问题时使用 sidecar 工件。
**暂存顺序会破坏工作线程（给定纪律的可能性很小，但影响重大）。** 在非 `Cuda` 运行时存在之前翻转 `default = ["cuda"]` 会产生一个可以编译但无法构建运行时的工作线程。 *缓解措施：*强制的阶段顺序 - 在第 2 阶段进入工作 CPU 服务循环之前绝不翻转默认值。
**不受信任的插件运行任意进程内代码（可能性低，影响严重）。**未沙箱的 `dlopen` 后端在服务器进程中执行；本机探针位于插件内部，可能会在 `catch_unwind` 完全保护主机之前使主机崩溃。 *缓解措施：*加载前签名/校验和验证；通过现有的 ZMQ 工作子进程隔离而不是进程内 `dlopen` 路由不受信任或实验性后端。

＃＃ 结论这个提案是一个重构，而不是重写，它通过建立在 RustInfer 已经拥有的三个东西的基础上而赢得了这一声明：一个精心设计的端口系列，其中 `MemoryPort` 已经讲原始字节，第二个后端 (`Cpu`) 已经实现了这些端口，以及一个干净的 DDD 分层，使 `domain/` 不受 FFI 影响。此设计所需的接缝是半建的；我们的工作是在正确的高度完成切割——高于 `MemoryPort` 和高级操作调用，低于 dtype `match`——而且说实话，现有代码*不*免费为我们提供抽象。
该提案有意坦诚地对待这些差距。这些端口不是对象安全的，因此擦除的 `BackendDyn` 表面是新的手写代码，必须 CI 锁定到通用表面。 CPU 后端并不实现每个操作，因此每个操作的回退是一个计量正确性路径，而不是一个免费终端。融合操作携带生命周期聚合，因此 ABI 约为 30 个 arg 结构，而不是 1 个 POD。在线 dtype 标记是 u16，而不是 u8，因为它必须寻址已注册的 dtype 范围。对工件进行统一命名（`infer-backend-cuda` 和随之而来的 `libinfer_backend_cuda.so` / `RUSTINFER_BACKENDS=name:path` 约定），保留描述一个系统的八个详细部分。
使该计划可执行的是始终绿色的分段：协调两个 `Device` 特征，在源代码级别折叠基础并提取内核，引入擦除特征和支持 CPU 的服务循环，*然后*动态加载，并且仅最后 `default = ["cuda"]` 翻转。工作人员永远不会停止构建，单态 `match T::DATA_TYPE` 热路径也永远不会受到干扰。回报是一个单独使用 `rustc` 构建的核心，并提供在自己的列车上构建和发布的无 GPU 加速器内核，以及一个可以在单个狭窄的、版本化的、仅附加的 C ABI 后面托管 CUDA、ROCm、Metal 和 CPU 的运行时，并且可以附加地实现未来的多后端，而无需破坏已加载的插件。

## 附录 A — 按部分划分的关键决定
承重决策和部门级风险的统一索引，用于快速审查和实施过程中的跟踪。
### 1. 存储库结构- **将过度分割的基础折叠成单个推断核心板条箱，其中包含 dtypes/QuantScheme/errors、MemoryPort、（合并的）设备特征、执行词汇表（ExecScope/Stream/Workspace/ActiveGuard/StepCtx）、存储和张量。将核心从 ~8 个箱子减少到 4 个（infer-core、infer-backend-abi、infer-runtime、infer-models）。** — 这些项目在项目级别相互递归：Tensor<T,D> 需要 MemoryPort； Storage<D> 是唯一的分配调用者；执行设备：MemoryPort； ExecScope::enter 返回 ActiveGuard<Self::Device>； ActiveGuard<D>在Device上是通用的，在Drop中调用scope.device()； Workspace<D>/StepCtx<D> 在设备上是通用的。 Rust 箱不能是循环的，因此任何分割（例如 infer-tensor 中的张量、infer-backend-abi 中的端口）都会产生牢不可破的循环。一个箱子使 DAG 非循环。 _已拒绝：_之前的 8 路拆分（infer-core/infer-tensor/infer-backend-abi/infer-ops/infer-graph/infer-runtime/...）将 Tensor 和 exec/Device 特征放置在单独的板条箱中，并准确地创建了它声称设计的周期。
- **仅保留 op-port 特征 (MathOps/FusedOps/DiffusionOps/CollectiveOps/Backend) 加上 infer-backend-abi 中新类型擦除的 BackendDyn+vtable+loader，通过一个向下箭头位于 infer-core 之上。** — op-port 特征名称 Tensor<T,Self>、Self::Scope 和 StepCtx<Self>，所有这些都位于推理核心；向下依赖于推理核心（而不是侧向于对等体）使图保持非循环，同时仍然将稳定的 ABI/加载器表面隔离在其自己的板条箱中。 _拒绝：_ 将 exec/tensor 机制放入 infer-backend-abi（会将基础重新合并到 ABI 箱中并模糊稳定性边界）；将操作端口保留在推断核心中（将强制后端板条箱依赖于整个面向运行时的表面）。
- **在移动过程中合并两个设备特征（将 ports::Device::{ExecCtx,name} 折叠到 exec-layer Device 中），或者作为后备，将 exec-layer 特征重命名为 ExecDevice；不要在 infer-core 的公共表面上发布两个名为 Device 的特征。** — 今天实际上有两个名为 Device 的不同特征（类型为 ExecCtx 的domain/ports/device.rs 和类型为 Scope: ExecScope 的domain/exec.rs）。将两者暴露在同一个已发布的板条箱名称下是一种可用性风险和不明确的导入陷阱。 _已拒绝：_ 在新的 crate 边界上保持两个设备特征不变（名称冲突、导入歧义）。
- **将静态通用/类型擦除接缝放置在 MemoryPort（在 infer-core 中）和高级操作调用（在 infer-backend-abi 中）；在插件内的 dtype 标签上重新单态化。** — MemoryPort 已经使用原始的 NonNull<u8>+sizes，并且 Cpu 和 Cuda 都以相同的方式实现它，因此接缝是半构建的。以操作粒度进行擦除会为每个操作消耗一个 fn-ptr 间接成本，而不会为每个元素消耗一个 fn-ptr 间接成本，并保留插件内匹配的 T::DATA_TYPE 热路径。 _拒绝：_ 以元素/存储粒度进行擦除（每个元素 vtable 成本）；将 dyn 调度推入 Tensor/Runtime（破坏单态模型代码）。
- **保持 infer-cpu-backend 静态链接作为始终存在的终端后备； CUDA/ROCm/Metal 仅加载 cdylibs。** — cpu/mod.rs 已经实现了每个端口并返回 OpError::Unsupported，使其成为自然的保证后备。静态链接保证了仅使用 rustc 进行核心构建和测试。 _已拒绝：_ 让 CPU 也成为一个插件（失去了仅使用 rustc 构建的保证和始终存在的终端）。_风险：_
  - 两个设备特征（ExecCtx 类型的 ports::Device；Scope 类型的 exec::Device）在移动过程中必须协调为一个；拙劣的合并会更改 Tensor<T,D> 的类型状态轴和 ExecScope::Device==Self 不变式，因此合并需要机械的、经过编译器检查的传递，而不是手动编辑。
  - 即使在塌陷为下层核心之后，基础箱仍然很大并且内部递归；需要注意的是，application/* 中的任何内容（例如 plan.rs、kv.rs）都不会以应该留在 infer-core 中而不是转移到 infer-runtime 的方式秘密地返回到 Tensor/exec。
  - 不透明 DeviceTensor 上的 dtype 标记将编译时匹配 T::DATA_TYPE 保证转换为 ABI 边界的运行时检查；错误的标签会导致内存损坏，因此边界必须重新验证每个条目的数据类型/形状。
  - 将 .cu 移动到通过驱动程序 API PTX/fatbin 加载的 cdylib 引入了首次加载 JIT 延迟和核心目前无法控制的磁盘缓存。
  - 瘦推断工作者仍然拥有 ZMQ 泵和插件发现；错误确定哪个应用程序/*代码是主机连接与运行时可能会使运行时逻辑滞留在二进制箱中。
  - 在 infer-backend-abi 风险内保持进程内 op-port 特征路径和 C-ABI vtable 路径同步； vtable 必须根据特征表面生成或测试。
### 2.后端抽象层- **在现有 MemoryPort 字节边界和高级 CoreOps/DiffusionOps/FusedOps 操作调用边界处精确切割静态到动态的接缝；保持上面的 Tensor<T,D> 单态化，下面的 dtype 匹配。** — MemoryPort 已经支持原始的 NonNull<u8>+sizes，并且 Cpu 和 Cuda 都实现了它；存储是唯一的 RAII 分配所有者，因此接缝是半建成的。以 op 粒度进行擦除，每个 matmul/attention 需要一个 fn-ptr，而不是每个元素，并且保留每个后端内的零开销匹配 T::DATA_TYPE 热路径。 _拒绝：_ 在张量/元素级别进行擦除（每个元素 vtable 成本，对 GEMM 吞吐量是致命的）；在模型级别上进行擦除（将强制重写所有模型/应用程序代码并失去类型状态安全保证）。
- **使 DeviceTensor 成为借用的 #[repr(C)] DLPack 形描述符（DTypeId 标记、byte_offset、owner_backend_id、MAX_RANK=8 内联形状/步幅），仅对一次同步 vtable 调用有效，由主机端 keep-alive 合约管理；主机在提交过程中将拥有的张量（及其 Arc<Storage>）保存在堆栈上。它不是零拷贝拥有导出。** — Tensor 通过 Arc<Storage<D>> (tensor.rs:21) 拥有字节，其 Drop 会释放分配； DeviceTensor 无法跨 C-ABI 携带 Arc，因此健全性来自主机为同步调用保持 Arc 活动状态，而不是来自引用计数传输。导出将 offset_elems*SIZE_BYTES 折叠为 byte_offset 并逐字复制步幅，以便子视图/非连续张量忠实地交叉。 DTypeId(u16) 和所有描述符字段已经存在于 Tensor 中，因此构造是字段副本。 MAX_RANK=8 涵盖所有LLM/扩散张量； over-rank 返回 OpError::Unsupported 并保留堆指针回退。 _已拒绝：_ 称其为免费的零拷贝导出（忽略 Arc<Storage> 所有权和整个 FFI 的生命周期）；跨 C-ABI 传输 Arc/refcount（Arc 超出边界没有任何意义）；默默地假设连续性（会破坏子视图张量）； c10 风格的 DispatchKeySet 内置（多轴键集是 RustInfer 缺乏的 autograd/功能化带来的意外复杂性）；默认情况下无界/堆排名（丢失证明每个操作交叉一次的单缓存行 POD）。
- **不对称地声明跨缝所有权规则：DeviceTensor 永远不会拥有；根据保持活动合约，主机拥有的存储支持的缓冲区对于一次调用是借出的；插件分配的持久缓冲区由具有随句柄移动的删除器的插件所拥有。** — 这两个方向不对称，将它们混为一谈是潜在的错误：“删除器随句柄移动”规则仅涵盖插件分配，而借入插件操作的主机 Arc<Storage> 需要反向主机端保持活动保证。将两者明确化可以缩小审稿人标记的差距。 _已拒绝：_ 单个对称“删除程序随句柄移动”规则（不覆盖主机借出缓冲区并使其在 FFI 中的生命周期未解决）。
- **在模型加载到捕获的 op vtable 时解析设备轴一次；将 dtype 调度保留为后端内的编译时匹配。使用简单的 (op_id, dtype, backend_id) 映射，而不是调度网格。 ** — TensorRT 的预解析 DAG 课程：在热路径上没有每次调用注册表遍历或字符串查找。 RustInfer 没有第二个调度轴来证明 PyTorch 风格的 64 位密钥集。 _Rejected:_ PyTorch 风格的每次调用 DispatchKeySet 表（意外复杂性）； ORT 风格的 OrtMemoryInfo 分配器查找（RustInfer 的 ExecScope/Storage 所有权更清晰）。
- **保留 OpError::Unsupported 作为每操作运行时回退信号，并静态链接 CPU 后端作为有保证的终端回退；在功能描述符中将功能功能与硬件兼容性分开；记录每个跨后端主机往返（其本身重新参与暂存缓冲区的保持活动合同）。** — CPU 后端已返回 Unsupported 并实现每个端口，从而启用 PJRT/TRT 无法执行的每操作 CUDA->CPU 回退。分割轴（TRT 课程）对于不受支持的 dtype 和太新的 arch 会产生明显的错误。记录往返可以避免 ORT/PyTorch 静默 Memcpy 延迟。 _已拒绝：_ 仅整个程序后备（PJRT/TRT — 对于 LLM 热路径来说太粗糙）；静默主机往返（破坏解码延迟）；将 CPU 后备置于插件 ABI 后面（它必须始终存在）。
- **使后端注册表成为一个拥有的、可删除的注册表对象（Vec<Box<dyn Backend>> by name+priority），静态CPU后端通过linkme进行自注册，动态后端在加载后显式注册。** - 启用多个后端的进程内共存、确定性启动、真正的卸载/热插拔以及用于多租户的每服务器注册表 - 避免顺序脆弱的静态初始化单例PyTorch/TVM/TRT 遗憾。 _Rejected:_ 进程全局单例注册表因静态初始化副作用而变异（不可卸载、顺序脆弱、容易出现段错误）；通过 dlopen 链接我（仅限链接时间，对于动态插件无用）。_风险：_
  -接缝在每个后端条目处重新验证DTypeId和owner_backend_id；错过验证意味着不匹配的 dtype 标记是静默内存损坏，而不是类型错误（当前编译时类型状态消除的擦除成本）。
  - 主机端保持活动合约不受 C-ABI 类型系统的强制执行：如果主机在后端操作完成之前删除拥有的 Tensor（释放其 Arc<Storage>），则 DeviceTensor 的 raw_ptr 会悬空，并且插件会读取已释放的内存。健全性取决于每个调用站点遵守的同步提交规则，而不是借用检查器。
  - 每操作 CUDA->CPU 回退可能会掩盖性能悬崖：如果热操作（例如，attention_paged）默默地回退，则即使正确性保持不变，解码延迟也会崩溃。日志记录可以降低可见性，但不能防止回归。
  - 对象安全的 dyn 设备/dyn 流投影必须忠实地从 exec.rs 再现 ActiveGuard 输入/恢复设备绑定规则；在动态边界上设置错误的保护寿命可能会导致错误的 CUDA 设备电流。
  - MAX_RANK=8 内联形状/步长上限意味着真正较高阶的张量返回 OpError::Unsupported，直到实现保留的堆指针变体； offset_elems 的 byte_offset/stride 折叠必须是精确的或子视图，并且非连续张量通过错误的寻址跨越接缝。
  - 后端选择时的功能交叉必须与插件实际实现的功能保持同步；夸大支持的功能位集会在运行时在可能不需要回退的上下文中重新引入 OpError::Unsupported 路径（例如，期望本机执行的基准测试）。
### 3. 异构执行引擎：调度程序、放置程序和调度程序- **在现有内存端口 (device.rs alloc_bytes/upload/download/copy_device_to_device) 以及高级操作端口 (MathOps/FusedOps/DiffusionOps) 处切断静态到动态的接缝，将每个操作降低为通过不透明 DLPack 形状的 DeviceTensor 进行一个 C-ABI vtable 调用，并在后端内的 dtype_tag 上重新单态化。** — 内存端口已经表示原始 NonNull<u8>+sizes 并且 Cpu 和 Cuda 都已经实现了相同的端口（CPU 已经返回 OpError::Unsupported 缺少操作），因此接缝是半建成的；以 op 粒度（不是每个元素）进行擦除为每个 matmul/attention 支付一个间接，并保留现有的零开销匹配 T::DATA_TYPE 热内核。现实的路径将这些端口重用为进程内后端特征加上 C-ABI 填充程序，而不是重写。 _Rejected:_ 每个元素擦除 (PyTorch TensorIterator) 会在内循环中添加间接；对运行时张量（candle Storage 枚举）的完全重写会丢弃单态化内核资产。
- **将 MVP 的范围限定为每个模型的一个活动后端（匹配当今的单设备/单流/block_size==1 不变式），并将整个跨后端放置/分区/传输子系统（GetCapability 分区器、DeviceTransfer 端口、对等复制矩阵、流依赖一致性）降级为“单后端运行时负载工作端到端”后面的明确 MVP 后阶段。将owner_backend_id保留在DeviceTensor中，将能力查询条目保留在核心vtable中，但从初始ABI表面中删除多后端分区器/DeviceTransfer/对等复制，稍后通过类型化扩展链附加地交付它们。** - 当前代码只有一个设备，每个ExecScope一个流，零跨设备移动，因此布局/传输机制没有模拟，也没有测试；解码路径将整个模型保留在一个后端，以便唯一的工作路径不使用该子系统。将其构建到第一个稳定的 ABI 中会使 ABI 过度适合未使用的功能。 Owner_backend_id 是两个字节，即使在单后端中也锚定删除器旅行与句柄规则； (op_id,dtype,backend_id) 三重和可删除的多条目注册表已经具有适合延迟情况的正确形状，因此扩展链 + 仅附加 struct_size 规则使多后端成为不间断的添加。 _拒绝：_ 在与构建解耦工作相同的高度呈现跨后端布局（模糊了可立即交付与推测，过度拟合第一个 ABI）；预先发明传输矩阵和分区器（没有当前代码模拟，未经唯一可交付成果的测试）。
- **调度键是在模型加载到每个操作 fn-ptr 计划中一次解析的最小（op_id、dtype、backend_id）三元组，而不是每个调用表；在 v1 中 backend_id 是常量，因此计划很简单，并且后 MVP 分区器仅填充 backend_id 而不更改密钥。 ** — 解码循环重复相同的操作序列数百万次，因此 ORT/TensorRT 解析一次并冻结优于每次调用查找； RustInfer 没有自动分级/功能化轴来证明多轴键集的合理性，并且三元组与多后端布局向前兼容。 _Rejected:_ PyTorch 64 位 DispatchKeySet 每次调用都会索引 — 明确标记为 RustInfer 缺乏的自动分级分层所产生的意外复杂性。
- **手工制作的 #[repr(C)] vtable，带有一个条目符号 rustinfer_get_backend_api，abi_version/struct_size 作为仅附加第一个字段，TRT 风格的 Core/Build/Runtime 分组，用于可选操作的类型化扩展链，每个条目上的 catch_unwind，在owner_backend_id 上键入的删除器旅行与句柄。 v1核心vtable是身份+单后端能力查询+单后端计划解析+per-op enqueue ONLY； DeviceTransfer/peer-copy/partitioner hooks 位于扩展链中，而不是核心中。** — op 集很小，固定，并且已经枚举为端口；手工制作的 vtable 比 abi_stable 更简单，PJRT 的 struct_size 仅附加规则可以便宜地购买前向+后向兼容，并且正是在不破坏加载插件的情况下添加延迟的多后端条目的原因； catch_unwind 和 per-backend free 可以防止 UB 和跨 DLL 双重释放，一旦任何后端被 dlopen'ed，即使只有一个后端，这也是一种危险。 _Rejected:_ abi_stable/stabby （更多仪式，仅 Rust 集合需要）； C++ vtable 走私 (PyTorch/ORT-bridge/TRT) — 排名第一的反模式；将传输/放置放入核心 vtable 中（将第一个 ABI 过度拟合到未执行的功能）。
- **将所有 .cu 移至独立的 infer-backend-cuda cdylib 中，该 cdylib 提供多架构 PTX/fatbin 并通过 cudarc 动态加载进行加载，因此工作核心使用零 CUDA 工具链进行构建； default=["cuda"] 变为运行时加载。将其视为独立的、有其自身优点的 MVP 的一半，它与 v1 调度/ABI 工作融合在一个可交付成果上：一个在运行时加载 CUDA 的干净构建工作线程。** — 直接消除 472 行 build.rs 耦合、nvcc/libclang/cuDNN 发现和主机 GPU 特定的 sm_XX 固定；每个参考运行时都将工具链保留在供应商插件内，而 cudarc 使其可以在纯 Rust 中实现。它正是产生第一个可加载的单后端插件的原因，因此它不需要多后端功能就有价值。 _已拒绝：_ 将 .cu 保留在功能后面（仍然在核心构建上强制使用完整的工具链）；单个主机检测到的 cubin（主机拱固定工件）。
- **保持CPU后端静态链接（linkme）作为始终存在的终端后备并可作为插件使用；发现是显式名称：注册到可删除的每服务器注册表中的路径；在 v1 中，注册表保存静态 CPU 基线和一个加载的加速器，并且跨后端传输节点/日志记录机制与多后端子系统的其余部分一起延迟。** — 静态 CPU 基线保证工作线程始终可以启动 CPU 驻留模型，即使 CUDA 插件无法 dlopen（并且稍后使每操作 CUDA->CPU 回退安全）；显式注册提供了确定性的加载/卸载和多租户友好的可删除注册表，其多条目形状对于后 MVP 情况已经是正确的。 _Rejected:_ Static-init 自注册（顺序脆弱、不可卸载、根据 PyTorch/TVM/TRT 容易出现段错误）；进程全局单例注册表； dir-scan 自动发现（存在加载版本不匹配的二进制文件的风险）。_风险：_
  - 即使在 v1 的单后端情况下，边界处的 dtype_tag 重新验证也是一项内存安全义务：错误的标签是损坏，而不是可恢复的错误。每个后端条目必须在取消引用之前进行验证，并进行对抗性测试。
  - cudarc 动态加载 + 多架构 PTX 将内核选择转移到驱动程序 JIT-at-load；必须验证首次加载延迟和磁盘上 JIT 缓存行为，并确认未列出架构的 PTX 回退覆盖范围。这种风险属于 MVP 的范围。
  - 每个外部“C”条目上的 catch_unwind 是强制性的； ABI 上任何未包装的恐慌都是 UB。需要 lint 或宏来统一执行。
  - 即使在单后端中，Deleter-travels-with-handle 也必须通过构造来强制执行（丢弃包装拥有后端的空闲 fn，以owner_backend_id 为键）：其插件库提前丢弃的 DeviceTensor 会导致卸载后使用。这是在 v1 中后端打开时生效的。
  - 保持 CPU 后端静态链接（linkme）并作为插件存在两次注册相同 backend_id 的风险；可删除注册表必须确定性地进行重复数据删除，包括在 v1 两次条目的情况下。
  - 插件内部的重新单态化意味着每个后端 cdylib 仍然编译完整的 dtype 叉积；必须监视每个后端 crate 的二进制大小和构建时间。
  - 仅附加 ABI 规则是整个延迟策略所依赖的机制：延迟的多后端（DeviceTransfer/partitioner/peer-copy）必须插入扩展链而不触及 v1 核心 vtable。意外的字段重新排序或未附加的添加会默默地破坏加载的插件和前向兼容保证。在 v1 发布之前需要进行 CI ABI 快照检查。
  - 延迟（后 MVP）：跨供应商传输总是托管阶段，因此未来在供应商之间分割 LLM 操作的图表将降低延迟；当分区器登陆时，它必须保持解码共存并记录每个传输节点。未在 v1 中执行，但 v1 ABI 必须保持可证明的可扩展性。
### 4.动态加载、插件架构和稳定的ABI- **将进程内特征路径（静态 CPU 后端）和 C-ABI 插件路径构建为同一后端逻辑的两个单独的消费者，而不是跨边界流动的相同 Rust 对象。该插件在私有 CudaInner 类型上重用端口特征 (CoreOps/FusedOps/MemoryPort) 作为内部实现细节；只有 #[repr(C)] POD、不透明句柄和 i32 代码跨越 .so 行。** — 该插件将 infer-core/infer-backend-abi 作为 Cargo deps 链接，因此其内部实现会看到 OpError/Tensor/CoreOps，但它仅在自己的工件中使用它们。如果主机和插件是由不同的 rustc/codegen 构建的（独立构建/发布的全部意义），则读取对方写入的任何 repr(Rust) 值都是 UB。保持 Trait impls 严格私有并仅交叉 repr(C) POD 使得独立编译听起来更合理。 _Rejected:_ 通过跨边界引用传递 Rust 特征对象 / OpError 枚举 / Capability-as-Rust-struct（独立代码生成下的 UB）；要求主机和插件共享单个已编译的工件（无法实现独立构建/升级，整个目的）。
- **OpError（包括不支持的）永远不会作为 Rust 枚举跨 FFI 传输。该插件 thunk 将其降低为保留的 i32 状态代码（不支持的独特代码，以触发 CPU 回退）加上可选的不透明 ErrorDetail 句柄；主机从代码中重建一个新的 OpError 主机端。** — OpError 是一个 repr(Rust) 枚举（在 ports/error.rs:5 处确认，不支持{backend,op}）。它的布局在独立编译中不稳定，因此无法跨 .so 行读取。从数字代码重新创建它可以保持现有的 Rust 错误路径（和每个操作的 CPU 回退）完好无损，同时边界保持纯数字。 _Rejected:_ 通过 extern C 的值/引用返回 OpError（UB，没有稳定的 repr(Rust) 布局）；共享错误字符串 Vec（.so 中没有稳定的 Vec 布局）。
- **固定兼容性合同：插件和主机必须共享相同的 infer-core / infer-backend-abi SOURCE 版本，但不需要共享已编译的工件、rustc 或 codegen 设置。 infer-backend-abi 仅包含 #[repr(C)] 定义； CI ABI 快照测试加上 abi_version/struct_size 门强制执行窗口。 ** — 协议是关于 C ABI 的数字含义（repr(C) 布局、整数编码、vtable 字段顺序），而不是任何 repr(Rust) 布局。这正是 repr(C) 在独立构建中保留的属性，而 repr(Rust) 则没有，因此它正是使插件独立性安全的行。 _已拒绝：_ 需要相同的编译二进制文件（无独立升级）；隐式保留版本契约（漂移时静默 UB）；将 repr(Rust) 类型放入共享 ABI 箱中。
- **精确地在现有的高级操作端口（CoreOps/MathOps/FusedOps/DiffusionOps）处切割静态通用/类型擦除接缝，将每个操作调用降低为一个 #[repr(C)] vtable fn 指针，采用不透明的 DeviceTensor POD + StreamHandle 并返回 i32，并在插件 thunk 内重新单态化在插件的私有特征 impl.** 中——MemoryPort 已经讲了原始的 NonNull<u8>+sizes，并且 Cpu 和 Cuda 都以相同的方式实现它，因此接缝是半构建的。以 op 粒度（不是每个元素）进行擦除需要每个 matmul/attention 进行一次间接调用，同时保留插件内部的零开销匹配 T::DATA_TYPE 热路径。这是增量重构，而不是重写。 _Rejected:_ 全局擦除张量元素类型（杀死单态内核匹配）； c10 风格的多轴 DispatchKeySet（RustInfer 缺乏 autograd 带来的意外复杂性）。
- **手工#[repr(C)] struct-of-fn-pointers，带有一个入口符号 rustinfer_get_backend_api(abi_version)->*const BackendVTable，struct_size/abi_version 第一个字段，仅附加，用于可选操作的类型化扩展链；按值作为 repr(C) POD 返回的功能。** — 不存在稳定的 Rust ABI。 op 集很小，固定，并且已经枚举为端口，因此手动 vtable 可以比 abi_stable 更少地提供完全控制。 PJRT 的 struct_size-first 仅附加规则购买了前向+后向兼容性，而无需冻结主要版本；扩展链添加融合操作而不破坏 ABI。 _Rejected:_ abi_stable （重、大的 dep，仅在跨线运送 Rust 集合时才需要）；刺刀（较轻，但强加其世界观）；通过 FFI 发送 Vec/String/dyn/OpError（UB，没有稳定的 Rust ABI）。
- **将所有 .cu + nvcc + bindgen + nvidia-smi 检测移至独立的 infer-backend-cuda cdylib（deps：用于重用端口特征的 infer-core，用于 repr(C) 类型的 infer-backend-abi），该库提供多架构 PTX/fatbin 并通过 cudarc 动态加载加载 CUDA；使用零 CUDA 工具链构建核心。** — 直接解决紧张问题 #2：今天 default=[cuda] 意味着如果没有完整的 CUDA 工具链 + 主机 GPU，则无法构建核心，并且工件是主机架构固定的。每个参考运行时都将工具链保留在供应商 .so 内； cudarc dlopens libcuda/nvrtc，因此消费者没有链接时 CUDA。驱动程序在加载时 JIT PTX 并将其缓存。插件的 infer-core/infer-backend-abi deps 编译成插件自己的工件；主机既不链接内核也不链接插件的 Rust 实现。 _已拒绝：_ 将 .cu 保留在功能后面的工作程序中（工具链耦合不变）；单个 nvidia-smi->sm_XX cubin（特定于主机 GPU）。
- **通过 libloading 显式入口点注册到拥有的、可删除的每服务器 BackendRegistry（env/config 名称：路径列表，PJRT 样式）中，并通过 abi_version 门之后的值作为 repr(C) POD 查询功能（）。保持 CPU 后端静态链接 (linkme) 作为始终存在的每操作后备，从不通过 FFI 作为本机 Rust 特征使用。** — 静态初始化自注册 (PyTorch/TVM/TensorRT) 顺序脆弱、不可卸载、容易出现段错误。显式入口点提供确定性加载和卸载（真正的热插拔），可删除注册表适合多租户服务器。已经返回 OpError::Unsupported 的静态 CPU 基线提供了 PJRT/TRT 无法提供的每操作 CUDA->CPU 回退，并且作为进程内 Rust 使用者，它永远不会触及 ABI。 _Rejected:_ 静态初始化构造函数注册；进程全局单例注册表；将 CPU 置于 C ABI 后面（将失去零 FFI 终端回退）。
- **强制执行 ABI 安全三位一体：删除器随句柄（缓冲区、流和 ErrorDetail 句柄）一起移动，错误作为 i32+不透明 ErrorDetail 句柄与每个条目 fn 上的 catch_unwind 交叉（OpError 重构主机端，从未传输），版本门在第一次调用时大声。 ** — 这三个规则由每个成功的稳定边界（tvm-ffi、PJRT）共享。跨 extern C 的恐慌是即时的 UB；交叉.so free 与不匹配的工具链是双重 free；读取由不同编译的工件编写的 repr(Rust) OpError 是 UB；未经检查的 ABI 不匹配不是 UB 错误。 RustInfer 内核合法地返回 Unsupported，这使得严格的数字错误传播至关重要。 _已拒绝：_ 让 FFI 陷入恐慌；释放主机中插件分配的缓冲区；将 OpError 作为 Rust 枚举传输；信任 ABI 兼容性，无需 struct_size/abi_version 门。_风险：_
  - 不透明的 DeviceTensor dtype_tag 将编译时类型状态转换为运行时检查；错误的标签是内存损坏，而不是类型错误。在发布版本中需要严格的边界验证，从而增加了单态世界从未支付过的少量每次调用成本。
  - 源版本兼容性窗口（主机和插件必须共享 infer-core/infer-backend-abi 源，即使不是编译的工件）仅由 abi_version 门加上 CI ABI 快照测试强制执行；不影响 abi_version 的 repr(C) 布局漂移将是静默的 UB，因此快照测试和“infer-backend-abi 中无 repr(Rust) 公共项”lint 是承载的。
  - 将 OpError 降低到 i32 会丢失结构化负载（不支持{backend，op}），除非不透明的 ErrorDetail 句柄携带字符串；如果详细句柄的生命周期与插件库无关，它可以在卸载后悬空（卸载后使用）。
  - 交付多架构 PTX/fatbin 以主机 GPU 特异性换取首次加载 JIT 延迟；驱动程序磁盘缓存可以缓解，但冷启动和 CI 临时节点将出现重复的 JIT 成本。
  - cudarc 动态加载必须达到与 build.rs 中当前 cuBLAS/cuBLASLt/cuDNN 前端使用情况相同的功能/版本；一些 fused/cuDNN 前端路径（flash_attn_gqa、conv）可能没有干净的驱动程序 API 等效项，并且可能会强制在插件内保留薄 cuDNN 链接。
  - FusedOps 默认方法当前回退到主机往返（例如，attention_paged_reference、scatter_kv_paged_reference 执行 to_host_vec）；如果它们作为热路径中的 CPU 回退运行，它们将降低 LLM 延迟，除非记录每个跨后端往返并且 CUDA 插件覆盖它们。
  - block_size==1 和serve_loop 中的<bf16,Cuda> 硬编码意味着第一个插件剪切仍然只执行一个数据类型/设备对； ABI 必须针对一般情况进行设计，而最初只测试一条路径，从而存在未使用 vtable 插槽的风险。
  - 手工滚动的仅附加 ABI 纪律仅与审查一样好；单个非附加字段重新排序或错过的 catch_unwind 会重新引入 UB。需要 CI ABI 快照测试和恐慌边界 lint。
  - 要使库在其创建的所有句柄的生命周期内保持活动状态，需要在注册表、流、张量和 ErrorDetail 句柄之间进行仔细的 Drop 排序；当 CUDA 流或错误句柄处于活动状态时过早 dlclose 是典型的卸载后使用段错误。
### 5.后端构建系统：独立构建和发布- **采用混合构建系统：Cargo 驱动每个后端 crate 的 Rust shell； CMake 在每个后端自己的 build.rs.** 中编译内核 - CMake 是唯一具有一流多架构 CUDA fatbin (CMAKE_CUDA_ARCHITECTURES) 以及并行 HIP/Metal 故事、sccache 缓存、跨工具链文件以及实际编写 .cu 文件的内核作者普遍熟悉的竞争者。内核编译是唯一需要供应商编译器的部分，因此将其隔离在后端板条箱的 build.rs（而不是工作人员的）中可以直接消除工具链耦合。 _Rejected:_ Bazel：最好的密封性/远程缓存，但强加了一个陌生的第二构建图和陡峭的学习曲线，对于一个 CUDA 后端来说是过度杀伤力。 XMake/Meson：可信，但 CUDA+HIP 深度较弱，并且关注度低得多。 cargo+cc（现状）：无法发出 fatbin，没有 HIP/Metal 路径，并且是工作工具链耦合的确切来源。
- **完全删除worker的build.rs并将所有.cu编译移动到独立的infer-backend-cuda cdylib中；将默认功能从 ['cuda'] 翻转为 []（CPU 基线）。** — 使 infer-worker 构建时不使用 nvcc、libclang、cuDNN 前端发现、nvidia-smi。 CUDA 工具链要求仅出现在正确的后端箱中。 cc/bindgen/walkdir 留下工作程序构建依赖项。 _已拒绝：_ 保留 SKIP_BUILD_KERNELS 逃逸舱口：只会推迟痛苦，因为静态外部“C”符号无法链接。将内核保留在工作程序背后的功能：每当构建 GPU 路径时，仍然会强制使用整个工具链。
- **用固定的 gencode 矩阵 (sm_80/86/89/90 +compute_90 PTX) 替换 nvidia-smi 主机架构检测，该矩阵作为 fatbin 发出，并由 CUDA 驱动程序在模块加载时 JIT 解析到正在运行的 GPU。** — 删除工件的主机 GPU 特异性；相同的 fatbin 可以在受支持的 arch 窗口中的任何 GPU 上运行，并通过驱动程序 JIT（缓存在磁盘上）为较新的卡提供 PTX 回退。镜像 TVM CUDAModule 和 TensorRT fatbin 实践。 _已拒绝：_ 每次构建 nvidia-smi 检测（当前）：将工件固定到构建主机的 GPU 并使 CI 矩阵毫无意义。单拱 cubin：无向前兼容性。
- **保持 CPU 后端静态链接到工作线程，作为始终存在的终端后备；在运行时通过 cudarc 动态加载 + libloading 加载 GPU 后端。** — CPU 后端已经实现了 src/infrastruct/cpu/ 中的每个端口，证明抽象可以托管具有零 GPU 工具链的非 CUDA 后端。这使得第一个可交付成果（不使用 CUDA 构建的工作程序）立即生效，并保持有保证的每操作回退目标。 cudarc dlopens libcuda/libnvrtc 因此消费者没有链接时 CUDA。 _已拒绝：_ 将 CPU 也置于 C-ABI 插件边界后面：失去始终存在的静态保证并使终端回退变得复杂。在构建时链接 libcuda：在使用者中重新引入工具链依赖项。_风险：_
  - PTX 的首次加载驱动程序 JIT（对于不在预构建 sm_ 集中的拱门）会增加冷启动时的延迟；必须依赖驱动程序的磁盘上 JIT 缓存并在 CI/启动中对其进行预热。
  - 维护每个后端的 CMake 构建为内核作者引入了第二种构建语言； CMake 作为领域通用语言缓解了这一问题，但仍然与纯 Cargo 工作流程有所不同。
  - cudarc动态加载必须覆盖当前bindgen允许列表公开的每个CUDA驱动程序/cuBLAS/cuDNN/nvrtc符号（图形、cuBLASLt、cuDNN前端转换）；任何间隙都会强制在插件内使用每个符号填充程序或供应商绑定。
  - 固定的gencode矩阵必须与支持的GPU保持同步；没有匹配的 PTX 后备的太新的架构在加载时会严重失败 - 可以接受，但需要在 backend.toml 中提供明确的功能/计算上限。
  - 通过 include_bytes 嵌入 fatbin！膨胀 cdylib；对于大型内核集，可能需要 sidecar 工件 + 路径解析，这使单文件插件的情况变得复杂。
  - 再现性取决于每个后端固定工具链映像（CUDA 版本、nvcc）；如果没有记录的构建清单，来自不同 CI 运行程序的 fatbin 可能会略有不同。
### 6. 内核开发工作流程- **将内核拆分为 AOT 多架构 fatbin（稳定/自动调整：GEMM、flash-attn、scatter_kv、fused qkv-rope、fused_add_rmsnorm）与 NVRTC-JIT-with-disk-cache（elementwise/reshape tail：add、ewise_mul、broadcast_mul、cast_fill、scalar、permute、split_cols、swiglu、softmax、绳）。源审计确认 JIT 列出的内核不会提取 cutlass/cutlass 标头，因此分区将 cutlass 模板完全保留在 AOT 端。** — AOT 内核不断运行并依赖于自动调整/cutlass 模板实例化，我们不想在进程启动时重新付费； JIT 尾部很小，机械数据类型专门化（匹配 T::DATA_TYPE 梯形图），并且不断编辑，因此运行时编译 + 缓存会在启动 shim 存在时提供长达数秒的编辑循环，并且 Rust 重建为零。 _已拒绝：_ All-AOT（今天的模型）保留了重新链接的痛苦； all-JIT 在性能关键的 GEMM/attention 上付出了不可接受的首次调用延迟，放弃了 cutlass 自动调整，并且会通过 NVRTC 强制使用可爱模板内核，而 NVRTC 无法轻易消耗它们。
- **将通用名称和参数 NVRTC 启动垫片作为 JIT 机制的明确先决条件任务，替换每内核 `unsafe extern "C"` 声明和 JIT 子集的 `match T::DATA_TYPE` 梯子；增量地将内核迁移到它上面。** — 在 add.rs:9-80 中验证（与 softmax.rs/rope.rs/scalar.rs/etc. 中的形状相同）：每个 JIT 列出的内核都通过硬声明的 per-dtype C 符号和在链接时解析的匹配阶梯来到达。通过这些包装器无法访问运行时重新编译的 CUfunction，因此“编辑 .cu，零 Rust 重建”为 false，直到名称键控驱动程序 API 启动器（CUfunction 查找 + void** arg 编组 + 启动几何结构，通过 KernelSpec）替换符号绑定包装器。 _拒绝：_纯粹通过将编译移至 NVRTC 来声明长达数秒的循环是免费的，忽略了包装器仍然解析链接时符号；保留每个符号的外部包装器并且仅交换 .cu 主体无法达到新编译的函数。
- **将“仅限编辑.cu，零 Rust 重建”DX 声明的范围限定为已迁移到启动垫片上的内核；对于未迁移的 JIT 合格内核，编辑 .cu 仍然意味着更改 Rust 包装器（AOT 式重建）。** — 关于迁移边界的诚实：快速循环是 shim 根据内核获得的属性，而不是运行时编译的自动结果。 KernelSpec 是 name + arg-marshalling 的唯一真实来源，在删除之前针对旧包装器进行了测试验证。 _已拒绝：_ 跨所有 JIT 列出的内核的全面 DX 声明夸大了迁移前状态，并隐藏了调用约定的大量重写。
- **将启动 shim 的 CUfunction 查找与磁盘缓存统一：shim 通过 (arch, src_hash, flag_hash) 向缓存请求函数；缓存满足进程内地图、磁盘或新的 NVRTC 编译的要求。使用缓存版本字节和关闭开关进行磁盘布局内容寻址； dtype/tile 变体是不同的 flag-hashes。** — Flags-in-key 使自动调整和 dtype-专业化变得合理（块大小和 dtype -D 变体共存），并符合经过验证的 TensorRT 定时缓存 / ORT 编译子图缓存规则；使 shim 和缓存成为一个结构的两个方面意味着名称+数据类型解析和编译或加载路径是单一机制；内容寻址使得跨进程共享和容器镜像预热变得安全。 _Rejected:_ 仅源哈希密钥在拱门和标志/数据类型变体之间发生冲突，导致错误的 cubin 加载；仅内存中的函数映射在重新启动后会失去优势；独立于缓存的填充程序会重复编译或重用决策。
- **后端 .so 仅在静默点进行热重载：通过 ExecScope 同步流、拆除运行时、删除旧的 vtable+Library、dlopen 新的、重建运行时。** — ABI 安全规则（库必须比它生成的每个句柄都寿命更长）意味着当旧 .so 中的任何 DeviceTensor/stream/CudaConfig 工作区处于活动状态时，重新加载是不安全的；首先静默是唯一的声音交换，并且仍然提供完全的热交换，而无需重新启动调度程序/服务器。 _已拒绝：_ 实时就地符号交换存在未完成设备句柄上卸载后使用 UB 的风险；进程重启违背了开发热重载的目的。
- **将 fatbin 作为 arch SET (sm_80;sm_86;sm_89;sm_90 +compute_90 PTX) 发送，而不是单个 nvidia-smi 派生的 sm_XX；将自动调优结果保留在磁盘缓存中，而不是烘焙到分布式 fatbin 中。** — 删除工件的主机 GPU 特异性（驱动程序在加载时选择 cubin，在较新的架构上选择 JIT PTX），同时自动调优仍然通过缓存专门针对每个部署，从而保持交付的工件可移植。 _拒绝：_单拱立方体（今天）是不可移动的；将调整烘焙到 fatbin 中使其成为特定于主机且不可传送的。_风险：_
  - JIT 启动 shim 是一个硬性先决条件，而不是副作用：在它替换 JIT 子集的每内核 extern“C”+ 匹配阶梯之前，编辑 JIT 列出的 .cu 仍然需要更改其 Rust 包装器，因此秒长的循环仅适用于迁移的内核。低估这个垫片会使头条新闻的 DX 声明变成泡影。
  - shim 中的 arg 编组将编译时 dtype/指针类型检查（add.rs 中的每个符号签名）用于运行时描述的 void** arg 列表； KernelSpec 声明的 ArgLayout 与内核的真实签名之间的不匹配是静默内存损坏，因此在删除旧包装器之前，必须针对旧包装器对每个内核编组进行测试验证。
  - NVRTC 无法轻易消耗弯刀/可爱的重核； AOT/JIT 分区必须将每个与 cutlass 相关的内核保留在 AOT 端。审核确认当前 JIT 列出的内核是无刀具的，但任何未来的 JIT 添加都必须重新审核，否则会在运行时重新引入工具链耦合。
  - 磁盘缓存过时：NVRTC 次要版本更新或驱动程序更改可能会默默地使缓存的 cubin 失效；缓存版本字节必须可靠地进行碰撞，否则会产生错误的代码执行结果。
  - 热重载的正确性取决于真正耗尽所有设备工作；旧 .so 中超出库寿命的任何泄漏流/句柄/工作空间都会在卸载 UB 后立即使用。
  - cudarc 动态加载将 CUDA 缺失故障从构建时转移到首次运行时；能力/负载错误必须是响亮且早期的，而不是推迟到请求热路径中。
  - 首次调用 JIT 和首次形状自动调整将尾部延迟添加到冷缓存后的首次解码/预填充；在容器映像中或在服务器预热时进行预热，以避免请求时间停顿。
  - 将 .cu 移至单独的 cdylib 会更改构建图和 CI；当前生成的主机 GPU 固定的单架构工件必须替换为 fatbin 架构集策略，否则未列出架构上的部署会回退到 PTX-JIT，但会产生延迟成本。
### 7. 运行时依赖管理和检测- **dlopen-probe 通过单个类型的握手符号 (rustinfer_get_backend_api)，每个插件在内部探测自己的本机堆栈，而不是主机直接 dlsym-ing CUDA 版本符号。** — 符号存在并不能证明可用性（驱动程序太旧仅在第一次真正调用时失败）；主机不应对每个后端的本机依赖关系图进行编码；失败的 dlopen/handshake 是一个普通的结果，而链接库中缺少符号会中止该过程。匹配 PJRT 的 GetPjrtApi 间接寻址和 PyTorch 的惰性 is_available 探测。 _拒绝：_主机直接从 CUDA 库读取导出的版本常量 (cudaRuntimeGetVersion)；带有构建时检测的静态链接（当前的 build.rs 失败模式）。
- **将检测分为两个显式轴：功能功能（可查询（op，dtype）位集）与硬件/运行时兼容性（粗略驱动程序/工具包/compute-cap接受拒绝门）。** - 让CUDA插件拒绝fp8（操作级回退），与拒绝具有单独响亮错误的太旧驱动程序（整个插件拒绝）截然不同。当前的 build.rs 将两者折叠为“nvcc 是否成功用于 sm_XX”。这是 TensorRT 的supportsFormatCombination vs HardwareCompatibilityLevel 课程和ORT 的两层模型。 _拒绝：_单一融合能力检查； PyTorch 的多轴 DispatchKeySet（因 RustInfer 缺乏 autograd/functionize 轴而被拒绝）。
- **保持现有的CPU适配器静态链接（通过linkme）作为无条件的stage-0终端后备，永远不会落后于C ABI；将 OpError::Unsupported 形式化为每个操作的回退信号。** — Cpu 类型已经实现了每个端口，并且已经为仅 GPU 操作返回 OpError::Unsupported，因此它是真正的、预先存在的接缝。 linkme 仅在链接时有效，在 dlopen 中无用，因此基线必须是静态的。这提供了 PJRT/TensorRT 无法做到的每操作 CUDA->CPU 回退，以及 ORT 始终附加 CPU-EP 的保证。 _拒绝：_ 仅将 CPU 作为插件提供（如果 dlopen 失败，则将不存在）；删除 Unsupported 以支持编译时保证（不可能跨越类型擦除的运行时边界）。
- **将 CUDA 内核作为多架构 PTX+fatbin 提供，并在任何其他 vtable 访问之前读取 abi_version/struct_size 作为第一个字段；编码驱动程序/运行时/构建版本与 CUDA 次要版本兼容性规则的三重比较。** — 具有驱动程序 JIT-at-load 的多架构 PTX 删除了当前 nvidia-smi->single-sm_XX 构建烘焙的主机 GPU 特异性（TensorRT/TVM 前向兼容）。第一个字段的版本控制是 PJRT 的 struct_size 规则；未经检查的 ABI 不匹配是 UB，而不是错误。 _已拒绝：_ 单个主机架构 cubin（当前行为，主机固定）；读取其他字段后检查 ABI 版本（UB 不匹配）。_风险：_
  - 本机探针位于每个插件内，因此有缺陷或恶意的插件仍然可能在 ABI/catch_unwind 规则完全保护它之前的第 3 阶段使主机进程崩溃；不受信任的后端应使用现有的 ZMQ 工作子进程隔离，而不是进程内 dlopen。
  - CUDA 次要版本向前兼容性在常见情况下保持不变，但已记录例外情况（某些驱动程序/运行时组合、MIG、特定 cuBLAS 版本）；版本三重检查可能需要每个库的覆盖表而不是单个主要.次要规则。
  - 通过主机往返的每操作 CPU 回退是正确的，但如果热操作（matmul/attention）意外回退，可能会默默地破坏解码延迟；日志记录/计量必须连接到 infer-scheduler 的 prometheus 路径，并且理想情况下是生产的硬故障模式，因此热路径回退是启动错误，而不是运行时意外。
  - 多架构 fatbin + PTX 增加了插件工件大小并增加了首次加载 JIT 延迟；驱动程序的 JIT 缓存必须预热/持久化，否则冷启动会回归。
  - 功能位集（op_mask/dtype_mask）必须与仅附加 ABI 保持同步；重新排序而不是默默附加的 op_id 枚举会破坏跨版本偏差的功能报告。
### 8. 分发和安装- **三个独立的分发列车（crates.io core / OCI-registry backend cdylibs / PyPI+extra-indexwheels）仅在C ABI处相遇。** - 匹配PJRT/ORT，其中wheels和EP.so仅在GetPjrtApi/GetApi(N)处相遇；让核心独立发布无GPU和后端版本。 _拒绝：_ 单一胖轮供应所有 CUDA 系列（多 GB，每次碰撞重新下载）；将内核保留在核心中（无法发布到 crates.io，主机架构固定）。
- **将 infer-worker default=["cuda"] 从编译时内核构建降级为捆绑插件的运行时 dlopen；将所有 .cu 移至 infer-backend-cuda cdylib 中；静态链接现有的 CPU 后端作为基线。** — build.rs 目前强制使用完整的 CUDA 工具链 + libclang + cuDNN-frontend + 主机 GPU 来构建核心； CPU 后端已经实现了每个端口并返回 OpError::Unsupported，因此它是一个现成的始终存在的基线。 _Rejected:_ 保持 SKIP_BUILD_KERNELS 转义（链接然后失败）；从 nvidia-smi 运送每个主机的 sm_XX cubin（主机固定，不可分发）。
- **PyTorch 风格的 +cu124 本地版本伴侣轮位于额外的索引上，加上一个 CLI，可通过 cudarc 探测 GPU 并获取匹配的签名 fatbin+PTX 工件。** — pip 无法在安装时探测 GPU； +cuXXX/extra-index 约定是 PyTorch 用户已经知道的，并且安装后 CLI 探测比索引 URL 猜测更可靠。 _已拒绝：_ 在 pip 安装时自动选择 CUDA（无 GPU 可见性）；单个 sm_XX cubin（与 PTX JIT-at-load 相比失去前向兼容性）。
- **显式路径/注册表文件/env 发现 (RUSTINFER_BACKENDS=name:path) 到拥有的可删除注册表中，以 abi_version 作为第一个 vtable 字段，在 dlopen 之前验证校验和+签名。** — 窃取 PJRT 的 name:path env 和 ORT 的显式路径注册，同时避免静态初始化单例；为多租户 axum 服务器启用热插拔和每服务器注册表；在加载前验证来源并在加载时验证兼容性。 _Rejected:_ 静态初始化自注册到进程全局中（PyTorch/TVM 模式 — 顺序脆弱、不可卸载、未签名的任意代码）；目录扫描魔法（有加载版本不匹配的二进制文件的风险）。_风险：_
  - 首次加载 PTX JIT 延迟取代了构建时主机固定；通过为 sm_80/86/89/90 + 磁盘缓存 JIT 提供 fatbin 可以缓解这一问题，但全新 arch 上的冷启动比预构建的 cubin 慢。
  - 本地版本的伴随轮无法在 PyPI 上运行，因此必须托管额外索引并保持可用；中断会中断 GPU 安装，而 CPU 安装会继续工作。
  - 降级 default=["cuda"] 会更改现有的构建/CI 调用和硬编码的 <bf16,Cuda> 服务循环；在运行时负载接缝到达之前，核心没有 GPU 路径，下游调用者必须采用注册表。
  - 签名/验证增加了密钥管理负担（共同签名/迷你签名密钥轮换）；密钥处理不当会阻止所有安装或破坏信任保证。
  - Manylinux glibc 底层 (2.28) 和每个 CUDA 系列矩阵乘以工件构建/测试表面； ABI 兼容性矩阵必须保持权威，否则 --auto 会解析为不匹配的二进制文件。
  - 未沙盒的 dlopen 后端在服务器进程中运行任意代码；仅高信任 - 不受信任/实验后端必须通过现有的 ZMQ 工作子进程进行路由。
## 附录 B — 该提案如何得到验证
这八个部分是独立起草的，然后在综合之前经过三个对抗性审查。研究结果被折回各个部分。镜头总结：
**横截面一致性和连贯性**这七个部分各自连贯，并共享一致的核心论文（在 MemoryPort + 高级操作端口处切割静态到动态的接缝，在插件内保持 dtype 匹配，将 .cu 移至 cdylib，静态链接 CPU 作为终端后备）。关于现有代码的共享技术声明在很大程度上是准确的：DTypeId(u16)，BF16=2/F8E4M3=5，注册表从 1024 开始，MemoryPort 的原始 NonNull<u8> 表面，serve_loop 中的 <bf16,Cuda> 硬编码，block_size==1，supports_graphs()，OpError::Unsupported{backend,op} 和 29 .cu / 471行build.rs全部经过验证。然而，有几个具体的横截面矛盾会让实现者感到困惑：(1) 后端 crate 名称上的完全命名冲突（infer-cuda-backend 与 infer-backend-cuda），其中存储库结构强制采用一种约定，而所有其他五个部分都使用相反的约定； (2) 过度声明，在抽象和分发部分中重复作为负载承担，即 CPU 后端“实现每个端口”并且是一个准备好的每操作回退目标 - 代码显示 CPU 对于许多 CoreOps 返回 Unsupported，并且只有通用主机往返 FusedOps 默认值，kernel_dev 和dynamic_loading 正确描述了这一点，因此该文档在每操作 CUDA->CPU 回退是否实际有效方面自相矛盾； (3) DeviceTensor dtype-tag 宽度（u8 与 u16）以及是否逐字采用 DLPack 布局与添加所有者字段的漂移； (4) 关于接缝到底在哪里的说法不一致（MemoryPort-and-ops 与 ops-only）。在将提案视为单一设计之前，应协调这些内容。
**生产现实主义/对抗性：静态通用到类型擦除边界的可行性、解码中的动态调度性能、C-ABI vtable 健全性（跨 .so 的恐慌/分配器/流生命周期）、JIT/fatbin 现实性、KV 一致性。**该提案的核心主张——“MemoryPort 的接缝已经完成了一半，所以这是一次重构，而不是重写”——半真半假，并且被夸大了。 MemoryPort (device.rs) 真正使用原始 NonNull<u8>+ 字节并且可以干净地擦除； DTypeId(u16) 真实存在，注册表基数为 1024； CPU后端真正实现了每个端口。这些基本事实是成立的。但提案想要擦除的操作调用边界不会传递原始指针 - 每个 MathOps/FusedOps/DiffusionOps 方法都采用完全类型的 Tensor<T, Self> 加上复合的、具有生命周期的聚合（KvView<'_,T,Self>、LayerKv<'_,T,Self>、StepCtx<'_,Self>、BatchPlan）。如果没有提案从未指定的实质性新 ABI 表面，扁平 DLPack 形状的 DeviceTensor POD 就无法表示这些。三个更深层次的问题未明确说明或错误：(1) 成本模型（“每个操作一个 fn-ptr，免费”）是根据 eager 路径进行评估的，但实际的解码热路径是围绕 CUDA 图捕获/重放（GraphRunner、step_graph、capture_sizes）以及多流无气泡管道和共享 cuBLAS/cuBLASLt/cuDNN 处理的 Arc<CudaConfig> 构建的 - 一个每操作 C-ABI vtable，重新验证每个条目上的数据类型与图形捕获能力不兼容并且在重放时不相关；接缝必须位于图/步骤粒度，而不是操作粒度，这与提案自己的调度模型相矛盾； (2) 跨 FFI 的恐慌并不是假设性的——今天 cudaSetDevice 失败时，enter_device() 实际上是恐慌！并且它在每个 ExecScope::enter 上运行，即在每个操作之前，因此在提案仅抽象提及的地方，catch_unwind 是强制性的； (3) “通过驱动程序 API / cudarc 加载 CUDA，无链接时 CUDA，fatbin+PTX” 故事与注意路径上的 cudnn_paged_attention.cu 和 cuDNN 前端以及 cuBLASLt 相冲突 - 这些不是 Driver-API/NVRTC-JIT-able 的，并强制在插件内部建立真正的 cuDNN/cuBLASLt 链接，而构建/JIT 部分会手动挥手。 KV 一致性被断言（“流排序，重用 ExecScope”），但实际的 KV 路径默认为主机往返（attention_paged/scatter_kv_paged 默认特征方法调用 _reference impls 执行 to_host_vec），并且系统使用工人拥有的凹凸 KV 分配器硬约束为 block_size==1 — 跨后端 KV 一致性未解决，它是通过代码路径断言的今天在主机内存中反弹。
**迁移可行性和开发人员经验**该提案总体上是增量的，并正确识别了真正的接缝：MemoryPort 是真正面向字节的（在domain/ports/device.rs 中验证），DTypeId(u16) 存在于从 1024 开始的注册表（domain/dtype/mod.rs:26），CPU 后端真正实现了每个端口并返回 OpError::Unsupported（infrastructure/cpu/mod.rs，error.rs），而 build.rs 确实如此nvidia-smi->sm_XX 检测、缺少 cuDNN 前端的恐慌以及静态链接 infer_kernels (build.rs:85,116,380)。构建解耦故事（将 .cu 移至 infer-backend-cuda cdylib，默认=[] CPU 基线）是合理的，可分阶段交付，并且是单个最高价值、最低风险的第一个交付。然而，该提案包含一个普遍存在的承载技术错误，破坏了四个部分的中心抽象：它重复地将 `dyn Backend`/`dyn Device`/`Box<dyn Backend>`/`Vec<Box<dyn Backend>>` 框架为现有端口的近乎自由的“对象安全投影”。现有的 op 端口（domain/ports/ 中的 MathOps、FusedOps、DiffusionOps）完全由 `T: Dtype` 上的通用关联函数组成（例如 `fn add<T: Dtype>(scope: &Self::Scope, ...)`，无 `&self`），而 `Backend`/`LlmBackend` 是这些函数的全面隐式超级特征。这些特征绝对不是对象安全的，并且代码库在任何地方都没有使用 `dyn`。今天你不能使用 `Box<dyn Backend>`，要使其工作，需要手动编写一个全新的 dtype 擦除、`&self` 接收器特征表面（每个 (op, dtype) 一个方法或标记分派的包装器）加上手动 fn-ptr vtable 加上保持与通用特征同步。这是真实的、大型的、手写的代码，而不是“投影”。该提案的风险部分提到“对象安全的动态设备/流投影必须忠实地再现 ActiveGuard”，但从未承认投影是从头开始的平行表面，而不是派生。这就是所谓的“重构而不是重写”与实际成本之间的差异。其次，分期主要被描述为最终状态架构；该提案主张增量性，但几乎没有提供具体的排序，而且它确实造成的一个排序风险非常严重：每个部分都将 default=['cuda'] 翻转到 CPU 基线，并将静态链接降级到运行时 dlopen，但serve_loop::run_with_model 是硬编码的 `M: DecoderModel<bf16, Cuda>` (serve_loop.rs:71) 并且工作箱具有 required-features=['cuda']。如果在类型擦除边界和存在 CPU 功能的服务循环之前翻转默认值，则工作程序二进制文件根本无法运行（没有 Cuda，硬编码的 Cuda）——一个长期存在的损坏工作程序窗口。第三，有两个不同的 `Device` 特征（ports/device.rs 和 exec.rs:13，后者是 `Device: MemoryPort` 和 `type Scope`），并且 crate-split 映射表永远不会消除哪些 Device/exec 部分去哪里，从而存在提案手挥手的 infer-tensor、infer-backend-abi 和 infer-exec 之间存在循环依赖的风险。 Net：首先交付构建解耦 + CPU 基线阶段（高价值、低风险，但以修复服务循环硬代码为门控），但动态调度/ABI 部分大大低估了手写的对象安全桥，需要一个明确的、构建绿色阶段计划才能可信。
