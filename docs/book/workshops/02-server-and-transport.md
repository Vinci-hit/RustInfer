## 讨论中的概念边界

| 讨论话题 | 已有理解 | 进一步区分 |
| --- | --- | --- |
| async 是状态机，同步工作会 block | 同步计算确实占用当前执行线程，async 不自动创建线程 | 暂停条件是等待的 Future 返回 Pending；channel、timer、JoinHandle 等也可以成为等待对象。占住一个线程不等于所有 runtime 线程都停止 |
| token 不按字符一一编码 | 字符数不能替代 token 数；常见 tokenizer 使用子词等编码 | token 也可能是字符片段、字节或特殊标记。高频片段成词表项取决于训练算法，不能概括成推理时按词组频率重新编码 |
| 轻量唤醒＋同步传输 | channel 保存业务消息，唤醒机制通知专用线程，由其集中调用 ZMQ API | Server 是 OS pipe；Scheduler 的相关桥接是 inproc PAIR。同步 send 返回不等于对端收到，当前 pipe 写入也没有非阻塞保证 |

channel 与线程通信是这段链路中的连接点：命令 channel 保存请求，唤醒 pipe 提醒通信线程检查队列；每条流的结果 channel 则把通信线程收到的消息交回 SSE 响应体。理解这三个位置，可以把输入处理、本地提交和结果返回串起来。

## 可以继续复述与推导的话题

可以选一个问题口述、画图或写下自己的推导，再围绕不明确的地方继续讨论。

1. 为什么 `infer_stream(req).await` 返回，并不表示首 token 已经生成？画出本地队列、ZMQ、Scheduler、Worker 四个位置，标出返回时最远能保证到哪里。
2. 如果改成“先向 pipe 写入通知，再将请求放入 channel”，构造一条生产者与消费者交错执行的时间线，说明可能增加等待的原因。
3. 分别考虑“ZMQ 线程长时间卡在发送”和“SSE 消费变慢、ZMQ 线程仍能收取结果”两个场景。哪些队列会继续被写入，哪些可能填满？再分别解释命令队列满、pipe 满、单请求结果队列满时的当前行为，不预设它们一定按某个顺序出现。
4. 从 `GeneratedToken.sequence_id` 出发，解释它如何变成 `StreamChunk.request_id`，再找到 SSE 的结果 channel。指出 Server pending、Scheduler 会话表和 Worker 序列表各保存什么。
5. 比较“同一线程发送后立即登记，再接收”和“发送、接收分属并发执行单元”两种结构。在哪一种结构中，快速回复可能在登记前被查表？先画交错顺序，再判断是否有竞态。
6. SPSC ring 中，消费者为什么必须先读取或移出消息，再发布 head？消息已经移出后，是否必须等业务处理完成才能归还槽位？
