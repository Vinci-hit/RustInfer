# From Single-Backend to Statically-Linked Multi-Backend: An Incremental Architecture-Refactor Proposal for RustInfer

> Architecture-refactor proposal for **RustInfer** — generated 2026-06-20, **revised 2026-06-20 to a statically-linked design** (see the Revision banner below). Scope: separate hardware backends into independent, compile-time-linked crates, keep execution fully monomorphized (zero per-op runtime dispatch), and let the core build with `rustc` alone when no GPU backend is selected. This document is a design proposal; it is grounded in the current `infer-worker` codebase and informed by the PyTorch dispatcher, ONNX Runtime execution providers, TVM runtime, OpenXLA/PJRT, and TensorRT — adopting their *modular-backend* lessons while deliberately **not** adopting runtime plugin loading.

> ## ⚠️ Revision: Static-Linked Backends (supersedes the dynamic-loading design)
>
> The original draft proposed a **runtime-loadable** plugin model: backends as `dlopen`ed `.so` files behind a stable C ABI, the device selected at *load time*, one function-pointer indirection per high-level op. After review, the project chose the **statically-linked, compile-time** model instead — the priority is raw performance and simplicity, and there is no requirement to ship prebuilt backend binaries that load without recompiling.
>
> **What this changes:**
> - **No runtime dispatch on the hot path.** `Tensor<T, D>` stays monomorphized over the device type `D` *all the way down into each backend*; the `match T::DATA_TYPE` kernels are reached by direct, inlinable calls. There is no vtable, no opaque `DeviceTensor`, no per-op function-pointer indirection. The seam between core and backend is the **Rust op-port trait surface**, resolved at compile time.
> - **Backends are independent crates linked statically and feature-gated** (`infer-backend-cuda` / `-rocm` / `-metal` / `-cpu`). Selecting a backend is a compile-time choice (Cargo feature); `cuda` off ⇒ the core + CPU backend build with `rustc` alone. Adding a backend = a new crate implementing the op-port traits + a feature, then recompile.
> - **No stable C ABI, no `abi_version` gate, no plugin discovery/registry, no GPU-probing install CLI** on the default path. Versioning is ordinary Cargo/semver across in-tree crates.
> - **Heterogeneous (multiple backends in one binary)** is achieved by compiling several backends in and dispatching at the *model / request* boundary (an enum or a per-backend monomorphized serve loop chosen at startup) — never per-op inside the decode loop.
>
> **What still applies unchanged** from the original draft: the **crate topology and foundation collapse** (§1 — `infer-core` holds the recursive foundation; this is already implemented), the **op-port trait surface** as the backend interface (§2, now read as a *static* trait boundary rather than a C ABI), the **kernel-development workflow** (§6), and **dependency detection** (§7).
>
> **What is superseded / demoted to an optional future** (kept for reference, clearly marked in-section): §3's runtime cross-backend dispatcher, **§4 (Dynamic Loading / Stable ABI)** in its entirety, and the **plugin-distribution half of §8** (prebuilt `.so` trains, `+cuXXX` companion wheels carrying backend binaries, the `rustinfer backend install --auto` fetch CLI). These remain a viable *optional* path **only** for a future "ship prebuilt backends without recompiling" use case; an `infer-abi` crate implementing that C ABI has been built and tested but is **not wired into the runtime**.
>
> Read the rest of the document with this banner as the controlling decision wherever it conflicts.

## Executive Summary

RustInfer is a Rust LLM and diffusion inference framework whose GPU runtime, `infer-worker`, is organized as a clean DDD layering: pure-Rust `domain/` ports, a CUDA `infrastructure/` adapter, and an `application/` orchestration layer. That design is a genuine asset, and this proposal is deliberately built on top of it rather than around it. The trouble is not the abstraction; it is that the abstraction is resolved entirely at *compile time*. `Tensor<T, D>` and `Runtime<T, D, M>` are monomorphized over the device type `D`, the device is chosen by which `impl` the compiler picks, the 29 `.cu` kernels live *inside* the worker crate, and `default = ["cuda"]` means the core literally cannot build without a full CUDA toolchain, `libclang`, cuDNN-frontend headers, and a host GPU whose compute capability is baked into the artifact by `nvidia-smi`. There is no in-process multi-backend, no runtime-loaded plugin, and no way to publish a GPU-free core to crates.io.

The north-star is a **statically-linked, multi-backend runtime** in which the core builds with `rustc` alone when no GPU backend is selected, accelerator kernels live in independent, compile-time-linked backend crates, and the device is chosen at *compile time* by which backend is feature-enabled and which `Tensor<T, D>` monomorphization runs — keeping the per-dtype `match T::DATA_TYPE` hot path fully monomorphized and directly callable, with **zero per-op runtime indirection**. The thing the original abstraction got right — compile-time resolution — is *preserved and extended*, not replaced; what changes is only *where the code lives* (independent crates) and *how a backend is selected* (a Cargo feature, not a hardcoded `Cuda`).

The headline decisions are five. **First**, the static-generic world never ends: `Tensor<T, D>` stays monomorphized over the device type from the runtime down into each backend's kernels. The boundary between core and backend is the **Rust op-port trait surface** (`CoreOps`/`MathOps`/`DiffusionOps`/`FusedOps`/`CollectiveOps`/`Backend`), resolved by the compiler — no opaque handles, no vtable, no C ABI. **Second**, those op-port traits move into an `infer-backend-abi` crate (Rust traits, depending on `infer-core`) so every backend crate can implement them without depending on the runtime; backends are selected and composed at compile time. **Third**, all `.cu` move into a standalone **`infer-backend-cuda`** crate (a static library with its own `build.rs`), gated behind a `cuda` Cargo feature; with the feature off, the worker + CPU backend build with no nvcc, no `libclang`, no cuDNN-frontend, no `nvidia-smi`. **Fourth**, the foundation collapses into `infer-core` (dtypes, `QuantScheme`, `OpError`, `MemoryPort`, the merged `Device`/`ExecScope` vocabulary, `Storage`, `Tensor<T,D>`) because those items are mutually recursive at the item level — *this is already implemented and green*. **Fifth**, the existing CPU adapter becomes **`infer-backend-cpu`**, always statically linked as the always-present baseline/fallback — with the honest caveat that it implements `MemoryPort` and exec fully, only a subset of `CoreOps`/`DiffusionOps` natively, and inherits `FusedOps` via host-round-trip reference defaults, so a per-op CPU fallback is a correctness path that can collapse latency on hot ops and must be metered (or compiled out in a single-backend build, where it does not arise).

The staged outcome is the discipline that makes this safe: the build stays green at every step. The foundation collapse into `infer-core` lands first (done); the op-port traits + their KV/plan view types peel into `infer-backend-abi` second; the CUDA and CPU adapters become their own crates behind features third; and only then is `default = ["cuda"]` re-examined. At no point does a function pointer enter the decode loop, and at no point is the monomorphized `match T::DATA_TYPE` hot path disturbed. The result is a core that builds GPU-free, accelerator kernels isolated in their own crates with their own toolchains, multiple backends compilable into one binary and selected at compile time, and full inlining preserved end to end.

## Current State: An Honest Assessment

### What is already good

The repository is in materially better shape than most pre-refactor codebases, and three things deserve explicit credit.

**The ports already exist and are well-factored.** `infer-worker/src/domain/ports/` defines a coherent abstraction family — `Device`/`MemoryPort`, `CoreOps` (`op_ports.rs`), `MathOps` (`math_ops.rs`), `DiffusionOps` (`diffusion_ops.rs`), `FusedOps` (`fused_ops.rs`), `CollectiveOps`, and the blanket-composed `Backend = LlmBackend + DiffusionBackend` (`backend.rs`). Critically, `MemoryPort` already speaks raw `NonNull<u8>` plus byte sizes, not typed tensors. This means the static-to-dynamic seam this proposal needs is *half-built already*: the lowest layer of the abstraction is type-erased in spirit.

**A second backend already implements the same ports.** `infrastructure/cpu/mod.rs` provides a `Cpu` marker type implementing the port family. Its mere existence is proof that the abstraction is real — it can host a non-CUDA backend — rather than a CUDA-shaped interface wearing a trait costume. This is the empirical foundation the whole plugin story rests on.

**The DDD layering is clean and the dispatch path is disciplined.** `domain/` is pure Rust with zero FFI; `infrastructure/cuda/` holds the adapter; `application/` wires `Runtime`, `DecodeEngine`, and `serve_loop`. The runtime dispatch path is principled: a trait method enters an `ExecScope` guard, unwraps the stream, and bottoms out in `match T::DATA_TYPE` selecting an `extern "C"` kernel symbol. The device is chosen at compile time by monomorphization; the dtype match is the only runtime dispatch. That `match T::DATA_TYPE` hot path is the framework's single biggest performance asset and the refactor must preserve it verbatim.

### The three root problems

**1. Backend selection is compile-time, so there is no in-process multi-backend and no runtime plugin.** `Tensor<T, D>` carries the device as a monomorphized generic parameter; `Runtime<T, D, M>` is likewise monomorphized; `serve_loop::run_with_model` is hardcoded to `M: DecoderModel<bf16, Cuda>` and uses `&Cuda`, `CudaScope`, and `Runtime<bf16, Cuda, M>` directly. Choosing a backend at runtime, loading one from disk, or running two in one process is structurally impossible today. Moving the device axis to runtime dynamic dispatch — type-erased tensors and opaque device handles at a stable boundary — is the core change, and *where* that seam falls is the crux of the entire proposal.

**2. The `.cu` kernels live inside the worker crate, so building the worker pulls the whole CUDA toolchain.** The 29 `.cu` files sit under `infrastructure/cuda/kernels/`, and the 471-line `build.rs` (behind the `cuda` feature) walks them, compiles every one through `cc::Build::cuda(true)` into a static `infer_kernels` lib, runs `bindgen` (needing `libclang`) over cuDNN-frontend and cutlass headers, and uses `nvidia-smi` to pin the artifact to the host GPU's `sm_XX`. With `default = ["cuda"]`, the *core cannot build* without all of this present.

**3. CUDA is mandatory for the build, so the core is unpublishable and host-pinned.** The `SKIP_BUILD_KERNELS` escape only defers the pain: skip the compile and the static `extern "C"` symbols fail to link. The artifact is GPU-specific by construction, cannot go to crates.io, and forces every CI runner and contributor onto a full GPU toolchain to touch even pure-Rust code.

### One correction the proposal must carry honestly

The CPU backend does *not* "implement every port." `cpu/mod.rs:42` is `impl FusedOps for Cpu {}` — an empty impl that inherits host-round-trip reference defaults (`attention_paged_reference`, `scatter_kv_paged_reference`, which round-trip through `to_host_vec`). The `Cpu` type implements `MemoryPort` and exec fully, a *subset* of `CoreOps`/`DiffusionOps` natively, and returns `OpError::Unsupported` for the rest. The fallback story must reflect this: per-op CUDA→CPU fallback is safe only for ops CPU actually supports, and a hot op like `attention_paged` falling back is a correctness-only path that collapses decode latency — hence the metering and hard-fail requirements that appear throughout.

## Target Architecture: The North-Star

> **↻ REVISED (see top banner).** The adopted end-state has **no C-ABI seam and no runtime function-pointer table**. The three concerns are: the **monomorphized core runtime**, the **`infer-backend-abi` op-port trait crate** (the seam — a set of *Rust traits*, resolved at compile time), and the **statically-linked backend crates** that implement those traits. `Tensor<T, D>` and the dtype axis stay monomorphized end to end. In the ASCII diagram below, read "THE SEAM: `rustinfer_get_backend_api` / `#[repr(C)]` vtable / opaque `DeviceTensor`" as **"THE SEAM: the `infer-backend-abi` Rust traits, monomorphized"**, and read each backend "cdylib" box as a statically-linked Rust crate. The crate *names and topology* in the diagram are correct and adopted; only the *boundary mechanism* (C ABI → Rust traits) and *backend selection* (dlopen → Cargo feature) change.

The end-state separates three concerns that are fused today: the **monomorphized core runtime** (above the seam), the **stable C ABI** (the seam itself), and the **loaded backends** (below the seam). Model code and the tensor type-state stay fully generic and zero-overhead; the device axis becomes a runtime function-pointer table; the dtype axis is re-monomorphized inside each plugin.

### Crate map (4 core crates, replacing the over-split design)

- **`infer-core`** — the foundation: dtypes, `QuantScheme`, `OpError`, `MemoryPort`, the *merged* `Device`/`ExecScope` vocabulary, `Storage`, `Tensor<T,D>`, `Workspace`/`ActiveGuard`/`StepCtx`. One crate because these items are mutually recursive at the item level (`Tensor<T,D>` needs `MemoryPort`; `Storage<D>` is the sole alloc caller; `Device: MemoryPort`; `ExecScope::enter` returns `ActiveGuard<Self::Device>`), so any split is an unbreakable Cargo cycle.
- **`infer-backend-abi`** — sits atop `infer-core` via one downward arrow: the op-port traits, the new `BackendDyn` erased trait, the `#[repr(C)]` vtable and per-op arg structs, and the `libloading` registry/loader. This is the stability surface; it contains *only* `#[repr(C)]` public items.
- **`infer-runtime`** — `Runtime`, `DecodeEngine`, `worker_state`, `worker_scheduler`, `serve_loop`, plus the thin `infer-worker` host wiring (ZMQ pumps, plugin discovery).
- **`infer-models`** — safetensors loader, LLaMA/Qwen, layer components.

### Naming rationale

Backend crates are named **`infer-backend-cuda` / `-rocm` / `-metal` / `-cpu`** (vendor as suffix). This is the form used by every concrete artifact in the proposal — the cdylib filename `libinfer_backend_cuda.so`, the release tree, and the `RUSTINFER_BACKENDS=cuda:/path/libinfer_backend_cuda.so` discovery convention — so it is adopted uniformly, overriding any earlier `infer-cuda-backend` ordering. The pattern reads as "an `infer` backend, for `cuda`," groups all backends adjacently in `ls`, and keeps the filename/crate-name correspondence trivial.

### Cross-cutting insights

- THE single hardest issue — where static-generic Rust transitions to type-erased C ABI — has a precise answer in this repo: the seam is ALREADY half-built. `MemoryPort::alloc_bytes/upload/copy_device_to_device` operate on raw `NonNull<u8>` + sizes, and BOTH Cpu and Cuda implement the identical ports. That is the cut line. Above it: `Tensor<T,D>` monomorphized. At it: an opaque `DeviceTensor{ raw_ptr, dtype_tag, shape/strides POD, owner_backend_id }`. Below it (inside the plugin .so): re-monomorphize on dtype_tag and run the EXISTING kernel match unchanged. The transition is one fn-ptr per high-level op, not a rewrite.
- How the four reference erasure representations map: DLPack DLTensor (TVM) = the most copyable wire format — adopt `Tensor<T,D> -> &DLTensor` at the FFI edge for zero-copy interop with PyTorch/CuPy/JAX for free; PJRT_Buffer = opaque-handle-carrying-dtype/dims-as-plain-data, the model for ownership (every handle wrapped in a Rust Drop calling the plugin's destroy fn); c10 Tensor = carries its own DispatchKeySet (too heavy — RustInfer needs no autograd/functionality axis, so resist the multi-axis keyset); ORT OrtValue = the warning that erasing to opaque tensors turns `match T::DATA_TYPE` compile guarantees into a RUNTIME check you MUST re-validate at the boundary (a wrong dtype_tag = memory corruption). Net: copy DLPack's struct + PJRT's ownership discipline; reject c10's keyset complexity.
- CRITICAL ABI-safety trinity that ALL successful stable boundaries share and RustInfer must adopt verbatim: (1) deleter/allocator travels WITH the handle — a buffer cudaMalloc'd by the CUDA plugin is freed ONLY by that plugin's free fn (tvm-ffi's #1 rule; prevents cross-DLL double-free when plugins are built by different toolchains); (2) errors cross as int-return + opaque-handle accessor, NEVER as unwinding — every extern"C" entry wraps `catch_unwind` (panic across FFI = instant UB); (3) version-gate on FIRST call via struct_size/abi_version (PJRT) and refuse loudly on mismatch — an unchecked mismatch is UB, not an error.
- RustInfer's architecture gives it ONE capability every reference system here lacks or regrets, and the design should lean into it: per-OP runtime cross-backend fallback. PJRT and TensorRT can only fall back at whole-program/build granularity; ORT and PyTorch do per-op fallback but via silent host round-trips that tank LLM latency. Because RustInfer owns the abstraction at the DEVICE level and the in-process CPU backend already returns OpError::Unsupported for every port, it can keep a clean per-op CUDA→CPU fallback chain — provided the CPU backend stays STATICALLY linked (not behind the C ABI) as the always-present terminal, and every host round-trip is logged so it never silently degrades inference latency.
- The pre-existing ZMQ worker-as-subprocess model is an under-appreciated ASSET for the plugin trust problem. Every reference system has total in-process trust (a backend .so runs arbitrary static-init code unsandboxed). For a multi-tenant server, RustInfer can isolate an untrusted/experimental backend in the existing worker subprocess rather than dlopening it into the scheduler/server process — version-gate at the C ABI for trusted plugins, process-isolate via the existing ZMQ seam for untrusted ones.
- Do NOT over-engineer the dispatch key. PyTorch's 64-bit DispatchKeySet (backend bits × functionality bits, alias expansion, BackendSelect) is explicitly flagged as accidental complexity born of autograd/functionalize layering RustInfer does not have. A simple `(op_id, dtype, backend_id)` resolved-once-at-model-load fn-ptr table (TensorRT's pre-resolve-the-DAG lesson) suffices; resist generalizing into a multi-axis keyset until a concrete second axis exists. Likewise reject ORT's awkward split allocator-by-OrtMemoryInfo lookups — RustInfer's existing ExecScope/Stream/Workspace ownership model is crisper; keep that clarity at the boundary and just expose memory-KIND (HBM/pinned/unified) as a discoverable attribute (PJRT_Memory's hard-learned Device-vs-Memory split).
- Burn's decorator pattern (Backend-wrapping-Backend for Autodiff/Fusion/Router) is the zero-kernel-touch way to add cross-cutting features RustInfer will want — CUDA-graph capture, quant-tier selection, tracing/profiling — as a wrapper over the port trait rather than edits to kernels or the ABI. Combined with PyTorch's decomposition-kernel idea (composite ops defined in terms of primitives, auto re-dispatched), a backend implementing only primitives can get broad op coverage 'for free'. This keeps the plugin surface small while the feature set grows.

### Per-dimension recommendations

**Where the static-generic world ends and the dyn/C-ABI world begins (the core change, tension #1).** Cut the seam at the EXISTING port methods — specifically at the boundary of `MemoryPort` (which already takes raw `NonNull<u8>` + sizes) and the high-level op calls in `OpBackend`/`FusedOps`/`MathOps`. ABOVE the seam keep `Tensor<T,D>`/`Runtime<T,D,M>` fully monomorphized for model code. AT the seam, lower each high-level op to a flat `#[repr(C)]` vtable call taking an opaque `DeviceTensor` (raw device ptr + runtime dtype tag + shape/strides POD + owning-backend-id), an opaque `StreamHandle(*mut c_void)`, and a small `#[repr(C)]` args struct. BELOW the seam, INSIDE each plugin .so, immediately re-monomorphize: the opaque handle's dtype tag drives the existing `match T::DATA_TYPE -> kernel_bf16x8` path verbatim. So device dispatch becomes a runtime fn-ptr; dtype dispatch stays compile-time-within-plugin. Pay ONE vtable indirection per matmul/attention, never per element. *(inspired by wgpu-hal (HAL trait + opaque Device/Queue/Buffer + runtime adapter enumeration) for the trait shape; PJRT_Buffer / c10 type-erased Tensor / DLPack for the opaque-tensor representation; TensorRT's per-op enqueue(desc, ptrs, stream) for the exact call shape.)* — The ports are ALREADY type-erased in spirit (MemoryPort speaks raw bytes; CPU+CUDA both implement them) — this is the proof the abstraction can host the seam without a rewrite. Erasing at the high-level op (not the element) means the vtable cost is amortized over a whole matmul/attention, matching how wgpu and PyTorch both place dispatch at op granularity. Keeping dtype monomorphized inside the plugin preserves RustInfer's single biggest current asset: zero-overhead `match T::DATA_TYPE` hot kernels.

**Plugin model & stable ABI.** Hand-rolled `#[repr(C)]` struct-of-extern"C"-fn-pointers, ONE exported entry symbol `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`, with `u32 abi_version` (or `usize struct_size`) as the FIRST field of the vtable AND of every args struct, fields APPEND-ONLY. Group the vtable to mirror TRT's Core/Build/Runtime split: an identity block (name, abi_version, backend_id, target compute-cap) always present, a registration/build block, and a hot-path runtime block (alloc/free/upload/copy_d2d/enqueue-per-op). Use a typed linked-list extension chain for optional/vendor ops (fp8 tiers, qkv_norm_rope_scatter, collectives) so the core vtable stays small and stable. Errors cross as a flat `#[repr(C)] i32` code + opaque error handle with accessor fns; NEVER unwind — wrap every entry fn in `catch_unwind`. Memory allocated by a plugin is freed ONLY by that plugin's free fn (deleter-travels-with-handle). Reserve abi_stable/stabby for later if the surface ever needs collections. *(inspired by PJRT (one GetPjrtApi symbol + struct_size append-only versioning + typed extension chain) as the primary model; tvm-ffi (deleter-travels-with-object, errors via int-return-not-unwind) for ownership/error rules; TensorRT (Core/Build/Runtime capability split, string-triple identity) for vtable grouping.)* — The op set is small, fixed, and already enumerated as ports, so a hand-rolled vtable is the pragmatic choice — less ceremony than abi_stable, full control of the small surface. PJRT's struct_size+append discipline buys forward AND backward compat without a frozen major version, the single cheapest stability mechanism. The extension chain is the clean answer to 'add a fused op without breaking the ABI'. Every reference system that smuggled C++ across the boundary (PyTorch C++ ABI, ORT provider-bridge, TRT vtables) is cited as the #1 anti-pattern to AVOID — a narrow versioned C ABI is the antidote.

**Kernel build / JIT decoupling (tension #2: .cu inside worker).** Move ALL .cu out of infer-worker into a standalone `infer-backend-cuda` cdylib crate with its OWN build.rs. That crate compiles kernels to PTX/fatbin covering a SET of arches (sm_80/86/89/90 + PTX fallback) and at runtime loads them via the CUDA Driver API through `cudarc` with the `dynamic-loading` feature (dlopens libcuda/libcudart/libnvrtc). The worker CORE then builds with ZERO CUDA toolchain — no nvcc, no libclang, no cuDNN-frontend discovery, no nvidia-smi host-arch detection. Flip `default=["cuda"]` from a hard compile dependency to merely 'load the bundled cuda plugin at runtime'. The driver JITs PTX to the running GPU at module load, cached on disk. *(inspired by PyTorch/ORT/TVM/PJRT all push kernel build entirely behind the backend .so (core compiles zero kernels); cudarc's runtime dynamic-loading for the no-link-time-CUDA unlock; TVM's CUDAModule(PTX→cuModuleLoadData) and TRT's PTX+cubin fatbin for multi-arch + JIT-at-load.)* — This directly resolves the worst pain: today `default=["cuda"]` means the core cannot build without a full CUDA toolchain and host GPU, and the artifact is host-arch-pinned. Every reference runtime keeps the toolchain inside the vendor plugin; cudarc makes that achievable in pure Rust with no link-time CUDA in the consumer. Shipping fatbin+PTX (not nvidia-smi→single sm_XX cubin) removes host-GPU-specificity at the cost of first-load JIT, which the driver caches.

**Capability discovery & graceful fallback.** Each plugin exports `extern "C" capabilities() -> #[repr(C)] Capabilities` (dtype bitset, op bitset, max-workspace, cuda-graph/paged-attention flags, min/target compute-cap, quant tiers), queried at load BEFORE any work. Split two axes explicitly: feature-capability (which (op,dtype) supported — queryable) vs hardware-compatibility (coarse compute-cap gate — accept/reject at load). Host scheduler selects backend per request from explicit config INTERSECTED with probed capability. Keep `OpError::Unsupported` as the per-op runtime fallback signal, mapped to a `#[repr(C)] i32`; on Unsupported, fall back op-by-op to the always-present in-process CPU backend (which already implements every port). Make every cross-backend host round-trip OBSERVABLE/logged. *(inspired by wgpu Features/Limits + ORT two-tier (GetSupportedDevices + per-model GetCapability) + always-appended CPU EP fallback; TensorRT's split of supportsFormatCombination vs HardwareCompatibilityLevel; PyTorch's loggable boxed cpu_fallback.)* — RustInfer can do BETTER than PJRT/TRT here: because it owns abstraction at the DEVICE level (not whole-program), it keeps per-op fallback that PJRT/TRT cannot. The CPU backend already returns Unsupported and implements every port — formalize it as the guaranteed terminal fallback (ORT's mandatory CPU EP). Splitting feature vs HW capability (TRT's lesson) lets a CUDA plugin cleanly refuse fp8 OR refuse a too-new arch with distinct, loud errors. Logging silent host round-trips avoids ORT/PyTorch's latency-killing hidden Memcpy footgun in the LLM hot path.

**Registration, discovery & distribution.** EXPLICIT entry-point registration, NOT static-init magic: host scans a config/env-listed plugins dir (steal PJRT_NAMES_AND_LIBRARY_PATHS=name:path;... ), `libloading::Library::new`, looks up the single `rustinfer_get_backend_api` symbol, checks abi_version, queries capabilities(), registers the returned vtable under a platform name + priority into an OWNED, droppable `Registry` object (not a process-global singleton). Ship each backend as standalone .so/.dylib/.dll (`infer-backend-cuda`/`-rocm`/`-metal`/`-cpu`), each independently built/versioned, with internal PTX/fatbin. CPU backend is BOTH statically linked (linkme self-registration, always-available baseline) AND available as a plugin. Each plugin records the protocol/ABI version it was built against; mismatch = clear LOUD load-time error, never UB. Keep the Library alive for the lifetime of every resource it created (plugin outlives its handles/streams). *(inspired by PJRT (env name:path list + register_plugin(priority) + independently-versioned wheels meeting only at the C ABI); ORT (explicit RegisterExecutionProviderLibrary by path, not dir-scan magic); TVM (string type_key→runtime index so independent builds agree by name not shared constant); linkme for in-binary CPU self-registration only.)* — Every reference system that registered via static-init side effects (PyTorch, TVM, TRT) is flagged as order-fragile, non-unloadable, and segfault-prone. An explicit entry-point the host calls after dlopen gives deterministic load AND unload (true hot-swap) and lets the registry be a droppable per-server object — exactly what a multi-tenant inference server wants, vs the process-wide singletons those frameworks regret. Explicit-by-path discovery (ORT) avoids accidentally loading a version-mismatched binary. linkme is link-time only and useless across dlopen, so it's reserved strictly for the in-process CPU baseline.

# Part II — Detailed Design

Each of the following eight sections corresponds to one of the design tasks. Every section is preceded by a one-paragraph bridge placing it in the larger architecture, and is grounded in the existing `infer-worker` ports and adapters rather than a greenfield ideal.

## 1. Repository Structure

*We begin with the crate topology because every later decision — where the ABI lives, which code is host wiring versus runtime, what can build without CUDA — is constrained by the Cargo dependency DAG. The central finding is that the foundation must *collapse*, not split further: the tensor, exec, and memory items are mutually recursive at the item level, so any split produces an unbreakable cycle.*

### Starting point and the constraint that shapes everything

RustInfer is today a single Cargo workspace (`resolver = "3"`) of five crates: `infer-protocol` (dependency-free shared message types), `infer-scheduler` (request scheduling and KV-allocator orchestration), `infer-server` (the axum HTTP/SSE front), `infer-worker` (the DDD-layered GPU runtime), and `infer-frontend` (a standalone Dioxus WASM UI on edition 2021). Only `infer-worker` carries real architectural weight, and only `infer-worker` carries the pain: its `build.rs` (472 lines, gated behind a `default = ["cuda"]` feature) walks `src/infrastructure/cuda/kernels/*.cu`, compiles all 29 `.cu` files through `cc::Build::cuda(true)` into a static `infer_kernels` lib, runs `bindgen` over `wrapper.h`, and uses `nvidia-smi` to detect the host compute capability and pin `-arch=sm_XX`. The consequence is stark: because `cuda` is a default feature and a hard *compile* dependency, the entire core cannot build without a full CUDA toolchain, libclang, cuDNN-frontend, and a physically present GPU. The `SKIP_BUILD_KERNELS` escape hatch only moves the failure to link time.

The single design objective of this restructure is therefore precise: *adding or building a backend must never touch — or even compile — the core.* Everything below follows from that.

### Monorepo-with-workspaces, plus a per-backend split — the hybrid, justified

There are three plausible shapes: one giant crate (today's `infer-worker`), a fully multi-repo design (core repo + one repo per backend), or a hybrid — a core monorepo workspace plus *separately buildable* backend crates that may live in-tree but compile and ship independently. I recommend the hybrid, and I reject the two extremes deliberately.

A fully multi-repo split is premature. The ports (`Device`, `MemoryPort`, `OpBackend`, the `FusedOps`/`DiffusionOps`/`Backend` hierarchy in `crates/infer-worker/src/domain/ports/`) are still moving; forcing a version-and-publish handshake across repo boundaries on an unstable trait surface would tax every change with a release dance, and CI would lose the ability to test core-plus-CUDA in one `cargo test`. Conversely, keeping `.cu` inside the worker crate is the proven failure mode. The hybrid keeps the *source* discoverable in one workspace while giving each backend its own `build.rs`, its own toolchain requirement, and its own artifact, so that `cargo build -p infer-runtime` needs no nvcc at all.

The decisive boundary is between code that is *compiled into the core* and code that is *loaded by the core*. The CUDA, ROCm, and Metal backends become standalone `cdylib` crates with their own build scripts, surfaced to the runtime through a single stable C ABI symbol and never appearing in the core's dependency graph. The CPU backend is the exception that proves the rule — it stays statically linked as the always-present terminal fallback (more below). The four mandated backend crates are named exactly: `infer-cuda-backend`, `infer-rocm-backend`, `infer-metal-backend`, `infer-cpu-backend`.

### Don't over-split the foundation: it is one recursive cluster

The first temptation is to chase a clean layered taxonomy — a crate for dtypes, a crate for the tensor, a crate for the ports — and the first lesson the existing source teaches is that this taxonomy is a lie the type system will not let you tell. The foundational types are not a stack of independent layers; they are a single mutually-recursive knot, and you must read `crates/infer-worker/src/domain/` carefully to see why.

Trace the references. `Tensor<T, D>` (in `tensor.rs`) is parameterized by `D: MemoryPort` and owns an `Arc<Storage<D>>`; `Storage<D>` (in `storage.rs`) is *the sole caller* of `MemoryPort::alloc_bytes`/`free_bytes`. `MemoryPort: Device`. But there are in fact **two** `Device` traits, and conflating them is exactly the trap. `domain/ports/device.rs` defines `Device` with an associated `type ExecCtx` — the original type-state axis for `Tensor<T, D>`. `domain/exec.rs` defines a *second* `Device: MemoryPort` carrying `type Scope: ExecScope<Device = Self>`, plus `enter_device`/`restore_device`. The exec-layer `Device` is intertwined with `ExecScope` (whose `enter()` returns `ActiveGuard<'_, Self::Device>`), with `Stream`, with `Workspace<D: Device>`, and with `StepCtx<'a, D: Device>` — and `ActiveGuard<D>` is itself generic over `Device` and calls back into `scope.device().restore_device(...)` in its `Drop`. Each of these mentions the others by name in its own definition. There is no acyclic ordering of these items into separate crates, because Rust crates cannot have circular dependencies and these definitions are circular *at the item level*.

It gets tighter one layer up. The op-port traits are not above this cluster — they are woven into it. `MathOps: Device` (the exec `Device`) takes `scope: &Self::Scope` and `&Tensor<T, Self>` arguments; `FusedOps` takes `ctx: &StepCtx<'_, Self>` and `&mut Tensor<T, Self>`. So `MathOps`/`FusedOps`/`DiffusionOps` reference `Self::Scope`, `StepCtx<Self>`, *and* `Tensor<T, Self>` simultaneously. The earlier instinct to put `Tensor` in one crate, the exec traits in a second, and the op ports in a third produces three crates that all need each other — the very cycle the design claims to "design out" but never actually severs.

The resolution is to stop splitting where the type system says *do not split*. All of the following live together in one foundational crate — call it **`infer-core`** — because they are mutually recursive by construction and separating them buys nothing but a fight against the borrow checker and the crate DAG:

- `Dtype`/`DataType` and the concrete leaf dtypes (`F32`/`BF16`/`F16`/`I32`/`I8`/`Fp8E4m3`/`Fp8E5m2`), `quant::QuantScheme`, and the `OpError`/`OpResult` error types (today `domain/dtype/`, `domain/types.rs`, `domain/ports/error.rs`);
- `MemoryPort` and **both** `Device` traits — which **must be merged into one, or one renamed, during the move** (see below), since shipping two traits named `Device` across a published crate boundary is a usability hazard;
- the whole exec vocabulary: `ExecScope`, `Stream`, `Workspace<D>`, `ActiveGuard<D>`, `StepCtx<D>`, `Rank`/`TopologyShape`/`QuantTier` (today `domain/exec.rs`);
- `Storage<D>` and `Tensor<T, D>` (today `domain/storage.rs`, `domain/tensor.rs`).

This is a deliberate retreat from the eight-way core split. The earlier proposal tried to lift `Tensor` into `infer-tensor` and the port traits into `infer-backend-abi`; those crates would have referenced each other through `MemoryPort`, `Storage`, `Self::Scope`, and `Tensor<T, Self>`, and no amount of careful ordering removes the cycle because the cycle is inherent. Collapsing them yields a clean DAG instead. On the two `Device` traits specifically: the recommended merge is to fold `ports::Device::{ExecCtx, name}` into the exec-layer `Device` (which already has `device_id`, `enter_device`, `restore_device` and the `MemoryPort` supertrait), so that one `Device` trait carries `type ExecCtx`, `type Scope: ExecScope<Device = Self>`, and the lifecycle hooks. If a full merge proves disruptive mid-refactor, the fallback is to rename the exec-layer one to `ExecDevice` and keep `ports::Device` as the pure type-state marker — but either way the duplicate name does not survive into `infer-core`'s public surface.

### Proposed crate set and how it maps onto what exists

With the foundation collapsed, the core reduces to a handful of crates with an explicit, acyclic arrow set. The mapping below lets reviewers trace every current module to its destination.

| New crate | Role | Carved out of (today) | Toolchain needed to build |
|---|---|---|---|
| `infer-protocol` | shared wire types (unchanged) | `infer-protocol` | rustc only |
| `infer-core` | dtypes, `QuantScheme`, errors, `MemoryPort`, the (merged) `Device`, `ExecScope`/`Stream`/`Workspace`/`ActiveGuard`/`StepCtx`, `Storage<D>`, `Tensor<T,D>` — the recursive foundation | `domain/dtype`, `domain/types.rs`, `domain/ports/{error,device}.rs`, `domain/exec.rs`, `domain/storage.rs`, `domain/tensor.rs` | rustc only |
| `infer-backend-abi` | the op-port traits (`MathOps`/`FusedOps`/`DiffusionOps`/`CollectiveOps`/`Backend`) **and** the new type-erased `BackendDyn` + `#[repr(C)]` vtable + loader | `domain/ports/{math_ops,fused_ops,diffusion_ops,collective,backend,sampler}.rs` (+ new ABI/loader) | rustc only |
| `infer-runtime` | `Runtime<T,D,M>`, `DecodeEngine`, `WorkerState`, KV pools, graph/plan execution, `GraphRunner`, CUDA-graph capture decorator | `application/*`, `domain/{kv,global_kv_alloc,plan}.rs` | rustc only |

The acyclic arrow set, stated outright so there is nothing to reconstruct: `infer-core` depends on nothing but `infer-protocol`. `infer-backend-abi` → `infer-core`. `infer-models` → `infer-core` + `infer-backend-abi`. `infer-runtime` → `infer-core` + `infer-backend-abi` + `infer-models`. Every backend crate (`infer-cpu-backend`, `infer-cuda-backend`, `infer-rocm-backend`, `infer-metal-backend`) → `infer-core` + `infer-backend-abi`, and **nothing in core depends on any backend crate**. `infer-worker` → `infer-runtime` + `infer-backend-abi` + (link-only) `infer-cpu-backend`. There are no back-edges; the only crate that needs nvcc is `infer-cuda-backend`, and it is a leaf.

A note on naming. I keep the `infer-` prefix the codebase already uses rather than introducing a second convention, and I name the abstraction crate `infer-backend-abi` rather than `infer-hal` or `infer-device` because it hosts *two* things at once — the in-process Rust op-port traits and the cross-`.so` C ABI — and "ABI" signals to the reader that crossing it is a stability contract. Crucially, `infer-backend-abi` does **not** host `Tensor`, `MemoryPort`, or the `Device`/`ExecScope` machinery — those sit one level down in `infer-core`, precisely so that `infer-backend-abi`'s dependency on the foundation is a single downward arrow and the op-port traits can name `Tensor<T, Self>`, `Self::Scope`, and `StepCtx<Self>` without dragging a peer crate into a cycle. `infer-worker` keeps its name but inverts its meaning: it stops being "the GPU runtime" and becomes the thin host process — the ZMQ control/data pumps from today's `serve_loop` plus plugin discovery — exactly mirroring how `infer-server` is a thin shell over `infer-scheduler`.

### Where the static-generic world ends and the type-erased world begins

This is the crux, and the existing code already tells us where to cut. `MemoryPort` is *already type-erased in spirit*: `alloc_bytes(size) -> NonNull<u8>`, `free_bytes(ptr, size)`, and the host/device copy primitives speak raw bytes and raw pointers, and both `Cpu` and `Cuda` implement them identically. That is the seam, half-built — and it lives in `infer-core`, below the op-port traits.

Above the seam, everything stays monomorphized exactly as today. `infer-core`'s `Tensor<T, D>`, `infer-runtime`'s `Runtime<T, D, M>`, and all of `infer-models` keep their compile-time type-state; model authors write the same generic Rust, and the `match T::DATA_TYPE` hot path is untouched. At the seam, each high-level op (`matmul`, `attention_paged`, `scatter_kv_paged`, `fused_add_rmsnorm`) lowers to a single `#[repr(C)]` vtable call carrying an opaque `DeviceTensor` (raw device pointer, a runtime dtype tag, POD shape/strides, and an owning `backend_id`), an opaque `StreamHandle`, and a small append-only args struct. Below the seam — *inside the plugin `.so`* — the dtype tag immediately re-monomorphizes back into the existing `match T::DATA_TYPE -> add_kernel_bf16x8` dispatch, verbatim. Device selection becomes one runtime fn-pointer per high-level op; dtype dispatch stays compile-time *within* the plugin. We pay one indirection per matmul or attention, never per element.

Concretely, `infer-backend-abi` exposes the op-port traits for the in-process path *and* a `BackendVTable` struct of `extern "C"` fn-pointers for the loaded path. The CPU backend implements the traits directly and links statically. The CUDA backend implements the traits internally and then wraps them in the vtable behind one exported `rustinfer_get_backend_api(abi_version) -> *const BackendVTable` symbol. The loader (also in `infer-backend-abi`, used by `infer-worker`) `libloading`s the `.so`, checks the version word, and registers the vtable into an owned, droppable `Registry` rather than a process global. This is the entire reason it is an incremental refactor and not a rewrite: the CPU backend in `infrastructure/cpu/mod.rs` *already* implements every port and *already* returns `OpError::Unsupported` for ops it lacks, proving the abstraction can host a non-CUDA backend before we write a single line of C ABI.

### How adding a backend never touches core

With this layout, `infer-cuda-backend` depends on `infer-backend-abi` and `infer-core`, but the dependency arrow never points back: no core crate depends on any backend crate. Building `infer-runtime`, `infer-backend-abi`, `infer-core`, or `infer-worker` requires only rustc. The `.cu` files, `bindgen`, the `nvidia-smi` arch probe, and the cuDNN discovery all move into `infer-cuda-backend/build.rs`, which compiles to multi-arch PTX/fatbin and is loaded at runtime through the driver API — so even the CUDA *consumer* needs no link-time CUDA. Adding `infer-rocm-backend` is then a matter of creating one `cdylib` crate that implements the same ports and exports the same symbol; the core workspace does not gain a dependency, a feature flag, or a `cfg`. The old `default = ["cuda"]` hard-compile coupling becomes, at most, a runtime default that says "load the bundled CUDA plugin if present," and the core finally builds — and tests against the static CPU backend — on any machine with nothing but a Rust toolchain.

## 2. Backend Abstraction Layer

> **↻ REVISED to a static trait boundary (see the Revision banner at top).** In the adopted static design there is **no type-erased dynamic world** — the seam is the **Rust op-port trait surface** (`CoreOps`/`MathOps`/`DiffusionOps`/`FusedOps`/`CollectiveOps`/`Backend`), kept generic and monomorphized, moved into the `infer-backend-abi` crate so each backend crate implements it directly. `Tensor<T, D>` stays monomorphized end to end; `MemoryPort` stays a generic trait (not a C-ABI byte interface). The paragraphs below that discuss an *object-safe / erased* surface, a `BackendDyn` trait, opaque `DeviceTensor` handles, or a `#[repr(C)]` vtable describe the **superseded** dynamic path (§4) and do **not** apply — they are retained only because the *capability analysis* of the op-port surface (which ops exist, what arguments they carry, the KV/plan view-type entanglement of `FusedOps`) is exactly the same analysis needed to peel these traits into `infer-backend-abi` as static Rust traits.

*With the crate boundaries fixed, the next question is the crux of the whole proposal: exactly where does the compile-time monomorphized world end and the type-erased dynamic world begin? This section pins the seam at the existing `MemoryPort` byte operations and the high-level op calls, and confronts head-on that the existing ports are *not* object-safe — the erased surface is new, hand-written code, not a free projection.*

### The problem, stated precisely

Today RustInfer has no backend abstraction at runtime — it has one at *compile* time. The `Tensor<T: Dtype, D: MemoryPort>` in `domain/tensor.rs` carries its device as a generic parameter `D`, the execution machinery in `domain/exec.rs` is parameterized as `ExecScope<Device = D>` with associated `Stream`/`Workspace<D>`, and the application `Runtime<T, D, M>` plus `serve_loop::run_with_model<M: DecoderModel<bf16, Cuda>>` are monomorphized and hardcoded to `<bf16, Cuda>`. The op traits (`CoreOps`, `DiffusionOps`, `FusedOps` in `domain/ports/`) are generic over `Self: Device` and dispatch entirely statically: a call to `CoreOps::add` resolves at compile time to `impl CoreOps for Cuda`, enters the `ExecScope` guard, unwraps the `CudaStream`, and bottoms out in `kernels::add::add` which does `match T::DATA_TYPE => add_kernel_bf16x8(...)`. There is no kernel registry, no device table — *the device is selected by monomorphization and the dtype by a `match`*. Consequently two backends cannot coexist in one process, and nothing can be loaded at runtime.

The redesign must introduce a runtime, object-safe backend model and a type-erased tensor that flows across backend boundaries — without rewriting the model code or discarding the zero-overhead `match T::DATA_TYPE` hot path that is RustInfer's single biggest performance asset. The entire design hinges on one question: **where does the static-generic world end and the dynamic world begin?** I will answer that first, because every other decision follows from it.

### Where the seam sits

The seam sits exactly at the existing `MemoryPort` boundary and at the high-level op-call boundary of `CoreOps`/`DiffusionOps`/`FusedOps` — and *nowhere finer*. This is not a new line to be invented; it is half-built already. `MemoryPort` (in `domain/ports/device.rs`) already speaks in raw `NonNull<u8>` and byte counts: `alloc_bytes(size) -> NonNull<u8>`, `unsafe upload(dst, src, size)`, `unsafe copy_device_to_device(...)`. `Storage<D>` (in `domain/storage.rs`) is already the *sole* call site of `alloc_bytes`/`free_bytes` — "the keystone of memory safety," as its own doc comment says, the only thing in the crate allowed to allocate or free, with every `Tensor` holding it as an `Arc<Storage<D>>` whose `Drop` releases the allocation. And critically, both `Cpu` and `Cuda` already implement the identical port set. The abstraction we need is therefore *provably hostable*: a non-CUDA backend (CPU) already lives behind these traits.

Above the seam, nothing changes. `Tensor<T, D>` stays monomorphized; model code in `models/` and `application/` keeps writing `Self::matmul(...)` against generic backend bounds; the type-state guarantee that you cannot pass a host pointer to a CUDA kernel is preserved verbatim. Below the seam, *inside each backend's compiled artifact*, nothing changes either: the dtype-driven `match T::DATA_TYPE => add_kernel_bf16x8` re-emerges unchanged. The transition happens *only at the seam*, and it costs exactly **one indirect call per high-level op** — per `matmul`, per `attention_paged`, per `fused_add_rmsnorm` — never per element and never per tensor view. This op-granularity placement is the same choice wgpu-hal and the PyTorch dispatcher make, and for the same reason: a vtable indirection amortized over a whole GEMM or flash-attention kernel is free; one amortized over an element is fatal.

Concretely, device dispatch becomes a runtime function pointer; dtype dispatch stays a compile-time `match` *inside the plugin*. The two axes that RustInfer conflates today — "which device" and "which dtype" — are cleanly split: device goes dynamic, dtype stays static-within-backend.

### The in-process object-safe trait family

We introduce four `dyn`-able traits that mirror, one-for-one, the existing ports — they are not a parallel universe but an object-safe *projection* of `Device`/`MemoryPort`/`ExecScope`/`Allocator`:

- `dyn Backend` — the registry-facing handle for a loaded backend instance. It owns identity (`backend_id`, `name`, target compute capability), exposes `capabilities() -> Capabilities`, enumerates devices, and vends the op vtable. It is the object-safe sibling of the existing blanket `Backend: LlmBackend + DiffusionBackend` super-trait in `domain/ports/backend.rs`.
- `dyn Device` — object-safe projection of `domain/exec::Device`. Holds a `DeviceId`, creates streams, and *is* an allocator (it carries the `dyn Allocator` role rather than splitting allocation out by a memory-info lookup the way ONNX Runtime does — RustInfer's `Storage`/`ExecScope` ownership model is crisper and we keep that clarity).
- `dyn Stream` — object-safe projection of `exec::Stream`, wrapping an opaque `StreamHandle(*mut c_void)` (a `cudaStream_t` for CUDA, `()`/unit for CPU). The existing `ActiveGuard`/`enter()` device-binding discipline maps onto an enter/restore pair on `dyn Device`.
- `dyn Allocator` — object-safe projection of the existing `Allocator` (the `Layout`-based port already used by diffusion VAE pools). Allocation and free are bound to the owning device so the *deleter travels with the handle* (more below).

These are the *in-process* traits — the abstraction every consumer programs against, whether the backend is statically linked or dynamically loaded. The statically-linked CPU backend implements them directly with no FFI. A `Box<dyn Backend>` is what the registry stores.

### The type-erased tensor and value

Across the seam flows a `DeviceTensor`: a *borrowed view*, never an owner, and — this is the crux — valid only for the duration of a single synchronous vtable call. It is a `#[repr(C)]` plain-old-data struct carrying `{ raw_ptr: *mut c_void, dtype: DTypeId, rank: u8, shape: [i64; MAX_RANK], strides: [i64; MAX_RANK], byte_offset: u64, owner_backend_id: u32 }`. It deliberately mirrors the **DLPack `DLTensor`** shape so that interop with PyTorch/CuPy/JAX is a layout coincidence rather than a conversion, but it is not a free Arc-less alias of `Tensor` — and the ownership story must be stated plainly, because erasure here is where RustInfer's compile-time RAII guarantees are temporarily suspended.

Two grounding facts make construction cheap. First, the runtime dtype tag *already exists*: `domain/dtype/mod.rs` defines `DTypeId(u16)` with stable constants (`BF16 = 2`, `F8E4M3 = 5`, ...) and an extensible registry starting at id 1024. The compile-time `Dtype::DATA_TYPE` and the runtime `DTypeId` are already two views of the same fact; the seam simply chooses the runtime one. Second, every field the descriptor needs is already materialized inside `Tensor<T, D>` — `shape`, `strides`, `numel`, `is_contiguous`, and `offset_elems` — so building a `DeviceTensor` is a field copy plus two cheap conversions, not an allocation.

But it is *not* a "free, zero-copy export," and the gap matters. `Tensor<T, D>` owns its bytes through `storage: Arc<Storage<D>>` (tensor.rs:21), whose `Drop` frees the device allocation when the last `Arc` releases. A `DeviceTensor` carries only `raw_ptr` — it cannot carry the `Arc`, because the struct must survive a C-ABI crossing where Rust's `Arc` machinery has no meaning. The export therefore obeys a **host-side keep-alive contract**: the projection `&Tensor<T, D> -> DeviceTensor` borrows the tensor, and the caller (always the host) guarantees the backing `Arc<Storage<D>>` outlives the call by holding the owning `Tensor` live on its own stack frame across the synchronous submit. Because every op-vtable call is synchronous from the host's perspective — it submits work onto the backend's stream and returns; the `Storage` is not freed until the host drops the `Tensor` after stream completion — the borrow is sound without any cross-FFI refcount transfer. There is also a second, narrower conversion to reconcile: the descriptor's `raw_ptr` and `byte_offset` are absolute bytes, while `Tensor` stores an `offset_elems` and `is_contiguous` flag; the export folds `offset_elems * T::SIZE_BYTES` into `byte_offset` (or into `raw_ptr` directly) and copies the strides verbatim, so a non-contiguous or sub-viewed tensor crosses faithfully rather than being silently assumed dense.

This split — *the plugin owns buffers it allocates and ships their deleter with the handle; the host owns `Storage`-backed buffers it merely lends for one call* — is the complete ownership rule across the seam. The two directions are not symmetric and must not be conflated: a host-owned `Arc<Storage>` is *borrowed* into the plugin for a call duration with a keep-alive obligation on the host; a plugin-allocated buffer that must persist (a workspace, a VAE pool slab) is *owned* by the plugin and freed through the deleter that travels with its handle. A `DeviceTensor` never owns anything; it is a descriptor.

The fixed `[i64; MAX_RANK]` arrays impose a concrete rank cap, which we set at `MAX_RANK = 8` — comfortably above every LLM and diffusion tensor in the codebase (the deepest are 5-D conv activations). Over-rank tensors are not silently truncated: the export returns `OpError::Unsupported` rather than producing a malformed descriptor, and a heap-pointer `shape_ptr`/`strides_ptr` variant is reserved as a future fallback should a genuine high-rank consumer appear. Picking a small inline cap keeps the descriptor a single cache-line-friendly POD that passes by value or by `&` without a heap touch, which is the whole point of crossing it once per op.

I deliberately reject c10's approach of baking a `DispatchKeySet` into the erased tensor. RustInfer has no autograd and no functionalization layer, so the multi-axis 64-bit keyset is accidental complexity born of a problem we do not have. The owner identity is a single `u32 backend_id`, nothing more.

The crucial discipline, inherited from ORT's `OrtValue` lesson: erasure turns the compile-time `match T::DATA_TYPE` *guarantee* into a runtime `DTypeId` *check that must be re-validated at the boundary*. A wrong `dtype` tag is memory corruption, not a type error; so is a stale `raw_ptr` whose `Storage` the host failed to keep live. The seam re-validates `dtype` and `owner_backend_id` on entry to every backend call, before the plugin's internal `match` runs. This validation, together with the keep-alive contract, is the price of erasure, and it is paid exactly once per op.

### Operator execution dispatch

How does an op find the right backend kernel? We resolve the device axis *once, at model load*, not per call — the lesson TensorRT learned by pre-resolving its DAG. At load, the chosen backend for a model is fixed and its op vtable is captured; the model's call sites then dispatch through that captured `dyn Backend` / op vtable. There is no per-call registry walk and no string lookup on the hot path. A simple `(op_id, dtype, backend_id)` mapping resolved once suffices; we explicitly refuse to generalize into a multi-axis dispatch grid until a concrete second axis exists.

Inside the backend, the call lands in the *same* code that exists today. For CUDA, the vtable's `add` thunk re-monomorphizes on the incoming `DTypeId` and calls the existing `match`-based wrapper — `add_kernel_bf16x8` and friends are untouched. The plugin is where static dispatch is reborn: device dynamism stops at the `.so` boundary; dtype dispatch stays a branch-predicted `match` over a handful of arms.

### Capability descriptors and fallback

Each backend exposes a `Capabilities` descriptor — a `#[repr(C)]` value queried *before* any work: a dtype bitset, an op bitset, max workspace, feature flags (paged-attention, cuda-graph capture, fp8 tiers `KvQuantTier`), and a compute-capability range. We split two axes that RustInfer's current "either it compiles or it doesn't" model cannot distinguish, following TensorRT's hard-won lesson: *feature capability* (is this `(op, dtype)` supported? — queryable, fine-grained) versus *hardware compatibility* (is this GPU arch in range? — a coarse accept/reject at load). This lets a CUDA backend refuse fp8 on an Ampere card with a different, loud error than refusing a too-new arch entirely.

For graceful degradation, we keep the existing `OpError::Unsupported` — already returned by the CPU backend's partial ops — as the per-op runtime fallback signal. This is RustInfer's structural advantage over PJRT and TensorRT, which can only fall back at whole-program granularity: because RustInfer owns the abstraction at the *device* level and the CPU backend already implements *every* port, it can fall back op-by-op from CUDA to CPU. The non-negotiable condition is that the CPU backend stays **statically linked** as the always-present terminal fallback (ORT's mandatory CPU EP), never behind the plugin ABI, and that **every cross-backend host round-trip is logged**. Silent `Memcpy` insertion is the latency footgun that quietly destroys LLM decode throughput in ORT and PyTorch; making it observable is mandatory, not optional. A host round-trip also re-engages the keep-alive contract above in the inverse direction: the staged host buffer must outlive the copy, and `Storage` ownership makes that explicit rather than incidental.

### Coexistence and the registry

Multiple backend instances coexist because the registry is an owned, droppable object — a `Registry` holding `Vec<Box<dyn Backend>>` keyed by platform name and priority — not a process-global singleton mutated by static-init side effects. A multi-tenant inference server can hold its own registry, register the static CPU baseline plus any dynamically loaded plugins, select a backend per request from config intersected with probed `Capabilities`, and drop the whole thing cleanly. The static CPU backend self-registers via `linkme` (link-time only); dynamic backends register explicitly after load. This gives deterministic startup and, because nothing is a global, true unload and hot-swap — exactly what the existing ZMQ worker-subprocess model already wants.

### Why this is a refactor, not a rewrite

The decisive observation is that the seam already exists in the codebase. `MemoryPort` already traffics in raw bytes; `Storage` already centralizes every allocation behind a single RAII owner; `DTypeId` already provides the runtime tag; `DLTensor`-shaped erasure is a layout choice, not new machinery; and the CPU backend already proves a non-CUDA backend can satisfy every port. The static-generic world above the seam is preserved intact, the dtype `match` below the seam is preserved intact, and the only genuinely new things are one fn-ptr indirection per high-level op, a borrowed `DeviceTensor` descriptor with a host-side keep-alive contract, and a registry object to hold coexisting backends. The C-ABI plugin shim (covered in the ABI/loading section) bolts *on top of* these in-process traits; it does not replace them.

## 3. Heterogeneous Execution Engine: Dispatcher, Placement and Scheduler

> **↻ REVISED (see top banner).** In the static design, "heterogeneous execution" means **several backends compiled into one binary and selected at compile time / startup**, dispatched at the *model or request* boundary (a top-level enum or a per-backend monomorphized serve loop) — **never a per-op runtime dispatcher inside the decode loop**. The MVP's "one active backend per model" restraint still holds and is in fact the common case. The text below describing a runtime placement/partitioning/peer-transfer subsystem behind an "append-only extension chain" belongs to the **superseded** dynamic path; in the static design those concerns, if ever needed, are handled by ordinary Rust generics + a startup-time backend selector, not a runtime dispatch grid.

*Having defined the seam, we scope what actually crosses it in the first release. The decisive move here is restraint: the MVP targets exactly one active backend per model — matching today's single-device, single-stream, `block_size == 1` invariant — and defers the entire cross-backend placement, partitioning, and peer-transfer subsystem behind an append-only extension chain so the first stable ABI is not over-fitted to an unexercised feature.*

### The problem, stated against the current code

Today RustInfer has exactly one execution model and it is resolved entirely by the Rust type checker. `Tensor<T, D>` carries the device as a generic parameter, `Runtime<T, D, M>` is monomorphized over it, and the public entry point `serve_loop::run_with_model<M>` is bound to `M: DecoderModel<bf16, Cuda>` and constructs a concrete `Runtime<bf16, Cuda, M>`. Every operator call — `MathOps::add(scope, a, b, dst)`, `FusedOps::attention_paged(...)` — is a static trait method that, inside the CUDA impl, enters an `ExecScope` guard, unwraps a `CudaStream`, and `match`es on `T::DATA_TYPE` to pick a kernel symbol. There is no runtime kernel registry and no runtime device choice; the device is selected at compile time by monomorphization and the dtype is selected by a `match` that the optimizer collapses. This is RustInfer's single biggest performance asset and the design below must not throw it away.

It also bounds what is realistic to ship first. The runtime today drives exactly one device, runs a single stream per `ExecScope`, and operates under `block_size == 1`. There is no in-process second backend, no cross-device pointer, and no notion of an operator running anywhere other than where its `Tensor`'s `D` says it does. Any honest plan must distinguish the change that makes the existing single-backend world loadable at runtime — which is the deliverable — from the multi-backend machinery that the existing code has never exercised. We draw that line explicitly below and let it govern what enters the first stable ABI.

The constraint we are ultimately asked to satisfy is the opposite of what the code assumes: do not assume a single active backend. Eventually we must discover backends, query their capabilities, place each operator on the best one, schedule work across several concurrently, and move tensors between them — CPU+CUDA, CUDA+Metal, multi-CUDA, arbitrary mixes. But "eventually" is the operative word. The intellectual core of the section is one question: where does the static-generic world end and the type-erased, dynamically-dispatched world begin? Answer that precisely for a single runtime-loaded backend first, and the multi-backend story becomes an additive extension rather than a second architecture.

### Where the seam sits

The seam is already half-built, and it sits at the memory port (`device.rs`) and the high-level op ports. `alloc_bytes`, `upload`, `download`, and `copy_device_to_device` already speak in raw `NonNull<u8>` plus byte counts, not in `Tensor<T, D>`. Both `Cpu` and `Cuda` already implement the identical port set, and the CPU backend already returns `OpError::Unsupported` for ops it lacks — the fallback signal is already in the type system. That is the proof the abstraction can host a non-CUDA backend without a rewrite, and it is the natural cut line. The realistic path is not a rewrite to runtime tensors; it is to treat these existing ports as the in-process backend trait and bolt a C-ABI plugin shim on top of them.

The rule is: above the seam, keep `Tensor<T, D>` and `Runtime<T, D, M>` fully monomorphized for model code; at the seam, lower each high-level operator to a single flat C-ABI vtable call over an opaque tensor; below the seam, inside each backend, immediately re-monomorphize on the dtype tag and run the existing `match T::DATA_TYPE -> kernel_bf16x8` path verbatim. Device dispatch becomes a runtime function pointer paid once per matmul or attention; dtype dispatch stays compile-time-within-the-backend. We pay one indirection per high-level op, never per element. This is the wgpu-hal placement (dispatch at op granularity) rather than PyTorch's per-element TensorIterator, and it is the only placement that preserves the hot kernels untouched.

Concretely, the opaque tensor — name it `DeviceTensor` — is a `#[repr(C)]` POD carrying a raw device pointer, a `dtype_tag: u16`, a `device_kind` and `device_id`, a small fixed-capacity shape/strides/offset block, and an `owner_backend_id`. It is deliberately the DLPack `DLTensor` shape with an owner field bolted on; adopting the DLPack layout at the FFI edge buys zero-copy interchange with PyTorch/CuPy/JAX essentially for free and is a far better wire format than inventing our own. The `owner_backend_id` field is worth keeping from day one even though the v1 runtime never reads it for a placement decision: it is two bytes, it is what a future multi-backend transfer layer will key on, and it is the anchor for the deleter-travels-with-handle rule (below) that we want enforced even in the single-backend case. Carrying it now costs nothing and avoids an ABI break later. We explicitly reject carrying a c10-style `DispatchKeySet` on the tensor: that 64-bit multi-axis keyset exists to layer autograd and functionalization, which RustInfer does not have. A `DeviceTensor` carries data plus identity, nothing more.

The hard safety consequence, which we state loudly because it is where corruption hides: the moment a tensor crosses the seam, the compile-time `match T::DATA_TYPE` guarantee becomes a runtime `dtype_tag` check that the backend MUST re-validate. A wrong tag is memory corruption, not a type error. This is the OrtValue lesson and the boundary must enforce it on every entry, in the single-backend build no less than in any future multi-backend one.

### What v1 is, and what is deferred

We commit to a phased scope, and we make the phase boundary load-bearing in the ABI rather than aspirational.

**v1 (the MVP, shippable against today's code).** Exactly one active backend per model — the same invariant the runtime already enforces, only now the backend is chosen at runtime instead of by monomorphization. The whole model lives on that one backend; attention, RMSNorm, RoPE, and the paged-KV ops stay co-resident; nothing moves across a device boundary during decode because there is no second device in the picture. The work is: lower the existing ports to the C-ABI vtable, load one backend (CUDA) as a plugin, resolve each op once at model-load into a function pointer, and run. The success criterion is "single-backend runtime-load works end to end" — the worker boots, `dlopen`s the CUDA plugin, resolves the plan, and serves decode at parity with today's monomorphized build. Nothing in v1 requires a transfer matrix, a partitioner, peer copies, or coherence protocol, because there is never more than one place an op can run.

**Post-MVP (gated behind v1 working end to end).** Multi-backend placement: a capability-driven partitioner, cross-backend transfer nodes, a dedicated transfer port, the peer-copy matrix, and stream-dependency coherence. This is a genuinely new subsystem — today there is one device, one stream per scope, `block_size == 1`, and zero cross-device movement, so none of it has an analog in the current code or a test that exercises it. Building it speculatively into the first stable ABI would over-fit that ABI to an unexercised feature. So it does not enter the core vtable. It arrives later as an additive extension through the typed extension chain (described under the ABI), keyed on the `owner_backend_id` we are already carrying. The first stable ABI therefore describes a single-active-backend world — which is exactly the world the rest of the codebase already lives in — and grows multi-backend support without a breaking revision.

This phasing is not a retreat from heterogeneity; it is the discipline that lets the first ABI be small and correct. The sections below specify the v1 dispatch and ABI in full, then sketch the deferred placement/transfer design so its eventual shape is understood and the v1 ABI is provably forward-compatible with it.

### The dispatch model — resolve once, not per call

We deliberately do not build a PyTorch-style per-call dispatch table. The reference systems split cleanly here: PyTorch indexes a fn-ptr grid by a `DispatchKeySet` on every single call; ONNX Runtime instead partitions the graph once at load via `GetCapability` and freezes a per-node plan; TensorRT resolves the DAG at build time and the runtime enqueue has no lookup at all. RustInfer's decode loop runs the same operator sequence millions of times, so the TensorRT/ORT model is the right one: resolve placement once, at model load, into a plan, then execute with zero dispatch overhead.

The dispatch key is therefore the minimal triple `(op_id, dtype, backend_id)`, resolved once at model-load into a per-op function pointer. `op_id` enumerates the existing port methods (the `MathOps` / `FusedOps` / `DiffusionOps` surface); `dtype` is the existing `Dtype::DATA_TYPE`; `backend_id` is the placement decision. In v1 `backend_id` is a constant — there is one backend — so the resolved plan is simply "every op points at the one loaded backend's fn-ptr for its `(op_id, dtype)`." The triple is shaped so that the post-MVP case, where `backend_id` actually varies per op, needs no change to the key, only a partitioner that fills it in. We reject generalizing this into a multi-axis keyset until a concrete second axis (autograd, functionalization) actually exists — every reference author who built the general keyset first now describes it as accidental complexity.

| Concern | Rejected approach | Chosen approach | Why |
|---|---|---|---|
| When to dispatch | Per-call table (PyTorch DispatchKeySet) | Resolve-once-at-load plan (ORT/TRT) | Decode loop repeats the same ops; pay resolution once |
| Key shape | 64-bit multi-axis keyset | `(op_id, dtype, backend_id)` triple | No autograd/functionalize axis exists to justify it |
| Dtype handling | Runtime registry lookup | `match T::DATA_TYPE` inside backend | Preserves existing zero-overhead kernel selection |
| Tensor identity | c10 keyset on tensor | DLPack-shaped POD + owner id | Free interchange; no inherited complexity |
| Multi-backend placement | In v1 core ABI | Deferred to extension chain | Unexercised today; keeps first stable ABI small |

### Placement and partitioning (deferred — design sketch)

This subsystem is post-MVP; it ships only after single-backend runtime-load works end to end, and it enters through the extension chain rather than the core vtable. We specify its intended shape so the v1 ABI can be shown to accommodate it additively.

Placement will be a two-phase, capability-driven partition modeled on ONNX Runtime's `GetCapability`. At load, the host enumerates registered backends, intersects each backend's probed `Capabilities` (a `#[repr(C)]` struct: dtype bitset, op bitset, max workspace, paged-attention and CUDA-graph flags, min/target compute-cap, quant tiers) with operator-level config and the model's required ops. Each backend is then offered the operator list and claims what it supports, in descending priority order. Whatever no accelerator claims falls to the CPU backend, which is always present and always last — the ORT mandatory-CPU-EP rule. The output is a frozen placement plan: an ordered list of (op, backend, resolved fn-ptr) with explicit cross-backend transfer nodes inserted at partition boundaries. Note that `Capabilities` is useful in v1 too — even a single backend must answer "do you support this `(op, dtype)`?" so the host can fail loudly at load rather than mid-decode — so the capability-query entry stays in the core vtable; only the multi-backend partitioner that consumes it across several backends is deferred.

For the LLM decode path specifically, the realistic plan keeps an entire model on one backend, which is precisely why v1 needs no partitioner at all: with a single resident backend the partition is trivially "everything here." When the partitioner does arrive, it remains general enough to split a diffusion graph or to offload a single unsupported op, and it honors the cross-cutting warning that silent host round-trips in the LLM hot path destroy latency — every transfer node is explicit and loggable, so a CUDA→CPU fallback inside a decode step is visible at load time, not a mystery at runtime.

We will split capability into two axes, taking the TensorRT lesson directly: feature-capability (is this `(op, dtype)` supported — queryable, drives per-op placement) versus hardware-compatibility (a coarse compute-cap accept/reject gate at load). This lets a CUDA backend cleanly refuse fp8 on an old card with a distinct, loud error from refusing a too-new architecture. The feature-capability query is the part that is live in v1; the per-op placement consumer is the deferred part.

### Cross-backend memory transfer and coherence (deferred — design sketch)

Transfer is also post-MVP and also enters via the extension chain. v1 has exactly one backend, so the only memory movement is the host↔device traffic the existing `upload`/`download`/`copy_device_to_device` already perform inside one backend — there is no cross-backend transfer to design for, and nothing about it belongs in the first stable ABI.

When multi-backend lands, transfer will be owned by a dedicated transfer port — call it `DeviceTransfer` — separate from compute, exactly as ORT and c10 separate data movement from kernels, and added as an extension struct rather than wedged into the core runtime block. The transfer matrix is resolved per backend pair: same-backend same-device uses the existing `copy_device_to_device`; CPU↔accelerator uses the existing `upload`/`download`; accelerator↔accelerator on the same vendor (multi-CUDA) uses a peer copy where available and a host-staged bounce otherwise; cross-vendor (CUDA↔Metal) always stages through pinned host memory. The coherence story is deliberately simple and stream-ordered, reusing the existing `ExecScope`/`Stream`/`synchronize` model: a transfer node is enqueued on the destination's stream with a dependency on the source's completion, and the existing `ActiveGuard` device-restoration discipline scales to multiple devices because `DeviceId` is already a first-class value in `exec.rs`. That the coherence model reuses primitives already present is the reason deferring it is safe — we are not painting ourselves into a corner, only declining to ship an unexercised matrix in v1.

The non-negotiable ownership rule, shared by every stable boundary that does not crash, applies in v1 already even with one backend: the deleter travels with the handle. Memory allocated by the CUDA backend is freed only by that backend's free function. Every `DeviceTensor` that owns storage is wrapped on the Rust side in a `Drop` that calls the owning backend's destroy function (the PJRT_Buffer ownership model), keyed by the `owner_backend_id` we carry from day one. This is what prevents a cross-DLL double-free when a backend is built by a different toolchain than the host — a hazard that exists the moment any backend is `dlopen`ed, well before there is a second backend. Memory KIND (HBM, pinned, unified) is exposed as a discoverable attribute on the allocator rather than as a separate allocator-lookup-by-memory-info — we keep RustInfer's crisp `ExecScope`/`Workspace` ownership and reject ORT's awkward `OrtMemoryInfo` indirection, while still respecting PJRT's hard-learned Device-vs-Memory distinction.

### The ABI and how backends are loaded

The plugin ABI is a hand-rolled `#[repr(C)]` struct-of-`extern "C"`-function-pointers with one exported entry symbol, `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`. The first field of the vtable and of every args struct is `abi_version`/`struct_size`, and fields are append-only — PJRT's single cheapest forward-and-backward compatibility mechanism, and the precise mechanism that lets the deferred transfer/placement entries be added later without breaking already-loaded plugins. The vtable is grouped, mirroring TensorRT's Core/Build/Runtime split: an always-present identity block (name, abi_version, backend_id, target compute-cap), a registration/build block (`capabilities()`, plan construction), and the hot-path runtime block (alloc/free/upload/copy/per-op enqueue). The v1 core vtable is exactly this much and no more: identity, single-backend capability query, single-backend plan resolution, and the per-op enqueue path. Multi-backend transfer (`DeviceTransfer`), peer-copy, and the cross-backend partitioner hooks are NOT in the core vtable; like other optional and vendor ops — fp8 tiers, `qkv_norm_rope_scatter`, collectives — they hang off a typed linked-list extension chain so the core stays small and stable and the first stable ABI is not over-fit to an unexercised feature. We reject `abi_stable` and `stabby` for now: the op set is small, fixed, and already enumerated as ports, so a hand-rolled vtable is less ceremony and gives full control; they remain a fallback if the surface ever needs to pass Rust collections. Errors cross as an `i32` code plus an opaque error handle with accessor functions, never as an unwind — every entry function wraps `catch_unwind`, because a panic across the FFI boundary is instant UB. `OpError::Unsupported`, which the CPU backend already returns, maps to a reserved code and remains the per-op fallback signal.

Discovery is explicit, not static-init magic. The host reads a config/env list (the PJRT `name:path;...` form), `libloading::Library::new`s each, looks up the single entry symbol, checks `abi_version`, calls `capabilities()`, and registers the vtable under a platform name and priority into an owned, droppable `Registry` — not a process-global singleton. Every reference system that registered via static-init side effects (PyTorch, TVM, TensorRT) is on record as order-fragile and non-unloadable; an explicit entry point gives deterministic load, true unload/hot-swap, and a per-server registry object, which is what a multi-tenant inference server wants. The `Library` is kept alive for the lifetime of every resource it created — the plugin outlives its handles and streams. In v1 the registry typically holds two entries (the static CPU baseline and one loaded accelerator) and the model binds to one of them; the registry's multi-entry shape is already correct for the post-MVP case without change.

The CPU backend is special and stays special: it is BOTH statically linked (via `linkme` self-registration, since `linkme` is link-time-only and useless across `dlopen`) AND available as a plugin. Static linking makes it the always-present terminal fallback that no `dlopen` failure can remove. In v1 this guarantees the worker can always boot a CPU-resident model even if the CUDA plugin fails to load; in the post-MVP world it is also what makes per-op CUDA→CPU fallback safe.

### Decoupling the build (the .cu pain)

This is the other half of the MVP, and it is independent of and complementary to the runtime-load work: it is shippable on its own merits and does not wait on any multi-backend feature. All CUDA kernel sources move out of `infer-worker` into a standalone `infer-backend-cuda` cdylib with its own `build.rs`. That crate compiles to multi-arch PTX/fatbin (sm_80/86/89/90 plus PTX fallback) and at runtime loads them via the CUDA Driver API through `cudarc`'s dynamic-loading feature, which `dlopen`s `libcuda`/`libnvrtc`. The worker core then builds with zero CUDA toolchain — no nvcc, no libclang, no cuDNN-frontend discovery, no `nvidia-smi` host-arch detection — directly dissolving the 472-line `build.rs` coupling and the `default = ["cuda"]` hard dependency. `default = ["cuda"]` changes meaning from "compile and link the toolchain" to "load the bundled CUDA plugin at runtime." Shipping fatbin+PTX rather than a single host-detected `sm_XX` cubin removes host-GPU-specificity; the driver JITs PTX to the running GPU at module load and caches it on disk. Every reference runtime keeps the kernel toolchain inside the vendor plugin; this is simply adopting that discipline. Because this decoupling is exactly what produces the first loadable single-backend plugin, it and the v1 dispatch/ABI work converge on the same deliverable: a worker that builds clean and loads CUDA at runtime.

### Integration with the scheduler and Runtime

The existing `Runtime<T, D, M>` survives as the per-backend execution unit, one monomorphized instance per resident backend, sitting below the seam. Above it, `DecodeEngine` and `serve_loop` lose their hardcoded `DecoderModel<bf16, Cuda>` bound and the concrete `Runtime<bf16, Cuda, M>` construction, and instead drive a type-erased `BackendHandle` resolved from the registry. In v1 that handle resolves to the single loaded backend, so the change to `serve_loop` is "pick the backend at runtime instead of naming it in a generic bound" — a contained edit, not a re-architecture. The `infer-scheduler` crate is untouched in its protocol: it already speaks to the worker over ZMQ in `protocol` message types, and that subprocess seam is a latent asset — an untrusted or experimental backend can be isolated in a worker subprocess rather than `dlopen`ed into the scheduler/server process, giving a sandbox option no reference system has. Trusted backends version-gate at the C ABI; untrusted ones process-isolate over the existing ZMQ pumps. The scheduler's placement input is the load-time plan; its runtime job — batching, KV allocation via `GlobalKvAllocator`, request admission — is unchanged, because placement was resolved once and the hot loop still sees a fixed sequence of resolved function pointers. None of this depends on multi-backend placement existing; the scheduler sees the same fixed fn-ptr sequence whether the plan came from a trivial single-backend resolution or a future partitioner.

Finally, cross-cutting features RustInfer will want — CUDA-graph capture, quant-tier selection, tracing — are added as Burn-style decorator backends wrapping the port trait, not as edits to kernels or the ABI, and broad op coverage for a thin backend comes from PyTorch-style decomposition kernels (composite ops expressed in primitives, auto-re-dispatched). The plugin surface stays small while the feature set grows — and the multi-backend placement and transfer subsystem, when it arrives, grows the same way: through the extension chain, additively, after the single-backend runtime-load deliverable is proven end to end.

## 4. Dynamic Loading, Plugin Architecture and Stable ABI

> **⚠️ SUPERSEDED (see the Revision banner at the top).** The project chose the **statically-linked** model, so this entire section is **not part of the adopted design**. It is retained as the specification for an *optional future* "ship prebuilt backends without recompiling" capability. An `infer-abi` crate implementing exactly this C ABI (entry symbol, `#[repr(C)]` append-only vtable, opaque `DeviceTensor`, version gate, `libloading` registry, plus a reference backend) **has been built and tested** but is **deliberately not wired into the runtime** — no function pointer enters the hot path. In the adopted design, backends are ordinary Cargo crates linked at compile time and the "boundary" is the Rust op-port trait surface of §2, resolved by the compiler. Read the rest of this section only if/when prebuilt-plugin distribution becomes a requirement.

*The seam only holds if the boundary itself is sound under independent compilation. This section specifies the stable ABI: one entry symbol `rustinfer_get_backend_api`, a `#[repr(C)]` append-only vtable, opaque handles, and the rule that host and plugin share the same *source* version of `infer-core`/`infer-backend-abi` but never a compiled artifact — so `OpError` is lowered to an `i32` and never transported as a Rust enum across the line.*

### The problem this section resolves

RustInfer is, today, a statically-linked monomorphized binary. `Tensor<T, D>` carries its device as a generic parameter (`tensor.rs`, `PhantomData<T>` over `Arc<Storage<D>>`), `Runtime<T, D, M>` is monomorphized over the device, and `serve_loop::run_with_model` is hard-bound to `M: DecoderModel<bf16, Cuda>` (confirmed at `application/serve_loop.rs:71`). The device is chosen by the compiler; the dtype is resolved by a `match T::DATA_TYPE` inside each kernel wrapper (e.g. `kernels/fused_qk_norm_rope.rs:120` dispatching to `fused_qk_norm_rope_cu_bf16`). There is no runtime backend selection, no in-process multi-backend, and no plugin surface at all. Worse, because every `.cu` file lives *inside* `infer-worker` and `build.rs` (471 lines, gated on `default=["cuda"]`) compiles all of them through `cc::Build::cuda(true)` into the static `infer_kernels` archive while bindgen runs over cuBLAS/cuDNN headers, the core crate physically cannot build without a full CUDA toolchain, libclang, cuDNN-frontend, and a host GPU whose compute capability `nvidia-smi` bakes into `sm_XX`. The artifact is host-GPU-specific by construction. `SKIP_BUILD_KERNELS` exists as an escape but then linking fails.

The goal is to let a backend be discovered, loaded, version-negotiated, and upgraded independently of the runtime, and to let the core build with zero CUDA toolchain — without throwing away the monomorphized hot path that is RustInfer's single biggest performance asset.

### Static vs dynamic vs plugin vs runtime-loaded: the recommendation

The four options are not mutually exclusive, and the right answer is a layered combination rather than a single mechanism:

| Mechanism | What it buys | Cost / why rejected as the *sole* answer |
|---|---|---|
| Pure static (today) | Zero dispatch overhead, simplest build graph | Core cannot build without CUDA; no runtime backend choice; no independent upgrade |
| Cargo features (compile-time `cuda`/`cpu`) | Cheap, no ABI | Still one device per binary; rebuild to swap; toolchain coupling unchanged |
| `dyn`-trait in-process (single binary, multiple backends linked) | Runtime selection, no FFI | All backends still link into one artifact → CUDA toolchain still required to build the binary; no independent upgrade |
| C-ABI plugin via `libloading` (recommended) | Independent build/version/upgrade; core needs no nvcc; true hot-swap | One vtable indirection per op; must hand-build and police a stable ABI; panic-across-FFI hazard |

The recommendation is: keep the CPU backend statically linked as an always-present in-process baseline (it already implements every port under `infrastructure/cpu/`, with `OpError::Unsupported` for ops it declines — confirmed by the `CoreOps` doc contract at `op_ports.rs:24` and the CPU module preamble at `infrastructure/cpu/mod.rs`), and move every accelerator (CUDA first, ROCm/Metal later) behind a C-ABI plugin loaded at runtime with `libloading`. This is the only option that simultaneously decouples the build (tension #2) and enables independent backend upgrades, while the static CPU baseline preserves a zero-FFI fallback path that no reference system here — not PJRT, not TensorRT — can offer at *per-op* granularity.

Note immediately the asymmetry this introduces, because it is the key to the whole design: the statically-linked CPU backend and a `dlopen`'d CUDA plugin are *two different kinds of consumer of the same port traits*, and they must be kept different on purpose. The CPU backend is consumed in-process as an ordinary Rust trait object/monomorphization — `Tensor<T, D>`, `OpError`, `CoreOps` all flow as native Rust values, no FFI, no ABI concern. The CUDA plugin is consumed across a `.so` boundary, where *no* Rust type may flow as a value. The same backend logic, two transports. Conflating them is exactly the trap the next sections are written to avoid.

### Where the static-generic world ends and the type-erased world begins (tension #1)

This is the crux, and the repo has already half-built the seam. The cut line is the existing `MemoryPort` trait (`ports/device.rs`): every method already speaks raw `NonNull<u8>` plus byte sizes — `alloc_bytes`, `free_bytes`, `upload`, `upload_async`, `download`, `copy_device_to_device`, `synchronize`. Both `Cpu` and `Cuda` implement it identically. That is proof the abstraction can host a non-CUDA backend, and it is exactly the granularity at which a C ABI wants to operate.

The seam sits at the boundary between the high-level op ports (`CoreOps`/`DiffusionOps`/`MathOps`/`FusedOps`) and their per-device implementations. Concretely:

- **Above the seam** — model code, `components/`, `Runtime<T, D, M>`, the KV machinery (`kv.rs`, `global_kv_alloc.rs`) — stays fully monomorphized over `Tensor<T, D>`. No model author ever sees a type-erased tensor. This preserves the compile-time type-state and the `Arc<Storage<D>>` RAII unchanged.
- **At the seam** — each high-level op call lowers to a single `#[repr(C)]` vtable fn-pointer call returning an `i32` status. The arguments are an opaque `DeviceTensor` POD (`{ raw_ptr: *mut c_void, dtype_tag: u8, rank: u8, shape: [i64; MAX_RANK], strides: [i64; MAX_RANK], offset_elems: i64, owner_backend_id: u32 }`), an opaque `StreamHandle(*mut c_void)`, and a small `#[repr(C)]` per-op args struct whose first field is `struct_size`.
- **Below the seam — *inside* the plugin `.so`** — a thin `extern "C"` thunk validates the args, then the `dtype_tag` immediately re-monomorphizes: it drives the *existing* `match T::DATA_TYPE → add_kernel_bf16x8` path verbatim, landing in the plugin's own private `impl CoreOps for CudaInner`. Device dispatch becomes one runtime fn-pointer; dtype dispatch stays compile-time *within the plugin*.

The cost is one indirect call per matmul / attention / rmsnorm — never per element. This matches where wgpu-hal and the PyTorch dispatcher both place their indirection (op granularity), and it is the representation discipline of PJRT_Buffer and DLPack's `DLTensor`: opaque handle carrying dtype and dims as plain data. We deliberately reject c10's multi-axis `DispatchKeySet` — RustInfer has no autograd/functionalize axis, so a `(op_id, dtype_tag, backend_id)` resolved-once-at-model-load table (TensorRT's pre-resolve-the-DAG lesson) is sufficient and far simpler.

One hard consequence must be stated plainly: erasing `Tensor<T, D>` to a `dtype_tag` converts a compile-time guarantee into a runtime check. A wrong `dtype_tag` at the boundary is memory corruption, not a type error (the OrtValue warning). The boundary layer must therefore validate `dtype_tag` against the op's declared signature on entry, in debug *and* release.

### What is the plugin, really: shared source, separate artifact (the independent-compilation contract)

Everything above hinges on one rule that is easy to state and easy to violate, so it gets its own treatment. The `infer-backend-cuda` crate is, internally, *ordinary RustInfer code*. It depends on `infer-core` and reuses the port traits — it contains a private `CudaInner` type with `impl MemoryPort for CudaInner`, `impl CoreOps for CudaInner`, `impl FusedOps for CudaInner`, written in the same style as today's `infrastructure/cuda/`. It sees `OpError`, it sees `Tensor`, it sees `Capabilities` as Rust types, and that is fine — *because it only uses them inside its own compilation unit*. Those trait impls are a private implementation detail of the plugin; **they never cross the `.so` boundary as Rust values.** The plugin is built, monomorphized, and laid out by its own `rustc`/codegen, and the host is built by a possibly different one. That is the entire point of independent build and release.

The consequence is non-negotiable and must be stated as a contract: **across the `.so` boundary there exists ONLY** the `#[repr(C)]` `BackendVTable`, the `#[repr(C)]` args/`DeviceTensor`/`Capabilities` PODs, opaque handles (`*mut c_void` for buffers, streams, and error details), and `i32` status codes. No `Vec`, no `String`, no `dyn`, no `&T`, no `OpError`, no trait object, no `repr(Rust)` value of any kind is ever read on one side after being written on the other. The reason is precise rather than superstitious: `repr(Rust)` layout is explicitly *not* stable across independent compilations, so a `Vec`, an `OpError`, or a `Capabilities`-as-Rust-struct produced by the plugin and read by the host (or vice versa) is reading bytes whose field order, padding, niche optimizations, and discriminant encoding the host did not agree to. That is undefined behavior, full stop. `#[repr(C)]` is the *only* layout the two independently-compiled artifacts are guaranteed to agree on, which is exactly why it — and nothing else — is allowed to cross.

This forces a specific, important treatment of `OpError`. `OpError` is a live `repr(Rust)` enum today — `pub enum OpError { Unsupported { backend, op }, … }` at `ports/error.rs:5` — and the existing per-op fallback story depends on a backend being able to *say* "I decline this op." It is tempting, and wrong, to hand that enum across the boundary. Instead: the plugin thunk catches its internal `Result<_, OpError>`, lowers it to a reserved `i32` status code (with a distinct, well-known code for `Unsupported` so the host knows to fall back to the CPU baseline), and optionally stashes the structured payload — the offending backend name and op name — behind an opaque `ErrorDetail` handle the host can later interrogate through dedicated `extern "C"` accessor functions (returning lengths and copying into host-provided buffers, never returning a Rust `String`). The host, on seeing the code, **constructs a fresh `OpError` on its own side** from that numeric code plus whatever it pulls out of the `ErrorDetail` handle. The Rust enum lives natively on both sides; it is simply never the thing that travels. This keeps the existing `OpError`-driven control flow — including the per-op CUDA→CPU fallback that `OpError::Unsupported` triggers — fully intact while the wire stays purely numeric.

The compatibility window that makes this sound is likewise precise: **the host and every plugin must be built from the same *source* version of `infer-core` and the shared ABI crate, but need not share a compiled artifact, a `rustc`, or codegen settings.** What they agree on is the *numeric meaning* of the C ABI — the field order and integer encodings of the `repr(C)` structs, the status-code enumeration, the vtable slot ordering — never any `repr(Rust)` layout. To make that agreement mechanical rather than aspirational, the `#[repr(C)]` boundary types live in a tiny dedicated crate, `infer-backend-abi`, that contains *only* `repr(C)` definitions and integer constants and *no* `repr(Rust)` public types at all; both host and plugin depend on it. A CI ABI-snapshot test diffs the layout of every boundary struct and the vtable against a checked-in golden file, and a lint forbids any non-`repr(C)` public item from appearing in `infer-backend-abi`. The `abi_version` / `struct_size` gate (below) then enforces the window at load time. This is the clean, mechanically-checkable line that lets the plugin be a genuinely independent artifact while remaining safe.

### The stable ABI: hand-rolled `#[repr(C)]` vtable, because Rust has none

There is no stable Rust ABI: we never send `Vec`, `String`, `dyn`, or any `repr(Rust)` type across the boundary, per the contract above. Three candidates exist. `abi_stable` brings layout-hash verification and stable collections but heavy ceremony and a large dependency; `stabby` is lighter but still imposes its worldview; a hand-rolled vtable gives full control of a *small, fixed, already-enumerated* op surface. Because the op set is precisely the existing ports — roughly thirty `CoreOps`/`DiffusionOps`/`FusedOps` methods, enumerated by the `OpBackend: CoreOps + DiffusionOps` blanket impl at `op_ports.rs:299` — the hand-rolled `#[repr(C)]` struct-of-`extern "C"`-function-pointers is the pragmatic choice. We reserve `abi_stable` only if the surface ever needs to ship Rust collections across the line, which the current design avoids entirely.

The design borrows PJRT's discipline wholesale. One exported entry symbol:

```
#[no_mangle]
pub extern "C" fn rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable;
```

`abi_version` (a `u32`, paired with `struct_size` as the first field of `BackendVTable` and of every args struct) is the universal version gate, checked on the *first* call; fields are **append-only**. This buys forward and backward compatibility without freezing a major version — the cheapest stability mechanism known, lifted directly from PJRT's `struct_size`-first convention. The vtable is grouped to mirror TensorRT's Core/Build/Runtime split: an always-present **identity block** (`name`, `abi_version`, `backend_id`, target compute-cap), a **registration/build block** (`capabilities()` returning a `#[repr(C)] Capabilities` POD *by value*, allocator setup), and a **hot-path runtime block** (`alloc`/`free`/`upload`/`copy_d2d`/per-op enqueue, every slot returning `i32`). Optional or vendor-specific ops (fp8 tiers from `QuantTier`, `qkv_norm_rope_scatter`, collectives from `ports/collective.rs`) hang off a typed linked-list **extension chain** so the core vtable stays small and stable — this is the clean answer to "add a fused op without breaking the ABI."

Three non-negotiable safety rules, shared by every successful stable boundary (tvm-ffi, PJRT) and adopted verbatim:

1. **Deleter travels with the handle.** A buffer `cudaMalloc`'d by the CUDA plugin is freed *only* by that plugin's `free` fn. Different plugins may be built by different toolchains; cross-`.so` `free` is a double-free waiting to happen. Every returned handle — buffers, streams, *and* the `ErrorDetail` handles described above — is wrapped in a Rust `Drop` that calls the originating plugin's destroy fn.
2. **Errors cross as `i32` + opaque error handle, never by unwinding and never as a Rust enum.** A panic across `extern "C"` is instant UB. Every entry fn wraps `std::panic::catch_unwind`, converts a caught panic into a reserved error code, and returns. `OpError` is reconstructed host-side from the code (and any `ErrorDetail` payload), never transported as a value. This is the single most important rule for a framework whose kernels can legitimately `OpError::Unsupported`.
3. **Version-gate loudly.** An unchecked ABI mismatch is UB; a checked one is a clear load-time error. `rustinfer_get_backend_api` returns null on unsupported `abi_version`, and the host refuses to register.

### Discovery, registration, version negotiation, independent upgrade

Registration is **explicit entry-point**, not static-init magic. Every reference system that self-registered via constructor side effects (PyTorch, TVM, TensorRT) is flagged as order-fragile, non-unloadable, and segfault-prone. Instead, the host scans a config/env list — stealing PJRT's shape, e.g. `RUSTINFER_BACKENDS=cuda:/opt/ri/libinfer_backend_cuda.so;rocm:...` — then for each entry: `libloading::Library::new`, resolve the single `rustinfer_get_backend_api`, check `abi_version`, call `capabilities()` (which returns the `#[repr(C)] Capabilities` POD by value), and register the returned vtable under a platform name and priority into an *owned, droppable* `BackendRegistry` object (not a process-global singleton). The handshake is therefore: ABI version gate first, then the `#[repr(C)] Capabilities` POD (dtype bitset, op bitset, max-workspace, cuda-graph / paged-attention flags, min/target compute-cap, quant tiers) queried *before* any work. Note that `Capabilities` crosses as a flat `repr(C)` value precisely so it does *not* fall foul of the independent-compilation contract — it is data, not a Rust struct passed by reference. A multi-tenant inference server wants exactly this: a per-server registry it can construct, populate, and drop, giving deterministic load *and* unload — true hot-swap. The `Library` is kept alive for the lifetime of every resource it created (the plugin must outlive its handles, streams, *and* its `ErrorDetail` handles).

Independent upgrade falls out of this design: because the only contract is the append-only C vtable plus the capability POD — and because the two sides share only source-version compatibility, never a compiled artifact — a new `libinfer_backend_cuda.so` (newer kernels, newer CUTLASS, a new fused op behind an extension-chain node) drops in without recompiling the runtime, exactly as a PJRT vendor wheel meets the core only at `GetPjrtApi()`. `linkme` is reserved strictly for the in-binary CPU baseline's self-registration — it is link-time only, operates on native Rust trait objects, and is useless (and unnecessary) across `dlopen`.

### Decoupling the build (tension #2)

All `.cu` files, `build.rs`'s `cc::Build::cuda(true)` invocation, the bindgen-over-cuDNN step, and the `nvidia-smi → sm_XX` detection move out of `infer-worker` into a standalone `infer-backend-cuda` cdylib crate with its *own* build script. That crate still depends on `infer-core` (to reuse the port traits for its private `CudaInner` impls) and on `infer-backend-abi` (for the `repr(C)` boundary types), but those are *source* dependencies compiled into the plugin's own artifact — the host links neither the plugin's kernels nor its Rust impls. The plugin compiles kernels to a multi-arch PTX/fatbin set (sm_80/86/89/90 plus a PTX fallback) and at runtime loads them through the CUDA Driver API via `cudarc` with its dynamic-loading feature, which `dlopen`s `libcuda`/`libcudart`/`libnvrtc`. The driver JITs PTX to the running GPU at module load and caches it on disk. The worker *core* then builds with no nvcc, no libclang, no cuDNN-frontend discovery, no host-arch detection — `default=["cuda"]` degrades from a hard compile dependency to "load the bundled CUDA plugin at runtime." This is what PyTorch, ORT, TVM and PJRT all do: the core compiles zero kernels; the toolchain lives inside the vendor `.so`.

### What crosses the boundary, what stays in-process

Crossing the C ABI, and nothing else: opaque device-buffer handles, the `DeviceTensor` POD (ptr + dtype tag + shape/strides), the `StreamHandle`, per-op `#[repr(C)]` args structs, the `Capabilities` POD, opaque `ErrorDetail` handles, and `i32` status codes — command *submission*, in TensorRT's `enqueue(desc, ptrs, stream)` shape. Staying firmly in-process and monomorphized, *as native Rust values on each side*: `Tensor<T, D>`, `Runtime<T, D, M>`, `OpError` (reconstructed host-side from the numeric code), the plugin's own private `impl CoreOps for CudaInner` trait objects, the scheduler-side KV orchestration, `ExecScope`/`Workspace`/`ActiveGuard` ownership (`exec.rs`), and all model graph logic. The in-process trait path (the static CPU backend, consumed as a Rust trait) and the C-ABI path (the CUDA plugin, consumed as a vtable of `extern "C"` pointers) are two *separate consumers of the same backend logic*, not the same objects flowing across the boundary — and that distinction is what keeps independent compilation sound. The host owns the stream and submits; the plugin owns its workspace (TensorRT's split). Burn's decorator pattern (a backend wrapping a backend) is the zero-ABI-touch way to layer CUDA-graph capture, quant-tier selection, and tracing on top of the port trait later, keeping the plugin surface small while features grow. And the pre-existing ZMQ worker-subprocess seam (`serve_loop` control/data pumps) remains the escape hatch for *untrusted* backends: version-gate trusted plugins at the C ABI, but process-isolate experimental ones over ZMQ rather than `dlopen`-ing arbitrary static-init code into the server.

## 5. Backend Build System: Independent Build and Release

*With the ABI defined, we can finally dissolve the build coupling that motivates the whole effort. Deleting the worker's 471-line `build.rs` and relocating all `.cu` compilation into the backend crate's own build is what lets the core build with no `nvcc`, no `libclang`, and no `nvidia-smi` host-arch pinning — and a fixed multi-arch fatbin replaces host detection so the artifact is portable.*

### The problem we are dismantling

Today the GPU toolchain is fused into the Rust crate graph. `crates/infer-worker/Cargo.toml` declares `default = ["cuda"]`, and the `cuda` feature pulls `cc`, `bindgen`, and `walkdir` as build-dependencies. The 471-line `crates/infer-worker/build.rs` then does four things that should never have been the worker's job: it walks `src/infrastructure/cuda/kernels/**/*.cu` and compiles all 29 `.cu` files through `cc::Build::cuda(true)` into a static archive `infer_kernels`; it runs `bindgen` over `wrapper.h` against `cuda_runtime`/`cublasLt`/`cudnn`/`cudnn_frontend` headers (requiring `libclang`); it performs heavy conda/venv discovery for CUDA, cuDNN-frontend, and the vendored cutlass headers, panicking if any is absent; and — most damaging — it shells out to `nvidia-smi --query-gpu=compute_cap` in `detect_cuda_arch()` to pick a single `-arch=sm_XX`. The artifact is therefore pinned to whatever GPU happened to be in the build host, and the core literally cannot compile without a full CUDA toolchain plus a visible GPU. The `SKIP_BUILD_KERNELS` escape hatch only defers the pain: the static `extern "C"` symbols in `kernels/add.rs` and its 27 siblings then fail to link.

The architectural goal of this section is narrow and concrete: make every backend repository build a versioned shared library plus multi-arch kernel artifacts on its *own* toolchain, and make `infer-worker` build with no nvcc, no libclang, no cuDNN-frontend discovery, and no `nvidia-smi`. The build system question is downstream of, and must serve, the runtime seam described elsewhere in this proposal: the `.cu` files move out of the worker into a standalone `infer-backend-cuda` cdylib, and the worker loads it through the CUDA Driver API at runtime. The build tool we choose is whatever best compiles *that* cdylib's kernels into a portable multi-arch blob.

### Evaluating build systems for the backend cdylib

The choice is not "what builds Rust" — Cargo builds the Rust shell of each backend crate regardless. The choice is "what compiles and packages the CUDA/HIP/Metal kernel objects that the cdylib embeds," because the kernel compile is the part that needs a vendor compiler (`nvcc`, `hipcc`, `metal`), multi-arch fatbin/PTX emission, and good caching across a large `.cu` set. The contenders are CMake, Bazel, XMake, Meson, cargo-native `cc`/`build.rs`, and a hybrid.

| Criterion | CMake | Bazel | XMake | Meson | cargo + cc/build.rs (status quo) | Recommended hybrid (Cargo shell + CMake kernel build) |
|---|---|---|---|---|---|---|
| CUDA/HIP/Metal toolchain integration | First-class `CUDA`/`HIP` languages, `CMAKE_CUDA_ARCHITECTURES`; Metal via custom commands | Possible via rules_cuda/community rules, immature for HIP/Metal | Native `add_rules("cuda")`, clean syntax, smaller ecosystem | CUDA support is thin, HIP/Metal essentially DIY | `cc::Build::cuda(true)` only; no fatbin, no HIP/Metal | CMake owns kernels per-backend; Cargo never sees a vendor compiler |

| Reproducibility | Good with pinned toolchain + lockable deps | Excellent (hermetic) but expensive to reach | Good | Good | Poor — conda/venv scanning makes builds host-dependent | Pin toolchain image + emit a manifest; reproducible enough |

Bazel offers the strongest reproducibility and remote cache but imposes a second, alien build graph that every kernel contributor must learn; for a five-crate project with one CUDA backend it is overkill and a familiarity tax. XMake and Meson are credible and pleasant, but neither matches CMake's depth of CUDA *and* HIP support nor its mindshare among the exact people who write `.cu`/`.hip` files. Staying on `cargo + cc` is the one option we reject outright: `cc` cannot emit a real fatbin, has no Metal/HIP path, and is what couples the toolchain to the worker in the first place.

We recommend the **hybrid**: keep Cargo as the build driver for the *Rust* surface of each backend crate (the cdylib's C-ABI entry, the dtype-monomorphized dispatch inside the plugin, the `libloading`/`cudarc` glue), and delegate the *kernel* compile to CMake invoked from each backend crate's own thin `build.rs`. This is deliberately the inverse of today's coupling. The worker's `build.rs` is deleted entirely; the kernel-building `build.rs` lives only inside `infer-backend-cuda` (and later `-rocm`, `-metal`), where requiring `nvcc`/`hipcc`/`metal` is correct and expected. CMake is chosen over Bazel/XMake/Meson because it is the only tool that simultaneously gives first-class multi-arch CUDA fatbin via `CMAKE_CUDA_ARCHITECTURES`, a parallel HIP `--offload-arch` story, sccache content-caching, cross-toolchain files for Jetson/aarch64, and — decisively — is already the build system every kernel author in this domain reaches for. The vendored cutlass/cute headers under `kernels/third_party` slot into CMake's include model with no special handling.

### How each backend repo builds its shared library + kernel artifacts

Each backend becomes a standalone crate producing a `cdylib`: `infer-backend-cuda`, `infer-backend-rocm`, `infer-backend-metal`, and `infer-backend-cpu` (the last is special — see below). The build has two stages.

Stage one, kernels, is owned by CMake. For CUDA it compiles every `.cu` currently under `crates/infer-worker/src/infrastructure/cuda/kernels/` — `flash_attn_gqa`, `matmul`, `scatter_kv_batch`, `qkv_norm_rope_scatter`, the lot — but instead of `-arch=sm_XX` it emits a **fatbin spanning a fixed arch set** plus a virtual PTX fallback: `-gencode arch=compute_80,code=sm_80` through `compute_90`, and `-gencode arch=compute_90,code=compute_90` so a newer GPU (sm_100, etc.) still loads via driver JIT of the embedded PTX. The output is *not* a static archive the consumer links. It is a relocatable kernel blob (`infer_kernels_cuda.fatbin`, or PTX modules) that the cdylib loads at runtime through the CUDA Driver API (`cuModuleLoadData` / `cuModuleLoadFatBinary`) via `cudarc`'s dynamic-loading feature, which dlopens `libcuda`/`libnvrtc` rather than link-binding them. This is the precise inversion of the current model: the symbol table the worker depends on (`add_kernel_bf16x8`, etc., declared `unsafe extern "C"` in `kernels/add.rs`) ceases to be a link-time dependency of `infer-worker` and becomes a runtime module lookup inside the plugin.

Stage two, the Rust cdylib, is owned by Cargo. The backend crate's `build.rs` invokes CMake, then tells Cargo to bundle the resulting fatbin (embedded via `include_bytes!` for a single-file plugin, or shipped alongside and resolved by a sidecar path). The bindgen step that today generates `OUT_DIR/bindings.rs` from `wrapper.h` moves here too — only the CUDA backend needs `libclang`, and only when actually rebuilding that backend. Crucially, the dtype dispatch is unchanged: inside the plugin the existing `match T::DATA_TYPE -> add_kernel_bf16x8` path in the kernel wrappers survives verbatim, because the C-ABI seam erases the *device* (runtime fn-ptr) while keeping the *dtype* monomorphized inside the plugin. The build system change is what makes that runtime seam shippable; it does not by itself move the seam.

The HIP and Metal backends reuse the identical two-stage shape: CMake `--offload-arch=gfx90a,gfx942` for ROCm fatbins loaded via the HIP module API; `metal`/`metallib` for Metal, loaded at runtime. No worker change is needed to add them — they are new cdylibs the host discovers by path.

The CPU backend is the deliberate exception and the reason this refactor is incremental rather than a rewrite. `crates/infer-worker/src/infrastructure/cpu/` already implements every port (`Device`, `MemoryPort`, `MathOps`, `FusedOps`, `DiffusionOps`), some returning `OpError::Unsupported`. It compiles with pure Rust and no GPU toolchain. It stays **statically linked** into the worker as the always-present terminal fallback, and may *also* be published as a plugin cdylib for symmetry. This is the proof that the abstraction can host a non-CUDA backend, and it means the very first deliverable — a worker that builds with zero CUDA toolchain — is just `default = []` with the CPU backend, no new kernels required.

### Replacing `nvidia-smi` host detection and `build.rs` kernel compilation

The two worst behaviors are removed by construction. `detect_cuda_arch()` and its `nvidia-smi` shell-out are deleted; arch selection moves from build-host detection to a *fixed compile-time matrix* (the gencode set above) resolved to the running GPU at *load* time by the driver, exactly as TVM's `CUDAModule` and TensorRT's fatbin do. The arch set lives in `infer-backend-cuda`'s CMake preset, versioned with the kernels, not discovered from whatever card is plugged into the CI runner. The worker's `build.rs` is deleted; `cc`/`bindgen`/`walkdir` leave the worker's build-dependencies entirely. `default = ["cuda"]` becomes `default = []` (CPU baseline), and "use CUDA" becomes a *runtime* decision: the host scans a configured plugins directory (PJRT-style `name:path` list), `libloading::Library::new` the cdylib, checks `abi_version`, queries `capabilities()`. The conda/venv/cuDNN-frontend scanning in `find_cudnn_frontend_include` and `find_cuda_path` is confined to the CUDA backend's CMake, where a missing toolchain is a legitimate "you cannot build this backend" error rather than "the core does not compile."

### Release artifact layout

Each backend is built and versioned independently, meeting the worker only at the C ABI. A release tree:

```
rustinfer-backends/
  cuda/0.1.0/
    libinfer_backend_cuda.so          # cdylib: C-ABI entry + dtype dispatch
    infer_kernels_cuda.fatbin         # sm_80/86/89/90 + compute_90 PTX
    backend.toml                      # abi_version, target compute-cap range,
                                      #   dtype/op capability bitset, build manifest
  rocm/0.1.0/
    libinfer_backend_rocm.so
    infer_kernels_rocm.hsaco          # gfx90a/gfx942 + fallback
    backend.toml
  metal/0.1.0/
    libinfer_backend_metal.dylib
    infer_kernels.metallib
    backend.toml
  cpu/                                 # statically linked baseline; plugin form optional
```

The `backend.toml` manifest is the contract the host reads before any work: the ABI version it was built against, the compute-cap window it accepts (a coarse hardware gate, distinct from per-(op,dtype) capability), the dtype/op bitset, and a build manifest (toolchain image digest, CUDA version, gencode list) for reproducibility and loud-on-mismatch loading. The worker tarball ships only the Rust binary plus the statically-linked CPU backend; GPU backends are fetched and dropped into the plugins directory per platform, each independently versioned. The CI matrix finally becomes meaningful: cells are (backend × target-triple), each producing one fatbin/cdylib pair, none of them dependent on the host GPU.

## 6. Kernel Development Workflow

*Moving kernels into a plugin changes how kernel authors work day-to-day, so this section defines the developer workflow. It splits kernels into an autotuned AOT fatbin (GEMM, flash-attention, fused ops) and an NVRTC-JIT-with-disk-cache tail (elementwise/reshape), and is candid that the headline 'edit `.cu`, zero Rust rebuild' loop is earned per-kernel only after a generic launch shim replaces the per-symbol `extern "C"` wrappers.*

### The current cost model, measured against the source

Today every kernel edit pays the worst-case price. `crates/infer-worker/build.rs` (472 lines, gated behind the `cuda` feature) walks `src/infrastructure/cuda/kernels/**/*.cu`, collects all 29 translation units (`add/add.cu`, `matmul/matmul.cu`, `flash_attn_gqa/*.cu`, `kv_cache/scatter_kv_batch.cu`, `qkv_norm_rope_scatter/*.cu`, and the rest), and hands the entire set to a single `cc::Build::cuda(true).opt_level(3).flag("-arch=sm_XX")` invocation that produces one static archive, `infer_kernels`. That archive is then statically linked into the worker via `cargo:rustc-link-lib=static=infer_kernels`. Because the unit of compilation is "all kernels into one `.a` that the Rust object files link against," touching a single character in `add.cu` triggers an `nvcc` recompile of that file, a re-archive, and — because the archive is a link input — a full relink of the `infer-worker` binary. Compounding this, `detect_cuda_arch()` shells out to `nvidia-smi --query-gpu=compute_cap` and bakes exactly one `sm_XX` into the build, so the artifact is pinned to the host GPU; `bindgen` re-runs over `wrapper.h` (cuda_runtime + cublasLt + cudnn + cudnn_frontend) needing `libclang`; and `find_cuda_path`/`find_cudnn_frontend_include` perform heavy conda/venv discovery that `panic!`s when absent. The net effect, called out as tension #2 in the brief, is that `default=["cuda"]` makes the core crate impossible to build without a complete CUDA toolchain and a physical GPU, while the kernel author's edit-build-test loop is dominated by toolchain re-entry and relink, not by the kernel change itself. The `nvrtc` library is already linked (`build.rs:54`) but no runtime-compilation code path exists — the link is dead weight.

It is worth being precise about *how* a kernel is reached, because the iteration cost is not only in `build.rs`; it is baked into the calling convention. Each kernel today is fronted by a hand-written Rust wrapper that declares its CUDA entry points as per-dtype `unsafe extern "C"` symbols and dispatches to them through a `match T::DATA_TYPE` ladder. `add.rs:9-80` is the canonical shape: it declares `add_kernel_bf16x8`, `add_kernel_fp16x8`, `add_kernel_float2_forward` (and the in-place variants), each with a fully spelled-out C signature, then `add::<T>` switches on `T::DATA_TYPE` and calls the matching symbol with `dst.data_ptr_mut()`, `a.data_ptr()`, `b.data_ptr()`, `n`, `stream`. Every one of the JIT-eligible kernels — `softmax.rs`, `rope.rs`, `scalar.rs`, `swiglu`, `ewise_mul.rs`, `broadcast_mul.rs`, `cast_fill`, `permute`, `split_cols`, `rope_interleaved` — follows the same template: a block of per-dtype `extern "C"` declarations and a dtype match that resolves, at link time, to a static symbol in `infer_kernels`. This is the crucial detail the redesign has to confront head-on: the wrapper is bound to a *link-time symbol*, so a kernel whose body is recompiled at runtime is simply unreachable through it. The fast loop cannot be conjured by relocating compilation to NVRTC alone.

### Target: two compilation regimes behind one backend boundary

The redesign splits kernels into two regimes and moves both out of the worker core. This rides on the seam established elsewhere in the proposal: all `.cu` and all CUDA toolchain dependence relocate into a standalone `infer-backend-cuda` cdylib with its own `build.rs`, leaving `infer-worker` to build with zero CUDA toolchain. The kernel author then never rebuilds the Rust core to iterate a kernel — they rebuild a single `.so`, or in the JIT regime (once the prerequisite shim below is in place), no Rust at all.

The first regime is ahead-of-time fatbin. The stable, performance-critical, autotuned kernels — GEMM and its cublasLt path (`gemm_cublaslt_bf16` in `matmul.rs`, which already threads a `workspace`/`workspace_size` through), the flash-attention family (`flash_attn_paged_decode`, `flash_attn_gqa_prefill`), `scatter_kv_batch`, the fused `qkv_norm_rope_scatter`, and `fused_add_rmsnorm` — are compiled once by the backend crate's `build.rs` into a multi-architecture fatbin. Critically, the arch list becomes a *set* — `sm_80;sm_86;sm_89;sm_90` plus a `compute_90` PTX entry as forward-compatible fallback — replacing today's single `nvidia-smi`-derived `sm_XX`. This is the TensorRT/PyTorch model: ship a fatbin that covers the deployment fleet, let the driver select the matching cubin at module load, and JIT the embedded PTX on any newer arch. The fatbin is loaded at runtime through the CUDA Driver API (`cuModuleLoadFatBinary` / `cuModuleGetFunction`) via `cudarc` with its `dynamic-loading` feature, which `dlopen`s `libcuda`/`libnvrtc` rather than link-binding them — this is what lets the *consumer* (the worker core) carry no link-time CUDA. We keep these kernels AOT because their performance depends on autotuning and template instantiation (cutlass/cute under `third_party`) that we do not want to re-pay at process start, and because they are edited rarely relative to how often they run. The partition is also a hard constraint, not a preference: NVRTC cannot easily ingest cute-template-heavy sources, so every cutlass-dependent kernel must stay on the AOT side. A source audit confirms the JIT-eligible set below pulls no cutlass/cute headers, so the cutlass templates remain entirely behind the fatbin path.

The second regime is NVRTC-JIT-with-disk-cache, and it is where iteration speed is won. The long tail of elementwise and shape-shuffling kernels — `add`, `ewise_mul`, `broadcast_mul`, `cast_fill`, `scalar`, `permute`, `split_cols`, `swiglu`, `softmax`, `rope`/`rope_interleaved` — are kernels whose source is small, whose dtype-specialization is mechanical (the `match T::DATA_TYPE -> add_kernel_bf16x8` ladder in `add.rs`), and which a kernel author tweaks constantly. These move to runtime compilation: the `.cu` source (or a `&str` template) is handed to NVRTC at first use, compiled to PTX, JIT-assembled to cubin by the driver, and the resulting `CUfunction` is cached in-process keyed by `(arch, kernel_source_hash, compile_flags)`. The payoff is that the author edits the `.cu`, and because the source is read at runtime (from the backend crate's data directory or an override path), there is no Rust rebuild and no relink — the next invocation recompiles only that one kernel.

### The prerequisite: a generic NVRTC launch shim that retires the per-symbol wrappers

The "edit-`.cu`-only, zero-Rust-rebuild" loop is not a free consequence of moving compilation to runtime; it is a property that has to be *built*, kernel by kernel, by replacing the calling convention itself. As established above, today's `add::<T>` reaches its kernel through a hard-declared `extern "C"` symbol selected by a `match T::DATA_TYPE` ladder — a link-time binding. A runtime-recompiled kernel produces a fresh `CUfunction` that no such declaration names, so it cannot be reached this way at all. Concretely, the JIT regime depends on first landing a generic name-and-args launch shim that supersedes the per-kernel `extern "C"` + match arms for the JIT'd subset. The shim takes a kernel *name* (e.g. `"add_bf16x8"`), looks the `CUfunction` up out of the cache (compiling on miss, below), packs the launch arguments into the driver's `void**` argument array, computes the launch geometry, and invokes `cuLaunchKernel` on the `ExecScope`'s stream. Sketched as an interface:

```rust
struct KernelSpec { name: &'static str, source_key: SrcHash, args: ArgLayout, grid: GridFn }
fn launch(scope: &CudaScope, spec: &KernelSpec, args: &[KernelArg]) -> OpResult<()>;
```

`KernelSpec` becomes the single source of truth for what was previously spread across the `extern "C"` signature (argument types and order) and the match ladder (dtype-to-symbol-name resolution). The dtype specialization that the type system performs today — picking `add_kernel_bf16x8` versus `add_kernel_fp16x8` — is re-expressed as a name derivation (`format!("add_{}x8", T::DATA_TYPE.suffix())`) plus a macro-define passed in the NVRTC flags, so the same `(arch, src_hash, flag_hash)` keying naturally separates the dtype variants.

This shim is a real, bounded rewrite of the calling convention across the JIT subset of the 29 wrapper files, and the proposal treats it as an explicit prerequisite task rather than an emergent benefit. Two consequences follow honestly. First, the "edit the `.cu` and rerun, no `cargo` at all" developer experience applies *only to kernels already migrated onto the shim*; for a JIT-eligible kernel that still carries its old `extern "C"` wrapper, editing the `.cu` still implies altering the Rust wrapper, exactly as today, because the wrapper still resolves a stale symbol. Migration is therefore incremental and the DX claim is scoped to the migrated frontier. Second, the shim trades the compile-time guarantees that the per-symbol signatures give us (each argument's pointer type and count checked by the Rust type system at the call site in `add.rs`) for runtime-described argument lists marshalled into `void**`. A mismatch between a `KernelSpec`'s declared `ArgLayout` and the kernel's true signature is silent memory corruption rather than a compile error, so each kernel's marshalling must be test-verified against the behavior of its old wrapper before that wrapper is deleted. The AOT kernels are unaffected: they keep their typed `extern`/cublasLt call paths inside the backend `.so`, where the toolchain still links them statically.

### The cache, keyed by (arch, kernel-hash, flags)

The disk cache is the mechanism that keeps JIT cheap across process restarts and turns "first run after edit" into the only slow run, and it is the same structure the launch shim consults: the shim asks the cache for a function by `(arch, src_hash, flag_hash)`, and the cache answers from its in-process map, from disk, or by invoking NVRTC. The key is a triple: the device compute capability string (`sm_90`), a hash of the canonicalized kernel source plus any included headers, and a hash of the NVRTC flag vector (`--gpu-architecture`, fast-math, `-default-device`, register caps, and the macro defines that specialize the launch — including the dtype define the shim emits). The value is the compiled cubin (or raw PTX). On a cache hit we skip NVRTC entirely and go straight to `cuModuleLoadData`; on a miss we compile, persist, and load. Including *flags* in the key is what makes autotuning sound: two tunings of the same source that differ only in a block-size `-D` define produce distinct keys and coexist, and the same mechanism keeps the per-dtype variants apart. The on-disk layout is a content-addressed directory (`$XDG_CACHE_HOME/rustinfer/kernels/<arch>/<src_hash>-<flag_hash>.cubin`) so it is safe to share across processes and to ship pre-warmed in a container image. This is deliberately the *same* keying discipline TensorRT uses for its serialized timing cache and ONNX Runtime uses for its compiled-subgraph cache; we are not inventing a scheme, we are adopting the proven one. A `RUSTINFER_KERNEL_CACHE=off` escape and a cache-version byte (bumped when the NVRTC major version or our codegen changes) guard against stale-cubin corruption.

### What the kernel author actually does

The developer experience is the point. For an AOT kernel, the author edits the `.cu`, runs `cargo build -p infer-backend-cuda` (which recompiles only that crate's changed translation unit and relinks one `.so`, never the worker), and the running server picks up the new backend on next load. For a JIT kernel *that has been migrated onto the launch shim*, the author edits the `.cu`, sets `RUSTINFER_KERNEL_OVERRIDE_DIR` to point at their working tree, and reruns — the shim notices the source hash changed, NVRTC recompiles that one kernel on first call, caches it, and the loop closes in seconds with no `cargo` invocation at all. For a JIT-eligible kernel not yet migrated, the loop is still the AOT-style `cargo build -p infer-backend-cuda` because the `extern "C"` wrapper has to be regenerated alongside the `.cu` — which is precisely the motivation to migrate it. The contrast with today is stark either way: a one-line change to `add.cu` currently forces `nvcc` + re-archive + full `infer-worker` relink; in the target it forces, at worst, a single-crate `.so` rebuild, and at best a lone NVRTC compile of `add.cu` and nothing else.

Hot-reload of a backend `.so` during development is the AOT-regime analogue. Because backends are loaded explicitly (`libloading::Library::new` on a path, then the single `rustinfer_get_backend_api` entry symbol, per the registration design), a dev-mode file watcher can detect that `infer-backend-cuda.so` was rebuilt, quiesce the device (drain in-flight streams, the existing `ExecScope::synchronize` already gives us the barrier), drop the old vtable and its `Library`, and `dlopen` the new one. The hard rule from the ABI-safety trinity applies: the `Library` must outlive every handle it produced, so reload is only safe at a quiescent point where no `DeviceTensor`, stream, or `CudaConfig` workspace allocated by the old `.so` is still live. In practice the dev loop tears down the `Runtime`, swaps the library, and rebuilds the `Runtime` — full hot-swap of compiled kernels without restarting the scheduler or server process.

### Autotuning

Autotuning lives entirely inside the backend `.so` and writes through the same `(arch, hash, flags)` cache. For a tunable kernel — tile sizes for the JIT elementwise kernels, or candidate cublasLt algorithms for GEMM — the backend, on first encounter of a problem shape, times a small set of candidates on the live GPU (exactly how `gemm_cublaslt_bf16` already receives a `workspace` to do real work), selects the winner, and persists the chosen flag-set keyed by `(arch, src_hash, problem_shape)`. For the JIT kernels this rides the launch shim directly: each candidate tile size is just a different macro-define in the NVRTC flag vector, so the candidates are already distinct cache keys and the winner is the one whose `(src_hash, flag_hash)` the shim records for that shape. Subsequent runs read the decision from cache and skip timing. This is the TensorRT tactic-selection model scoped down to our small op set; it is opt-in per kernel and never blocks the request hot path beyond the first observation of a shape. Because the result is host-GPU-specific by nature, it is cached, never baked into a distributed artifact — the shipped fatbin stays portable, and tuning specializes it per deployment.

### ROCm and Metal analogues

The regime split is portable. An `infer-backend-rocm` cdylib compiles its AOT kernels with `hipcc` to a multi-target code object (`gfx90a;gfx942`) loaded via the HIP module API, and its JIT tail uses `hipRTC` behind the identical launch shim and the same `(arch, source-hash, flags)` disk cache — `gfx90a` simply replaces `sm_90` in the key. An `infer-backend-metal` cdylib leans into Metal's runtime-shader-compilation model, which is JIT by default: `.metal` source compiled to a `MTLLibrary` at runtime, with Metal's own pipeline-state cache plus our disk cache of the precompiled `.metallib` keyed by `(gpu-family, shader-hash, function-constants)`. In all three the principle holds: the toolchain (`nvcc`/`hipcc`/`metal`) and the runtime compiler (`nvrtc`/`hiprtc`/`MTLDevice`) live inside the vendor `.so`, the worker core builds with none of them, a single name-keyed launch shim fronts the runtime-compiled functions, and the cache turns repeated and cross-restart compilation into a one-time cost keyed identically across vendors.

## 7. Runtime Dependency Management and Detection

*A loadable backend must be discovered, version-checked, and gracefully degraded at runtime rather than at build time. This section splits detection into two explicit axes — feature capability (queryable op/dtype bitsets) versus hardware compatibility (a coarse driver/compute-cap gate) — and formalizes `OpError::Unsupported` against the statically-linked CPU baseline as the per-op fallback signal, with every cross-backend round-trip metered.*

### The problem we are actually solving

Today RustInfer has no runtime dependency management; it has *build-time* dependency *coupling*, which is worse. The `infer-worker` `build.rs` (472 lines, gated on `default=["cuda"]`) walks `crates/infer-worker/src/infrastructure/cuda/kernels/*.cu`, compiles every one with `cc::Build.cuda(true)` against a single `nvidia-smi`-detected `sm_XX`, hard-links `cublas`, `cublasLt`, `cudnn`, `nvrtc`, `cudart`, and `panic!`s if it cannot find the cuDNN-frontend headers or libclang. The `SKIP_BUILD_KERNELS` escape only moves the failure from compile to link. The practical consequence is that the *entire core cannot build* on a machine without a full CUDA toolchain and a matching host GPU, and the artifact it does produce is pinned to that host's compute capability. There is no notion of "the CUDA driver is too old," "cuBLAS is absent," or "fall back to CPU" — those conditions are simply unrepresentable because the dependency is resolved by the linker, not by the program.

The redesign described elsewhere in this proposal moves the CUDA kernels into a standalone `infer-backend-cuda` cdylib loaded at runtime via `libloading`, with the worker core building against zero CUDA toolchain. That move is what *creates* the need for genuine runtime dependency detection: once a backend is a `.so` discovered at startup rather than a linked symbol resolved at build, the host must answer three questions before trusting it — *is the library loadable, are its transitive native dependencies present and version-compatible, and what subset of work can it actually accept*. This section defines that probe sequence, the capability and health report it produces, and the degradation policy that consumes it.

We deliberately separate two concerns that the current build conflates and that ONNX Runtime and TensorRT both learned to split: **feature capability** (which `(op, dtype)` pairs a backend supports — a queryable, fine-grained property) versus **hardware/runtime compatibility** (a coarse accept/reject gate over driver, toolkit, and compute-capability versions). The build.rs collapses both into "did nvcc succeed for `sm_XX`." We keep them on distinct axes so a CUDA plugin can refuse fp8 on an Ampere card (a feature gap, op-level fallback) while a too-old driver refuses the whole plugin (a compatibility gate, load-time rejection) with distinct, loud errors.

### dlopen-probe over version symbols

For native dependency detection we choose **dlopen-probe with a typed handshake symbol** over reading exported version constants. Concretely, the host never links `libcuda`, `libcublas`, or `libcudnn`; the `infer-backend-cuda` plugin does its own discovery internally (via `cudarc`'s dynamic-loading feature, which `dlopen`s `libcuda`/`libnvrtc`/`libcudart`), and exposes the *result* of that discovery to the host through a single C-ABI entry point. The host's job is only to `dlopen` the plugin and call `rustinfer_get_backend_api(abi_version)`; the plugin's job is to internally probe its own native stack and report it.

We reject the alternative of having the host directly `dlsym` version symbols like `cudaRuntimeGetVersion` out of the CUDA libraries, for three reasons grounded in how PyTorch and JAX actually behave. First, symbol presence is a poor proxy for usability: `cudaRuntimeGetVersion` resolving tells you nothing about whether `cudaMalloc` will succeed on a driver that is present but too old — the classic "CUDA driver version is insufficient for CUDA runtime version" failure that surfaces only on first real call. Second, the host should not need to know the internal native dependency *graph* of every backend; that knowledge belongs to the plugin, exactly as PJRT pushes all device discovery behind `GetPjrtApi()` and the vendor `.so`. Third, dlopen-probe degrades gracefully by construction: a failed `libloading::Library::new` or a failed handshake is an ordinary `Result`, whereas a missing symbol in a *linked* library is a process that never started. This mirrors how PyTorch lazily initializes CUDA — `torch.cuda.is_available()` is a probe that catches the absence and returns `false` rather than aborting — and how JAX enumerates PJRT plugins and silently omits the ones that fail to initialize, leaving the CPU backend as the floor.

### The probe sequence at startup

The host owns a droppable `BackendRegistry` (not a process-global singleton — see the registration section), and runs the following ordered probe per candidate plugin discovered from the config/env plugin list. The ordering matters: each stage is cheaper and more fundamental than the next, and a failure at any stage is recorded as a structured `BackendHealth` entry rather than a panic, so the server always finishes startup with *some* viable backend.

| Stage | Question | Mechanism | Failure handling |
|---|---|---|---|
| 0. CPU baseline | Is the terminal fallback present? | Statically linked `Cpu` via `linkme` self-registration — never dlopened | Cannot fail; this is the floor |
| 1. Load | Is the `.so` openable and our symbol present? | `libloading::Library::new` + `dlsym("rustinfer_get_backend_api")` | Record `Unloadable{path, dlerror}`, skip plugin |
| 2. ABI gate | Was it built against a compatible boundary? | First field `abi_version`/`struct_size` of the returned vtable, checked before any other field is read | Record `AbiMismatch{built, host}`, refuse loudly, skip |
| 3. Native probe | Are libcuda/cublas/cudnn present and the driver new enough? | Plugin-internal `probe() -> NativeProbe`: dlopens its own native deps, calls `cudaDriverGetVersion`/`cudaRuntimeGetVersion`, compares against built-against | Record `RuntimeIncompatible`, demote plugin, keep registry healthy |
| 4. Hardware gate | Does the live GPU meet the plugin's min compute-cap? | `capabilities().min_compute_cap` vs probed device compute-cap | Reject this device for this backend; other devices may still pass |
| 5. Capability query | Which `(op, dtype)` are actually supported? | `capabilities() -> Capabilities` (dtype bitset, op bitset, quant tiers, cuda-graph/paged-attention flags, max workspace) | Per-op gaps recorded; resolved later by fallback |

Stage 0 is what makes the whole scheme safe. Because the existing `Cpu` adapter in `crates/infer-worker/src/infrastructure/cpu/mod.rs` already implements every port — `Device`, `HostDevice`, `MemoryPort` over `std::alloc`, and the op traits, with GPU-specific ops returning `OpError::Unsupported` — it is the guaranteed terminal fallback that ORT formalizes as its always-appended CPU EP. We keep it *statically linked* and never behind the C ABI, precisely because `linkme` registration is link-time and useless across `dlopen`; the CPU backend must be present even if every plugin fails to load.

Stages 1 and 2 are the ABI-safety discipline the boundary requires: read `abi_version`/`struct_size` *first*, before dereferencing any other vtable field, because an unchecked layout mismatch is undefined behavior, not an error. This is PJRT's `struct_size`-as-universal-version-gate applied verbatim.

Stages 3 and 4 are the runtime compatibility checks that the build.rs cannot express today. The native probe inside the plugin compares three versions that must align: the **driver** version (`cudaDriverGetVersion`, what `libcuda` reports), the **toolkit/runtime** version (`cudaRuntimeGetVersion`, what `cudart` was built from), and the **built-against** version baked into the plugin at its own build time. CUDA's minor-version compatibility guarantee — a runtime built against 12.x runs on any 12.y driver with y≥x — is exactly the rule this stage encodes: forward-compatible across minor versions within a major, rejected loudly across a major boundary. Shipping the kernels as multi-arch PTX+fatbin (sm_80/86/89/90 plus PTX fallback) rather than a single `nvidia-smi`-derived cubin is what lets stage 4 *accept* a GPU the plugin was not specifically built for: the driver JITs the PTX at module load, the way TensorRT's fatbins and TVM's `cuModuleLoadData` provide JIT-at-load forward compatibility. This directly removes the host-GPU-specificity that the current build bakes in.

### The capability and health report structure

Two distinct `#[repr(C)]` structures cross the boundary, mirroring the feature/hardware split. `Capabilities` is the static, queryable feature descriptor returned by `capabilities()`: a `dtype_mask` (bitset over `F32/BF16/F16/I32/I8/Fp8E4m3/Fp8E5m2`, matching `domain/dtype`), an `op_mask` over a stable `op_id` enumeration of the port methods, the supported `KvQuantTier`s, boolean flags for cuda-graph capture and paged-attention (formalizing the existing `ExecScope::supports_graphs()` already present in `domain/exec.rs`), `max_workspace_bytes`, and `min`/`target_compute_cap`. `BackendHealth` is the dynamic, per-attempt report the host accumulates during the probe: the stage reached, the structured failure reason, and — for loaded backends — the resolved driver/runtime/built-against version triple and the enumerated devices with their per-device compute-cap and free memory. The registry surfaces both upward to the dispatcher and out via the existing `prometheus` metrics path in `infer-scheduler`, so "CUDA plugin demoted: driver 535 < required 545" is an observable startup event, not a silent capability hole.

### Capability reporting up to the dispatcher and automatic selection

Selection is the intersection of explicit operator intent with probed capability, never magic auto-detect. The scheduler chooses a backend per request from a config-declared preference order, filtered to backends whose `BackendHealth` is healthy and whose `Capabilities` cover the request's required `(op, dtype)` set — the model's dtype, whether it needs paged attention, whether it needs an fp8 tier. This is wgpu's `Features`/`Limits` model and ORT's two-tier `GetSupportedDevices` + per-model `GetCapability`, not PyTorch's accidental 64-bit `DispatchKeySet`; RustInfer has no autograd or functionalization axis, so a resolved-once `(op_id, dtype, backend_id) -> fn_ptr` table built at model load (TensorRT's pre-resolve-the-DAG lesson) is sufficient and we explicitly reject generalizing to a multi-axis keyset until a concrete second axis exists.

The current `serve_loop::run_with_model<M: DecoderModel<bf16, Cuda>>` is hardcoded to `<bf16, Cuda>`; this is the call site that automatic selection replaces. The selection happens *above* the static-generic seam: the host picks a `backend_id`, and the monomorphized `Runtime<T, D, M>` is instantiated for the chosen device behind a small dispatch enum or the type-erased boundary defined in the dispatch section. The capability report is what makes that choice safe rather than a hardcode.

### Graceful, observable degradation

Degradation operates at two granularities, and RustInfer can do strictly better here than PJRT or TensorRT, which fall back only at whole-program or build granularity. At **load granularity**, a backend that fails stages 1–4 is absent from the registry; the scheduler simply never selects it, and the request lands on the next preference (ultimately the always-present CPU baseline) — JAX's behavior when a PJRT plugin fails to initialize. At **op granularity**, the existing `OpError::Unsupported { backend, op }` (already defined in `crates/infer-worker/src/domain/ports/error.rs` and already returned by the CPU adapter and by unimplemented CUDA ops) becomes the per-op fallback signal: a CUDA plugin that refuses fp8 matmul returns `Unsupported`, and the dispatcher routes *that op* to the CPU backend via a host round-trip. The critical discipline, learned from ORT's and PyTorch's latency-killing hidden `Memcpy` insertion, is that every such cross-backend round-trip is logged and metered — silent degradation in the LLM decode hot path is the footgun to avoid. The CPU backend's per-op `Unsupported` is therefore not a defect to remove but the formalized terminal of the fallback chain, kept statically linked so it is unconditionally reachable.

The net effect: the worker core builds with no CUDA toolchain, the startup probe turns "won't link" into a structured, observable health report, and the server degrades from CUDA to a disabled op set to pure CPU along a path that is explicit, version-gated, and never undefined behavior.

## 8. Distribution and Installation

> **↻ REVISED (see top banner).** In the static design, distribution is **ordinary Cargo**: the workspace publishes `infer-core` and the backend crates (`infer-backend-cuda` etc.) as normal crates; a consumer picks a backend via a Cargo feature and `cargo build` links it in. A GPU build needs the CUDA toolchain *at build time* (it compiles `.cu`); a CPU-only build (`--no-default-features`) needs only `rustc`. The parts of this section about **prebuilt backend `.so` trains on an OCI registry, `+cuXXX` companion wheels carrying backend binaries, the `rustinfer backend install --auto` GPU-probing fetch CLI, signature-verified `dlopen`, and the runtime ABI compatibility matrix** are **superseded** — they belong to the optional prebuilt-plugin path (§4) and apply only if "install a backend without recompiling" later becomes a requirement. The Python-wheel packaging *shape* (a base wheel + a CUDA build) still applies, but each wheel bundles a **statically-linked** binary rather than a loadable `.so` payload.

*Finally, independent build implies independent *release*. This section defines three distribution trains — a GPU-free core on crates.io, backend cdylibs on an OCI registry, and PyTorch-style `+cuXXX` companion wheels on an extra index — that meet only at the C ABI, with explicit `name:path` registry discovery and signature verification before any `dlopen`.*

### What we are distributing, and why the current shape blocks it

RustInfer today ships nothing distributable. The workspace `Cargo.toml` (resolver 3, five crates) declares `infer-worker` with `default = ["cuda"]`, and that feature pulls `dep:cc`, `dep:bindgen`, and `dep:walkdir` into the build graph. The 471-line `crates/infer-worker/build.rs` then walks `src/infrastructure/cuda/kernels/*.cu`, compiles all 29 `.cu` files through `cc::Build::cuda(true)`, runs `bindgen` over `wrapper.h` against `cuda_runtime`/`cublas`/`cudnn`/`cudnn_frontend`, and links `cublas`/`cublasLt`/`cudnn`/`nvrtc`. It discovers CUDA through conda/venv heuristics and derives a single `sm_XX` from `nvidia-smi`. The net effect: the *core* crate cannot be built — let alone published — without a full local CUDA toolchain, `libclang`, the cuDNN-frontend headers, vendored CUTLASS under `third_party`, and the *exact host GPU* that will run it. `SKIP_BUILD_KERNELS` exists but then linking fails. There is no crates.io story, no wheel, and the produced binary is host-arch-pinned.

The distribution strategy is therefore not a packaging afterthought; it is the externally visible consequence of the runtime-loading refactor described elsewhere in this proposal. Once the static-generic seam is cut at the existing `MemoryPort` boundary in `crates/infer-worker/src/domain/ports/device.rs` (raw `NonNull<u8>` + sizes — already type-erased in spirit, already implemented by both `Cpu` and `Cuda`), the kernels move out of the core into a standalone `infer-backend-cuda` cdylib, and *only then* does the core become a clean, GPU-free Rust crate that can be published. I describe the artifact taxonomy, the registry/discovery mechanism, the compatibility matrix, and the concrete end-user UX, mirroring PyTorch and ONNX Runtime ergonomics where they earned their reputation and diverging where RustInfer can do better.

### Artifact taxonomy: three independent release trains

I propose three distribution trains that meet *only* at the stable C ABI, exactly as PJRT wheels and the ONNX Runtime EP `.so` files meet only at `GetPjrtApi()`/`GetApi(N)`.

| Train | Artifact | Contains | Toolchain to *consume* | Registry |
|---|---|---|---|---|
| Rust core | `infer-worker`, `infer-protocol`, `infer-scheduler`, `infer-server` crates | pure Rust, ports + monomorphized `Tensor<T,D>` + statically-linked CPU backend | stable Rust only, no CUDA | crates.io |
| Backend plugins | `infer-backend-{cuda,rocm,metal}` cdylib (`.so`/`.dylib`/`.dll`) | PTX/fatbin (multi-arch) + `#[repr(C)]` vtable + `cudarc` dynamic loader | the GPU driver only (no nvcc, no link-time CUDA) | OCI/CDN registry |
| Python | `rustinfer` wheel + `rustinfer-cuda12x` wheel | server/CLI binary + bundled core; backend `.so` payload | `pip`, manylinux glibc | PyPI + extra index |

The cardinal rule, taken verbatim from PJRT's `struct_size`-first discipline and tvm-ffi's deleter-travels-with-handle rule, is that none of these trains share a Rust ABI. The core crate publishes to crates.io with *no* GPU dependency because `default` no longer implies `cuda`; the `cuda` feature is demoted from "compile kernels in-process" to "at runtime, locate and `dlopen` the bundled CUDA plugin." A buffer `cudaMalloc`'d inside `infer-backend-cuda` is freed only by that plugin's `free` fn-ptr, so the three trains can be built by three different toolchains and still interoperate safely.

### Rust crate distribution (crates.io, no GPU deps)

Publishing requires that `infer-worker` build on docs.rs and on a clean CI runner. Concretely: delete the `[build-dependencies] cc/bindgen/walkdir` block, delete `build.rs`'s kernel compilation, and make the CPU backend (`src/infrastructure/cpu/mod.rs`, which already implements every port and returns `OpError::Unsupported` for GPU-only ops) the always-statically-linked baseline via `linkme` self-registration. A Rust user then writes `cargo add infer-worker` and gets a working CPU-only inference runtime with zero CUDA on the machine — the equivalent of `pip install torch --index-url .../cpu`. GPU acceleration is opt-in at runtime, not at compile time.

The plugin crates (`infer-backend-cuda`) are *not* normal library crates and should not be the primary crates.io dependency, because they carry large PTX/fatbin payloads and a vendored kernel build. They are built as `crate-type = ["cdylib"]` and published as binary artifacts (below), with a thin `infer-backend-cuda-sys` shim on crates.io only for users who want to compile the plugin themselves. This mirrors how `torch` the wheel and the CUDA kernels are decoupled: 99% of users download a prebuilt artifact; the 1% who rebuild use the source crate.

### Python wheel distribution (manylinux + local-version tags)

The Python surface must be indistinguishable from `pip install torch` for an inference user who never touches Rust. I recommend the PyTorch *and* PJRT hybrid: a base wheel plus per-CUDA-family local-version identifiers, served from an extra index.

The base `rustinfer` wheel is `manylinux_2_28_x86_64` (and `aarch64`, plus `macosx_*_arm64` for Metal). It bundles the server/CLI binary, the core crates compiled, and the statically-linked CPU backend — runnable with no GPU. GPU support ships as a *companion* wheel carrying the backend `.so`, tagged with a local version: `rustinfer-cuda==0.5.0+cu124`. The `+cu124` local-version segment is PyTorch's exact convention and pip honors it. Because PyPI forbids local-version uploads, those companion wheels live on an extra index, and the documented install command is:

```
pip install rustinfer rustinfer-cuda --extra-index-url https://download.rustinfer.org/whl/cu124
```

For the CPU-only path: `pip install rustinfer` — no index gymnastics. I deliberately reject vendoring every CUDA family into one fat wheel (the artifact would be multi-gigabyte and re-download on every minor bump) and I reject auto-selecting CUDA at install time (pip cannot probe the GPU). Instead, the *CLI* probes the GPU and fetches the correct backend after install, which is strictly more reliable than pip's index-URL guessing and is the one place RustInfer should improve on PyTorch's ergonomics rather than copy them.

### The CLI that fetches the right backend for the detected GPU

This is the centerpiece of the end-user UX and the part that replaces `build.rs`'s `nvidia-smi → sm_XX` host-pinning. After `pip install rustinfer` (or `cargo install infer-cli`), the user runs:

```
rustinfer backend install --auto
```

The CLI loads `libcuda` through `cudarc`'s dynamic-loading path, queries the driver for compute capability and CUDA driver version, resolves that against the published *ABI matrix* (below), downloads the matching `infer-backend-cuda` artifact from the registry, verifies its checksum and signature, and writes it into the plugins directory with a registry-file entry. `rustinfer backend list` shows installed backends, their ABI version, target compute caps, and capability bitsets; `rustinfer backend install cuda --arch sm_90` forces a specific artifact for air-gapped or cross-provisioning cases. This is ONNX Runtime's explicit `RegisterExecutionProviderLibrary(path)` philosophy — registration by explicit path, never directory-scan magic — wrapped in a fetch step. The artifact ships *fatbin + PTX* covering `sm_80/86/89/90`, so a single download runs on a range of GPUs and the driver JITs PTX for anything newer, caching the result on disk. We trade `build.rs`'s build-time host-pinning for a one-time first-load JIT, which is exactly the PyTorch/TensorRT fatbin tradeoff.

### Automatic backend discovery at runtime

Discovery follows PJRT's `PJRT_NAMES_AND_LIBRARY_PATHS` model, hardened against accidental version mismatch. The host (server or worker) resolves backends in this precedence order: an explicit `RUSTINFER_BACKENDS=cuda:/path/libinfer_backend_cuda.so;cpu:builtin` environment variable; then a registry file at `$XDG_DATA_HOME/rustinfer/backends.toml` written by the CLI; then a default plugins directory next to the binary. For each entry the host calls `libloading::Library::new`, looks up the single exported symbol `rustinfer_get_backend_api(abi_version: u32) -> *const BackendVTable`, checks the ABI version, calls `capabilities()`, and registers the vtable under a platform name plus priority into an *owned, droppable* `Registry` — not a process-global singleton mutated by static-init. This matters for a multi-tenant `infer-server` (the axum/SSE crate): the registry is a per-server object, backends can be hot-swapped, and the `Library` is kept alive for the lifetime of every stream/buffer it created. The statically-linked CPU backend is always present as the terminal fallback, so discovery can never produce an empty registry.

### Multi-version compatibility: the runtime ↔ backend ABI matrix

Three independent version axes must be reconciled at load time, loudly, never as UB: the *protocol* version (`infer-protocol` v0.1 message types), the *plugin ABI* version (the `#[repr(C)]` vtable contract), and the *backend↔hardware* version (compute capability and CUDA driver). I recommend PJRT's single cheapest mechanism: a `u32 abi_version` (or `usize struct_size`) as the first field of the vtable and of every args struct, with fields append-only. The host refuses to register a plugin whose `abi_version` exceeds what it understands, and a plugin built against a newer protocol than the running core fails the handshake with a clear message. The published *compatibility matrix* is part of the registry metadata: each artifact records `(plugin_abi_version, protocol_version_range, min_compute_cap, target_compute_caps, cuda_driver_min)`, and the CLI's `--auto` resolution is just a query over this matrix. This is the discipline ONNX Runtime's provider-bridge *lacked* (exact-version-locked, an acknowledged anti-pattern) and that the plugin-EP path with `GetApi(N)` got right.

### Binary artifact management: registry, checksums, signing

Backend `.so` artifacts are large and security-sensitive (they run unsandboxed in-process unless isolated behind the existing ZMQ worker subprocess seam). I recommend an OCI-compatible registry/CDN as the source of truth, addressed by content digest, fronted by `download.rustinfer.org`. Every artifact carries a SHA-256 checksum recorded in the registry file and verified by the CLI before the `.so` is ever `dlopen`ed, and is signed (sigstore/cosign or minisign) with the public key embedded in the CLI; an unsigned or mismatched artifact is refused, not warned about. The Python companion wheels carry the same `.so` payloads with the same digests, so the wheel path and the CLI-fetch path converge on identical, verifiable binaries. This closes the trust gap that every reference system (PyTorch's import-time static-init, TVM's registry ctors) simply assumes away, and it is the natural complement to the "version-gate on first call, refuse loudly" ABI rule: we verify *provenance* before load and *compatibility* at load.

### End-to-end UX summary

A Python user runs `pip install rustinfer rustinfer-cuda --extra-index-url .../cu124`, or `pip install rustinfer` for CPU, then `rustinfer serve --model ...`. A Rust user runs `cargo add infer-worker` (CPU-capable immediately) and `rustinfer backend install --auto` to fetch the GPU plugin matched to their detected device. In both worlds the core is GPU-free, the backend is a separately-versioned signed artifact discovered by explicit path or registry file, and the only contract between them is a narrow, append-only C ABI — the same separation that lets PyTorch, ONNX Runtime, and PJRT ship a small core and many independently-released backends.

## Migration Roadmap: Always-Green, Incremental

The governing rule is that **the build is green at the end of every stage** and **the `default = ["cuda"]` flip happens last**. The danger to design around is concrete: `serve_loop::run_with_model` is hardcoded to `M: DecoderModel<bf16, Cuda>` and the worker bin has `required-features = ["cuda"]`. Removing `cuda` from `default` before a CPU-or-erased serve loop exists yields a worker that compiles but cannot construct a runtime. Each stage below reuses the existing port seam rather than rewriting it.

> **↻ REVISED to the static sequence (see top banner).** Stage 0 and the foundation collapse are **done and green**; the dynamic Stages 3–4 are replaced by static crate-splitting. The static sequence:

### Stage 0 — Reconcile the two `Device` traits ✅ *(implemented)*

Renamed the exec-layer trait to `ExecDevice` (and `HostDevice` → `ExecHostDevice`) so the public surface has a single `Device`. Mechanical, compiler-checked, green; 55 tests pass.

### Stage 1 — Collapse the foundation into `infer-core` ✅ *(implemented)*

`infer-core` now owns the recursive foundation — `types`, `dtype`/`quant`, `error`, `device` (`MemoryPort`/`Device`), `storage`, `tensor` (`Tensor<T,D>`), `exec` (`ExecScope`/`Workspace`/`StepCtx`/`CommAxis`), and the `BatchPlan` cluster. The worker re-exports each module so all `crate::domain::…` paths resolve unchanged. Builds with `rustc` alone; both the no-CUDA and CUDA gates are green.

### Stage 2 — Peel the op-port traits into `infer-backend-abi` *(next)*

Move `CoreOps`/`MathOps`/`DiffusionOps`/`FusedOps`/`CollectiveOps`/`Backend` (and the `impl_math_ops_via_core_ops!` macro) into a new `infer-backend-abi` crate (Rust traits, depending on `infer-core`). So the move drags `kv` + `component` + `SampledToken` down with the traits, with their `Cpu`/`Cuda` tests relocated to the worker. Stays fully static; no behavior change. Delivers: a backend-interface crate that backend crates can implement without depending on the runtime.

### Stage 3 — Extract the backends into their own static crates

Move `infrastructure/cpu` → **`infer-backend-cpu`** and `infrastructure/cuda/**` (incl. the 29 `.cu` + `build.rs`) → **`infer-backend-cuda`**, each implementing the `infer-backend-abi` traits and depending only on `infer-core` + `infer-backend-abi`. `infer-backend-cuda` is a normal Rust crate that statically links its compiled kernels (a `staticlib`/`cc` archive), gated behind the worker's `cuda` feature. The CPU backend always links. Delivers: the CUDA toolchain is confined to one leaf crate; `cargo build -p infer-worker --no-default-features` needs no nvcc.

### Stage 4 — Peel the runtime and re-examine the default

Move `application/*` + `models/*` into `infer-runtime` / `infer-models`. Make the worker bin select its backend by Cargo feature and monomorphize the serve loop accordingly (a startup-time selector when several backends are compiled in). Re-examine whether `default = ["cuda"]` should become `default = []` so the published `infer-core`/runtime build GPU-free out of the box. No function pointer is introduced at any stage.

### Optional / future — prebuilt-plugin distribution

If "install a backend without recompiling" is ever required, the **already-built `infer-abi` crate** (C ABI vtable + `DeviceTensor` + loader + reference backend) can be wired in as an *additional*, opt-in path behind a feature — without disturbing the static default. This is the only place the superseded §4/§8 material would be reactivated.

## Risk Register

The risks below are the ones that span sections; each detailed section carries its own local risks.

**Dynamic-dispatch overhead on the decode hot path (medium likelihood, high impact).** The decode loop repeats the same op sequence millions of times; a per-call registry walk or string lookup would be fatal. *Mitigation:* resolve the device axis once at model load into a captured per-op fn-ptr plan (`(op_id, dtype, backend_id)`), keep the dtype `match T::DATA_TYPE` monomorphized *inside* the plugin, and erase only at op granularity — one indirection per matmul/attention, never per element. The seam deliberately sits above `MemoryPort`'s byte ops and the high-level op calls, not at the tensor element level.

**ABI soundness under independent compilation (medium likelihood, critical impact).** A `repr(C)` layout drift that does not bump `abi_version`, an un-`catch_unwind`'d panic crossing the line, a cross-`.so` free of a host-allocated buffer, or transporting `OpError` (a `repr(Rust)` enum, confirmed at `ports/error.rs`) as a Rust value across FFI are all silent UB, not errors. *Mitigation:* a CI ABI-snapshot test plus a "no `repr(Rust)` public item in `infer-backend-abi`" lint; a panic-boundary lint forcing `catch_unwind` on every entry; deleter-travels-with-handle keyed on `owner_backend_id`; `OpError` lowered to an `i32` status plus an opaque `ErrorDetail` handle and reconstructed host-side.

**The erased surface is new code, not a projection (high likelihood, high impact).** Verified ground truth: `math_ops.rs:16` `fn add<T: Dtype>(...)` and the `FusedOps` methods are generic free functions with no `&self` receiver, and `Backend` is a blanket super-trait over them (`backend.rs`) — so the ports are *not* object-safe and `Box<dyn Backend>` cannot compile today. *Mitigation:* scope `BackendDyn` and its per-dtype adapter as the bulk of the dynamic-dispatch work, and gate it with a CI lockstep test against the generic surface. Drop the word "projection" everywhere.

**Fused ops cannot cross as a single `DeviceTensor` POD (high likelihood, high impact).** `attention_paged` takes `KvView<'_,T,Self>`, `scatter_kv_paged` takes `LayerKv<'_,T,Self>`, and every fused method takes `StepCtx<'_,Self>` (verified `fused_ops.rs:62-98`). A lone DLPack-shaped descriptor cannot encode these. *Mitigation:* a distinct `#[repr(C)]` arg struct per fused op that flattens the aggregate into arrays of `DeviceTensor` handles plus a `BatchPlan` POD; treat this as a real ~30-struct surface regenerated from or tested against the trait surface.

**dtype-tag erasure converts a type guarantee into a memory-safety obligation (medium likelihood, critical impact).** The on-wire `dtype_tag` is standardized at **u16** to match `DTypeId` and the ≥1024 registry range. A wrong tag is corruption, not a recoverable error. *Mitigation:* every backend entry re-validates `dtype_tag`, `owner_backend_id`, and shape/strides before dereferencing, tested adversarially.

**CPU fallback masks a performance cliff (medium likelihood, high impact).** The CPU backend implements `MemoryPort`/exec fully but only a *subset* of `CoreOps`/`DiffusionOps` natively and inherits `FusedOps` via host-round-trip defaults (`cpu/mod.rs:42` is `impl FusedOps for Cpu {}`). A hot op like `attention_paged` falling back is correct but collapses decode latency. *Mitigation:* log and meter every cross-backend round-trip into the scheduler's prometheus path; offer a production hard-fail mode so a hot-path fallback is a startup error, not a silent runtime surprise.

**Fatbin size and first-load JIT latency (medium likelihood, medium impact).** Multi-arch fatbin + PTX trades host-pinning for cold-start driver JIT and a larger cdylib. *Mitigation:* ship `sm_80/86/89/90 + compute_90` PTX, rely on the driver's on-disk JIT cache, pre-warm in the container image and at server warmup, and use a sidecar artifact if `include_bytes!` inflation becomes a problem.

**Staging order breaks the worker (low likelihood given discipline, critical impact).** Flipping `default = ["cuda"]` before a non-`Cuda` runtime exists yields a worker that compiles but cannot build a runtime. *Mitigation:* the mandated stage order — never flip default before Stage 2 lands a working CPU serve loop.

**Untrusted plugins run arbitrary in-process code (low likelihood, critical impact).** An unsandboxed `dlopen`'d backend executes in the server process; the native probe lives inside the plugin and can crash the host before `catch_unwind` fully protects it. *Mitigation:* signature/checksum verification before load; route untrusted or experimental backends through the existing ZMQ worker-subprocess isolation rather than in-process `dlopen`.

## Conclusion

> **↻ REVISED (see top banner).** Net of the static decision: the refactor keeps the **crate topology** (foundation in `infer-core`, op-port traits in `infer-backend-abi`, backends in their own crates, runtime/models peeled out) but replaces the **C-ABI/dynamic-loading boundary with a compile-time Rust-trait boundary**. `Tensor<T, D>` stays monomorphized end to end, backends are statically linked and feature-gated, and there is **zero per-op runtime dispatch**. The conclusion paragraphs below are written for the original dynamic design; treat their references to a "type-erased seam", "C ABI", "loaded plugins", or "dynamic dispatch" as superseded — the durable claims (refactor not rewrite, build on the existing well-factored ports, stay green at every stage, preserve the `match T::DATA_TYPE` hot path) all hold *more strongly* in the static design, since nothing is erased at all.

This proposal is a refactor, not a rewrite, and it earns that claim by building on three things RustInfer already has: a well-factored port family in which `MemoryPort` already speaks raw bytes, a second backend (`Cpu`) that already implements those ports, and a clean DDD layering that keeps `domain/` FFI-free. The seam this design needs is half-built; the work is to finish cutting it at exactly the right altitude — above `MemoryPort` and the high-level op calls, below the dtype `match` — and to be honest where the existing code does *not* hand us the abstraction for free.

The proposal is deliberately candid about those gaps. The ports are not object-safe, so the erased `BackendDyn` surface is new hand-written code that must be CI-locked to the generic surface. The CPU backend does not implement every op, so per-op fallback is a metered correctness path, not a free terminal. The fused ops carry lifetime-bearing aggregates, so the ABI is ~30 arg structs, not one POD. And the on-wire dtype tag is u16, not u8, because it must address the registered dtype range. Naming the artifacts uniformly — `infer-backend-cuda` and the `libinfer_backend_cuda.so` / `RUSTINFER_BACKENDS=name:path` conventions that follow from it — keeps the eight detailed sections describing one system.

What makes the plan executable is the always-green staging: reconcile the two `Device` traits, collapse the foundation and extract kernels at the source level, introduce the erased trait and a CPU-capable serve loop, *then* dynamic loading, and only last the `default = ["cuda"]` flip. At no point does the worker stop building, and at no point is the monomorphized `match T::DATA_TYPE` hot path disturbed. The payoff is a core that builds with `rustc` alone and ships GPU-free, accelerator kernels that build and release on their own trains, and a runtime that can host CUDA, ROCm, Metal, and CPU behind a single narrow, versioned, append-only C ABI — with the multi-backend future reachable additively, without ever breaking a loaded plugin.

## Appendix A — Key Decisions by Section

A flat index of the load-bearing decisions and section-level risks, for quick review and for tracking during implementation.

### 1. Repository Structure

- **Collapse the over-split foundation into a single infer-core crate holding dtypes/QuantScheme/errors, MemoryPort, the (merged) Device trait, the exec vocabulary (ExecScope/Stream/Workspace/ActiveGuard/StepCtx), Storage, and Tensor. Reduce the core from ~8 crates to 4 (infer-core, infer-backend-abi, infer-runtime, infer-models).** — These items are mutually recursive at the item level: Tensor<T,D> needs MemoryPort; Storage<D> is the sole alloc caller; exec Device: MemoryPort; ExecScope::enter returns ActiveGuard<Self::Device>; ActiveGuard<D> is generic over Device and calls scope.device() in Drop; Workspace<D>/StepCtx<D> are generic over Device. Rust crates cannot be circular, so any split (e.g. Tensor in infer-tensor, ports in infer-backend-abi) produces an unbreakable cycle. One crate makes the DAG acyclic. _Rejected:_ The prior 8-way split (infer-core/infer-tensor/infer-backend-abi/infer-ops/infer-graph/infer-runtime/...) which placed Tensor and the exec/Device traits in separate crates and created exactly the cycle it claimed to design out.
- **Keep only the op-port traits (MathOps/FusedOps/DiffusionOps/CollectiveOps/Backend) plus the new type-erased BackendDyn+vtable+loader in infer-backend-abi, sitting atop infer-core via one downward arrow.** — The op-port traits name Tensor<T,Self>, Self::Scope, and StepCtx<Self>, all of which live in infer-core; depending downward on infer-core (not sideways on a peer) keeps the graph acyclic while still isolating the stable ABI/loader surface in its own crate. _Rejected:_ Putting the exec/tensor machinery in infer-backend-abi (would re-merge the foundation into the ABI crate and blur the stability boundary); leaving op ports in infer-core (would force backend crates to depend on the whole runtime-facing surface).
- **Merge the two Device traits during the move (fold ports::Device::{ExecCtx,name} into the exec-layer Device) or, as a fallback, rename the exec-layer trait to ExecDevice; do not ship two traits named Device in infer-core's public surface.** — There are literally two distinct traits named Device today (domain/ports/device.rs with type ExecCtx, and domain/exec.rs with type Scope: ExecScope). Exposing both under one published crate name is a usability hazard and an ambiguous-import trap. _Rejected:_ Leaving both Device traits as-is across the new crate boundary (name collision, import ambiguity).
- **Place the static-generic / type-erased seam at MemoryPort (in infer-core) and the high-level op calls (in infer-backend-abi); re-monomorphize on a dtype tag inside the plugin.** — MemoryPort already speaks raw NonNull<u8>+sizes and both Cpu and Cuda implement it identically, so the seam is half-built. Erasing at op granularity costs one fn-ptr indirection per op, never per element, and preserves the match T::DATA_TYPE hot path inside the plugin. _Rejected:_ Erasing at element/Storage granularity (per-element vtable cost); pushing dyn dispatch up into Tensor/Runtime (destroys monomorphized model code).
- **Keep infer-cpu-backend statically linked as the always-present terminal fallback; CUDA/ROCm/Metal are loaded cdylibs only.** — cpu/mod.rs already implements every port and returns OpError::Unsupported, making it the natural guaranteed fallback. Static linking guarantees the core builds and tests with rustc alone. _Rejected:_ Making CPU a plugin too (loses the build-with-rustc-only guarantee and the always-present terminal).

_Risks:_
  - The two Device traits (ports::Device with type ExecCtx; exec::Device with type Scope) must be reconciled into one during the move; a botched merge changes the type-state axis of Tensor<T,D> and the ExecScope::Device==Self invariant, so the merge needs a mechanical, compiler-checked pass rather than hand edits.
  - Even after collapsing to infer-core, the foundation crate is large and internally recursive; care is needed that nothing in application/* (e.g. plan.rs, kv.rs) secretly reaches back into Tensor/exec in a way that should have stayed in infer-core vs moved to infer-runtime.
  - The dtype tag on the opaque DeviceTensor turns a compile-time match T::DATA_TYPE guarantee into a runtime check at the ABI boundary; a wrong tag is memory corruption, so the boundary must re-validate dtype/shape on every entry.
  - Moving .cu to a cdylib loaded via driver-API PTX/fatbin introduces first-load JIT latency and a disk cache the core does not control today.
  - The thin infer-worker still owns ZMQ pumps and plugin discovery; mis-scoping which application/* code is host wiring vs runtime could leave runtime logic stranded in the binary crate.
  - Keeping the in-process op-port trait path and the C-ABI vtable path in sync inside infer-backend-abi risks drift; the vtable must be generated from or tested against the trait surface.

### 2. Backend Abstraction Layer

- **Cut the static-to-dynamic seam exactly at the existing MemoryPort byte-boundary and the high-level CoreOps/DiffusionOps/FusedOps op-call boundary; keep Tensor<T,D> monomorphized above it and the dtype match below it.** — MemoryPort already speaks raw NonNull<u8>+sizes and both Cpu and Cuda implement it; Storage is the sole RAII allocation owner, so the seam is half-built. Erasing at op granularity costs one fn-ptr per matmul/attention, never per element, and preserves the zero-overhead match T::DATA_TYPE hot path inside each backend. _Rejected:_ Erasing at the tensor/element level (per-element vtable cost, fatal to GEMM throughput); erasing higher up at the model level (would force rewriting all model/application code and lose the type-state safety guarantee).
- **Make DeviceTensor a borrowed #[repr(C)] DLPack-shaped descriptor (DTypeId tag, byte_offset, owner_backend_id, MAX_RANK=8 inline shape/strides) valid only for one synchronous vtable call, governed by a host-side keep-alive contract; the host holds the owning Tensor (and its Arc<Storage>) live on the stack across the submit. It is NOT a zero-copy owning export.** — Tensor owns bytes via Arc<Storage<D>> (tensor.rs:21) whose Drop frees the allocation; a DeviceTensor cannot carry the Arc across C-ABI, so soundness comes from the host keeping the Arc alive for the synchronous call rather than from a refcount transfer. The export folds offset_elems*SIZE_BYTES into byte_offset and copies strides verbatim so sub-views/non-contiguous tensors cross faithfully. DTypeId(u16) and all descriptor fields already exist in Tensor, so construction is a field copy. MAX_RANK=8 covers all LLM/diffusion tensors; over-rank returns OpError::Unsupported with a reserved heap-pointer fallback. _Rejected:_ Calling it a free zero-copy export (ignores Arc<Storage> ownership and lifetime across FFI); transferring an Arc/refcount across the C-ABI (Arc has no meaning past the boundary); silently assuming contiguity (would corrupt sub-viewed tensors); c10-style DispatchKeySet baked in (multi-axis keyset is accidental complexity from autograd/functionalization RustInfer lacks); unbounded/heap rank by default (loses the single-cache-line POD that justifies crossing once per op).
- **State the cross-seam ownership rule asymmetrically: a DeviceTensor never owns; host-owned Storage-backed buffers are LENT for one call under the keep-alive contract; plugin-allocated persistent buffers are OWNED by the plugin with a deleter that travels with the handle.** — The two directions are not symmetric and conflating them is the latent bug: the 'deleter travels with the handle' rule only covers plugin allocations, while a host Arc<Storage> lent into a plugin op needs the inverse host-side keep-alive guarantee. Making both explicit closes the gap the reviewer flagged. _Rejected:_ A single symmetric 'deleter travels with handle' rule (does not cover host-lent buffers and leaves their lifetime across FFI unaddressed).
- **Resolve the device axis once at model load into a captured op vtable; keep dtype dispatch as a compile-time match inside the backend. Use a simple (op_id, dtype, backend_id) mapping, not a dispatch grid.** — TensorRT's pre-resolve-the-DAG lesson: no per-call registry walk or string lookup on the hot path. RustInfer has no second dispatch axis to justify a PyTorch-style 64-bit keyset. _Rejected:_ PyTorch-style per-call DispatchKeySet table (accidental complexity); ORT-style allocator-by-OrtMemoryInfo lookup (RustInfer's ExecScope/Storage ownership is crisper).
- **Keep OpError::Unsupported as the per-op runtime fallback signal with the CPU backend statically linked as the guaranteed terminal fallback; split feature-capability from hardware-compatibility in the Capabilities descriptor; log every cross-backend host round-trip (which itself re-engages the keep-alive contract for the staged buffer).** — The CPU backend already returns Unsupported and implements every port, enabling per-op CUDA->CPU fallback that PJRT/TRT cannot do. Splitting axes (TRT lesson) gives distinct loud errors for unsupported dtype vs too-new arch. Logging round-trips avoids ORT/PyTorch silent-Memcpy latency footgun. _Rejected:_ Whole-program-only fallback (PJRT/TRT — too coarse for an LLM hot path); silent host round-trips (destroys decode latency); putting the CPU fallback behind the plugin ABI (it must always be present).
- **Make the backend registry an owned, droppable Registry object (Vec<Box<dyn Backend>> by name+priority), with the static CPU backend self-registering via linkme and dynamic backends registering explicitly after load.** — Enables in-process coexistence of multiple backends, deterministic startup, true unload/hot-swap, and per-server registries for multi-tenancy — avoiding the order-fragile static-init singletons PyTorch/TVM/TRT regret. _Rejected:_ Process-global singleton registry mutated by static-init side effects (non-unloadable, order-fragile, segfault-prone); linkme across dlopen (link-time only, useless for dynamic plugins).

_Risks:_
  - The seam re-validates DTypeId and owner_backend_id at every backend entry; a missed validation means a mismatched dtype tag is silent memory corruption rather than a type error (the cost of erasure that the current compile-time type-state eliminates).
  - The host-side keep-alive contract is unenforced by the type system across the C-ABI: if the host drops the owning Tensor (releasing its Arc<Storage>) before a backend op completes, the DeviceTensor's raw_ptr dangles and the plugin reads freed memory. Soundness depends on the synchronous-submit discipline being honored at every call site rather than on a borrow checker.
  - Per-op CUDA->CPU fallback can mask a performance cliff: if a hot op (e.g. attention_paged) silently falls back, decode latency collapses even though correctness holds. Logging mitigates visibility but does not prevent the regression.
  - Object-safe dyn Device/dyn Stream projections must faithfully reproduce the ActiveGuard enter/restore device-binding discipline from exec.rs; getting the guard lifetime wrong across a dyn boundary risks leaving the wrong CUDA device current.
  - The MAX_RANK=8 inline shape/strides cap means a genuinely higher-rank tensor returns OpError::Unsupported until the reserved heap-pointer variant is implemented; the byte_offset/stride folding from offset_elems must be exact or sub-viewed and non-contiguous tensors cross the seam with wrong addressing.
  - Capabilities intersection at backend-select time must stay in sync with what the plugin actually implements; a capability bitset that overstates support reintroduces the OpError::Unsupported path at runtime in a context where fallback may not be desired (e.g. a benchmark expecting native execution).

### 3. Heterogeneous Execution Engine: Dispatcher, Placement and Scheduler

- **Cut the static-to-dynamic seam at the existing memory port (device.rs alloc_bytes/upload/download/copy_device_to_device) plus the high-level op ports (MathOps/FusedOps/DiffusionOps), lowering each op to one C-ABI vtable call over an opaque DLPack-shaped DeviceTensor, and re-monomorphizing on dtype_tag inside the backend.** — The memory port already speaks raw NonNull<u8>+sizes and both Cpu and Cuda already implement the identical ports (CPU already returns OpError::Unsupported for missing ops), so the seam is half-built; erasing at op granularity (not per element) pays one indirection per matmul/attention and preserves the existing zero-overhead match T::DATA_TYPE hot kernels. The realistic path reuses these ports as the in-process backend trait plus a C-ABI shim, not a rewrite. _Rejected:_ Per-element erasure (PyTorch TensorIterator) would add indirection in the inner loop; full rewrite to runtime tensors (candle Storage enum) discards the monomorphized kernel asset.
- **Scope the MVP to exactly one active backend per model (matching today's single-device/single-stream/block_size==1 invariant), and demote the entire cross-backend placement/partition/transfer subsystem (GetCapability partitioner, DeviceTransfer port, peer-copy matrix, stream-dependency coherence) to an explicitly post-MVP phase gated behind 'single-backend runtime-load works end to end.' Keep owner_backend_id in DeviceTensor and the capability-query entry in the core vtable, but cut the multi-backend partitioner/DeviceTransfer/peer-copy from the initial ABI surface, delivering them later additively via the typed extension chain.** — The current code has exactly one device, one stream per ExecScope, and zero cross-device movement, so the placement/transfer machinery has no analog and no test; the decode path keeps the whole model on one backend, so that subsystem is unused by the only working path. Building it into the first stable ABI would over-fit the ABI to an unexercised feature. owner_backend_id is two bytes and anchors the deleter-travels-with-handle rule even in single-backend; the (op_id,dtype,backend_id) triple and droppable multi-entry Registry already have the right shape for the deferred case, so the extension chain + append-only struct_size discipline make multi-backend a non-breaking addition. _Rejected:_ Presenting cross-backend placement at the same altitude as the build-decoupling work (blurs shippable-now vs speculative, over-fits the first ABI); inventing the transfer matrix and partitioner up front (no current-code analog, untested by the only deliverable).
- **Dispatch key is the minimal (op_id, dtype, backend_id) triple resolved once at model-load into a per-op fn-ptr plan, not a per-call table; in v1 backend_id is constant so the plan is trivial, and the post-MVP partitioner only fills backend_id in without changing the key.** — The decode loop repeats the same op sequence millions of times, so ORT/TensorRT resolve-once-and-freeze beats a per-call lookup; RustInfer has no autograd/functionalize axis to justify a multi-axis keyset, and the triple is forward-compatible with multi-backend placement. _Rejected:_ PyTorch 64-bit DispatchKeySet indexed per call — explicitly flagged as accidental complexity born of autograd layering RustInfer lacks.
- **Hand-rolled #[repr(C)] vtable with one entry symbol rustinfer_get_backend_api, abi_version/struct_size as append-only first field, TRT-style Core/Build/Runtime grouping, typed extension chain for optional ops, catch_unwind on every entry, deleter-travels-with-handle keyed on owner_backend_id. The v1 core vtable is identity + single-backend capability query + single-backend plan resolution + per-op enqueue ONLY; DeviceTransfer/peer-copy/partitioner hooks are in the extension chain, not the core.** — The op set is small, fixed, and already enumerated as ports; a hand-rolled vtable is less ceremony than abi_stable and PJRT's struct_size append-only discipline buys forward+backward compat cheaply and is exactly what lets deferred multi-backend entries be added without breaking loaded plugins; catch_unwind and per-backend free prevent UB and cross-DLL double-free, which is a hazard the moment any backend is dlopen'ed even with one backend. _Rejected:_ abi_stable/stabby (more ceremony, only needed for Rust collections); C++ vtable smuggling (PyTorch/ORT-bridge/TRT) — the #1 cited anti-pattern; putting transfer/placement in the core vtable (over-fits the first ABI to an unexercised feature).
- **Move all .cu into a standalone infer-backend-cuda cdylib that ships multi-arch PTX/fatbin and loads via cudarc dynamic-loading, so the worker core builds with zero CUDA toolchain; default=["cuda"] becomes load-at-runtime. Treat this as an independent, on-its-own-merits half of the MVP that converges with the v1 dispatch/ABI work on a single deliverable: a clean-building worker that loads CUDA at runtime.** — Directly dissolves the 472-line build.rs coupling, the nvcc/libclang/cuDNN discovery, and host-GPU-specific sm_XX pinning; every reference runtime keeps the toolchain inside the vendor plugin and cudarc makes it achievable in pure Rust. It is exactly what produces the first loadable single-backend plugin, so it needs no multi-backend feature to be valuable. _Rejected:_ Keeping .cu in-crate behind a feature (still forces full toolchain on core build); single host-detected cubin (host-arch-pinned artifact).
- **Keep the CPU backend BOTH statically linked (linkme) as the always-present terminal fallback AND available as a plugin; discovery is explicit name:path registration into a droppable per-server Registry; in v1 the registry holds the static CPU baseline plus one loaded accelerator, and the cross-backend transfer-node/logging machinery is deferred with the rest of the multi-backend subsystem.** — Static CPU baseline guarantees the worker can always boot a CPU-resident model even if the CUDA plugin fails to dlopen (and later makes per-op CUDA->CPU fallback safe); explicit registration gives deterministic load/unload and a multi-tenant-friendly droppable registry whose multi-entry shape is already correct for the post-MVP case. _Rejected:_ Static-init self-registration (order-fragile, non-unloadable, segfault-prone per PyTorch/TVM/TRT); process-global singleton registry; dir-scan auto-discovery (risks loading version-mismatched binaries).

_Risks:_
  - The dtype_tag re-validation at the boundary is a memory-safety obligation even in v1's single-backend case: a wrong tag is corruption, not a recoverable error. Every backend entry must validate before dereferencing, tested adversarially.
  - cudarc dynamic-loading + multi-arch PTX shifts kernel selection to driver JIT-at-load; first-load latency and on-disk JIT cache behavior must be validated, and PTX fallback coverage for unlisted arches confirmed. This risk is in scope for the MVP.
  - catch_unwind on every extern "C" entry is mandatory; any un-wrapped panic across the ABI is UB. Needs a lint or macro to enforce uniformly.
  - Deleter-travels-with-handle must be enforced by construction (Drop wrapping the owning backend's free fn, keyed on owner_backend_id) even in single-backend: a DeviceTensor whose plugin Library was dropped early causes use-after-unload. This is live in v1 the moment a backend is dlopen'ed.
  - Keeping the CPU backend both statically linked (linkme) and as a plugin risks two registrations of the same backend_id; the droppable Registry must dedupe deterministically, including in the v1 two-entry case.
  - Re-monomorphizing inside the plugin means each backend cdylib still compiles the full dtype cross-product; binary size and build time per backend crate must be watched.
  - The append-only ABI discipline is the mechanism the entire deferral strategy relies on: deferred multi-backend (DeviceTransfer/partitioner/peer-copy) must slot into the extension chain without touching the v1 core vtable. An accidental field reorder or non-appended addition silently breaks loaded plugins and the forward-compat guarantee. Needs a CI ABI-snapshot check before v1 ships.
  - Deferred (post-MVP): cross-vendor transfer always host-stages, so a future graph that splits an LLM op across vendors will tank latency; when the partitioner lands it must keep decode co-resident and log every transfer node. Not exercised in v1, but the v1 ABI must remain provably extensible to it.

### 4. Dynamic Loading, Plugin Architecture and Stable ABI

- **Frame the in-process trait path (static CPU backend) and the C-ABI plugin path as TWO SEPARATE CONSUMERS of the same backend logic, not the same Rust objects flowing across the boundary. The plugin reuses the port traits (CoreOps/FusedOps/MemoryPort) over a private CudaInner type as an INTERNAL implementation detail; only #[repr(C)] PODs, opaque handles, and i32 codes cross the .so line.** — The plugin links infer-core/infer-backend-abi as Cargo deps so its internal impl sees OpError/Tensor/CoreOps, but it only USES them within its own artifact. If host and plugin are built by different rustc/codegen (the whole point of independent build/release), reading any repr(Rust) value written by the other side is UB. Keeping the trait impls strictly private and crossing only repr(C) PODs makes independent compilation sound. _Rejected:_ Passing Rust trait objects / OpError enum / Capabilities-as-Rust-struct by reference across the boundary (UB under independent codegen); requiring host and plugin to share a single compiled artifact (defeats independent build/upgrade, the entire purpose).
- **OpError (including Unsupported) is NEVER transported as a Rust enum across FFI. The plugin thunk lowers it to a reserved i32 status code (distinct code for Unsupported to trigger CPU fallback) plus an optional opaque ErrorDetail handle; the host reconstructs a fresh OpError host-side from the code.** — OpError is a repr(Rust) enum (confirmed at ports/error.rs:5, Unsupported{backend,op}). Its layout is not stable across independent compilation, so it cannot be read across the .so line. Re-creating it from a numeric code keeps the existing Rust error path (and per-op CPU fallback) intact while the boundary stays purely numeric. _Rejected:_ Returning OpError by value/reference across extern C (UB, no stable repr(Rust) layout); a shared error-string Vec (no stable Vec layout across .so).
- **Pin the compatibility contract: plugin and host must share the same infer-core / infer-backend-abi SOURCE version, but need NOT share a compiled artifact, rustc, or codegen settings. infer-backend-abi contains ONLY #[repr(C)] definitions; a CI ABI-snapshot test plus the abi_version/struct_size gate enforce the window.** — Agreement is on the numeric meaning of the C ABI (repr(C) layouts, integer encodings, vtable field order), not on any repr(Rust) layout. This is precisely the property repr(C) preserves across independent builds and repr(Rust) does not, so it is the exact line that makes plugin independence safe. _Rejected:_ Requiring identical compiled binaries (no independent upgrade); leaving the version contract implicit (silent UB on drift); putting repr(Rust) types in the shared ABI crate.
- **Cut the static-generic / type-erased seam exactly at the existing high-level op ports (CoreOps/MathOps/FusedOps/DiffusionOps), lowering each op call to one #[repr(C)] vtable fn-pointer taking an opaque DeviceTensor POD + StreamHandle and returning i32, and re-monomorphizing on dtype_tag INSIDE the plugin thunk before it lands in the plugin's private trait impl.** — MemoryPort already speaks raw NonNull<u8>+sizes and both Cpu and Cuda implement it identically, so the seam is half-built. Erasing at op granularity (not per element) costs one indirect call per matmul/attention while preserving the zero-overhead match T::DATA_TYPE hot path INSIDE the plugin. This is an incremental refactor, not a rewrite. _Rejected:_ Erasing the tensor element-type globally (kills the monomorphized kernel match); c10-style multi-axis DispatchKeySet (accidental complexity from autograd RustInfer lacks).
- **Hand-rolled #[repr(C)] struct-of-fn-pointers with one entry symbol rustinfer_get_backend_api(abi_version)->*const BackendVTable, struct_size/abi_version first field, append-only, typed extension chain for optional ops; Capabilities returned as a repr(C) POD by value.** — No stable Rust ABI exists. The op set is small, fixed, and already enumerated as ports, so a hand-rolled vtable gives full control with less ceremony than abi_stable. PJRT's struct_size-first append-only discipline buys forward+backward compat without freezing a major version; the extension chain adds fused ops without breaking the ABI. _Rejected:_ abi_stable (heavy, large dep, needed only if shipping Rust collections across the line); stabby (lighter but imposes its worldview); sending Vec/String/dyn/OpError across FFI (UB, no stable Rust ABI).
- **Move all .cu + nvcc + bindgen + nvidia-smi detection into a standalone infer-backend-cuda cdylib (deps: infer-core for reused port traits, infer-backend-abi for repr(C) types) that ships multi-arch PTX/fatbin and loads CUDA via cudarc dynamic-loading; core builds with zero CUDA toolchain.** — Directly fixes tension #2: today default=[cuda] means the core cannot build without a full CUDA toolchain + host GPU and the artifact is host-arch-pinned. Every reference runtime keeps the toolchain inside the vendor .so; cudarc dlopens libcuda/nvrtc so the consumer has no link-time CUDA. Driver JITs PTX at load and caches it. The plugin's infer-core/infer-backend-abi deps compile into the plugin's own artifact; the host links neither kernels nor the plugin's Rust impls. _Rejected:_ Keeping .cu in worker behind a feature (toolchain coupling unchanged); single nvidia-smi->sm_XX cubin (host-GPU-specific).
- **Explicit entry-point registration via libloading into an owned, droppable per-server BackendRegistry (env/config name:path list, PJRT-style), with capabilities() queried as a repr(C) POD by value after the abi_version gate. Keep CPU backend statically linked (linkme) as always-present per-op fallback, consumed as a native Rust trait never via FFI.** — Static-init self-registration (PyTorch/TVM/TensorRT) is order-fragile, non-unloadable, segfault-prone. An explicit entry point gives deterministic load AND unload (true hot-swap) and a droppable registry suits a multi-tenant server. The static CPU baseline that already returns OpError::Unsupported gives per-op CUDA->CPU fallback that PJRT/TRT cannot offer, and as an in-process Rust consumer it never touches the ABI. _Rejected:_ Static-init constructor registration; process-global singleton registry; putting CPU behind the C ABI (would lose the zero-FFI terminal fallback).
- **Mandate the ABI-safety trinity: deleter travels with the handle (buffers, streams, AND ErrorDetail handles), errors cross as i32+opaque ErrorDetail handle with catch_unwind on every entry fn (OpError reconstructed host-side, never transported), version-gate loudly on first call.** — These three rules are shared by every successful stable boundary (tvm-ffi, PJRT). Panic across extern C is instant UB; cross-.so free with mismatched toolchains is a double-free; reading a repr(Rust) OpError written by a differently-compiled artifact is UB; an unchecked ABI mismatch is UB not an error. RustInfer kernels legitimately return Unsupported, making disciplined numeric error propagation essential. _Rejected:_ Letting panics unwind across FFI; freeing plugin-allocated buffers in the host; transporting OpError as a Rust enum; trusting ABI compatibility without a struct_size/abi_version gate.

_Risks:_
  - The opaque DeviceTensor dtype_tag converts compile-time type-state into a runtime check; a wrong tag is memory corruption, not a type error. Requires strict boundary validation in release builds, adding a small per-call cost the monomorphized world never paid.
  - The source-version compatibility window (host and plugin must share infer-core/infer-backend-abi source even though not the compiled artifact) is enforced only by an abi_version gate plus a CI ABI-snapshot test; a repr(C) layout drift that does not bump abi_version would be silent UB, so the snapshot test and a 'no repr(Rust) public item in infer-backend-abi' lint are load-bearing.
  - Lowering OpError to an i32 loses structured payload (Unsupported{backend,op}) unless an opaque ErrorDetail handle carries the strings; if the detail handle's lifetime is not tied to the plugin Library it can dangle after unload (use-after-unload).
  - Shipping multi-arch PTX/fatbin trades host-GPU-specificity for first-load JIT latency; driver disk cache mitigates but cold-start and CI ephemeral nodes will see recurring JIT cost.
  - cudarc dynamic-loading must reach feature/version parity with the current cuBLAS/cuBLASLt/cuDNN-frontend usage in build.rs; some fused/cuDNN-frontend paths (flash_attn_gqa, conv) may have no clean Driver-API equivalent and could force keeping a thin cuDNN link inside the plugin.
  - FusedOps default methods currently fall back to host round-trips (e.g. attention_paged_reference, scatter_kv_paged_reference do to_host_vec); if these run as the CPU fallback in the hot path they will tank LLM latency unless every cross-backend round-trip is logged and the CUDA plugin overrides them.
  - block_size==1 and the <bf16,Cuda> hardcoding in serve_loop mean the first plugin cut still only exercises one dtype/device pair; the ABI must be designed for the general case while only one path is initially tested, risking unexercised vtable slots.
  - Hand-rolled append-only ABI discipline is only as good as review; a single non-appended field reorder or a missed catch_unwind reintroduces UB. Needs a CI ABI-snapshot test and a panic-boundary lint.
  - Keeping the Library alive for the lifetime of all handles it created requires careful Drop ordering across the registry, streams, tensors, and ErrorDetail handles; premature dlclose while a CUDA stream or error handle is live is a classic use-after-unload segfault.

### 5. Backend Build System: Independent Build and Release

- **Adopt a hybrid build system: Cargo drives the Rust shell of each backend crate; CMake compiles the kernels inside each backend's own build.rs.** — CMake is the only contender with first-class multi-arch CUDA fatbin (CMAKE_CUDA_ARCHITECTURES) plus a parallel HIP/Metal story, sccache caching, cross-toolchain files, AND universal familiarity among the kernel authors who actually write the .cu files. The kernel compile is the only part needing a vendor compiler, so isolating it in the backend crate's build.rs (not the worker's) directly removes the toolchain coupling. _Rejected:_ Bazel: best hermeticity/remote cache but imposes an alien second build graph and steep learning curve, overkill for one CUDA backend. XMake/Meson: credible but weaker CUDA+HIP depth and far less mindshare. cargo+cc (status quo): cannot emit a fatbin, no HIP/Metal path, and is the exact source of the worker-toolchain coupling.
- **Delete the worker's build.rs entirely and move all .cu compilation into a standalone infer-backend-cuda cdylib; flip default features from ['cuda'] to [] (CPU baseline).** — Makes infer-worker build with no nvcc, no libclang, no cuDNN-frontend discovery, no nvidia-smi. The CUDA toolchain requirement lands only in the backend crate where it is correct. cc/bindgen/walkdir leave the worker build-dependencies. _Rejected:_ Keeping SKIP_BUILD_KERNELS escape hatch: only defers pain because the static extern "C" symbols then fail to link. Keeping kernels in-worker behind a feature: still forces the whole toolchain whenever the GPU path is built.
- **Replace nvidia-smi host-arch detection with a fixed gencode matrix (sm_80/86/89/90 + compute_90 PTX) emitted as a fatbin and JIT-resolved to the running GPU by the CUDA driver at module load.** — Removes host-GPU-specificity of the artifact; the same fatbin runs on any GPU in the supported arch window, with PTX fallback for newer cards via driver JIT (cached on disk). Mirrors TVM CUDAModule and TensorRT fatbin practice. _Rejected:_ Per-build nvidia-smi detection (current): pins the artifact to the build host's GPU and makes the CI matrix meaningless. Single-arch cubin: no forward compatibility.
- **Keep the CPU backend statically linked into the worker as the always-present terminal fallback; load GPU backends at runtime via cudarc dynamic-loading + libloading.** — The CPU backend already implements every port in src/infrastructure/cpu/, proving the abstraction can host a non-CUDA backend with zero GPU toolchain. This makes the first deliverable (a worker that builds with no CUDA) immediate, and keeps a guaranteed per-op fallback target. cudarc dlopens libcuda/libnvrtc so the consumer has no link-time CUDA. _Rejected:_ Putting CPU behind the C-ABI plugin boundary too: loses the always-present static guarantee and complicates the terminal fallback. Linking libcuda at build time: re-introduces a toolchain dependency in the consumer.

_Risks:_
  - First-load driver JIT of PTX (for arches not in the prebuilt sm_ set) adds latency on cold start; must rely on the driver's on-disk JIT cache and warm it in CI/startup.
  - Maintaining a CMake build per backend introduces a second build language for kernel authors; mitigated by CMake being the domain lingua franca but still a divergence from a pure-Cargo workflow.
  - cudarc dynamic-loading must cover every CUDA Driver/cuBLAS/cuDNN/nvrtc symbol the current bindgen allowlist exposes (graphs, cuBLASLt, cuDNN-frontend conv); any gap forces a per-symbol shim or a vendored binding inside the plugin.
  - The fixed gencode matrix must be kept in sync with supported GPUs; a too-new arch with no matching PTX fallback fails loudly at load — acceptable but needs a clear capability/compute-cap gate in backend.toml.
  - Embedding the fatbin via include_bytes! inflates the cdylib; for large kernel sets a sidecar artifact + path resolution may be needed, complicating the single-file plugin story.
  - Reproducibility depends on pinning the toolchain image (CUDA version, nvcc) per backend; without a recorded build manifest, fatbins from different CI runners may differ subtly.

### 6. Kernel Development Workflow

- **Split kernels into AOT multi-arch fatbin (stable/autotuned: GEMM, flash-attn, scatter_kv, fused qkv-rope, fused_add_rmsnorm) vs NVRTC-JIT-with-disk-cache (elementwise/reshape tail: add, ewise_mul, broadcast_mul, cast_fill, scalar, permute, split_cols, swiglu, softmax, rope). Source audit confirms the JIT-listed kernels pull no cutlass/cute headers, so the partition keeps cutlass templates entirely on the AOT side.** — AOT kernels run constantly and depend on autotuning/cutlass template instantiation we do not want to re-pay at process start; the JIT tail is small, mechanically dtype-specialized (the match T::DATA_TYPE ladder), and edited constantly, so runtime compile + cache gives a seconds-long edit loop with zero Rust rebuild once the launch shim exists. _Rejected:_ All-AOT (today's model) keeps the relink pain; all-JIT pays unacceptable first-call latency on perf-critical GEMM/attention, discards cutlass autotuning, and would force cute-template kernels through NVRTC which cannot easily consume them.
- **Make a generic name-and-args NVRTC launch shim an explicit prerequisite task for the JIT regime, replacing the per-kernel `unsafe extern "C"` declarations and `match T::DATA_TYPE` ladder for the JIT'd subset; migrate kernels onto it incrementally.** — Verified in add.rs:9-80 (same shape in softmax.rs/rope.rs/scalar.rs/etc.): each JIT-listed kernel is reached by a hard-declared per-dtype C symbol and a match ladder resolved at link time. A runtime-recompiled CUfunction is unreachable through those wrappers, so 'edit .cu, zero Rust rebuild' is false until a name-keyed driver-API launcher (CUfunction lookup + void** arg marshalling + launch geometry, via KernelSpec) replaces the symbol-bound wrappers. _Rejected:_ Claiming the seconds-long loop is free purely by moving compilation to NVRTC ignores that the wrapper still resolves a link-time symbol; keeping the per-symbol extern wrappers and only swapping the .cu body cannot reach the freshly compiled function.
- **Scope the 'edit-.cu-only, zero-Rust-rebuild' DX claim to kernels already migrated onto the launch shim; for unmigrated JIT-eligible kernels, editing the .cu still implies altering the Rust wrapper (AOT-style rebuild).** — Honesty about the migration boundary: the fast loop is a property the shim earns per kernel, not an automatic consequence of runtime compilation. KernelSpec is the single source of truth for name + arg-marshalling, test-verified against the old wrapper before deletion. _Rejected:_ A blanket DX claim across all JIT-listed kernels overstates the pre-migration state and hides a substantial rewrite of the calling convention.
- **Unify the launch shim's CUfunction lookup with the disk cache: shim asks cache for a function by (arch, src_hash, flag_hash); cache satisfies from in-process map, disk, or fresh NVRTC compile. Disk layout content-addressed with cache-version byte and off switch; dtype/tile variants are distinct flag-hashes.** — Flags-in-key makes autotuning and dtype-specialization sound (block-size and dtype -D variants coexist) and matches the proven TensorRT timing-cache / ORT compiled-subgraph-cache discipline; making shim and cache two faces of one structure means name+dtype resolution and the compile-or-load path are a single mechanism; content-addressing makes it safe to share across processes and pre-warm in container images. _Rejected:_ Source-hash-only key collides across arches and flag/dtype variants causing wrong-cubin loads; an in-memory-only function map loses benefit across restarts; a shim independent of the cache duplicates the compile-or-reuse decision.
- **Backend .so hot-reload only at a quiesced point: synchronize streams via ExecScope, tear down Runtime, drop old vtable+Library, dlopen new, rebuild Runtime.** — The ABI-safety rule that a Library must outlive every handle it produced means reload is unsafe while any DeviceTensor/stream/CudaConfig workspace from the old .so is live; quiescing first is the only sound swap and still gives full hot-swap without restarting scheduler/server. _Rejected:_ Live in-place symbol swap risks use-after-unload UB on outstanding device handles; process restart defeats the purpose of dev hot-reload.
- **Ship fatbin as an arch SET (sm_80;sm_86;sm_89;sm_90 + compute_90 PTX) instead of the single nvidia-smi-derived sm_XX; keep autotuning results in the disk cache, never baked into the distributed fatbin.** — Removes host-GPU-specificity of the artifact (driver selects cubin at load, JITs PTX on newer arches) while autotuning still specializes per deployment via the cache, keeping the shipped artifact portable. _Rejected:_ Single-arch cubin (today) is non-portable; baking tuning into the fatbin makes it host-specific and unshippable.

_Risks:_
  - The JIT launch shim is a hard prerequisite, not a side effect: until it replaces the per-kernel extern "C" + match ladder for the JIT subset, editing a JIT-listed .cu still requires altering its Rust wrapper, so the seconds-long loop applies only to migrated kernels. Underestimating this shim turns the headline DX claim into vapor.
  - Arg marshalling in the shim trades compile-time dtype/pointer type-checking (the per-symbol signatures in add.rs) for runtime-described void** arg lists; a mismatch between KernelSpec's declared ArgLayout and the kernel's true signature is silent memory corruption, so per-kernel marshalling must be test-verified against the old wrapper before the old wrapper is deleted.
  - NVRTC cannot consume cutlass/cute-heavy kernels easily; the AOT/JIT partition must keep every cutlass-dependent kernel on the AOT side. Audit confirms the current JIT-listed kernels are cutlass-free, but any future JIT addition must be re-audited or it reintroduces toolchain coupling at runtime.
  - Disk cache staleness: an NVRTC minor-version bump or driver change can invalidate cached cubin silently; the cache-version byte must be bumped reliably or wrong-code execution results.
  - Hot-reload correctness hinges on truly draining all device work; any leaked stream/handle/workspace from the old .so outliving the Library is immediate use-after-unload UB.
  - cudarc dynamic-loading shifts CUDA-absence failures from build time to first-run; capability/load errors must be loud and early, not deferred into the request hot path.
  - First-call JIT and first-shape autotuning add tail latency to the very first decode/prefill after a cold cache; pre-warm in the container image or at server warmup to avoid a request-time stall.
  - Moving .cu into a separate cdylib changes the build graph and CI; the host-GPU-pinned single-arch artifacts currently produced must be replaced by a fatbin arch-set policy or deployments on unlisted arches fall back to PTX-JIT with a latency cost.

### 7. Runtime Dependency Management and Detection

- **dlopen-probe via a single typed handshake symbol (rustinfer_get_backend_api), with each plugin internally probing its own native stack, rather than the host directly dlsym-ing CUDA version symbols.** — Symbol presence does not prove usability (driver-too-old fails only on first real call); the host should not encode each backend's native dependency graph; and a failed dlopen/handshake is an ordinary Result whereas a missing symbol in a linked lib aborts the process. Matches PJRT's GetPjrtApi indirection and PyTorch's lazy is_available probe. _Rejected:_ Host directly reading exported version constants (cudaRuntimeGetVersion) from the CUDA libs; static linking with build-time detection (the current build.rs failure mode).
- **Split detection into two explicit axes: feature capability (queryable (op,dtype) bitsets) vs hardware/runtime compatibility (coarse driver/toolkit/compute-cap accept-reject gate).** — Lets a CUDA plugin refuse fp8 (op-level fallback) distinctly from refusing a too-old driver (whole-plugin rejection) with separate loud errors. The current build.rs collapses both into 'did nvcc succeed for sm_XX'. This is TensorRT's supportsFormatCombination vs HardwareCompatibilityLevel lesson and ORT's two-tier model. _Rejected:_ A single fused capability check; PyTorch's multi-axis DispatchKeySet (rejected as accidental complexity RustInfer lacks the autograd/functionalize axis for).
- **Keep the existing Cpu adapter statically linked (via linkme) as the unconditional stage-0 terminal fallback, never behind the C ABI; formalize OpError::Unsupported as the per-op fallback signal.** — The Cpu type already implements every port and already returns OpError::Unsupported for GPU-only ops, so it is the real, pre-existing seam. linkme is link-time only and useless across dlopen, so the baseline must be static. This gives per-op CUDA->CPU fallback that PJRT/TensorRT cannot do, and ORT's always-appended-CPU-EP guarantee. _Rejected:_ Shipping CPU only as a plugin (would be absent if dlopen fails); removing Unsupported in favor of compile-time guarantees (impossible across a type-erased runtime boundary).
- **Ship CUDA kernels as multi-arch PTX+fatbin and read abi_version/struct_size as the first field before any other vtable access; encode driver/runtime/built-against version triple comparison with CUDA minor-version compatibility rules.** — Multi-arch PTX with driver JIT-at-load removes the host-GPU-specificity the current nvidia-smi->single-sm_XX build bakes in (TensorRT/TVM forward-compat). Version-gating on the first field is PJRT's struct_size discipline; an unchecked ABI mismatch is UB, not an error. _Rejected:_ A single host-arch cubin (current behavior, host-pinned); checking ABI version after reading other fields (UB on mismatch).

_Risks:_
  - The native probe lives inside each plugin, so a buggy or malicious plugin can still crash the host process during stage 3 before the ABI/catch_unwind discipline fully protects it; untrusted backends should use the existing ZMQ worker-subprocess isolation rather than in-process dlopen.
  - CUDA minor-version forward-compatibility holds in the common case but has documented exceptions (certain driver/runtime combinations, MIG, specific cuBLAS builds); the version-triple check may need a per-library override table rather than a single major.minor rule.
  - Per-op CPU fallback via host round-trip is correct but can silently destroy decode latency if a hot op (matmul/attention) unexpectedly falls back; the logging/metering must be wired into infer-scheduler's prometheus path and ideally a hard-fail mode for production so a hot-path fallback is a startup error, not a runtime surprise.
  - Multi-arch fatbin + PTX increases plugin artifact size and adds first-load JIT latency; the driver's JIT cache must be warmed/persisted or cold starts regress.
  - Capability bitsets (op_mask/dtype_mask) must stay in sync with the append-only ABI; an op_id enumeration that is reordered rather than appended silently corrupts capability reporting across a version skew.

### 8. Distribution and Installation

- **Three independent distribution trains (crates.io core / OCI-registry backend cdylibs / PyPI+extra-index wheels) that meet only at the C ABI.** — Matches PJRT/ORT where wheels and EP .so meet only at GetPjrtApi/GetApi(N); lets core publish GPU-free and backends version independently. _Rejected:_ Single fat wheel vendoring all CUDA families (multi-GB, re-download per bump); keeping kernels in-core (cannot publish to crates.io, host-arch-pinned).
- **Demote infer-worker default=["cuda"] from compile-time kernel build to runtime dlopen of a bundled plugin; move all .cu into infer-backend-cuda cdylib; statically link the existing CPU backend as baseline.** — build.rs currently forces a full CUDA toolchain + libclang + cuDNN-frontend + host GPU just to build the core; the CPU backend already implements every port and returns OpError::Unsupported, so it is a ready-made always-present baseline. _Rejected:_ Keeping SKIP_BUILD_KERNELS escape (linking then fails); shipping per-host sm_XX cubin from nvidia-smi (host-pinned, not distributable).
- **PyTorch-style +cu124 local-version companion wheel on an extra index, plus a CLI that probes the GPU via cudarc and fetches the matching signed fatbin+PTX artifact.** — pip cannot probe the GPU at install time; the +cuXXX/extra-index convention is what PyTorch users already know, and a post-install CLI probe is strictly more reliable than index-URL guessing. _Rejected:_ Auto-selecting CUDA at pip-install time (no GPU visibility); single sm_XX cubin (loses forward compat vs PTX JIT-at-load).
- **Explicit path/registry-file/env discovery (RUSTINFER_BACKENDS=name:path) into an owned droppable Registry, with abi_version as first vtable field, checksums+signature verified before dlopen.** — Steals PJRT's name:path env and ORT's explicit-path registration while avoiding static-init singletons; enables hot-swap and per-server registries for the multi-tenant axum server; verify provenance before load and compatibility at load. _Rejected:_ Static-init self-registration into a process global (PyTorch/TVM pattern — order-fragile, non-unloadable, unsigned arbitrary code); directory-scan magic (risks loading version-mismatched binary).

_Risks:_
  - First-load PTX JIT latency replaces build-time host-pinning; mitigated by shipping fatbin for sm_80/86/89/90 + disk-cached JIT, but cold-start on a brand-new arch is slower than a prebuilt cubin.
  - Local-version companion wheels cannot live on PyPI, so the extra-index must be hosted and kept available; an outage breaks GPU installs while CPU installs keep working.
  - Demoting default=["cuda"] changes existing build/CI invocations and the hardcoded <bf16,Cuda> serve loop; until the runtime-load seam lands, the core has no GPU path and downstream callers must adopt the registry.
  - Signing/verification adds a key-management burden (cosign/minisign key rotation); a mishandled key either blocks all installs or undermines the trust guarantee.
  - manylinux glibc floor (2.28) and per-CUDA-family matrix multiply the artifact build/test surface; the ABI compatibility matrix must be kept authoritative or --auto resolves to a mismatched binary.
  - An unsandboxed dlopen'd backend runs arbitrary code in the server process; high-trust only — untrusted/experimental backends must be routed through the existing ZMQ worker subprocess instead.

## Appendix B — How This Proposal Was Validated

The eight sections were drafted independently, then put through three adversarial review lenses before synthesis. Findings were folded back into the sections. The lens summaries:

**cross-section consistency and coherence**

The seven sections are individually coherent and share a consistent core thesis (cut the static-to-dynamic seam at MemoryPort + high-level op ports, keep dtype match inside the plugin, move .cu into a cdylib, statically link CPU as the terminal fallback). The shared technical claims about the existing code are largely accurate: DTypeId(u16) with BF16=2/F8E4M3=5 and registry start at 1024, MemoryPort's raw NonNull<u8> surface, the <bf16,Cuda> hardcode in serve_loop, block_size==1, supports_graphs(), OpError::Unsupported{backend,op}, and the 29 .cu / 471-line build.rs are all verified. However there are several concrete cross-section contradictions that will confuse implementers: (1) a flat-out naming collision on the backend crate names (infer-cuda-backend vs infer-backend-cuda) where repository_structure mandates one convention and all five other sections use the opposite; (2) an over-claim, repeated as load-bearing in the abstraction and distribution sections, that the CPU backend 'implements every port' and is a ready per-op fallback target — the code shows CPU returns Unsupported for many CoreOps and only has generic host-round-trip FusedOps defaults, which kernel_dev and dynamic_loading correctly describe, so the document contradicts itself on whether per-op CUDA->CPU fallback actually works today; (3) drift in the DeviceTensor dtype-tag width (u8 vs u16) and in whether DLPack layout is adopted verbatim vs with an added owner field; (4) inconsistent statements about where exactly the seam sits (MemoryPort-and-ops vs ops-only). These should be reconciled before the proposal is treated as a single design.

**Production realist / adversarial: feasibility of static-generic to type-erased boundary, dyn dispatch perf in decode, C-ABI vtable soundness (panic/allocator/stream lifetime across .so), JIT/fatbin realism, KV coherence.**

The proposal's central claim — "the seam is already half-built at MemoryPort, so this is a refactor not a rewrite" — is half-true and oversold. MemoryPort (device.rs) genuinely speaks raw NonNull<u8>+bytes and is cleanly erasable; DTypeId(u16) genuinely exists with a registry base of 1024; the CPU backend genuinely implements every port. Those grounding facts hold. BUT the op-call boundary the proposal wants to erase does NOT pass raw pointers — every MathOps/FusedOps/DiffusionOps method takes fully-typed Tensor<T, Self> plus compound, lifetime-bearing aggregates (KvView<'_,T,Self>, LayerKv<'_,T,Self>, StepCtx<'_,Self>, BatchPlan). A flat DLPack-shaped DeviceTensor POD cannot represent these without a substantial new ABI surface the proposal never specifies. Three deeper problems are under-specified or wrong: (1) the cost model ("one fn-ptr per op, free") is evaluated against the eager path, but the actual decode hot path is built around CUDA-graph capture/replay (GraphRunner, step_graph, capture_sizes) plus a multi-stream bubble-free pipeline and shared cuBLAS/cuBLASLt/cuDNN handles living in Arc<CudaConfig> — a per-op C-ABI vtable that re-validates dtype on every entry is incompatible with graph capturability and irrelevant at replay; the seam must sit at graph/step granularity, not op granularity, which the proposal's own dispatch model contradicts; (2) panic-across-FFI is not hypothetical — enter_device() literally panic!s on cudaSetDevice failure today, and that runs on every ExecScope::enter, i.e. before every op, so catch_unwind is mandatory at a place the proposal only mentions abstractly; (3) the "load CUDA via Driver API / cudarc, no link-time CUDA, fatbin+PTX" story collides with cudnn_paged_attention.cu and cuDNN-frontend on the attention path plus cuBLASLt — these are not Driver-API/NVRTC-JIT-able and force a real cuDNN/cuBLASLt link inside the plugin, which the build/JIT sections hand-wave. KV coherence is asserted ("stream-ordered, reuse ExecScope") but the actual KV path defaults to host round-trips (attention_paged/scatter_kv_paged default trait methods call _reference impls doing to_host_vec) and the system is hard-constrained to block_size==1 with a worker-owned bump KV allocator — cross-backend KV coherence is not solved, it is asserted over a code path that today bounces through host memory.

**migration-feasibility and developer-experience**

The proposal is broadly INCREMENTAL and correctly identifies the real seam: MemoryPort is genuinely byte-oriented (verified in domain/ports/device.rs), DTypeId(u16) exists with a registry starting at 1024 (domain/dtype/mod.rs:26), the CPU backend really implements every port and returns OpError::Unsupported (infrastructure/cpu/mod.rs, error.rs), and build.rs really does nvidia-smi->sm_XX detection, panics on missing cuDNN-frontend, and statically links infer_kernels (build.rs:85,116,380). The build-decoupling story (move .cu into infer-backend-cuda cdylib, default=[] CPU baseline) is sound, shippable in stages, and the single highest-value, lowest-risk first deliverable. HOWEVER, the proposal contains one pervasive, load-bearing technical error that undermines the central abstraction across four sections: it repeatedly frames `dyn Backend`/`dyn Device`/`Box<dyn Backend>`/`Vec<Box<dyn Backend>>` as a near-free 'object-safe projection' of the existing ports. The existing op ports (MathOps, FusedOps, DiffusionOps in domain/ports/) are composed ENTIRELY of generic associated functions over `T: Dtype` (e.g. `fn add<T: Dtype>(scope: &Self::Scope, ...)`, no `&self`), and `Backend`/`LlmBackend` are blanket-impl super-traits of these. Such traits are categorically NOT object-safe, and the codebase uses `dyn` nowhere. You cannot `Box<dyn Backend>` today, and making it work requires writing an entirely new dtype-erased, `&self`-receiver trait surface by hand (one method per (op, dtype) or a tag-dispatched wrapper) PLUS a manual fn-ptr vtable PLUS keeping that in sync with the generic trait. That is real, large, hand-written code, not a 'projection.' The proposal's risk sections mention 'object-safe dyn Device/Stream projections must faithfully reproduce ActiveGuard' but never acknowledge that the projection is a from-scratch parallel surface, not a derive. This is the difference between the claimed 'refactor not rewrite' and the actual cost. Second, the staging is described mostly as end-state architecture; the proposal asserts incrementality but provides almost no concrete ordering, and the one ordering hazard it does create is severe: every section flips default=['cuda'] to CPU-baseline and demotes the static link to runtime dlopen, but serve_loop::run_with_model is hardcoded `M: DecoderModel<bf16, Cuda>` (serve_loop.rs:71) and the worker bin has required-features=['cuda']. If default is flipped before the type-erased boundary and a CPU-capable serve loop exist, the worker binary cannot run at all (no Cuda, hardcoded Cuda) — a long-lived broken-worker window. Third, there are two distinct `Device` traits (ports/device.rs and exec.rs:13, the latter `Device: MemoryPort` with `type Scope`), and the crate-split mapping tables never disambiguate which Device/exec pieces go where, risking a circular dep between infer-tensor, infer-backend-abi and infer-exec that the proposal hand-waves. Net: ship the build-decoupling + CPU-baseline stage first (high value, low risk, but gated on fixing the serve-loop hardcode), but the dynamic-dispatch/ABI sections substantially understate the hand-written object-safety bridge and need an explicit, build-green stage plan before they are credible.
