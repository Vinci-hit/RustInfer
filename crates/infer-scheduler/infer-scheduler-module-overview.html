一句话定位

infer-scheduler 是 RustInfer 三进程架构里的中控调度进程：从 HTTP Server 接收已 tokenize 的请求，维护请求状态和 KV 资源，把可执行 batch 发给 GPU Worker，再把 Worker 输出聚合成响应返回给 Server。

当前主线能力

主线已调整为 LLM + Slot KV + Scheduler 控制 admission/chunk + Worker 自循环 decode。Scheduler 发送显式 PrefillSegmentMeta，Worker 按 sequence_id 回传精简 StepOutput。

3. 整体架构

Scheduler 位于 HTTP Server 和 Worker 之间。它不做 tokenizer，也不跑模型；它维护调度状态、资源元数据和通信协议。

HTTP Server

接收 OpenAI 风格请求，完成 tokenizer，把 InferenceRequest 发给 Scheduler。

request_id, input_ids, max_tokens, sampling, priority, stream。

infer-scheduler

维护 WaitingQueue、prefilling、decoding、ActiveRequestTable 和 KvManager。

每轮调用 SchedulingPolicy::schedule 生成 BatchPlan，再用 batch_builder 编成 Worker 命令。

GPU Worker

接收 WorkerCommand::Prefill，执行 prefill，并在内部自循环 decode。

逐步回传 StepOutput { prefill_done, tokens }；token 使用 sequence_id 而非字符串 request_id。

设计重点：当前不是“Scheduler 每个 decode step 都发命令”的模式，而是 “Scheduler 发 prefill / continuation，Worker 内部 decode，自行持续上报 step output”。这减少了每 token 的 IPC 往返。

启动顺序

  • Scheduler 启动并 bind IPC socketmain.rs 创建 frontend ROUTER、worker PUSH/PULL 和 control ROUTER。
  • Worker 连接控制面并 HelloScheduler 回复 SchedulerHello，如果 CLI 带 --model 则下发 LoadModel。
  • 等待 WorkerReady拿到 worker capacity 后构造 WorkerGroup::from_single_ready。
  • 进入事件循环开始同时监听 frontend request 和 worker output。

4. 请求生命周期

请求生命周期采用 type-state 设计：Sequence<Queued>、Sequence<Prefilling>、Sequence<Decoding>、Sequence<Finished> 是不同类型，状态转换通过消费旧对象产生新对象，避免在编译期之外误用状态字段。

Queued
进入等待队列
从 Server 收到已 tokenized 请求，创建 RequestMeta 和 RequestHandle。
Prefilling
分配 KV
policy 选中后，从 KvManager 分配 slot/block，发送 prompt 或 chunk。
Continuation
长 prompt 分块
如果启用 chunked prefill，则记录本轮 chunk size，下一轮继续补齐。
Decoding
收 token
prefill 完成后进入 decode；Worker 每步返回 token，Scheduler 追加输出。
Finished
响应并释放
EOS 或 max_tokens 后发送 InferenceResponse，释放 KV，记录 metrics。

内部状态容器

容器类型/位置职责
waiting_queueWaitingQueue按 priority 降序、同 priority FIFO 组织等待请求；preempted 请求可插到同优先级前部。
prefillingVec<Sequence<Prefilling>>已分配 KV、正在 prefill 或等待下一块 prefill 的请求。
decodingVec<Sequence<Decoding>>已完成 prefill、正在接收 Worker decode token 的请求。
active_requestsActiveRequestTable生命周期 ledger，用于记录 Waiting / Prefilling / Decoding / Cancelling 等状态；不是 Worker decode 的驱动源。
current_chunk_sizesVec<(RequestId, usize)>记录本轮新选中的 segment，用于 batch builder 只发送本轮 segment，避免重发旧 in-flight chunk。

5. 调度循环与核心状态

SchedulerEngine<P, F, W> 是顶层 orchestrator，泛型约束把调度策略、frontend transport、worker transport 都抽象成 trait，因此单测可以换成 channel transport，生产使用 ZMQ transport。

事件循环

event_loop::run_event_loop 每轮先 poll_next_event，再根据事件处理：

  • 新请求：校验、分配 sequence_id、入队；LLM 模式会立即尝试继续投喂 Worker。
  • Worker output：解析 prefill_done 和 token，推进状态、完成请求；然后继续尝试调度。
  • Transport shutdown：退出。

worker_busy 的新边界

worker_busy 不再用于 LLM 路径背压；LLM 可以持续向 Worker 投喂 prefill segment。该标志只保留给 diffusion 这种 batch-in batch-out 模式。

一次 LLM 调度迭代

run_iteration()
  1. LLM 路径不受 worker_busy 阻塞；diffusion 仍保留 busy gate
  2. 构造 RunningSet：只把无 inflight 的 prefilling 作为 continuation 候选
  3. 构造 TokenBudget：max_batch_tokens + max_num_seqs
  4. 调用 policy.schedule(waiting, running, budget, cache_state)
  5. execute_plan：分配 slot，并为每个选中请求设置 inflight segment
  6. batch_builder：只把本轮选中的 segment 编成 WorkerCommand::Prefill
  7. worker.send_batch(data)；LLM 不设置 worker_busy

收到 Worker output 后

handle_step_output_llm(data)
  1. 解码 StepOutput { prefill_done, tokens }
  2. 对 prefill_done 的 sequence_id ack inflight segment
  3. final prefill ack 后先转入 decoding，再处理同 step 的首个 token
  4. 对 token 按 sequence_id 追加输出，使用 Worker 返回的 finished 判断完成
  5. 完成的 decoding 序列：finish → free KV → send InferenceResponse → metrics

6. 调度策略

调度策略由 SchedulingPolicy trait 抽象。策略不直接修改 Engine 状态，只读取 WaitingQueue、RunningSet、TokenBudget、CacheState，返回 BatchPlan。

策略实现当前行为
ContinuousBatchingPolicy主线先保留所有 decode 序列的一 token 预算，再调度已在 prefilling 的 continuation chunk，最后从 waiting queue 选择新请求。
DiffusionPolicy简化版如果没有运行中 batch，则从 waiting queue 取最多 max_batch_size 个请求；TODO 中计划按 height/width shape 分组。
PriorityPolicy未实现当前调用会 warn 并返回空计划。实际 priority 目前只体现在 WaitingQueue 排序。
PreemptionStrategy未接入Disabled 返回失败，Recompute/Swap 返回 NotImplemented；Engine 在 KV 分配失败时只是把请求放回队首并停止本轮。
注意：BatchPlan.decode_batch 会被 policy 填充，但当前 batch_builder 只在存在 prefilling 时发送 PrefillBatchCmd；decode 的实际推进由 Worker 内部自循环负责，因此 Scheduler 侧无需每步发送 decode command。

7. KV Cache 设计

KvManager 是 Scheduler 对 KV 资源的统一抽象。当前运行时根据 SchedulerMode 和 KvCacheMode 选择具体实现。

SlotKvManager

当前可用

维护 Vec<bool> bitmap，每个请求占一个 slot。分配 first-fit，完成后释放 slot。

NoopKvManager

Diffusion 使用

不做真实 KV 分配，返回 dummy Slot(0)；用于 diffusion 这种 Scheduler 侧无 KV 管理的模式。

PagedKvManager

stub

内部持有 PagedBlockAllocator 和 block size，但 allocate/extend 尚未实现。

Paged KV 已经预留的组件

组件职责状态
PagedBlockAllocator管理 physical block id、free list、ref count、hash lookup、LRU eviction_order。元数据实现
BlockTable每个 sequence 的 logical block → physical block 映射。基础结构
NoPrefixCacheprefix cache 关闭时始终 miss。可用
RadixTreeCache未来做 SGLang 风格 radix/trie prefix sharing。始终 miss
Evictor未来抽象 LRU/LFU；目前 LRU 集成在 allocator。预留
当前限制：CacheState 在 Engine 调度时还是固定的空快照（free_blocks/total_blocks/utilization 都为 0），policy 目前没有真正基于 KV 压力做决策。LLM 主线当前主要依赖 slot 分配和 max_batch_tokens/max_num_seqs 做 admission。

8. 通信与协议

数据面和控制面都使用 MessagePack，但 socket 角色不同。ZMQ socket 本身不是 async-friendly，因此实现采用 dedicated std thread + tokio mpsc bridge。

链路协议/Socket消息说明
Server → SchedulerZMQ ROUTER, MessagePackInferenceRequest包含已 tokenize 的 input_ids、sampling、priority、stream 等。
Scheduler → ServerZMQ ROUTER replyInferenceResponse / StreamChunk当前主流程发送完整响应，stream chunk 接口未实际使用。
Scheduler → WorkerZMQ PUSHWorkerCommand::Prefill, Cancel发送显式 prefill segment；字段包括 flattened input_ids、q_start_loc、sequence_id、kv_slot、segment_start/end、prompt_len、completion。
Worker → SchedulerZMQ PULLStepOutput热路径精简为 prefill_done: Vec<u64> 与 token 列表：sequence_id, token_id, finished。
Worker 控制面ZMQ ROUTERHello, Progress, Ready, ErrorScheduler 等待 WorkerReady 后才进入调度循环。

生产与测试 transport

  • ZmqFrontendTransport / ZmqWorkerTransport：生产 IPC。
  • ChannelFrontendTransport / ChannelWorkerTransport：进程内 mpsc，用于单元测试或 mock worker。
  • MsgPackCodec：统一封装 rmp_serde encode/decode。

9. 完成度与风险清单

已经比较明确的设计

  • crate 层边界清晰，核心对象集中在 SchedulerEngine。
  • 请求生命周期 type-state 设计可读性好，状态转换明确。
  • policy / cache / transport 都是 trait-based，便于替换实现。
  • Slot KV 与显式 PrefillSegmentMeta 对齐，chunk 写入位置语义清楚。
  • Worker hot path 使用 sequence_id，避免每 token 序列化字符串 request_id。
  • 控制面已经为 WorkerGroup / TP / PP 扩展预留了结构。

需要谨慎看待的点

  • 空 input / 超长 prompt 目前只 warn 并 return，未向客户端返回 error response。
  • Engine 构造的 CacheState 尚未接入真实 KvManager 状态。
  • Paged KV、prefix cache、priority policy、preemption 都有接口但未完成。
  • stop sequences 从协议进来，但 Engine 当前把 stop_sequences 置为空，未处理。
  • streaming 接口存在，但当前完成后一次性返回。
  • Diffusion 仍使用 token/request 抽象占位，缺少图片结果协议与 shape-aware batch。

10. 建议演进路线

如果后续要把这个 scheduler 从当前主线推进到更完整的生产调度器，建议按依赖关系拆成以下阶段。

  1. 补齐错误响应路径空 input、超长 prompt、KV 分配失败、worker error 等都应返回明确 ResponseStatus::Error，避免客户端悬挂。
  2. 把真实 KV 状态接入 CacheState至少先让 Slot 模式暴露 free slots / capacity，让策略可以看到资源压力。
  3. 完善 stream 与 stop sequence按 stream=true 发送 StreamChunk；使用协议中的 stop_sequences 做终止判断。
  4. 实现 Paged KV 的最小闭环allocate、extend、free、block table wire format 与 Worker PagedAttention 对齐。
  5. 接入 prefix cache 与 preemption先做 NoPrefixCache → RadixTreeCache；再做 recompute preemption，最后考虑 swap。
  6. 扩展 WorkerGroup从单 rank ready gate 扩展到多 rank barrier，并用 effective capacity 驱动 SchedulerConfig。
  7. Diffusion 独立协议化引入 diffusion request meta、shape-aware batching、image output response，避免复用 token response 的语义缺口。
