RustInfer API Server 架构设计文档

OpenAI 兼容的 HTTP 网关层实现规范

系统定位

infer-server 是 RustInfer 推理系统的前端网关。它对外暴露完全兼容 OpenAI 规范的 RESTful HTTP API，对内通过 ZMQ 与底层的 Scheduler 推理引擎进行高性能通信。作为协议转换层和流量出入口，它的设计目标是：高并发、低延迟、可观测、标准兼容。

HTTP Client │ ▼ (Axum Router) [ Middleware (Trace, CORS, ReqID) ] │ ▼ (Handlers) [ Chat / Completions / Images API ] │ ▼ (Domain Logic) [ Chat Template ] ──► [ Tokenizer ] │ ▼ (Async-Sync Bridge) [ ZMQ Client Thread ] │ ▼ (IPC / TCP) [ Scheduler Backend ]

核心模块职责说明

🚀 核心启动 (main.rs / lib.rs)

职责： 应用程序生命周期管理与依赖注入。

  • 解析 CLI 参数与环境变量
  • 初始化 Tracing 日志系统
  • 构建 AppState 共享状态 (依赖注入)
  • 绑定端口并启动 Axum 异步服务器
  • 处理优雅停机 (Graceful Shutdown)

⚙️ 状态与配置 (state.rs / config.rs)

职责： 运行环境抽象与线程安全的数据共享。

  • 符合 12-Factor 原则的环境变量配置
  • AppState 封装 ZMQ Client、Tokenizer、ModelInfo 等核心依赖
  • 使用 Arc<AppState> 在所有 HTTP Handler 间实现无锁并发读取

🌐 路由与中间件 (router.rs / middleware/)

职责： HTTP 流量路由分配与请求拦截。

  • 注册 OpenAI 兼容的端点 (/v1/chat/completions 等)
  • 提供运维端点 (/health, /ready, /metrics)
  • RequestId 中间件：为每个请求注入 UUID，实现全链路追踪
  • 配置 CORS 与 HTTP Trace 记录

📡 客户端层 (client/)

职责： 屏蔽底层通信细节，抽象推理接口。

  • 定义 InferClient Trait，实现解耦
  • ZmqClient 实现：采用独立 Worker 线程模式，隔离 ZMQ 的同步阻塞与 Tokio 的异步调度
  • 支持 Oneshot (非流式) 和 Stream (流式) 两种交互协议
  • 实现基于 Drop trait 的自动取消机制，防止客户端断开导致的资源泄漏

🔌 API 控制器层 (api/)

职责： OpenAI 协议解析与业务逻辑串联。

  • Chat/Completion：验证请求 -> 应用 Chat Template -> 分词(Tokenize) -> 发起推理 -> 结果封装
  • Streaming：基于 Server-Sent Events (SSE) 的流式响应
  • 处理增量 UTF-8 解码，防止多字节字符被截断导致乱码
  • Images：处理 Diffusion 模型的图像生成与 Base64 编码

🛡️ 错误处理 (error.rs)

职责： 统一异常捕获与标准化响应。

  • 定义 AppError 枚举，映射领域错误到 HTTP 状态码 (400, 404, 429, 500)
  • 实现 IntoResponse，自动将内部错误转换为 OpenAI 标准的错误 JSON 格式
  • 收敛所有 Result 错误处理，避免 Panic

📝 提示词模板 (chat/)

职责： OpenAI 消息格式到模型特定格式的转换。

  • 定义 ChatTemplate Trait
  • 实现 Llama 3 格式 (<|start_header_id|>)
  • 实现 Qwen 3 格式 (<|im_start|>)
  • 基于策略模式，易于扩展新模型

关键设计模式与工程实践

1. 异步-同步桥接 (Async-Sync Bridge) 设计

ZMQ API 是同步阻塞的，而 Axum 运行在 Tokio 异步运行时中。直接在 Handler 中调用 ZMQ 会阻塞 Tokio 调度线程 (Thread Starvation)。

解决方案： 采用专门的 ZMQ Worker 线程。Tokio 任务通过 tokio::sync::mpsc 发送消息给 Worker 线程，Worker 线程执行 ZMQ 调用后，通过 oneshot (单次) 或 std::sync::mpsc (流式) 将结果异步回调给 Tokio 任务。实现了完美的 IO 隔离。

2. RAII 与资源自动回收 (Graceful Degradation)

在流式请求中，如果客户端中途断开连接 (例如用户刷新页面)，系统必须通知后端引擎停止生成，避免浪费显卡算力。

解决方案： 设计了 StreamHandle。它包装了接收通道，并实现了 Drop Trait。当 HTTP 连接断开，Axum 释放资源触发 Drop 时，自动向后端发送 Cancel 指令，做到了业务代码无侵入的资源回收。

3. 渐进式 UTF-8 安全解码 (Incremental UTF-8 Decoding)

大模型是按 Token 吐出结果的，一个中文汉字通常被编码为 3 个字节，可能被拆分在两个连续的 Token 中。直接对部分 Token 转换为 String 会导致解析失败或乱码。

解决方案： 在 streaming.rs 中维护解码缓冲区，仅当收集到完整的 UTF-8 字符序列时才进行 String 转换并下发 SSE Chunk，保证了客户端看到的总是合法字符。

4. 面向接口编程 (Trait-based Abstraction)

核心业务逻辑只依赖 InferClient 和 ChatTemplate 这两个 Trait。这使得 HTTP 层与具体的通信协议 (ZMQ) 和具体的模型 (Llama/Qwen) 完全解耦。未来如果需要迁移到 gRPC，或者接入新的模型结构，只需要新增实现类，无需修改 API 控制器层代码，符合开闭原则 (OCP)。
